## 3. 跨册机制索引

> 同一套机制在多个分册以不同面目出现 —— 实现一次，四处受益；反之漏掉一处，四处出问题。

| 机制 | 出现处 | 在哪些地方复用 |
|------|-------|--------------|
| **幂等键** | #13 #17 #18 #20 #37 | 重试去重 → 副作用防重 → 取消补偿 → 队列去重 → batch 回填，同一个 key 语义贯穿 |
| **断点 / 挂起点持久化** | #5 #16 #18 #25 #64 | checkpoint 是共同底座：续跑、`waiting_user` 挂起、取消、审批、优雅停机 drain |
| **多租户过滤** | #12 #32 #46 #49 | 字段带 `tenant_id` → 检索强制 `WHERE` → 元数据提取 → 向量库 metadata filter |
| **脱敏与凭据** | #26 #30 #38 | 顺序是「脱敏在前、日志在后」；Key 运行时注入、不进代码、不落日志 |
| **缓存** | #8 #36 | prompt 缓存（相同前缀命中）与语义缓存（相似问题命中）是两条不同的省钱路径 |
| **窗口治理** | #7 #8 #11 #47 | 压缩 / 动态组装 / reasoning 不丢弃 / 工具结果截断 —— 同一件事的四个面 |
| **沙箱执行** | #24 #54 | 执行环境（E2B / Docker / 子进程）与最小权限（白名单 / 只读 / 资源限制）是一体两面 |
| **状态机** | #4 #16 | 事件状态机（一次 run 内的事件序列）≠ 运行状态机（跨 run 的生命周期），别混成一个 |
| **确定性** | #61 #68 | 注入随机源；且 `seed` 只管 content，思考模式下 reasoning 每次不同 |
| **测试 / 评估 / 调试 / 飞轮** | #58 #59 #60 #61 #62 #63 | 测试测代码、评估测输出、trace 回放定位、badcase 回流成评估集 |
| **工具返回值即上下文** | #2 #8 #10 #68 #70 | 工具描述与 schema 决定「调不调、怎么调」，返回截断决定「喂回多少」 |

## 4. 十四册摘要

### ① 核心循环（#1-12）

> agent 能不能「跑起来」的全部要害都在这册：单次模型调用如何变成多轮工具循环。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 1 | 并行工具调用 + 部分失败 | 并发执行、成败都回填、并行语义不可拆 | P0 |
| 2 | 错误自纠错 | 错误信息要「可操作」，不是甩一个 `422` 让模型猜 | P0 |
| 3 | 无限循环防护 | 软限制（轮末判）与 kill switch（立刻断）是两种东西 | P0 |
| 4 | 流式事件状态机 | 七类事件（#4 六类 + #7 压缩）+ 四条不变量，违反即抛错，不让乱序流进前端 | P0 |
| 5 | checkpoint 断点续跑 | 关键是记录「执行到哪一步」，恢复不重跑 | P0 |
| 6 | 强制结构化输出 | `response_format` + `json_schema`，校验失败带错误重试 | P1 |
| 7 | 上下文压缩 | 摘要 + 截断，但绝不能破坏 `tool_calls` 结构 | P1 |
| 8 | 上下文工程 | 主动决定放什么、丢什么；关键信息避开中段 | P2 |
| 9 | 意图识别 + 澄清 | 指代消解 + 反问澄清 + 跟随意图漂移，不硬猜 | P2 |
| 10 | Tool calling 协议细节 | 参数语义 + 消息结构合法性 + finish_reason 六态 | P0 |
| 11 | reasoning 处理 | 两条通道分离；用量计数取对字段 | P0 |
| 12 | Agent 后端数据模型 | 六实体设计（落地五实体）+ event sourcing + TTL | P2 |

**硬骨头**

- **#1 并行语义被破坏就不可逆**：并行的结构标志是「多个 `tool_calls` 在同一个 assistant message 里」。若把并行结果拆成多个顺序轮次回填，模型看到的历史就变成「一次只调一个工具」，**后续会退化成串行调用** —— 回填与回放都必须保住这个结构。
- **#4 七类事件里有两类最容易做错**：`reasoning` 是**旁路通道**（任意非终局位置可发，不参与主序列、不改变状态）；`error` 承担异常结束（没有答复就不该有 `final`）。终局事件**恰好一个**，由 loop 单一出口产出；guard 刹车时 `LoopResult.content=None`。**降级话术（模板回复 / 转人工）归 server 层，框架不编造用户文案**。
- **#4 文本边界的三条判定**：工具轮的助手正文归 `thinking`（会被拼合链剔除，属过程叙述），终止轮正文才是 `final`；无叙述的工具轮不发 `thinking`（不产空事件）；**截断轮是例外** —— 它的正文是答案素材，一律不发 `thinking`，否则要么与 `final` 重复展示、要么把已作废内容推给用户。
- **#4 `delta` 不是权威值**：`delta` 只作渐进预览，`final.content` 才是权威值（前端收到即覆盖缓冲）。截断场景（CONTINUE 跨轮拼合 / CONDENSE 丢弃前缀）下只累加 delta，会把已作废的内容显示出来。
- **#3 软限制与硬打断不能互相替代**：`max_turns` / token 预算 / wall-clock 都是「这一轮结束后才判断」；kill switch 是「任意时刻立刻打断」。且 `CancelledError` 不重试不吞 —— **kill switch 优先于重试**（#13）。
- **#10 `length` 截断不能当答案返回**：CONTINUE 用 **prompt 式续写**（前缀回填 + system 指令），未采用 DeepSeek 的对话前缀续写，四条理由 —— ① `base_url` 是 client 级配置，为一条边缘路径把全框架押上 beta 通道不划算；② 前缀续写要求末条消息为 `assistant`，与「`tool` 消息必须紧跟带 `tool_calls` 的 `assistant`」冲突；③ 与思考模式的交互官方未定义；④ 该特性本意是**输出格式引导**，不是截断续写。实测（2026-09-11，`max_tokens=100` 强造两次截断）prompt 式已够用：两处接缝均为跨消息完整句，最终 401 字零重复。
- **#10 finish_reason 的两个陷阱**：`insufficient_system_resource` 与 `aborted` 是**服务端中断**，内容可能是半截，不能当最终答复（loop 判 `SERVER_INTERRUPTED`）；而且那次响应**已经计费**（见 #13「双计费不给假账」）。
- **#11 reasoning 回填是「按文档执行」的样本**：官方要求带 `tools` 的请求回填 wire 历史（缺失或为空即 400）。2026-09-11 实测 11 组条件（`deepseek-flash` / `deepseek-v4-pro` × 默认与 beta 端点 × httpx 裸调与官方 SDK × 流式与非流式 × 缺失 / 空串 / null / 部分回传）**均未复现该 400** —— 但不复现不等于契约不存在，框架仍按文档执行，以保留交错思考（模型跨工具调用复用推理链）。另注意 token 计数取 `usage.completion_tokens_details.reasoning_tokens`，**不是顶层同名字段**。
- **#5 三实现的能力差异要先声明再使用**：用 `saver.capabilities` 声明，避免「以为能回溯其实不能」。内存有历史；Redis `mode="history"`（Stream 流水账 + MAXLEN 裁剪 + TTL）有历史，`mode="latest"`（对齐 langgraph 的 `ShallowRedisSaver`）只留最新一帧，`load` / `history` 明确报能力错；Postgres 一帧一行有全历史。
- **#5 恢复的三个关键决定**：续跑以快照为起点、**计数器接着数**（轮数 / token 预算跨断点仍算数），已完成 Turn 的工具**不重跑**；快照停在「工具还没有结果」时先补做欠下的调用再继续，**不重问模型一次**；序列化 = JSON + 类型标签（`{"__charagent_type__": "datetime"}`）+ `schema_version` 逐级迁移（v1 裸消息列表 → v2 结构化 state；版本比当前新则拒读）。Postgres 用**同步驱动 + `asyncio.to_thread`**（psycopg 异步连接在 Windows 默认事件循环上不可用）。
- **#4 两条通道别混**：`event_sink` 是事件出口（传输必须可靠，异常向上传播），`HookPoint.ON_EVENT` 是扩展点（插件异常被隔离留痕）—— 同一份事件喂两条通道，P2 观测无需自建出口。
- **#7 压缩是「投影」不是「删历史」**（2026-09-22 落地）：账本（`state.history`）append-only 一字不改，每次模型调用前把它投影成一份**视图**（system + 摘要 + 最近 N 个提问）再发出去 —— 于是快照 / 续跑 / time-travel 回溯看到的仍是全量（快照只多了「压到哪一步」那两个字段）。三件套：窗口裁剪（切点只落在**提问**处，于是 assistant 与它的 `tool` 消息永远同进退，不会切出上游 400 的序列）、老工具结果截断（正在回答的那个提问的内容不截）、**滚动摘要**（连上一条摘要一起重压，不是只压新掉的那段 —— 只压新段的话更早的信息会被逐次稀释到消失）。触发靠**估算**（字符启发式 + 一个从上游真实 `input_tokens` 反推出来的固定开销；权威值只有 API 的 usage，估算只用来判阈值），且**判据量的是这一轮的投影而不是账本**（账本 append-only 只增不减，拿它判的话压完一次就永远超线 —— 滞回来自「投影因上一刀推过切点而变小」），压到「阈值 × 水位线比例」以下才停手（不然每次调用都得压一次，摘要调用也就每次都花一次钱）。摘要失败**本轮不切刀**（退到只投影：切点一旦推进，`[covers, cut)` 那段的原文就既不在摘要里也不在视图里），「允许丢信息」只留给上游明确报超窗口时的**紧急压缩**（`emergency`：不问阈值也不问水位线，裁到只剩最近 1 个提问）。降级原因走日志 + `metadata.view.warning` —— 失败时**不发** `context_compacted` 事件（什么都没压，就不该留一条「压缩过」的痕迹）。**投影与切刀是两件事**（2026-09-23 修，ticket 23）：投影**每一轮都做**（摘要替换掉它覆盖的那一段），阈值只管「要不要再切一刀」—— 曾经两者合成一句「不超阈值就原样返回」，而那个 `unchanged` 是**全量账本**，于是压过之后每隔一轮视图就失效一次、账本随即把估算顶回大值、再下一轮又切一刀（真机八轮模拟：2 压 3 跳、4 压 5 跳，摘要调用白烧一半）。**摘要那一次调用固定 `thinking=False` 且带自己的预算**（`summary_max_tokens`，2026-09-23 由 512 调到 1024）—— 真机实测：不关思考的话推理先把预算吃光、正文为空，于是「摘要失败」每压一次就报一次，整个第三件套在生产里等于没生效（`thinking` 那一步不改，是因为它漏掉的代价是整片功能静默失效，不该留给下一个接线的人；摘要是机械压缩，思考在这里买不到什么）。压掉的信息没有丢（旧帧还在快照里）；「长期记忆 + 按需检索」是另一个组件（#4 情景记忆），不在此列。不配 `compactor` 时行为与从前逐字一样。
- **#12 记录、水合、淘汰是三件事，别混**（2026-09-22 落地，ticket 17；说的是 #12 那几张实体表**什么时候写、怎么读回、什么时候能丢**）：快照管**接着跑**（会被压缩改写成摘要视图）；记录（`charagent_messages` / `charagent_runs`，见 `db/recorder.py`）管**给人看** —— 持久、只增不减、永不压缩；水合（`ChatSession._hydrate_once`）管**重启后把快照里的历史读回内存**。水合**不是** `resume`：后者是「接着跑」（补做欠着的工具调用再问模型一次），前者只读历史然后正常 `ask`。水合撞上「工具调用没有结果」的半路时，补一条「结果未知」的 `tool` 回填（进程可能死在工具执行中间，说「未执行」是撒谎；而丢掉那半截会把模型推向重发写操作）、**绝不重放**。会话内存只是**缓存**：`SessionRegistry` 因此可以按空闲 TTL 淘汰登记项，下一次 `acquire` 重新装配、由水合把历史接回来 —— 淘汰的正当性**来自**水合，两件事一起才成立（正在跑的会话永不淘汰）。记录写不进去只降级：日志 + 下一次成功写入时补一条**可见**的提示行（「这中间有一轮对话没能记录下来」），绝不让这一句问不出来；发不了事件是因为它跑在运行收尾之后 —— 那条流已被终局事件关掉。

**落地**：`agent/loop.py` + `agent/guard.py`（#1-3、#10-11）、`agent/compaction.py`（#7 估算器 + 策略 + 默认实现）、`stream/bus.py`（#4）、`checkpoint/`（#5，含 `utils/history.py` 的表格视图回放；v4 起进度含压缩的账）、`db/`（#12 五实体 + alembic 迁移 + 仓储 + `recorder.py` 的会话记录 —— 后者是 `db/` 的第一个生产调用方）。

> 上游（模型 / 网络 / 工具）都不可靠，这册决定出错时是优雅降级还是整个任务报废。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 13 | 模型重试 + 退避 + 幂等键 | 只重瞬态、退避带 jitter、重试本身就烧钱 | P0 |
| 14 | 熔断 + failover | 三态（关闭 / 打开 / 半开）+ 切换备份模型 | P1 |
| 15 | 工具超时 + 取消 | 分层超时（模型 60s / 工具 10-30s / run 总超时） | P1 |
| 16 | 运行状态机 | 模型只「建议」，推进状态的是执行层 | P1 |
| 17 | 幂等 + Saga 补偿 | 真实副作用必须防重；失败逆序补偿 | P1 |
| 18 | 流式中断 / 取消 | 优雅终止 + 释放资源 + 不半截状态 | P1 |
| 19 | 业务降级兜底 | 模板回复 / 搜索直出 / 固定 workflow / 部分结果 / 转人工 | P1 |
| 20 | 并发排队 + 异步任务队列 | 同一 thread 不并发写；长任务异步化 | P1 |

| 22 | 限流算法 | 四种算法 × 三个维度（user / tenant / model） | P1 |

**硬骨头**

- **#13 重试的边界**：只重试瞬态（429 / 5xx / 网络超时），4xx 直接放弃；判据读异常自带的 `retryable` 标记，**未声明的异常（工具错误 / 编程错误）一律不重试**；耗尽时最后一个异常**原样上抛**（traceback 保真）。
- **#13 退避与预算**：退避 = `min(initial_delay * multiplier^(n-1), max_delay)` 再乘 `(1 - jitter * u)`（jitter=0 纯指数、1 即 full jitter，等待永不越过基准）；上限三条 —— `max_attempts` / `max_elapsed_seconds`（**预判**：本次等待已会撞破预算就不等）/ `max_delay`。注入缝 `sleep` / `time_source` / `random_source` 让测试零真实等待、断言精确（#61）。
- **#13 双计费不给假账**：「上游中断」（`insufficient_system_resource`）那次响应**已经计费**，也当瞬态重试（可在构造期关掉），被丢弃的用量随 `on_retry` 的 `RetryAttempt`（含原样响应，可读 usage）交回调用方挂预算。
- **#13 重试放哪一层**：包在**模型调用层**（`RetryingChatModel` 组合包装 ChatModel，SPI 用法），loop 与 model 零改动 —— 这是「在哪切一刀」的典型判断。
- **#16 是全框架的主心骨**：模型只「建议」下一步动作，真正推进状态的是执行层（runtime）—— 这样多轮之间状态才一致、可控。状态集合：`created` / `running` / `waiting_tool` / `waiting_user` / `retrying` / `failed` / `finished` / `cancelled`。
- **#17 #18 副作用与取消是一对**：幂等键（`request_id` / `task_id` / `operation_id`）标识一次操作；Saga 正向依次执行、任一步失败**逆序补偿**；取消时要连带释放协程与连接，已执行的副作用关联幂等键走补偿，不留半截状态。
- **#17 的调用方定了：HITL 挂起-恢复（2026-09-24 改判）**。它挡的是「**同一个动作被执行两次**」，而框架里此前**不存在这条路径** —— 重试只包模型调用（见上一条「重试放哪一层」），工具执行是「跑一次 → 失败文本回填 → **模型自己决定要不要再发一次**」（`tool/executor.py` 的 `execute_tool` 永不抛异常、无循环、无超时），而模型重发**是一次新的调用**，不是同一个动作的重放。
  **2026-09-22 曾记过「两个都还没做，所以 #15 与 #17 要么一起做、要么都不做」—— 那条判断 2026-09-24 改判。** 原文给的理由是「超时造成『结果未知』，而『结果未知』必须先靠幂等解决」，这说的是 **#15 依赖 #17**，从头到尾没说 #17 依赖 #15：依赖方向是单向的，所以可以拆。而 #17 缺的从来不是"超时"这个调用方，是**任何**调用方 —— HITL 的挂起-恢复**正是原文自己点名的两条之一**，且恢复被触发两次不是理论风险（`POST /runs/{run_id}/resume` 是 HTTP 端点，双击、重发、重试都会产生第二次，而重放的是"给这一单付款"）。于是：**L3 做 #17，#15 继续推后**（分级超时那套设计原样留在上文，等真机上一次工具卡住时再取用）。
  重放的键是 `(run_id, message_id, tool_call_id)` —— 三列，不是两列（上游每轮从 `call_0` 重新编号，少了 `message_id` 在多轮之间会撞，见 `db/schema.py` 那段注释）。存储要**连持久化一起补**：P0 这个进程内 dict 记不住跨进程的重放，而两次恢复**跨进程**（`db/README.md` 已规划 `idempotency_keys` 表）。同一段话也写在 `retry/idempotency.py` 的模块 docstring 里。
- **#20 #21 #22 是同一问题的三个尺度**：进程内 asyncio 队列（单实例）→ 分布式锁（跨进程互斥，进程内锁失效）→ 限流算法（固定窗口 / 滑动窗口 / 令牌桶 / 漏桶）。P0 形态是进程内幂等 store，Redis + TTL + Saga 属后续阶段。

**落地**：`retry/policy.py`（退避与上限）、`retry/chat_model.py`（组合包装）、`retry/idempotency.py`（`IdempotencyKey` + 进程内 `IdempotencyStore`，claim / complete / release）、`retry/executor.py`。

### ③ 安全（#23-30）

> 危害成立需要三个条件同时具备 —— 这册的关键是**先判断危害是否真成立**，再决定护栏密度。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 23 | Prompt Injection 防护 | 致命三合一 + 四层纵深防御 | P1 |
| 24 | 工具沙箱 / 最小权限 | 只读账号、SQL 白名单、命令白名单、参数校验 | P1 |
| 25 | HITL 高危审批 | 挂起 → 人工批准 → 从断点恢复，不从头重跑 | P1 |
| 26 | 敏感信息脱敏 | 日志进之前先脱敏；按字段类型脱敏而非正则碰运气 | P1 |
| 27 | 审计 / 合规轨迹 | 合规官能重构出完整推理路径 | P1 |
| 28 | 数据合规删除权 | 物理删除 + 级联衍生数据 + 能证明已删 | P2 |
| 29 | 输出护栏 + 幻觉控制 + 引用溯源 | 输出侧同样要防注入；grounding + 拒答 + 逐句引用 | P1 |
| 30 | SSRF + RBAC + 密钥管理 | fetch URL 类工具就是攻击面；角色 + 密钥轮换 | P1 |

**硬骨头**

- **#23 危害成立的三个条件**：不可信输入（用户 / 外部文档）+ 私有数据 + 对外通信（工具能联网 / 发消息），**三者齐备才构成真正的注入危害**。防护是纵深四层（输入 / 检索 / 工具 / 输出），单层被绕过还有下一层兜底；外部文档只能当 data 读，不能当 instruction 执行。越狱与知识库投毒都是注入的变体。
- **#24 落点修订（2026-09-18）**：agent **不再直连业务库**，本难点的落地形态改为「agent 侧出站目标白名单 + 参数校验 / 业务系统侧 internal 端点收口读写权限 / 身份不进工具签名」；数据库侧的三条要求以「业务系统自己的最小权限」形式保留。
- **#25 高危审批的完整链条**：`needs_approval` 标记 → runtime 检测到就挂起（**绝不自动执行**）→ 挂起点持久化（记录挂在哪个 `tool_call` + 审批上下文）→ 审批后从断点恢复 → 拒绝回填失败原因给模型 / 超时走降级。**模型细化（2026-09-18）**：加**金额分层**（≤ 阈值且符合规则的不算高危，自动通过）与**角色分离**（发起方不得审批自己发起的挂起项）；「绝不自动执行」约束的是**被判为高危**的那些操作。
- **#26 与 #38 的交汇点**：脱敏必须发生在日志之前。要点不是「打码」而是**结构化脱敏** —— 知道这是个手机号，就按手机号规则打码，而不是靠正则碰运气。
- **#29 输出侧不能只靠输入侧防护**：工具返回内容被模型当指令执行、外部数据污染输出 —— 输出侧同样要护栏（有害内容过滤 / 格式校验 / 二次 PII 检查 / 防数据出逃）。幻觉缓解 = grounding（强制基于检索结果回答）+ 低置信转人工 + 明确「不知道」的拒答；引用溯源（逐句引用）是 RAG 落地的标配。
- **#28 与 #31 的软删除是两回事**：软删除为可追溯，合规删除要**物理移除**并级联到衍生数据（向量 / checkpoint 快照 / trace），且删除后要能证明已删 —— 不能「删了但检索还能搜到」。

**落地**：本册暂未落地为独立包（`agent/guard.py` 是 #3 的循环防护，不属本册）；#24 的落点已于 2026-09-18 修订；**#26 的日志脱敏**已于 2026-09-25 落地为 `redact/` 包（框架给规则与协议、业务给字段名单，见 `CharApp/docs/adr/0019`）—— 其中「按字段类型打码」那一半还等 #38 的结构化日志来喂，**框架自己打的异常栈**也还没过出口（同为 #38 的落点）。

**硬骨头**

- **#38 是后面三项的前提**：日志不结构化、id 不贯穿，#41 的 trace 检索与 #59 的调试都无从谈起。脱敏前置（#26）→ 结构化日志（#38）→ trace 回放调试（#59）是一条链。
- **#40 的价值在定位**：trace 里记版本号，出问题才能定位到「哪个版本、哪次运行」；灰度发布 + 回滚是配套动作。

**落地**：本册只落了 **#41 的一小块，而且没接外部 trace 工具** —— 项目自己写了一个只读入口
`CharAgent/client/trace.py`（`python -m CharAgent.client.trace <run_id> [--view]`）：按
`run → tool_call` 的层级打出一次运行的每一次工具调用（工具名 / 参数原文 / 结果 / 耗时 / 状态）
+ 三档用量与金额（金额与算式是**运行收尾那一刻算好写进库的**，见 `CharApp/docs/adr/0018`），
`--view` 那一档再打每帧的上下文视图与估算漂移；承载它的是 `charagent_tool_calls` 表
（2026-09-25 有了第一个生产调用方，见 `CharApp/docs/adr/0016`）。**没接 OpenTelemetry / Langfuse
那一类**：本项目要的是「给个编号就能回看这一次」，不是一套跨服务的 span 存储。
**#38 整片仍然空着**（结构化日志 + id 贯穿）：框架自己打的**异常栈**至今不过业务递给它的那个
日志出口（五个模块各自 `logging.getLogger("charagent.<子包>")`，仓里没有统一出口），#26 那半
「按字段名打码」也就还没有喂它的数据 —— 两件事同一个落点，等 #38 一起做。

### ⑦ 多 agent（#42-44）

> 三个 P2，但每个都是「设计阶段就要定」的选择题。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 42 | 多 agent 拓扑与状态共享 | Supervisor vs P2P；共享黑板 vs 私有记忆 | P2 |
| 43 | 多 agent 协作与纠错 | Critic 模式；subagent 失败不能拖垮主 agent | P2 |
| 44 | 多 agent 控制流风险 | handoff 循环检测；互相等待的死锁预防 | P2 |

**硬骨头**

- **拓扑与状态是两个独立决策**：不要捆在一起选 —— 拓扑决定「谁指挥谁」，状态共享决定「各自看到什么」。
- **三条控制流风险要显式处理**：子 agent 隔离（失败不外溢）、handoff 循环（A→B→A 要检测并打破）、死锁（多 agent 互相等对方结果）。

### ⑧ RAG（#45-49）

> 从「知识怎么进去」到「怎么证明检索变好了」。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 45 | 知识注入选型（RAG / 微调 / 长上下文） | 三者是组合关系，不是二选一 | P1 |
| 46 | RAG 数据摄取 | 垃圾进垃圾出，清洗比调 chunk 参数更根本 | P1 |
| 47 | RAG 检索工具 | 分块 / 父子索引 / 混合检索 / rerank / rewrite / 增量 | P1 |
| 48 | RAG 检索评估 | 三层排查：召回 / 排序 / 生成，先定位再优化 | P2 |
| 49 | RAG 前沿深化 | GraphRAG / RAGAS / 向量库选型与 metadata filter | P2 |

**硬骨头**

- **#45 三者的分工**：RAG 兜底知识广度（便宜、灵活、可解释、可溯源）+ 微调固化行为（风格 / 格式 / 术语，贵、需训练数据、知识更新要重训）+ 长上下文处理局部推理（跨文档、无检索误差，但贵、慢、受窗口上限）。
- **#46 决定检索上限**：文档解析、表格抽取（PDF 表格、扫描件 OCR 是真实项目的高频坑）、清洗去重、元数据提取（标题 / 章节 / 来源 / 时间戳，供 #32 过滤与 #29 溯源）。**摄取结果质量决定检索上限** —— 清洗比调 chunk 参数更根本。
- **#47 每一环都能单独优化**：chunk size / overlap 调优、父子索引（小 chunk 检索 + 大 chunk 喂模型）、embedding 选型、混合检索（BM25 + 向量）、rerank、query rewrite、增量更新。**一个易漏的坑**：embedding 模型升级后向量空间不兼容，旧向量不能与新查询混用 —— 需全量 re-embedding 或用版本号隔离。
- **#48 先定位层再谈优化**：检索不到（召回问题）/ 检索错（排序问题）/ 生成错（生成问题）；指标用命中率、MRR、忠实度、幻觉率；积累 badcase 集做回归。**「怎么证明 RAG 变好了」必须用指标对比，而不是「感觉准了」**。

### ⑨ 能力扩展（#50-54）

> 五个 P2，但彼此定位差异很大 —— 混起来会选错。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 50 | MCP 集成 | 三类能力（不止 tools）+ 传输从 SSE 到 Streamable HTTP | P2 |
| 51 | Agent Skills | 三级渐进披露 + 三级路由；description 是路由的索引 | P2 |
| 52 | A2A 协议 | Agent Card + 任务与消息；agent ↔ agent | P2 |
| 53 | 多模态 agent | 视觉输入 / 多模态工具 / image 消息结构 | P2 |
| 54 | 代码解释器 / 工具执行环境 | 沙箱 + 资源限制 + stdout / stderr / 产物回填 | P2 |

**硬骨头**

- **#50 别把 MCP 只当工具**：三类能力是 tools / resources（只读资源）/ prompts（提示词模板）；生命周期 `initialize` → `tools/list` → `tools/call`；`sampling` 允许 server 反向请求 client 调 LLM；多 server 场景要解决工具发现、权限、路由、同名仲裁。
- **#51 与 MCP 的分工**：MCP 提供「**连接**」（怎么调到工具），Skill 提供「**知识**」（怎么做好某类任务），两者互补而非替代。路由三级：L1 规则粗筛（关键词 / 意图）→ L2 语义召回（embedding top-k）→ L3 模型终选。选错要能检测并让它重选。
- **#52 一句话区分**：MCP 是 agent ↔ 工具，A2A 是 agent ↔ agent。
- **#54 与 #24 是同一件事的两面**：执行环境（E2B / Docker / 子进程隔离）必须配资源限制与超时（CPU / 内存 / 磁盘）；执行结果 stdout / stderr / 文件产物要回填给模型。

### ⑩ 架构与策略（#55-57）

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 55 | Planning 范式 | ReAct / Plan-and-Execute / Reflection / Replan 的区别在「计划何时产生、何时修正」 | P2 |
| 56 | Workflow vs Agent | 路径确定用 workflow，不确定才用 agent | P2 |
| 57 | Agent 框架对比 | 落点不是选型，而是能否讲清「框架替你做了什么」 | P2 |

**硬骨头**

- **#56 的实践原则**：用 workflow 做骨架兜底，**局部**不确定环节才用 agent —— 而不是整个系统二选一。
- **#57 的判断标准**：何时用框架、何时自研，核心诉求是**控制力还是开发速度**；LangGraph 的图模型 vs 手写 while 循环的差异要能说清。面试表达上，「能讲清框架替你做了什么、为什么那么设计」是理解深度的分水岭。

### ⑪ 评估与迭代（#58-60）

> 测试回答「代码对不对」，这一册回答「输出好不好」。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 58 | Agent 评估体系 | 四维度 + LLM-as-judge 的三种偏差与三种缓解 | P2 |
| 59 | Agent 调试 | 靠 trace 回放而非复现 —— 因为行为本身有随机性 | P2 |
| 60 | 数据飞轮 | 收集 → 归因 → 对症下药 → 回归验证 | P2 |

**硬骨头**

- **#58 四个维度**：任务成功率（端到端做完没有）、工具选择正确率、回答质量（相关性 / 忠实度 / 无害性）、轨迹质量（有没有走弯路、反复调同一个工具）。
- **#58 LLM-as-judge 的三种系统性偏差**：位置偏差（偏爱排前面的）、长度偏差（偏爱长的）、自我偏好（偏爱自己模型的输出）。缓解：多 judge 交叉打分、交换候选顺序、用结构化 rubric（明确打分标准而非自由发挥）。
- **#59 为什么 agent 难调试**：普通程序行为确定，agent 行为有随机性（温度采样），同一输入可能不同输出 —— **所以要靠 trace 而非复现**。定位时回看当时上下文，判断是 prompt 问题、工具结果问题还是模型本身问题（决策归因）。
- **#60 闭环四步**：badcase 收集（点踩 / 人工标注 / 自动检测）→ 归类到「检索 / 生成 / 工具 / 意图」（**而不是笼统说「答错了」**）→ 对症下药（调 prompt、改工具描述、加 skill、补数据）→ 回归验证并让 badcase 进评估集。没有数据飞轮的 agent 是一次性的。

### ⑫ 测试（#61-63）—— 全册 P0

> 三册全 P0：可测性与「能跑」同级。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 61 | mock 与确定性 | mock LLM 三形态 + 注入随机源（seed 有明确边界） | P0 |
| 62 | 分层测试与轨迹断言 | 三层测试 + 断言工具调用轨迹 + 统计通过率 | P0 |
| 63 | 快照 / 契约测试 + 测试边界 | 快照防回归；测试与评估的边界要划清 | P0 |

**硬骨头**

- **#61 mock LLM 三形态**：固定返回 / 脚本化序列返回（第一次调 A 第二次调 B）/ 录制回放（record-replay）—— 让 loop 测试不依赖真实模型。
- **#61 确定性的边界必须写清**：`temperature=0` + `seed` 固定 + 注入随机源。**但思考模式下 `temperature` 不生效、`top_p` 下限 0.95、`seed` 仅保证 content 可复现** —— 想靠 seed 让整条链路（含 reasoning）可复现是不成立的。
- **#62 轨迹断言**：不只断言最终答案，还断言「调了哪些工具、调用顺序、参数」是否符合预期轨迹；非确定性测试用**多次运行的通过率**，而非单次通过。
- **#63 测试与评估的分界**：测试测「代码对不对」（确定性，可 mock），评估（#58）测「输出好不好」（非确定性，用 LLM-as-judge）—— 划线划错会导致两边都做不好。

### ⑬ 工程化与部署（#64-67）

> 从「本机能跑」到「多实例、可发布、不泄漏」。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 64 | 无状态化与水平扩展 | 状态外置；agent 任务长且有状态，drain 要专门设计 | P2 |
| 65 | asyncio 并发模型 | 阻塞 IO 陷阱、取消语义、GIL 下的模型选择 | P0 |
| 66 | 延迟优化 | 流式场景用户感知的是 TTFT，不是总延迟 | P2 |
| 67 | 工程化底座 | 连接 / 配置 / 迁移 / 依赖 / 泄漏 / 异常六件套 | P2 |

**硬骨头**

- **#65 是 P0 的原因**：阻塞 IO 陷阱（sync `requests` 会阻塞事件循环，必须 `httpx.AsyncClient`）、`asyncio.gather` 的 `return_exceptions`、取消语义（`Task.cancel` 与 `CancelledError` 传播，对应 #18）、GIL 下 asyncio / 线程池 / 进程池的选择。
- **#64 agent 任务的特殊性**：直接 kill 会丢进度。graceful shutdown 要有 drain 策略（SIGTERM → 停止接新请求 → 等存量任务完成或迁移）；**#5 的状态外置 + 断点续跑正是让 drain 可选的底座**。另需权衡 sticky session vs 状态外置，以及进程内队列（#20）在多实例下的升级路径。
- **#66 的关键区分**：TTFT（首 token 延迟）vs 总延迟 —— 流式场景用户感知的是前者；手段是缓存命中、模型分级（#36）、减少工具往返。
- **#67 六件套**：连接池生命周期（复用 / 泄漏 / 池耗尽）、配置与 secrets（12-factor）、schema 迁移（alembic）与向前兼容、依赖锁定与 SDK 升级不兼容、长运行进程的资源泄漏（task 泄漏 / 缓存无界增长 / 连接未关闭）、异常分类与上报（Sentry）—— **注意这最后一条区别于 #2 的 agent 错误自纠错**。

### ⑭ 横切基础点（#68-70）

> 不单独属于某一层，但每一层都被它们影响。

| 编号 | 难点 | 要害 | 阶段 |
|------|------|------|------|
| 68 | 横切点（工具描述 / 采样 / 思考模式约束 / 背压） | 工具描述写给「没见过系统的初级工程师」看 | P0-P1 |
| 69 | Prompt Engineering | system prompt / few-shot / CoT / 版本化与 A/B | P0-P1 |
| 70 | 工具设计方法论 | 粒度 / 数量 / 参数三条 tradeoff | P0 |

**硬骨头**

- **#68 工具描述的标准**：要明确参数含义、副作用、失败模式、使用时机 —— 模型才能正确选择何时调用（落地 `tool/decorator.py`）。
- **#68 思考模式的采样约束（实测 2026-09-11 `deepseek-flash`）**：`temperature` 不生效（设置不报错但被忽略）；`top_p` 下限 0.95（更小值被静默抬升）；`seed` 仅保证 content 可复现，reasoning 每次不同。另需透传 `max_tokens`（**思维链与正文共享配额**；官方取值 1 ~ 384K，不传时非思考默认 8K / 思考 64K / effort=max 时 128K）与 `thinking` / `reasoning_effort`（默认开启且 effort=high，是成本大头）。**思考模式有两条独立开关路径**：`thinking.type`（enabled / disabled）与 `reasoning_effort`（none / low|high|max）—— 同时显式传入且方向相反时服务端行为未定义，框架在 `model/utils/config.check_thinking_params` 里 **fail fast**。
- **#69 与 #8 的区别（面试常考）**：prompt 工程管「**指令怎么写**」，上下文工程管「**信息怎么组织进窗口**」。
- **#70 三条 tradeoff**：粒度（一个工具只做一件事 —— 太粗难被正确调用、太细增加选择负担）、数量（工具越多模型越容易选错）、参数（越少越好，复杂参数用结构化 schema）。
