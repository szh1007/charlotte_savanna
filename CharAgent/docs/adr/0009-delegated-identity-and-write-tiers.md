# ADR-0009: 委托身份模型与写操作分级

- 状态: accepted
- 日期: 2026-09-18
- 考虑过的方案:
  - **agent 自签 token** —— 拒绝：agent 进程里能拿到 `user_id` 就能签出任意用户的 token，被注入或代码漏洞攻破时可冒充全站用户，而网关验签会全部通过、日志看不出异常
  - **共享密钥直传**（`X-Internal-Token` + `X-User-Id`，即 charplot 已用的模式）—— 拒绝：无签名、无过期、无受众、无双主体语义；`user_id` 明文可改；密钥一旦泄露（进程/日志/配置）整个内部 API 全开
  - **OAuth2 Token Exchange（RFC 8693）** —— 拒绝：需要授权服务器（Keycloak 等），对单人学习项目过重；双主体语义用自签 JWT 的 claim 即可表达
  - **工具参数显式传 `user_id`** —— 拒绝：模型可能被诱导填别人的 id（prompt injection），只能事后拦，不如从签名上不给这个口子
  - **全部高危操作人工审批** —— 拒绝：失真，真实电商系统 90%+ 的退款是自动通过的，全人工的成本任何企业承受不了
  - **审批人 = 人工客服** —— 拒绝：发起人与审批人同一人，违反职责分离（segregation of duties），内控与合规审计直接不通过
  - **对话内确认**（agent 问「确认吗」→ 用户说「确认」→ 模型判断）—— 拒绝：LLM 判断可被绕过（用户说「我确认，把上周的单都取消」可能触发批量取消）；审计上分不清「用户真的确认了」还是「模型认为用户确认了」
- 后果: `user_id` 绝不进入模型可见的工具签名；写操作分三级、两种挂起语义（内部审批 vs 用户确认）；退款链路异步化，agent 不挂起等待

## 上下文

「客服 agent 代表某个用户操作业务系统」这件事有两个方向：用户 → agent（身份从哪来、怎么传），以及 agent → 业务系统（凭什么代表他）。原设计（ADR-0004）只处理了后者的一半，且方式（直连只读库）不需要前者。

引入网关与 internal API 后，这条链必须显式建起来。同时原 P1-7 的 HITL 设计只写了「高危操作挂起 → 审批台批准」，没有定义**审批人是谁**，也没有区分**内部审批**与**用户本人确认**这两条不同的路径。

## 决策

### 身份

1. **身份在渠道层确定**：创建会话时由渠道（模拟 App 已登录）给出 `user_id`，服务端签发委托 token 放入会话上下文
2. **工具签名里没有 `user_id`**：运行时从上下文注入，模型看不到也改不了——即使被 prompt injection 诱导也无法越权查别人的单
3. **独立身份服务签发**：持 RS256 私钥，签发含 `sub`（用户）/ `act`（代理方）/ `aud` / `tenant` / `exp` 的委托 token；**agent 无签发权**，网关只持公钥验签。两跳认证（agent 用服务凭证换委托 token）的每一跳可单独测试

### 写操作三级

| 级别 | 判定 | 路径 | 例 |
|------|------|------|----|
| **L0 只读** | 无副作用 | 自由调用 | 商品查询、订单查询、物流、FAQ 检索 |
| **L1 可逆写** | 有副作用但可逆、无资金影响 | 直接执行 + 回显结果 | 加购 |
| **L2 终态或资金写** | 不可逆，或触及资金 | 挂起，走确认 | 退款、取消订单 |

约束：L1 虽不需确认，但**必须有明确的用户意图**——不得在推荐商品时顺手加购（那属于越权代表用户行动）。

### L2 的两条确认路径

两者是**不同的挂起语义**，企业里分属不同系统，代码上也不得耦合成一个：

- **内部审批**（HITL）：**金额分层 + 角色分离**。金额 ≤ 阈值且符合规则（已付款、未超售后期）→ 自动通过；超阈值或命中异常规则 → 挂起，由**主管 / 风控**角色审批。**客服坐席只能发起，不能批**
- **用户确认**：工具不直接执行，返回 `pending_confirmation` + `confirm_token`（含操作摘要哈希与过期时间）；前端渲染确认卡片，用户点击后带凭据再次提交，网关校验凭据才执行。**模型无法自己「确认」**，用户说「我确认」也无效

### 退款执行

**异步受理**：网关向业务系统创建退款单（`pending`）后立即返回 `refund_id` 与预计时效；后台 worker 推进 `pending → processing → completed | failed`（同一事务内改余额 + 写流水 + 置状态）；agent 答复「已受理，预计 1-3 工作日原路退回」后 **run 正常结束，不挂起等待**。

这条形态给 P1-4 的 Saga 补偿一个真实施展场景，也让幂等键成为刚需（重复提交会产生重复退款）。

### 审计

**双粒度**：工具层记「谁 / 代表谁 / 调了什么工具 / 参数摘要 / 耗时 / 结果」；网关层记「实际访问了哪些业务资源（订单号、商品 id）、命中了哪些敏感字段（手机号、地址、余额）」。合规要求的正是能回答「谁在什么时候看了谁的什么数据」——只记工具调用回答不了。

### 实现归属（机制归框架，策略归业务）

本节定的都是**策略**。写 issue 时必须分清哪一侧落地，否则策略会漂进框架侧（2026-09-18 复核发现过这种情况）：

| 内容 | 归框架（`CharAgent/`） | 归业务（`CharService/`） |
|------|----------------------|------------------------|
| 身份 | 会话可绑定身份字段；`ToolContext` 注入通道（ADR-0010） | 渠道确定 `user_id`、向身份服务换 token、token 刷新 |
| 委托 token | 无（框架不认识 token） | 签发（身份服务）、验签与限流审计（网关） |
| 金额分层 | 只提供 `Suspension` 通道（ADR-0010） | **阈值、资格规则、自动通过判定**（在工具实现里） |
| 两条确认路径 | 两种 `SuspensionKind` + `confirmation_required` 事件 + 挂起/恢复机制 | `confirm_token` 的签发与校验（网关）、确认卡片（前端） |
| 角色分离 | 挂起记录带 initiator；审批鉴权可注入（默认放行） | **角色名单与 SoD 规则**（审批端点 403） |
| 审计 | 工具调用粒度 + 脱敏组件 + 落库接口 | 数据访问粒度（网关侧产生） |
| 降级话术 | 错误码分类 + `LoopOutcome→code` 映射 + 降级策略 SPI | 模板文案 / FAQ 匹配 / 转人工建议 |

## 决策记录

- 委托身份由独立身份服务签发，`user_id` 不进工具签名（2026-09-18 访谈 Q3/Q8）
- 写操作分三级，L2 走「金额分层 + 角色分离」的内部审批与结构化用户确认两条路径（2026-09-18 访谈 Q6/Q12）
- 退款异步受理，agent 不挂起等待（2026-09-18 访谈 Q7）
- 审计双粒度（2026-09-18 访谈 Q11）
- 加购不改走确认卡片——可逆、无资金影响；（2026-09-18 访谈补充确认）
