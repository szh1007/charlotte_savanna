一、先看一个你会遇到的现象

不看定义，先看现场。下面这段代码是真实项目里会出现的东西，和隔离级别有关：

-- 事务 A
BEGIN;
SELECT balance FROM wallet WHERE user_id = 42;   -- 读出来：100

-- 此刻事务 B 提交：给 42 号转了 50 块

SELECT balance FROM wallet WHERE user_id = 42;   -- 再读一次，读到多少？
COMMIT;

第二次 SELECT 读到 100 还是 150？

答案取决于你在哪个数据库上跑 —— MySQL 默认读到 100，PostgreSQL 默认读到 150。 两个库都在你项目里跑着（MySQL 是 minimall，PostgreSQL 是 CharAgent 的快照层），所以这不是学术问题，是你代码里正在发生的事。

这就是隔离级别。它的定义只有一句话：

一句话定义

隔离级别 = 并发事务之间「能看见对方多少」的约定。

它不是「越严越好」—— 每往上加一层隔离，你就要多付一层代价（锁更多、冲突更多、甚至要重试）。面试问这个，考的是你能不能说清那条取舍线画在哪、为什么画在那儿。

二、先把出问题的现象认全

你要背的不是级别，是异常。级别只是「容忍哪些异常」的组合。三个异常，全部用同一个例子讲：

场景

你去柜台取号，柜员查你的账户余额，然后你问「能不能给我打个余额证明」，柜员再查一次 —— 两次查询之间，你老婆在另一个窗口转走了 400 万。

① 脏读（Dirty Read）—— 读到了别人还没提交的东西

柜员读了另一个窗口正在操作但还没确认的余额，告诉你「你有 500 万」。然后那个操作被撤销了 —— 你依据一个从未真实存在过的数字做了决定。

危险在哪：你看到的数据从来没被系统承认过。这是三个异常里唯一一个「看到不存在的世界」的。

② 不可重复读（Non-Repeatable Read）—— 同一条记录，读了两次，值不一样

柜员第一次查是 500 万，第二次查是 100 万。两次读的是同一行，中间被别人改了并提交了。

危险在哪：一个事务内部自相矛盾。如果你拿第一次的读数去算利息、拿第二次的读数去扣款，结果就是错的。

③ 幻读（Phantom Read）—— 同一组条件，查了两次，行数变了

柜员查「余额大于 100 万的所有账户」，第一次查出 3 个。她再查一次 —— 4 个。多出来的那一个，是别人新插入的。

和②的区别：②是已有行被改，③是结果集里凭空多出/少了行。这个区别是理解 InnoDB 间隙锁的唯一入口，别跳过。

三、四个级别 = 四种「容忍哪些异常」的选择

SQL 标准定义了四个级别。它们不是四套不同机制，而是同一条光谱上的四档：

隔离级别 脏读 不可重复读 幻读 直觉
READ UNCOMMITTED 可能可能可能 几乎不做隔离
READ COMMITTED 不可能可能可能 只看别人已提交的；每条语句重新取一次快照
REPEATABLE READ 不可能不可能标准允许可能（MySQL 用间隙锁消除） 整个事务一个快照
SERIALIZABLE 不可能不可能不可能 等价于串行执行
面试的坑就在最后一行

「REPEATABLE READ 防止幻读」这句话，在 MySQL 上成立、在 PostgreSQL 上要小心。 PostgreSQL 的 RR 在官方文档里叫 snapshot isolation（快照隔离），它不阻塞写入 —— 两个事务各读各的快照、各自写入，不一定有谁来报错。仍有异常能漏过去（写偏斜）， 要彻底解决得用 SERIALIZABLE（PG 的实现叫 SSI）。

MySQL 的 RR 则通过 next-key lock（记录锁 + 间隙锁） 把间隙也锁住，所以插入会被挡住，幻读在 MySQL 的 RR 下确实被压掉了。

一句话记住：MySQL 的 RR ≈ 快照读 + 间隙锁堵幻读；PostgreSQL 的 RR = 纯快照隔离，更接近标准的 SERIALIZABLE 由 SSI 兜底。

四、回到你的 Django 项目

上面那个 100 还是 150 的问题，在你项目里的样子：

from django.db import transaction

with transaction.atomic():
    a = Profile.objects.get(user_id=42).balance      # 第一次读

    # ……这中间，另一个进程/请求改了并提交了（比如充值到账）

    b = Profile.objects.get(user_id=42).balance      # 第二次读
    print(a, b)
  • 跑在 MySQL（你的 app.minimall）上 —— 默认 REPEATABLE READ，a == b
  • 跑在 PostgreSQL（你的 CharAgent 快照层）上 —— 默认 READ COMMITTED，a != b

同一个 transaction.atomic()，两个数据库给出不同结果。 Django 不会替你屏蔽这个差异 —— atomic() 管的是「要么全做要么全不做」（原子性）， 不管「事务内两次读之间别人能不能改」（隔离性）。这两件事经常被混在一起，面试里说出来就是区分度。

可以查一下你自己的库 
-- MySQL
SELECT @@transaction_isolation;

-- PostgreSQL
SHOW transaction_isolation;

六、留下来反复看的东西

参考答案：面试被问「你们用的什么隔离级别」的 60 秒口述

「我们 MySQL 侧走 InnoDB 默认的 REPEATABLE READ，也就是说一个事务里的多次读看到同一个快照， MySQL 还会用 next-key lock 把范围间隙也锁住，所以幻读在我们的读路径上基本不出现。 代价是并发写同一范围时会互相等，我们的写操作都用 select_for_update() 显式加锁， 而不是依赖隔离级别的隐式锁 —— 因为隐式锁的行为在不同版本和不同索引设计下不一样，显式的更好推理。 PostgreSQL 侧（快照层）走的是默认的 READ COMMITTED，因为那块不需要跨语句一致性， 反而更在意并发度，RC 的锁更少。」

注意这段话的结构：级别 → 它带来什么保证 → 代价 → 我怎么处理代价。面试官要的是这条链，不是名字。

三个异常的最小判据（先自己回忆再看）
异常一句话判据关键差异
脏读 对方没提交我就读到了 唯一一个「数据从未存在过」的
不可重复读 同一行读了两次，值不一样，中间对方已提交 对方已提交
幻读 同一条件读了两次，行数不一样 变的是集合，不是值

记忆锚：脏读 = 未提交 · 不可重复读 = 同一行 · 幻读 = 结果集。

概念扩展：缓存三兄弟的对照卡（矫正诊断里那次术语错位）
名字它到底是什么解法你项目里的对应
穿透 查的数据根本不存在，缓存和数据库都没有 → 每次都打到库 空值缓存（+ 布隆过滤器） cache.py 里缓存空结果那段
击穿 单个热点 key 过期瞬间，大量并发同时去重建它 分布式锁，只让一个请求去查库回填 cache.py:_lock_and_load() 的 SETNX + Pub/Sub
雪崩 大批 key 同时失效（或缓存整个挂了），请求一起涌向数据库 TTL 加随机抖动、多级缓存、熔断 cache.py 里的 TTL 随机化 ±20%

区分口诀：穿透 = 数据不存在；击穿 = 一个 key 过期；雪崩 = 一批 key 同时过期。
