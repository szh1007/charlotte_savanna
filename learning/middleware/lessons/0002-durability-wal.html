零、先清一笔旧账（两分钟，别跳过）

上一课讲的是「事务之间能看见对方多少」。现在换个方向，问一个更基础的问题：

不看第 1 课，用一句话说清「不可重复读」和「幻读」的分界线是什么？

变的是「某一行的值」还是「结果集的行数」。 同一行读了两次值不同 → 不可重复读；同一条件读了两次行数变了 → 幻读。

想不起来也正常 —— 这恰恰说明「需要提取而不是重读」。翻回 第 1 课的测验做一遍，比把正文重看一遍有用得多。

一、先问一个反直觉的问题

你执行了 COMMIT，数据库回你「成功」。此刻 ——

问题

此刻，这行数据被写进磁盘了吗？

答案是 大概率没有。数据还在内存里。而且更反直觉的是：这不是 bug，这是设计。

如果每次提交都要把数据行写到磁盘上它该在的位置，那你一生中大部分提交都会卡在磁盘的寻道上 —— 数据行散落在表空间的各个位置，一次提交可能只改一个字段，却要随机写好几个页。 那么问题就变成了：明明没写进去，它凭什么敢跟你保证？

二、答案是一条路径，不是一个开关

要讲清楚 D，你得先在脑子里画出三层存储。这三层的区别就是整节课的骨架：

层是什么进程崩溃会丢吗断电会丢吗
① 进程内存 redo log buffer、数据页缓冲 丢 丢
② OS page cache 进程已经 write() 给操作系统了，但 OS 还没往盘片上送 不丢 丢
③ 磁盘 fsync() 之后才算真正落地 不丢 不丢
这三层是整个「持久化」话题的地基

write() ≠ 落地。 write() 只是把数据交给了操作系统 —— 它进了 page cache， 进程崩了没事，机器断电就没了。 只有 fsync()（或 fdatasync()）才是「把这份数据交给物理设备」。

面试里凡是问「会不会丢数据」，本质都在问同一句话： 「哪一层为止？用什么频率叫 fsync？」

三、Write-Ahead Log：把随机写换成顺序写

现在可以回答第一节那个问题了。数据库用的办法叫 WAL（Write-Ahead Log，预写日志）：

一句话定义

在把数据行写回它该在的位置之前，先把「我改了什么」顺序追加到一个日志的末尾。

为什么这样就能快：

  • 数据行是随机写 —— 表空间里 A 表第 3 页、B 表第 800 页，一次事务改几处就得跳几次，机械盘上每次都是寻道
  • 日志是顺序追加 —— 永远往末尾写，不需要找位置。这是磁盘最喜欢的访问模式
  • 而且日志可以攒一批再刷 —— 一次 fsync 覆盖几十个事务，平摊下来每次提交的代价就很小了

那数据行什么时候写？交给后台线程慢慢来（MySQL 的 page cleaner、PostgreSQL 的 checkpointer / background writer）。反正崩溃重启时，日志里有完整的记录，照着重放一遍就能把欠的补上。

于是「提交成功」的真实含义是

「我改了什么」这条日志，已经落到磁盘上了 —— 而不是「数据已经写进它最终的位置」。 这是第 5 题那个空缺的标准答案，也是区分「背过 ACID」和「理解 ACID」的分界线。

四、关键转折：安全不是绝对的，是个旋钮

到这儿有个陷阱。你可能以为 D 是「要么保证要么不保证」的二值属性 —— 不是。

「每次提交都叫一次 fsync」是可以关掉的。 关掉之后性能大涨，代价是崩溃时丢掉最近一小段。 下面是两个库各自的旋钮：

MySQLPostgreSQL
旋钮名 innodb_flush_log_at_trx_commit synchronous_commit
默认值 1（每次提交 fsync） on（每次提交 fsync）
调松它 2：提交时只写到 OS page cache，每秒才 fsync 一次
0：连 OS page cache 都不一定写，每秒一次		 off / local：提交时不 fsync，交给 WAL writer 稍后刷
付出什么 掉最近的 1 秒事务 掉最近的几十毫秒到一小段 WAL
换来什么 大量小事务的吞吐（省掉每次提交那次同步 IO）

注意两个库的默认值不同：MySQL 默认就选最安全的那一档，PostgreSQL 把 synchronous_commit 的默认值定在 on，但整个 PostgreSQL 生态里大量部署把它调成 off 换吞吐。这是刻意的设计取舍，不是谁的疏忽 —— 而你在面试里能说出「这两个默认值不一样、为什么」，比背 ACID 五个字强得多。

六、为什么会有两个日志

你如果去翻 MySQL 的目录，会发现有两个日志在同时写：redo log 和 binlog。为什么不合并成一个？

redo logbinlog
谁写的InnoDB 存储引擎MySQL server 层
内容物理层面的页改动 ——「第 N 页第 M 个偏移改了这几个字节」逻辑层面的语句/行变更 —— 给复制用
干什么用崩溃恢复：重启后把没落盘的数据页补回来主从复制与基于时间点的恢复
能循环用吗能 —— 数据页落盘后，这段日志就可以被覆盖不能 —— 从库还没消费完就不能删

它们职责不同，所以必须同时写。而「必须同时写」就带来一个新问题：两份日志怎么保证一致？ 如果 redo 写成功了、binlog 没写成功就崩了，重启后主库有这条数据、从库没有 —— 主从直接不一致。

MySQL 的解法是两阶段提交（2PC）：redo log 先写 prepare 状态 → binlog 写 → redo log 写 commit 状态。 崩溃恢复时，如果一个事务的 redo 是 prepare 但没有对应的 binlog，就回滚掉它。 这个机制的名字值得记住，它是「跨组件一致性」的经典模板 —— 后面讲消息队列的 outbox 模式时，你会看到同一个思路换个场景又出现一次。

七、留在你项目里的痕迹

你已经在不知不觉地做持久化取舍了
  • CharAgent 用 PostgreSQL 存快照 —— 这个选择的隐含前提是「快照必须真的持久」， 也就是说你的 synchronous_commit 不能关。如果哪天为了吞吐把它调成 off， 那就等于接受了「断电后最近几次 run 的断点信息可能丢」—— 而你还指望 --resume 能续上。
  • minimall 用 MySQL —— 走的是默认 1，也就是说订单、余额这类数据 在「提交成功」之后是真的算数的。这一档换来的是每次下单都付一次同步 IO 的代价 —— 在你自己跑的单机环境里看不出来，但它是真实存在的成本。
  • 你的 Redis 缓存是故意不持久的 —— 这是个「正确的取舍」，因为缓存丢了能重算。 但同样的道理，Redis 一旦被用来存不能重算的东西（比如你项目里的分布式锁、或者会话）， 持久化配置就必须重新讨论。这条我们留到缓存那节课。

九、留下来反复看的东西

60 秒口述：被问「你们的数据库怎么保证不丢数据」

「分两层说。第一层是机制：数据库不会在提交时把数据页写回它该在的位置，那样太慢， 它走 WAL —— 先把改动顺序追加到日志里并 fsync，数据页由后台线程慢慢刷，崩溃了就靠日志重放。 所以我们说的『提交成功』，准确含义是『改动日志已经落盘』。 第二层是旋钮：这个 fsync 是可以关的。MySQL 的 innodb_flush_log_at_trx_commit 默认是 1， 也就是每次提交都同步落盘，我们线上保持默认，因为订单和余额不能丢； PostgreSQL 那边 synchronous_commit 也是 on，因为我们的快照层要支持断点续跑，丢了就白跑。」

结构：机制一层 + 取舍一层 + 我为什么这么选。三层缺一层都会显得像背的。

三层存储的判据（先自己回忆再看）
问题答案
进程崩溃还活着吗看数据有没有离开进程内存（write() 过没有）
断电还活着吗看数据有没有被 fsync() 送到物理设备
怎么知道该担心哪一层问自己：这个旋钮是在「每次提交」还是「每秒」叫 fsync

概念扩展：第 1 课的隔离级别，和本课的持久性怎么合起来记

ACID 里的这四条，各自在问一个不同层的问题 —— 分开记才不糊：

字母在问什么由什么实现
A 原子性一半成功一半失败怎么办undo log（做错了怎么撤回）
C 一致性约束和业务规则前前后后成立吗靠前面三条兜出来的结果，不是独立机制
I 隔离性并发事务之间能看见对方多少MVCC + 锁（第 1 课）
D 持久性说成功了之后能不能扛住崩溃WAL（本课）

容易混的一对是 undo 和 redo：undo 是「反悔用的」（要回滚时照着它撤）， redo 是「补课用的」（崩了之后照着它重放）。一个往前翻，一个往后翻。
