# ⑪ 评估与迭代（#58-60）

> 返回 [难点清单索引](../README.md#难点清单)

| ID | 难点 | 详细细节 | 阶段 |
|----|------|----------|------|
| 58 | Agent 评估体系 | • 评估维度：任务成功率（端到端做完没有）、工具选择正确率（该用哪个工具用对没有）、回答质量（相关性 / 忠实度 / 无害性）、轨迹质量（有没有走弯路、反复调同一个工具） | P2 |
| | | | • LLM-as-judge：用 LLM 当裁判给 agent 输出打分，省人工但 LLM judge 有系统性偏差——位置偏差（偏爱排前面的）、长度偏差（偏爱长的）、自我偏好（偏爱自己模型的输出） | |
| | | | • 缓解 LLM judge 偏差：多 judge 交叉打分、交换候选顺序、用结构化 rubric（明确打分标准而非自由发挥） | |
| | | | • GoldenSet 构建：评估集要覆盖难易分布和场景分布，标注成本是瓶颈，常见做法是线上采样 + 人工精标 | |
| | | | • 离线评估 vs 在线评估：离线用固定评估集跑回归，快但与真实分布有偏差；在线看真实流量指标，准但慢 | |
| 59 | Agent 调试 | • trace 回放：agent 出问题时，从记录的 trace 恢复执行现场，逐步回看每一轮模型看到了什么、做了什么决定 | P2 |
| | | | • 决策归因：模型为什么这么选？回看当时的上下文（prompt、历史、工具结果），定位是 prompt 问题、工具结果问题还是模型本身问题 | |
| | | | • 为什么 agent 难调试：普通程序行为确定，agent 行为有随机性（温度采样），同一输入可能不同输出，所以要靠 trace 而非复现 | |
| 60 | 数据飞轮 | • badcase 收集：用户点踩、人工标注、自动检测（工具报错、护栏拦截）都是 badcase 来源 | P2 |
| | | | • 归类分析：把 badcase 归因到「检索问题 / 生成问题 / 工具问题 / 意图问题」，而不是笼统说「答错了」 | |
| | | | • 改进闭环：根据归因对症下药——调 prompt、改工具描述、加 skill、补数据 | |
| | | | • 回归验证：改进后跑评估集确认没退化，badcase 进评估集防止再犯 | |
| | | | • 这是 agent 持续变好的核心方法论：没有数据飞轮的 agent 是一次性的，有数据飞轮的才越用越好 | |
