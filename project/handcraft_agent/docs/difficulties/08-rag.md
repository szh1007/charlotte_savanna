| 45 | 知识注入选型（RAG / 微调 / 长上下文） | • RAG：知识频繁更新、需引用溯源、按需检索，便宜、灵活、可解释 | P1 |
| | | | • 微调（Fine-tuning）：固化风格 / 格式 / 领域术语、稳定输出、降低每次推理成本，但贵、需训练数据、知识更新需重训 | |
| | | | • 长上下文：一次性少量文档、跨文档推理、无检索误差，但贵、慢、受窗口上限 | |
| | | | • 三者组合：RAG 兜底知识广度 + 微调固化行为 + 长上下文处理局部推理 | |
| 46 | RAG 数据摄取 | • 文档解析：PDF / Word / HTML / Markdown 的结构化提取（pypdf / unstructured / python-docx） | P1 |
| | | | • 表格抽取：PDF 表格、扫描件 OCR，是真实项目的高频坑 | |
| | | | • 数据清洗：去噪、去重、格式归一化、无效内容过滤 | |
| | | | • 元数据提取：标题、章节、来源、时间戳，供后续过滤（#32 多租户）和引用溯源（#29） | |
| | | | • 摄取结果质量决定检索上限：垃圾进垃圾出，清洗比调 chunk 参数更根本 | |
| 47 | RAG 检索工具 | • chunk 分块：按 size / overlap 切文档，太小丢上下文、太大检索不准，要调优 | P1 |
| | | | • 父子索引：用小 chunk 做检索、用大 chunk（父块）喂给模型，兼顾检索精度和上下文完整性 | |
| | | | • embedding 选型：不同向量模型的向量质量不同，直接影响检索效果 | |
| | | | • 混合检索：BM25（经典的关键词相关度排序算法）关键词检索 + 向量语义检索加权融合，弥补纯向量对精确关键词不敏感 | |
| | | | • rerank：粗召回后用重排模型精排，提高最相关结果排前面的概率 | |
| | | | • query rewrite：检索前改写或扩展用户问题，提升召回率 | |
| | | | • 增量更新：文档变化时增量更新索引，不用每次全量重建 | |
| | | | • embedding 模型升级后向量空间不兼容，旧向量不能和新查询混用，需全量 re-embedding 或用版本号隔离 | |
| 48 | RAG 检索评估 | • 评估指标：命中率（hit rate）、MRR（Mean Reciprocal Rank，平均倒数排名——正确答案排第 1 得 1 分、排第 2 得 1/2 分，衡量正确结果排得有多靠前）、忠实度（faithfulness）、幻觉率 | P2 |
| | | | • 三层排查：检索不到（召回问题）/ 检索错（排序问题）/ 生成错（生成问题），先定位是哪一层出的问题 | |
| | | | • badcase 集：积累失败案例做回归测试 | |
| | | | • 怎么证明 RAG 变好了：用指标对比，而不是拍脑袋说「感觉准了」 | |
| 49 | RAG 前沿深化（GraphRAG / RAGAS / 向量库选型） | • GraphRAG：知识图谱增强检索，处理多跳问题与全局问题 | P2 |
| | | | • RAGAS 评估框架：faithfulness（忠实度）/ answer relevancy（答案相关性）/ context precision（上下文精确率，检索结果中有多少被回答用到）/ context recall（上下文召回率，回答所需信息有多少被检索到） | |
| | | | • 向量库选型：pgvector / FAISS / Milvus / Chroma 的对比（性能 / 规模 / 运维） | |
| | | | • 向量库 metadata filter：按 tenant_id 等元数据过滤（关联 #32） | |
