# ② 稳定性/降级（#13-22）

> 返回 [难点清单索引](../README.md#难点清单)

| ID | 难点 | 详细细节 | 阶段 |
|----|------|----------|------|
| 13 | 模型重试 + 退避 + 幂等键 | • 只对瞬态错误重试（429 限流、5xx 服务端故障、网络超时）；4xx 客户端错误（如参数错）重试也没用，直接放弃 | P0 |
| | | | • 指数退避 + jitter：重试间隔按指数增长，并加随机抖动，避免大量请求同时重试造成「惊群」 | |
| | | | • 幂等键：重试可能导致副作用重复执行，用幂等键去重（用唯一标识记录已执行过的请求，重复请求直接返回已有结果，详见 #17） | |
| | | | • 重试会重复计费 token：幂等键防的是「副作用重复」，但 token 已经花出去了，重试本身就重复烧钱 | |
| | | | • 降费手段：缓存模型响应、记录已消费 token、重试次数与总预算挂钩 | |
| 14 | 熔断 + failover | • 熔断器三态：关闭（正常工作）/ 打开（熔断，快速失败）/ 半开（试探是否恢复） | P1 |
| | | | • 供应商连续失败达到阈值就熔断，不再把请求打给已经挂掉的供应商，给它恢复时间 | |
| | | | • failover：熔断时自动切换到备份模型，保证服务整体可用 | |
| 15 | 工具超时 + 取消 | • 分层超时：模型调用约 60s、单个工具执行 10-30s、整个 run 一个总超时，各层独立控制 | P1 |
| | | | • 工具卡死（无限等待外部响应）时要能主动取消，而不是让任务无限挂起 | |
| 16 | 运行状态机 | • 状态集合：created（已创建）/ running（运行中）/ waiting_tool（等待工具执行完）/ waiting_user（等待用户输入，如 HITL 审批）/ retrying（重试中）/ failed / finished / cancelled | P1 |
| | | | • 核心原则：模型只「建议」下一步动作，真正推进状态的是执行层（runtime），这样多轮之间状态才一致、可控 | |
| 17 | 幂等 + Saga 补偿 | • 真实副作用动作（下单、退款、发通知）重复执行会有实际后果，必须防止重复 | P1 |
| | | | • 幂等键：用 request_id / task_id / operation_id 标识一次操作，重复请求直接返回已有结果，不再执行 | |
| | | | • Saga 事务：多步真实操作正向依次执行，任一步失败则逆序补偿已执行的步骤（把已下的单退掉） | |
| 18 | 流式中断/取消 | • 用户中途停止或断连，要优雅终止整个执行，而不是粗暴杀进程 | P1 |
| | | | • 取消正在执行的工具，释放协程、网络连接等资源 | |
| | | | • 已经执行过的真实副作用要关联幂等键走补偿，不能留下半截状态 | |
| 19 | 业务降级兜底 | • 模型挂了 → 降级到模板回复或搜索直出，保证用户至少能拿到一个答案 | P1 |
| | | | • RAG 检索失败 → 降级到 FAQ 规则匹配 | |
| | | | • agent 多轮都失败 → 降级到确定的 workflow 路径（不用模型动态决策） | |
| | | | • 超时 → 返回已经算出的部分结果，而不是空手而归 | |
| | | | • 最终兜底：转人工客服 | |
| 20 | 并发请求排队 + 异步任务队列 | • 同一个 thread 上长任务还在跑，新请求来了要排队（FIFO，先进先出），等前一个结束再处理，不能并发写坏同一个会话状态 | P1 |
| | | | • 排队策略可选择：排队等待 / 打断当前任务 / 直接拒绝新请求 | |
| | | | • 长任务异步化：HTTP 立即返回一个 task_id，后台继续跑，前端用 SSE 或轮询拉进度 | |
| | | | • 队列实现分两层：进程内 asyncio 队列（简单、零部署）vs 分布式 MQ（Celery / Redis / RabbitMQ / Kafka，多实例场景） | |
| | | | • 并发状态锁：同一个 thread 同一时刻只允许一个任务写状态 | |
| | | | • 幂等去重：同一个请求重试不会重复入队 | |
| | | | • 背压/限流：队列积压到阈值时拒绝或降级，防止拖垮整个服务 | |
| 21 | 分布式锁 | • 多实例部署下，同一个 thread 的 checkpoint 写、队列消费需要跨进程互斥，进程内锁（#20 的并发状态锁）失效 | P1 |
| | | | • Redis SETNX（SET if Not eXists，仅当 key 不存在时才能设置成功）实现分布式锁，锁要有 TTL + 自动续租，防止持锁进程崩溃导致死锁 | |
| | | | • 释放锁要校验 owner（用唯一 token），防止误删别人的锁 | |
| | | | • 惊群：多个等待者同时抢锁，用队列化等待或随机退避缓解 | |
| 22 | 限流算法 | • 固定窗口：实现简单但窗口切换瞬间可能流量翻倍 | P1 |
| | | | • 滑动窗口：更平滑但内存占用更高 | |
| | | | • 令牌桶：允许突发，适合 LLM 请求这类突发流量 | |
| | | | • 漏桶：严格匀速，适合下游有硬性吞吐上限的场景 | |
| | | | • 限流维度：per user / per tenant / per model，多级限流组合 | |
