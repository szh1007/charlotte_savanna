# Bugfix 0004 — 合并下载进度条来回跳 + 任务列表出现空占位卡

> 记录日期: 2026-08-20 | 状态: 已修复 | 涉及文件: `backend/task_manager.py`、`frontend/src/views/Home.vue`、`tests/test_downloads.py`

两个独立问题，均出现在音视频合并下载（bugfix/0003 引入）上线后的真实使用中。

---

## 问题 1: 下载进度条先后独立显示视频和音频的进度

### 问题现象

下载 DASH 分离流档位（B 站全部分档）时，进度条先走完一遍 0→100%（视频流），随后**又回到 0 重新走一遍**（音频流），最后才完成。两个下载阶段割裂，像两个任务先后下载。

### 原因追溯

yt-dlp 对合并表达式（`{format_id}+bestaudio*/{format_id}`）的处理是**先后下载两个独立流**：先视频流，再音频流，最后 ffmpeg 合并。每个流都独立触发 `progress_hook`，且各自从 0 报进度：

```
[download]   0.0% of   45.71MiB   ← 视频流 30016 (自身 0→100%)
[download] 100.0% of   45.71MiB
[download]   0.0% of   20.20MiB   ← 音频流 30280 (重新 0→100%)
[download] 100.0% of   20.20MiB
```

`_progress_hook` 直接把每个流的百分比透传到任务 `progress`，音频流开始时把整体进度重置回 0——前端进度条来回跳（真实抓包验证，见下）。

### 如何修复

`_progress_hook(task_id, merge_audio)` 对合并任务**按流均分合成整体进度**：

- 通过 `d["info_dict"]["format_id"]` 区分流（视频流 30016 / 音频流 30280，真实验证有效）
- 首个流占整体 0~50%，第二个流 50~100%：`overall = (流序号 + 当前流百分比) / 均分数 × 100`
- 首个流下载期间未知后续流数，按双流均分占位（`n = max(已见流数, 2)`）
- **全程单调不减**：视频流 100% → 整体 50%，音频流从 50% 继续，无回退跳变
- 非合并任务（合一格式，`merge_audio=False`）保持原样不受影响

`_run_download` 把 `task.merge_audio` 传给 `_progress_hook`。

**验证**：

- 集成测试：模拟双流进度事件（视频流 10/50/100% → 音频流 10/50/100%），断言整体进度序列 `[5, 25, 50, 55, 75, 99]`（99 为下载中上限，完成时置 100）——单调不减，无回退
- 真实环境：360p 档真实下载抓包，确认 yt-dlp 双流事件 `format_id` 正确区分（30016 / 30280），合并产物生成正常（45.71 MiB + 20.20 MiB → 合并 MP4）

> 均分权重 50/50 是展示近似（视频流通常远大于音频流，真实占比约 70/30），但保证单调不跳变，满足「合在一起展示」的诉求。精确按字节占比需要音频流大小提前可知，而它在视频流下载完才出现，无法避免首流阶段跳变，故不采纳。

## 问题 2: 下载完成后任务列表多出一个「下载任务 #N」空占位

### 问题现象

刚打开网页，解析并下载第一个视频，下载完成后任务列表显示**两个任务**：一个是刚下载好的（标题正常），另一个是标题为空、显示「下载任务 #2」的占位卡，且永远停留在排队/解析状态。用户没有点击过它，却多出了一个「下载任务」。

### 原因追溯

竞态链（同一 task_id 产生两张卡）：

1. **后端先发事件、后返回响应**：`create_download` 创建任务后先执行解析（耗时秒级），期间已发布 `resolving` 状态事件；解析完成校验入队后才返回 HTTP 响应
2. **SSE 事件先于响应到达**：前端 `handleTaskUpdate` 收到未知 task_id 的事件 → 触发防抖刷新 `scheduleRefresh`（300ms 后 `refreshTasks` 全量拉取列表）
3. **拉回解析中任务的空快照**：`refreshTasks` 拉到后端列表时该任务还在解析中，`title` 未回填（为空），但 `kind=download` 通过过滤进入列表——此时列表里已有这张 title 空的卡
4. **响应返回后无条件再构造一张**：`handleDownload` 收到 `task_id` 后 `unshift` 本地构造任务卡（title 来自解析结果，非空）——**未检查是否已存在同 id 任务**，同一 task_id 现在有两张卡
5. **SSE 只更新第一张**：后续状态事件 `findIndex` 只匹配第一张卡，第二张永远停在 `queued`/`resolving` + 空 title → 显示「下载任务 #2」占位

触发条件（解析耗时 > 300ms 防抖窗口，B 站解析通常 1~3 秒）**几乎必然发生**。

### 如何修复

前端两处（`Home.vue`）：

1. **`handleDownload` unshift 去重**：构造前检查 `tasks.some(t => t.task_id === task_id)`，已存在（防抖刷新先拉回）则不再构造，杜绝重复卡
2. **`refreshTasks` 改为合并式更新**：本地任务（SSE 实时状态 + 解析结果完整标题）优先保留，后端列表只**补充本地缺失的任务**——`Map` 合并，`local ? {...t, ...local} : t`。全量替换会把解析期间 title 为空的快照覆盖到本地卡上，标题丢失变成占位

两个修复分别覆盖竞态的两条路径（刷新先到 / 响应先到），缺一不可。

**验证**：前端无测试设施，通过路径推演覆盖两条竞态时序（响应先到：SSE 事件合并在已有卡上；刷新先到：unshift 去重不重复构造）。真实使用确认不再出现多余占位卡。

> 备选方案（未采纳）：后端在创建 download 任务时同步返回完整任务元信息（title/cover），前端完全不用 refreshTasks 拉取——但解析是同步阻塞的，无法在响应前拿到 title；改为异步解析则要重构状态机，改动大，不划算。后端把 SSE 事件补上 title 字段（`events.task_event`）也可行，但事件为高频轻量契约，塞全量元信息违背快照语义，且 refreshTasks 的合并式更新已彻底解决，无需画蛇添足。
