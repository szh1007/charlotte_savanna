新标签页则是新的一段 (各聊各的, 用户故事 25). 历史里只有 user / assistant 两类消息, 工具的返回正文进不来 (与事件流同一条 脱敏纪律, 见 CharApp 的 adr/0003). 这条读历史用的是 POST 而不是 GET: 会话编号是私密数据, 不该出现在 URL 上 (访问 日志 / 浏览器历史 / Referer 都会跟着它走), 而 GET 带 cookie 还是跨站可触发的. 与提问、取消同一个形状 (POST + JSON + CSRF). 左栏是会话列表 (issue 19): 打开页面时拉一次 `POST /minimall/agent/conversations/` (第四条路, 铺在 issue 18), 列出这个买家聊过的每一段 —— 标题 + 相对时间, 点一下 切过去. 会话编号按 ADR-0002 的纪律**不进地址栏**, 所以切换只动内存与 sessionStorage: 选中态是画出来的, 不是 URL 里的一个参数. 「新对话」也**不落库**: 会话行是第一条消息发出去时由记录器创建的 (issue 17 的 懒创建), 所以点了新对话又不用, 列表里不会多出一条空壳. 为什么不用 `EventSource` (它本来能白送帧解析): 它只能发 GET、也带不了自定义头, 于是认证只能靠 cookie、问句只能进 URL —— 而这个端点有副作用 (真跑模型真花钱), 按语义就不该是 GET, 问句进 URL 还会落进访问日志. 换 POST + fetch 之后由 Django 的 CSRF 中间件接管跨站防护. 帧解析**不手写**: 交给 `eventsource-parser` 的 `EventSourceParserStream` —— 那是 一段有细节的活 (按空行切帧、跨 chunk 的半个帧、**一个汉字被 TCP 切成两半**时的 增量解码), 别人已经写对并维护着了. 页面这边只剩胶水: 发什么样的请求, 把七类事件 画成什么样子. 这个项目的重点在后端流式 (框架的 SSE 层 + BFF 的透传), 前端不值得 自己造一遍解析器. 但这个库**不走 CDN, 用的是仓库里的本地副本** (static/vendor/eventsource-parser/). 商城别的页面 (htmx / Alpine) 走 CDN 没问题 —— 它们属于渐进增强, 加载失败顶多少点 交互;
