## 一、BFF 每次转发新建 `httpx.Client`（真机 ~690 ms）

### 现状

`app/minimall/views_bff.py` 里 **3 处**创建，全是"每次请求新建、作用域结束即关"：

| 位置 | 用途 |
|------|------|
| `:815` `client = stack.enter_context(httpx.Client(timeout=UPSTREAM_TIMEOUT))` | 问答流（`open_upstream`） |
| `:957` `with httpx.Client(timeout=timeout) as client:` | `_call_upstream`，五条普通路共用 |
| `:1103` `with httpx.Client(timeout=CANCEL_TIMEOUT) as client:` | 取消 |

无连接池复用、无模块级单例。本文件**没有** `AsyncClient`。

### 但这里有一条**必须先回应**的既有理由

`open_upstream` 的 docstring（`:805-807`）明写着这是**有意的**：

> 「用每次请求一个 `httpx.Client`：Django 没有可靠的进程退出钩子」

**这条理由是成立过的**，不能装作没看见。它防的是"进程级连接池没人关"。所以本片要做的不是"改成单例"，是**在承认那条代价的前提下换一个更划算的**：

- **代价现在有数了**：本机 ~690 ms（issue 25 的真机观测），而且它落在**首字之前** —— 用户先看到一次空转
- **那条理由的前提是"多 worker"**：项目自己已经写明部署是**单进程**（`CharAgent/server/sessions.py:43-48` 的「单进程」一节，`SessionRegistry` 与 `RunRegistry` 都在进程内）。单进程下 `atexit` 是**可靠**的
- 于是：**模块级共享一个 client + `atexit.register(client.close)`**，并把"依赖单进程"这个前提写在 docstring 里 —— 与 `sessions.py` 那条前提**同源**，不是新引入的假设

**要核一件事**：`httpx.Client` 的连接池在**流式响应**（`iter_bytes`）与普通请求之间共用是否安全。`open_upstream` 的长连接与 `_call_upstream` 的短请求如果共用一个池，长连接会占住连接额度 —— 实施时按 `httpx.Limits` 配连接数，或**给流式那条单独留一个 client**。**两者都不违反"不再每次新建"**，选哪个看实施时测到的数。

### 实施记录（2026-09-25）

**那 690 ms 花在哪儿**（实测，不是猜）：`httpx.Client.__init__` 会为「主传输 + 两个代理传输」各建一个 SSL 上下文，`ssl.create_default_context()` 里的 `load_verify_locations` 本机一次约 **310 ms**（读系统证书库），三次就是 ~930 ms。而 `CHARAPP_SERVER_URL` 是 `http://127.0.0.1:1007`，那些上下文一次都用不上。单次 `httpx.Client()` 构造+关闭实测 **930 ms**。

**选了一条 client 还是两条**：**一条**（`_LIMITS = httpx.Limits(max_connections=10, max_keepalive_connections=10)`）。理由是并发上界本来就小（页面同一时刻只跑一个运行，`finished` 那道门管着），十倍余量足够；额度真被占满的代价写在注释里（在池子上等 `pool` 超时，而不是立刻回话）。

**实测数字**（本机基准：上游换成一个只回 200 的本机 HTTP 服务，跑的是**真的** `views_bff` 那几个转发函数；脚本见 `D:\__WorkSpace__\Temp\bench_bff_client.py`）：

| 路径 | 改前 中位数 / 最小 | 改后 中位数 / 最小 |
|------|------------------|------------------|
| 列会话（带搜索词） | 815.7 / **690.1** ms | 15.4 / 2.6 ms |
| 读历史 | 822.4 / 810.7 ms | 2.4 / 2.0 ms |
| 改标题 | 840.5 / 811.7 ms | 8.7 / 3.0 ms |
| 置顶 | 837.0 / 815.0 ms | 9.5 / 2.8 ms |
| 取消 | 973.6 / 895.9 ms | 15.8 / 2.8 ms |
| 问答首字（开流+收干） | 961.2 / 936.2 ms | 9.1 / 2.9 ms |

改前那个 **690.1 ms** 与 issue 25 真机观测的 ~690 ms 对上了。

**超时逐次传**：共享之后客户端上不设默认 timeout（三条路耐心不同：120 秒 / 10 秒），每个调用点自己传 `timeout=`；客户端上那份默认值一旦被谁当成兜底依赖上，「取消只等十秒」就悄悄没了。

**新踩到的坑（已用测试钉住）**：`Upstream.stack` 上一版攒着**它自己新建的**客户端，收尾时一并关掉是对的；改成共享之后如果还留着那一下，表现是「这一次问答之后整个进程的转发全废」。

**复用带来的新失败面（2026-09-25 查清，结论是"不用改代码"）**

原始怀疑（写在上一版交接里）：助手服务重启后，池子里那条闲置连接已经死了，复用它发出去的那一次会失败一次。**查下来这个说法偏重了**，真相分两半：

| 情形 | 实测结果 |
|------|---------|
| 上游被杀 → **隔一会儿**（0.2 秒就够）再发 | **成功**，而且上游新实例收到的是**一条新连接** |
| 上游被杀 → **同一瞬**发请求（对面关连接的信儿还没到本机） | 抛 `httpx.ReadError`（WinError 10054），那一次失败；再发一次就好 |

第一行是常态：**httpx 自己认得出**。机制在 httpcore 的 `http11.py` 里 —— 判断一条闲置连接还能不能用时，除了 keepalive 到点，还会看那个 socket 是不是已经"可读"（对面关了连接才有这个状态，`server_disconnected` 那一条，底层是 `is_socket_readable`），认出来就换一条新连接。也就是说，**只要对面关连接的信儿已经到本机，就不会复用那条死连接**。

第二行才是漏网的：请求恰好落在上游咽气的那一瞬 —— 但那一瞬上游正不在，**重发换来的还是「联系不上」**，用户能看见的结果一模一样。

**所以没做重发**（一度写完又撤了）：先试过"可以对它安全重发的五条路重发一次"，量下来没有任何用户能看见的差别 —— 多一层代码、多一个"到底发了几次"的疑问，换不来收益。按 ticket 备注那句「别为了兑现规划去改一个不划算的东西」撤掉，只把这段实测写进 `_LIMITS` 那段注释（省得下次有人重新怀疑一遍）。

脚本：`D:\__WorkSpace__\Temp\probe_stale_conn2.py`（两个口径）、`probe_httpcore_behavior.py`（甲/乙 对照）、`probe_pool_expiry.py`（池子状态 + 时间戳）。

**连接额度那条问号的答案**：拿真实 socket 量过 —— 先把一条上游流**开着不读**（连接被占住，正是 ticket 担心的那种），再发三条短请求：5.1 / 23.5 / 4.7 ms，没有被饿死；随后那条流照常读完 31 帧（30 个 thinking + `relay` 补的那个终局事件），共享客户端仍然活着。脚本：`D:\__WorkSpace__\Temp\bench_bff_concurrency.py`。

### 验收

- [x] 同一次会话里连续发三条短请求（改标题 / 置顶 / 搜索），首字节延迟相对基线明显下降（**记录实测数字**）—— 见上表，690~970 ms → 2~16 ms
- [x] 流式问答不受影响：`POST chat/` 的 SSE 透传行为一字不改（既有用例全绿）—— `test_bff` 103 → 109 个全过

## 二、历史响应的竞态：`loadHistory` 缺一道闸门

### 现状

**闸门的样板在前端，不在 BFF**（BFF 侧没有任何序号闸门）：

| 函数 | 位置 | 防竞态方式 |
|------|------|-----------|
| `loadConversations` | `agent.html:1105-1151` | ✅ **递增 ticket + 回来比对**：`:1103` 定义 `listRequests = 0`，`:1110` 取号 `const ticket = ++listRequests`，`:1149` 回来时 `if (ticket !== listRequests) return` 丢弃旧响应。注释 `:1098-1102` 把竞态讲清楚了（"慢的那一份会盖掉快的那一份"） |
| `loadHistory` | `agent.html:679-724` | ⚠️ 只有一个布尔 `finished`（模块级，`:265`）：`:685` "用户已经在问了，别把历史盖到新一轮上"、`:717` "等这份 JSON 的工夫，用户可能已经问出去了" |

**差别**：ticket 能区分"两次加载谁更新"；布尔只能区分"聊没聊过"。于是**两次并发 `loadHistory` 之间无法判先后** —— 快速切会话时，先发的慢响应仍可能盖掉后发的快响应，**看到的是上一个会话的历史**。

`loadHistory` 的调用点只有三处（`:361` 重试按钮、`:1199` 切会话、`:1242` 首屏），**快速切会话正是触发路径**。

### 做法

**照 `listRequests` 再来一道 `historyRequests`** —— 修法现成，不需要新设计。注意 `:353-364` 那条 `historyFailed` 的判据（它 2026-09-23 因为不用 `finished` 而漏过一次）**要一起改成 ticket 口径**，否则两道判据会打架。

### 验收

- [x] 快速连续切三次会话，最终显示的是**最后点的那一个**（旧响应被丢弃）
- [x] 失败路径（`:353-364`）与新闸门口径一致，不会把"上一个会话的失败"报到当前会话头上
- [x] 重试按钮与首屏两条路径不受影响

### 实施记录（2026-09-25）

**做法**：照 `listRequests` 再来一道 `historyRequests`（取号 → 回来比对 → 旧的丢掉），渲染前与失败路径**共用一个号**（`historyFailed(ticket, mayHaveHistory)`，三处失败落点全传）。`!finished` 那两道守卫原样保留 —— 它们防的是「话正在说」，与这道「位置过期了」是两回事。

**真机验证（浏览器 + 受控延迟，双向都跑过）**：三个会话 A/B/C，A 最慢（6 秒）最后落地、C 最快（2 秒）最先落地，快速连点 A→B→C。

| | 聊天区最终内容 | 判读 |
|---|---|---|
| **修复前**（模板回退到 HEAD） | `会话C…会话B…会话A…` 三段叠成一屏 | 缺陷复现（用户最后点 C，屏幕上却多出 A、B 的内容） |
| **修复后** | `会话C…` 只有一段 | 旧响应被丢弃 |

失败路径同法验过：A 改成 6 秒后回 502，修复前它那份失败会落在当前这一段上，修复后不再冒出来。

**注意**：验模板改动必须**重启 Django**（跑久的 runserver 会继续发旧模板 —— 这次就踩了一次，白跑两轮；见 `memory` 里那条「浏览器验前端要起新实例」）。

**原先留下的那一条边界，已按用户要求补上（2026-09-25 第二轮）**：用户**在等历史时提问**、而那次提问快过历史加载时，回来的历史会追加到那一轮下面。补的办法是**加载期间不让问**：

- 新增 `historyLoading` 这面旗 + `syncComposer()` **唯一一个开关出口**（`input.disabled` / `send.disabled` / 三个示例按钮一起），`loadHistory` 一进来就拿、`finally` 里放（正身 `loadHistoryBody` 里到处是提前 return，摊在一起就会漏一次解锁，输入区从此锁死）；
- 放开时按号判：连切会话时旧那次回来得早，它一放用户就能在还没画完时提问；
- 示例按钮是"提问"的另一个入口，一起锁；
- `setChatPlaceholder` 里也调一次 `syncComposer()` —— 真机上抓到过：横幅被摘下来的那段时间锁上，挂回来时那三个按钮是死的（"答完一轮再点新对话，按钮点不动"）；
- 顺带：加载完若没人占着光标，把光标放回输入框（首屏原本是进页面就落在里面，禁用会把它摘掉）。

**浏览器实测**（延迟 3 秒的历史 + 记录 `/chat/` 请求）：加载中输入框/发送/示例按钮全禁用、程序化构造的提交也发不出去（0 条）；加载完全部恢复、光标回到输入框；切会话期间同样锁住、切完放开且**光标不被抢走**；新的空会话横幅挂回后按钮可用、点它能真问出去。

- 两条都**不碰协议**：不改 BFF 与 CharApp 之间的请求/响应形状，不改 SSE 帧格式。L3b 要在这两处之上加东西（确认卡、`/resume` 转发），本片是**先把地基抹平**。
