## 具体任务

### 1. 两条 ADR（照 0001–0004 的格式与长度）

> 编号顺延：ticket 20 在本片之前落了 **ADR-0007（删除是软删）**，所以这两条是
> **0008 / 0009**。

**ADR-0008「一段对话有两种表示」**
- 决策：**账本是账本、视图是视图** —— 快照 append-only 存全量、只追加不改写；每次模型调用前把「系统提示 + 压缩摘要 + 最近 N 轮」算成一份**视图**发给模型；而**给人看的记录永不压缩**
- 三条门槛逐条写：**难回退**（它决定压缩写在哪、会话历史从哪读、前端看到什么，改它要动框架 + 业务 + 前端三处）· **反直觉**（"为什么用户看到的历史比模型看到的多"是必问题）· **真实取舍**（被否的三条：只压展示 / 只压发给模型的视图 / 两份都留全量 —— 各自的代价写清）
- 代价照记：**两边的历史从此不一致**，排查"模型为什么忘了"要去快照、排查"用户看到什么"要去记录表

**ADR-0009「对话记录落在框架自己的 db 层」**
- 决策：`charagent_threads` / `charagent_runs` / `charagent_messages` 三张表由框架写入与查询，`tenant_id` / `user_id` 进 `RunContext`
- 被否的替代：业务侧 Django/MySQL 新建模型（框架已经把这套设计完了，业务侧重建等于抄一遍 `hidden` / `reasoning` / `tool_call_ids`）· 只靠快照（用错表：快照是循环的工作数据，Redis 模式的 `MAXLEN` / TTL 会吃掉历史）· 让业务自己加路由（框架的 `db/` 包就永远没有生产调用方 —— 而"没人用过的接口等于没设计过"正是这个项目立项的理由）
- 代价照记：**Postgres 成为业务的硬依赖** · **框架从此要认识两个身份字符串**（`payload` 不透明那条纪律的有意例外）· 记录是**事后投影**，进程被 kill 在写入前会丢最后一轮
