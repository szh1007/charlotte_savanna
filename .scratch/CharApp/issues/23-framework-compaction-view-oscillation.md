# 23 · 框架侧：压缩的视图每隔一轮失效（摘要压过之后，下一轮又把全量账本发出去）

**Status:** done

**Type:** bug

**Blocked by:** 无

**上游:** `CharAgent/docs/DESIGN.md` #7（上下文压缩：账本 / 视图分离）；`CharApp/docs/PLAN.md` §5（L2.5：长对话触发压缩后单请求 token 不再增长）

## 现象

一段长会话里，**每隔一轮**发生一次「压一次 + 下一轮把全量账本原样发出去」的循环。用框架自己的策略 + 锚回灌跑 8 轮（阈值 3000 / 留 2 轮 / 水位线 0.6；2026-09-23，Claude 代跑）：

| 轮 | 账本 tok | 锚 | 估算 | **发出 tok** | 发出条数 | 压了吗 | 带摘要 |
|---|---|---|---|---|---|---|---|
| 1 | 2972 | — | 2972 | 2972 | 13 | ✗ | ✗ |
| 2 | 3468 | 2972 | 3468 | **1036** | 6 | ✓ | ✓ |
| 3 | 3964 | 1036 | 1532 | **3964** | 17 | ✗ | **✗** |
| 4 | 4460 | 3964 | 4460 | **1038** | 6 | ✓ | ✓ |
| 5 | 4956 | 1038 | 1534 | **4956** | 21 | ✗ | **✗** |
| 6 | 5452 | 4956 | 5452 | **1038** | 6 | ✓ | ✓ |
| 7 | 5948 | 1038 | 1534 | **5948** | 25 | ✗ | **✗** |
| 8 | 6444 | 5948 | 6444 | **1038** | 6 | ✓ | ✓ |

两条后果同时发生，方向相反：

- **省钱那一半没生效**：单请求 token 不是「不再增长」，而是**一半的轮次跳回全量账本**（而且它一直长）
- **该省的那一半反而花了**：每压一次就来一次摘要调用，于是**每隔一轮烧一次摘要**

## 根因

`TrimAndSummarize.apply` 把「**要不要投影**」和「**要不要再切一刀**」合成了一件事（`agent/compaction.py`）:

```python
before = counter.count(history)
unchanged = CompiledView(messages=list(history), ...)   # ← 全量账本, 摘要不参与
if before < self.threshold_tokens:
    return unchanged                                    # ← 不切 = 不投影
```

而「不切」之所以会在压过之后立刻发生，是因为**锚测的是"上一次请求"的大小**（`AnchorTokenCounter`：锚 = 上次上游回报的 `input_tokens`）：

1. 第 N 轮压了一刀 → 发出去的是小视图 → 上游回报的 `input_tokens` 小 → **锚落到小值**
2. 第 N+1 轮：估算 = 小锚 + 增量 ≈ 依旧小于阈值 → 判定「不用压」→ **把全量账本发出去**，摘要那条根本不带上
3. 上游回报的是全量账本的大小 → 锚回到大值 → 第 N+2 轮又超阈值 → 再压一刀（再烧一次摘要）→ 回到第 1 步

也就是说：**估算在跟账本走，而发出去的东西在两者之间跳**，于是每个量都是对的，合起来是错的。

## 为什么不是"有意为之"

- 模块 docstring 的承诺是「账本 append-only，**视图越聊越短**」；实际是视图**每隔一轮**才短一次
- 对模型也不好：上下文在「摘要版」与「全量版」之间来回跳，每两轮一次 —— 这不是任何取舍想要的形状
- 现有的两条用例**各自都对**，合起来漏掉了它：`test_under_the_threshold_nothing_is_touched` 钉的是「没超阈值就原样发」（原样 = 账本），`test_compacting_twice_in_a_row_does_not_happen` 钉的是「刚压完别立刻再压」—— 后者正是上面第 2 步那个状态，用例把它当成"滞回生效"了
- 真机那两次验收没照出来，是因为阈值被压到 **800**（远低于固定开销 ~6.2k）—— 那种配置下**每轮都超阈值**，看不到"隔一轮"的循环（见 issue 18 记录 §四）

## 怎么修（三选一，lead 待定）

| # | 做法 | 代价 |
|---|---|---|
| **a** | **投影与切分家**：视图**每轮都按现有 `summary` / `summary_covers` 构造**；「要不要再切一刀」单独判（判的对象是**账本**，不是上一次请求） | 估算口径要重做：锚测的是请求（会随投影变），判「账本长大了没」得另算一个跟账本走的量 |
| **b** | **把锚落在账本上**：`note_usage` 时把「这次请求被裁掉那段的估算」加回锚里（锚 ≈ 账本口径）；投影每轮照做 | 锚不再是纯粹的上游权威值（变成"权威值 + 启发式补丁"），口径要写清 |
| **c** | **最小改动**：`unchanged.messages` 换成「按现有 summary / covers 投影出来的视图」——低于阈值时也投影，但不切新刀、不调摘要 | 同 a：判「该不该再切」的量仍然跟着上一次请求走，滞回会变得迟钝 |

倾向 **a + c**：**投影永远做，切不切另判**；账本口径的估算单独给一个量（真分词器或启发式都行，`TokenCounter` 协议本来就是可换的）。b 是把两个量挤进一个数的应急做法。

## 验收

- [x] 压过之后，**后续每一轮**发给模型的消息都带摘要（用 `_capturing_model` / `MockLLM.calls` 断言，逐轮比）
- [x] 连续 N 轮里，**摘要调用次数 ≤ 需要的次数**（不再每隔一轮烧一次）；水位线的滞回仍然有效（不因为修这个而变成每轮都切）
- [x] 单请求输入**单调不增长**：一段账本持续变长的会话里，发出消息的估算大小保持在阈值 × 水位线附近（今天的形状是「一半轮次跳到全量」）—— 实测读作「锯齿但有界」：修后 1532 → 2028 → 2524 → 1038（涨到阈值就切一刀），**不是**严格单调；锯齿是水位线的设计（不切就没必要压），要更小就调阈值
- [x] 既有用例里那两条（`test_under_the_threshold_nothing_is_touched` / `test_compacting_twice_in_a_row_does_not_happen`）按新语义重写或补注释 —— 它们现在描述的是缺陷的一半
- [x] 真机：一段长会话跑 8+ 轮，逐轮记录发出的大小与摘要调用次数（见下面的真机表）

## 实际开发情况 2026-09-23

### 一、修法与落点（选的是票里的 a + c）

**投影每轮都做，切不切另判**：

| | 什么时候做 | 做什么 |
|---|---|---|
| **投影** | **每一轮** | 视图 = 第 0 条 + 摘要 + 摘要没覆盖到的一切（切点 `max(summary_covers, 1)`） |
| **再切一刀** | 账本估算到阈值时 | 扩大摘要覆盖（重压摘要）+ 裁到最近 N 个提问 + 截短老工具结果 |

三处细节实现时才定下来（都写在代码注释里）：

1. **投影那一路不截断工具结果**（`_view(..., truncate_tools=False)`）：截断与裁剪同属「再切一刀」那一半的手段，跟投影分开 —— 否则「没压过的那一轮」也会被悄悄改正文，而 `compacted` / 事件的语义会跟着糊掉.
2. **没切刀的那一轮 `dropped` / `truncated` / `summarized` 都保持「什么都没做」**（于是不发 `context_compacted` 事件 —— 上一次压缩已经报过一次了），但 `saved_tokens` 如实报（它确实比账本小）.
3. **估算口径不动**（锚仍是「上一次请求的 input_tokens + 增量」）：投影修好之后「发出去的」与「估算的」是同一种形状了，振荡的根因此消失 —— 这也是为什么不用动 `AnchorTokenCounter`.

| 步 | 账本 tok | 修前发出 | 修后发出 | 修前摘要调用累计 | 修后摘要调用累计 |
|---|---|---|---|---|---|
| 1 | 2972 | 2972 | 2972 | 0 | 0 |
| 2 | 3468 | **1036** | **1036** | 1 | 1 |
| 3 | 3964 | **3964**（跳回全量） | **1532**（带摘要） | 1 | 1 |
| 4 | 4460 | 1038 | 2028 | 2 | 1 |
| 5 | 4956 | **4956** | **2524** | 2 | 1 |
| 6 | 5452 | 1038 | 1038（切一刀） | 3 | 2 |

| 10 | 7436 | 1038 | 1038 | 6 | 3 |

### 三、真机复验（阈值 9000 / 水位线 0.5，CharApp 服务 + 真 DeepSeek，会话 `fix22b`）

八句话（前三句带工具，把账本顶过阈值），逐帧看 `metadata.view`（ticket 22 新加的观察值，正好用来验这条）：

| 帧 | 账本条数 | 记下的视图消息 | 带摘要 | 丢 / 截 |
|---|---|---|---|---|
| 1–6（没超阈值） | 3 → 34 | None（视图就是账本） | — | 0/0 |
| **7（切一刀）** | 36 | **19 条** | **✓** | 18/1 |
| **8（刚压完，低于阈值）** | 38 | **21 条** | **✓** | 0/0 |

**第 8 帧就是这条缺陷的正面证据**：账本 38 条，发出去的只有 21 条且**带着摘要** —— 修之前这一轮会把全量 38 条原样发出去（那时视图与账本相同，帧里会记 None）. 同一段会话里第 8 句问「我的幸运数字是几」答出 **88**（那句在更早的轮次里），说明摘要不是摆设.

### 五、边界与开放项

- **它是「不再隔一轮失效」，不是「请求不再增长」**：视图里的尾巴仍随账本长，到阈值再切 —— 这是水位线的设计（不加这一条，每次调用都得压一次）. 想更小就调阈值，别指望它自己收住.
- **压缩仍然只影响这一次请求**：账本、帧、记录表一字未动（老规矩）.
- **没做的**：票里 b（把锚落在账本口径上）没采用 —— 投影修好之后锚与请求同形，没有理由再给锚打启发式补丁.
