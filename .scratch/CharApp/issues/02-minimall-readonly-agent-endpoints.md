# 02 · 商城侧：9 个只读接口

**Status:** ready-for-agent

**Type:** task

**Blocked by:** 无

**上游:** `../PRD.md` §4.3 / §4.10

## 做什么

在商城应用 `app/minimall/` 里新增一组**专门给助手用**的只读接口。

**本 issue 一个数据模型都不改。** 不改表结构、不改业务函数、不动缓存代码。只加接口。（退款申请是后面的 issue，属于第二阶段。）

## 具体任务

1. **新增一组接口**，前缀 `/api/minimall/agent/`，9 个只读接口：

   | # | 路径 | 需要用户身份 | 返回 |
   |---|------|------------|------|
   | 1 | `products/` | 否 | 商品列表（支持关键词搜索、分类、价格区间、排序、页码） |
   | 2 | `products/<slug>/` | 否 | 商品详情，**含库存** |
   | 3 | `categories/` | 否 | 分类树 |
   | 4 | `featured-products/` | 否 | 运营标记的精选商品 |
   | 5 | `cart/` | 是 | 当前用户的购物车 |
   | 6 | `orders/` | 是 | 当前用户的订单列表 |
   | 7 | `orders/<order_no>/` | 是 | 当前用户的订单详情 |
   | 8 | `profile/` | 是 | 当前用户的余额与基本信息 |
   | 9 | `addresses/` | 是 | 当前用户的收货地址 |

2. **认证：内部令牌，且必须 fail closed**
   - 请求头带一个内部令牌，用常量时间比较
   - **环境变量没配置令牌时，拒绝一切请求** —— 不给"忘了配置就默认放行"的机会
   - 参照项目里已有的同类实现（charplot 应用已经有一模一样的模式），**照它的写法来，不要另起一套**

3. **用户身份从请求头取**
   - 需要身份的接口从 `X-User-Id` 头取用户 ID
   - 归属校验沿用商城现有做法：查不到就返回 404（不是 403，防枚举）

4. **商品数据直查数据库，不走 Redis 缓存**（PRD §4.3 的决定）
   - 原因：商品详情缓存最长约 12 分钟，助手报"还剩 3 件"而那是 12 分钟前的数字，买家会当事实
   - 所以这几个接口**不要**调用现有的缓存函数，直接查库

5. **新增面向助手的序列化**
   - 现有商品列表的序列化器**不包含库存**，助手的版本要包含
   - 新增独立的序列化模块，显式声明"这是给助手看的契约"，而不是照抄网页用的那套

6. **写测试**

## 验收

- [ ] 9 个接口全部可用，返回真实数据
- [ ] 无令牌 → 拒绝
- [ ] 错误令牌 → 拒绝
- [ ] **未配置令牌环境变量 → 全部拒绝**（这条最容易漏，必须单独测）
- [ ] 用户隔离：用买家 A 的身份取不到买家 B 的订单/购物车/地址
- [ ] **不走缓存**：改掉某个商品库存后，立刻请求详情能读到新值（这条证明直查库生效）
- [ ] 商城现有测试全绿（38 个）

## 备注

- 归属校验的写法参照商城现有接口（用 queryset 过滤 + `get_object_or_404`），保持一致
- 页码参数现在是没有防御的（非数字会 500）—— **本 issue 不要顺手修它**，那不是这里的事
- 9 个接口里前 4 个是公开数据（不需要用户身份），后 5 个需要。不要把公开接口也强制要求 `X-User-Id`
