## 做什么

**L1b 的主验收切片**：浏览器打开 minimall 的客服页，用已有登录状态问一句「我最近的订单到哪了」，看到流式回答 —— 内容是真实订单。多买家各自登录、各自看到自己的数据。

这一片把最后一层（Django BFF + 前端）接上，链路才算走完。

## 具体任务

### 1. Django BFF 端点

`/api/minimall/agent/` 这个前缀已经属于「token 认证的内部端点」（issue 02），BFF 是**session 认证的用户面端点**，两回事 —— 换个前缀，别混在一起。

职责只有三件，多一件都不做：

1. **认证**：登录用户才能用；未登录跳登录页，不是 500、也不是空流
2. **取身份**：`user_id` **只从 session 取，绝不看请求参数**（见下方第 6 条）
3. **转发 + 透传**：带内部令牌 + `X-User-Id` 打 CharApp 服务，SSE 逐块透传给浏览器

BFF **不做业务判断** —— 不判断「这句话该不该问」、不改写问题、不缓存回答。

### 2. SSE 逐块透传的实现选择

Django 的 `manage.py runserver` 是同步 WSGI + 多线程。转发侧的合理选择是**同步 httpx 流式读 + `StreamingHttpResponse`**，不要为了「异步」把 BFF 复杂化。

（真要上 ASGI 是部署期的事，与 L1b 的目标无关。）

### 5. 会话标识的第三段

`thread_id = minimall:{user_id}:{conversation_id}`（PRD §4.11）。

- `conversation_id` 由前端**每个标签页**生成 —— 用户故事 25「两台设备各聊各的」靠它成立
- 框架对 `thread_id` 有校验：非空、≤128 字符、不含空白与控制字符（`checkpoint/utils/types.py:54-88`）。把生成规则设计成天然满足，不要靠传进去才报错

### 6. 跨进程错误传播

L1b 相比 L1a 多出来的五个新变量之一，也是最容易漏的一个。三种故障要各自有明确的用户可见表现：

| 故障 | 浏览器上看到什么 |
|------|-----------------|
| CharApp 服务没起来 | 一句人话，不是白屏 |
| 商城没起来 | 助手说「暂时查不到」，不是伪造数据 |
| 模型报错 / 额度用尽 | 明确的错误提示，不是转圈到超时 |

### 与初稿的出入（都是拍过板的，不是漂移）

1. **前缀选 `/minimall/agent/`**：初稿只说「换个前缀，别与内部端点混」。选它是因为它落在浏览器那一侧（用户面），且与 `/api/minimall/agent/` 一眼可分。
2. **页面与 SSE 同在一个 `urls_bff.py`**：`urls_api.py` / `urls_html.py` 那一刀是按**认证模型**切的（DRF 接口 / 页面）；BFF 两条路由是同一个接入面（同前缀、同 session 认证、一起改），拆开只会让人来回跳。理由写进了模块 docstring。
3. **重连守卫加在服务端**（带 `Last-Event-ID` → 409）：初稿说「终局后客户端 `close()`，**必要时**让 BFF 关响应」。实测确认**只关响应拦不住重连** —— `EventSource` 在任何一次流结束（含正常收线）之后都会自动重连，只有客户端 `close()` 能叫停，而客户端那一半服务端测不到。所以两道都上：客户端 `close()`（治本）+ 服务端 409（若前端哪天漏了，也不会白跑一次模型）。**非 200 会让 `EventSource` 永久失败而不重试**，正是想要的语义。
4. **`conversation_id` 必填**（助手服务那边有默认值 `web`，BFF 不给）：那是给直接调接口的调用方留的；浏览器每开一个标签页就生成一个，缺了只能是前端出错，塞默认值会让两个标签页**悄悄**共用一段对话 —— 正是故事 25 要防的串台。宁可 400。
5. **错误码原样保留并据此分派话术**：初稿只要求「三种故障各自有明确表现」。实现时把上游的结构化拒绝（框架 `server/utils/errors.py` 的 `unauthorized` / `thread_busy` / `not_configured`）也接了过来 —— `thread_busy`（上一句还没答完）有自己的一句话，其余走兜底。把「服务好好的但拒绝了」说成「客服暂时联系不上」是错的归因。
6. **`CHARAPP_SERVER_URL`**：初稿没提，但 Django 得知道助手服务在哪；默认值与 `CHARAPP_SERVER_PORT` 的默认值成对。

### 计划外但必须做的

1. **`base.html` 加 `extra_head` / `extra_script` 两个 block**：页面要带自己的样式与脚本，而 base 没有注入点。加的是空 block，对既有页面零影响。
2. **`.env` / `.env.example` 补 `CHARAPP_SERVER_URL`**（见上）。
3. **守卫「会话编号天然合法」**：BFF 的长度上限必须按**整串** `minimall:{买家}:{对话}` 算，不是按第三段算。框架卡的是整串 128（`CharApp` 侧装配会话时走 `check_identifier`），只量第三段会让 117 字符的编号穿过 BFF、到服务端才炸，用户看到的是「客服暂时联系不上」而不是「请求不合法」—— 正是初稿那句「把生成规则设计成天然满足，不要靠传进去才报错」要避免的。这条是 **spec 评审抓出来的**，单测用框架自己的 `check_identifier` 钉住边界（恰好 128 放行 / 129 拒绝）。

### 定稿前发现并修掉的两个真问题

1. **多行 `{# #}` 注释被渲染到页面上**（自己踩的）：Django 的 `{# #}` 只吃单行，写在导航里的多行注释原样渲染成了页面文字。浏览器实跑时看见的（`淘宝 {# 智能客服入口... #} 客服 ¥500000.00`），改成 `{% comment %}` 并补了一条断言（导航里不出现 `{#` / `{%`）。
2. **改名的漏改**：`_localize` → `_with_user_copy` 之后有一处调用点没跟着改（ruff 的 F821 抓到的）。

### 明确不处理

1. **页面上不渲染历史消息**：L1b 不做历史接口（框架的会话历史是给模型看的）。刷新页面 = 新对话，会话编号也跟着换新 —— 初稿备注里已声明的边界。
2. **工具调用轨迹原样展示**（含框架那句「请勿使用相同参数重试」）：那条是**框架写给模型的**可操作提示。留在页面上是刻意的 —— 它是给人看的排查窗（也是演示时讲「模型看到了什么」的素材），翻译它等于替模型写话。用户真正该看到的那句话在下面的答复正文里（商城挂掉时模型会说「暂时查不出来」）。
3. **BFF 不做缓存 / 不做会话历史接口 / 不改写问句**：初稿定的三条，一条没多。
4. **不接 `ban` / 限流 / 审计**：L1b 范围外。

### 与「谁是用户文案的负责人」有关的记录

框架只发事实（错误码 + 说明），用户看到的话分三处：**答复正文**归模型（它拿得到工具失败的回填），**错误提示**归 BFF 的 `ERROR_COPY`，**工具轨迹**原样透传。这条分工写进了 `views_bff.py` 的模块 docstring，也是「文案写在哪一层要有说法」那句话的落点。

## 追加：从 `EventSource` 换成 `fetch`（POST）2026-09-21

**起因**（自查，不是别人提的）：这个端点有副作用却做成 GET，跨站防护只剩 `SameSite=Lax` —— 而 Lax 挡不住**顶层导航**：任何用户访问的网站上写一句 `location = '…/minimall/agent/chat/?message=…'`，就能让登录用户**真跑一次模型**（真花钱），且不需要点击。次要两条：问句在 query 里会落进访问日志；浏览器读不到非 200 响应体，导致「连不上服务」只能假装 200 往流里塞错误帧。完整论述见 `CharApp/docs/adr/0002`。

**改了什么**

| 位置 | 之前 | 现在 |
|------|------|------|
| 端点方法 | `GET` + query 参数 | `POST` + JSON 请求体（`message` / `conversation_id`） |
| 跨站防护 | 靠 `SameSite=Lax` | Django 的 CSRF 中间件（`X-CSRFToken`；缺了 → 403） |
| 前端 | `EventSource` | `fetch` + `eventsource-parser`（CDN 引入、版本钉死；帧解析与 UTF-8 分片交给库） |
| 失败回法 | 一律 200，错误塞进流里 | **拿到流之前**的失败回真状态码（502/503 + `{"error": …}`）；只有「响应头已发出」的中途失败仍走流里 |
| 重连 | 客户端 `close()` + 服务端 `Last-Event-ID` → 409 | 不存在（`fetch` 不自动重连），两道口子连同 2 条测试一起删 |
| 问句长度 | 不限 | 2000 字符（超了 400 `message_too_long`） |
| GET 打这个端点 | 正常跑 | 405 + 一句人话（有副作用的动作不该是一条链接就能触发的） |
| 跑飞刹车 | 只配了轮数（10） | 轮数 + token 预算（6 万）+ 墙钟（90 秒）—— 后两条框架本来就支持，之前没接 |

刹车这一条**两个入口都生效**（它是 `MinimallService` 的字段默认值，不是 HTTP 那侧的东西）：命令行入口也一起被限在 6 万 token / 90 秒，而 `cli.py` 没有对应开关（用默认值，改的话改 `service.py` 的常量）。这是有意的 —— 烧的是同一份 API 账单，开发者一边看着也未必注意；真要放开，把字段显式传 `None` 就行。
