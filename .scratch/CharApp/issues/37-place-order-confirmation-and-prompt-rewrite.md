## 一片一句话

把 L1 那句写在 prompt 里的"下单前问一句确认吗"**换成框架级的挂起**，并**把 prompt 里那句话删掉** —— 否则模型会既问一句又触发一张确认卡，用户被问两次。

## 这一片为什么排在最后

因为它是**纯复用**：`Decision.requires_approval`（34）、确认卡（36）、恢复端点（34/36）三样都在了，本片只加**一条裁决**、**删一句 prompt**。它是 L3b 的最后一个业务增量，也是"框架级确认能覆盖多个场景"的第二个证据。

## 一、护栏加一条裁决

在 `CharApp/minimall/guardrail.py`（L2 建的那个插件）里，对 `place_order` 返回：

```python
if tool.name == PLACE_ORDER_TOOL:          # 常量已在 :53
    return Decision.requires_approval(
        prompt="确认要下这一单吗？",
        needs=(),                          # 纯「是 / 否」，不要用户补任何数据
    )
```

**`needs=()` 是关键**：确认卡据此渲染成**只有两个按钮、没有输入框**（issue 36 定的两态）。代付那条是"带数据的确认"，这条是"纯是非的确认"—— **同一套机制，两种形态**，这正是本片要证明的东西。

## 二、两个插件同点共存：拒绝优先于挂起

`place_order` 现在会同时被**两条业务规则**看：护栏的"8 次写预算 / 5000 元上限"（L2）与刚加的"需要确认"（本片）。而 `HookRegistry.decide()`（`hooks/registry.py:180-217`）是**遍历 handlers 取第一个非放行者**（`:212-217`）。

于是**注册顺序会决定用户体验**：确认排在前面时，一个**会超预算**的下单会先弹确认卡、用户确认完才被拒。

**修法（在 issue 34 的 `decide()` 改动里一并做）**：**拒绝优先于挂起** —— 遍历全部 handlers，任一 `reject` 直接生效；没有任何 `reject` 时才看有没有 `requires_approval`。这样"拒绝"与"挂起"的语义各自干净，**不依赖注册顺序**。

**本片负责验它**：先用掉写预算（或下一个超 5000 的单），断言结果是一条**拒绝**而不是一张确认卡。

## 三、prompt 改写（这一片最容易被漏的一步）

L1 的 prompt 里有"下单前问一句确认吗"那类要求（`CharApp/minimall/prompt/system/v2.prompt`）。框架级挂起上线后，**那句话必须删**：

- 不删 → 模型先问一句，用户说"好"，模型再调工具 → **弹出第二张卡** → 用户被问两次
- 删了 → 模型直接调工具 → 挂起 → **卡片替模型问**

**做法**：出 `v3.prompt`（v2 不删，留着 —— 它是 L4 的 A/B 素材），把 `CharApp/minimall/prompt/manifest.yaml` 的 `default` 改成 `v3`。

> 于是**代付这条链路在 v3 里仍然走不通**（35 的真机是拿一份临时提示词
> `D:/__WorkSpace__/Temp/hitl35prompt/system/v3.prompt` 跑通的，那一份就是这一节的
> 草稿：把「不能替买家付款」改成「**付款由买家本人点头** —— 你可以发起（调
> `pay_my_order`），但那一单会停下来等他本人输一次密码；不要向他要密码，也不要在

### 四处改判（票据的前提与实体对不上，都写进了注释或下面的真机）

1. **票据 §二说「`place_order` 会被**两条业务规则**看，于是注册顺序决定体验」—— 实体里只有一个插件。**
   两条规则都在 `WriteGuardrail.__call__` 里（`service.py` 那唯一一处装配只注册了它一条），
   所以"注册顺序"在本业务里根本不存在，本片的做法是**同插件内的先后**（预算 → 金额 →
   挂起）**加上**框架那条跨插件的优先级（34 的 `decide()`）。两半都有用例：
   `test_the_budget_beats_the_suspension`（同插件，两条挂起各验一遍）与框架那一条。

2. **票据 §三要删的那句话，v2 里并不存在。**
   `git log -S"确认吗"` 全仓只在 PRD §4.7 的**计划**里出现过（"第一阶段：靠提示词，
   要求模型下单前问一句"），而 v2 正文只写着「动手之前先说清……讲完就做」——
   **那一步从来没实现过**。所以这一条落成的是**正向指令**：不许在对话里再问一句、
   "卡替他问过了"、示例按新流程改写（示例是行为最强的锚）。三处都进了 v3。

3. **§三补记说「直接把那段搬进 v3 即可」，实际做的是合并重写。**
   三处偏离，都有理由：① 付款与下单**合并成第 1 条禁则**（两件事是同一个道理，写两遍

   「不透露内部实现」那一节的自洽）；③ 示例补了**取消之后**那一条分支。
   因为 ③，验收第 4 条的证据必须**重跑**——已经用真 v3 重验（见真机表第 4 行）。

**顺手撞出来的两件事**（都记进残留）：

- **顺序做 9 次写、走不到第 9 次**：第一次尝试「依次改成 1..8 然后下单」时，模型老老实实
  一步一次，第 8 次之后**框架的 token 预算**先到了（BFF 回的是 `token_budget` 那句
  「这次要查的东西太多了…」）—— 所以预算那条规则在**顺序**跑法下几乎摸不到，它拦的是
  「同一条回复里并发的多次写」（那是它设计时防的形态）。
- **模型的两次拒绝都很在理**：并行同字段的 8 次改量、以及"同一条回复里发 9 个调用"，
  它都拒了并说清理由（"改的是同一个字段, 并行等于互相覆盖, 最后剩几件是随机的"）。
