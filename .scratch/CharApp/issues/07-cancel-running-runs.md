# 07 · 取消：浏览器上按「停止」，运行真的停下

**Status:** done

**Type:** task

**Blocked by:** 06

**上游:** `../PRD.md` §4.9（L1b）、`CharApp/docs/PLAN.md` §4、`CharAgent/docs/DESIGN.md` #18

## 做什么

一次运行跑到一半，用户在页面上按「停止」，它真的停下来 —— 四层切穿：框架端点 → 业务服务 → BFF → 前端按钮。

这一条是 L1b 里**唯一**跨越全部四层的功能，也是它值得单独成片的原因：任何一层没接，行为就不成立。

## 已经替你确认过的事实

| 事实 | 出处 |
|------|------|
| 取消语义已经定死：就是 `asyncio.Task.cancel()`，只是触发源从终端信号换成 HTTP 请求 | `client/app.py:293-294` |
| **框架在取消时不产终局事件**，注释写明「error(cancelled) 由 server 层负责」 | `agent/loop.py:349-351` |
| 取消是**协作式**的：落在下一个 `await`。同步工具跑在 `asyncio.to_thread` 里，取消停的是 await，**不是那个线程** | `tool/executor.py:171` |
| 取消之后 `ChatSession` 会把已完成的工作收进历史（`_reclaim_progress`），所以接着说一句「继续」就能接上 | `client/session.py:301-347` |
| 框架已有先例：取消中途工具，断言 <2s 且**零泄漏任务** | `tests/test_loop_guard.py:319-345` |

## 具体任务

### 1. 框架侧（`CharAgent/server/`）

- 取消端点：`POST runs/{id}/cancel`。run 登记表与 `run_id` 在 04 里已经立好，这里只是接上
- **补一个终局事件**：框架不产它，所以是本层的责任。理由不是「补个好看的结尾」，而是**SSE 流需要一个明确的终止信号** —— 否则前端只能靠超时或断连猜，重连陷阱（06 第 4 条）也收不干净
- 明确语义边界并记录：取消一个已结束的 run / 不存在的 run，各自返回什么

### 2. 业务侧

把取消端点从框架的接缝暴露出来 —— 如果 04 的接缝设计对了，这里应该只是配置，不是新逻辑。

### 3. BFF

转发取消请求到 CharApp 服务。**身份从 session 取**（与 06 同一条纪律）—— 不能让人取消别人的运行。

### 4. 前端

「停止」按钮 + 调取消接口 + 收到终局事件后收尾。

### 5. 取消之后能接着走

`ChatSession` 会把已落盘的进度收回历史（只做加法），所以用户接着说「继续」就是一次普通提问，模型看着历史自己接上 —— 这是框架已经做好的能力（`client/session.py:102-107`）。**要在页面上真的验一遍**，不只是框架测试里绿。

### 6. 写测试

## 验收

- [x] 浏览器上按「停止」，正在跑的运行在 1-2 秒内停下，SSE 流有**干净的结尾**（不是静默断连）
- [x] 停下之后说一句「继续」→ 接着走，**不重做已完成的步骤**
- [x] 取消一个已经结束的 run → 不是 500
- [x] 取消一个不存在的 run → 明确回应
- [x] 客户端直接断开连接 → 服务端不泄漏任务（对齐框架 `test_loop_guard.py` 已有的断言方式）
- [x] 取消**不影响**同一进程里其他买家的运行
- [x] 不能取消别人的运行（身份从 session 取，不看参数）

## 备注

- **取消是协作式的**：对只读工具（本阶段）无所谓，但写操作阶段要重新考虑 —— 一个已经发出去的加购/下单请求不会因为 await 被取消而回滚。**这条要写进备注，别留到 L2 才想起来**
  - **落实位置 (2026-09-21 实现时补记)**: 写在 `app/minimall/views_bff.py` 的 `AgentCancelView` docstring 里 (「Important」一段), 并且把「前提变了就得回来改」的触发条件写明白了 (工具能改数据的那一天, 要按 DESIGN #17/#18 上幂等键与补偿), 不是一条泛泛的提醒
- 框架的 `KillSwitch` **不要用** —— 它是给终端 Ctrl-C 用的（同步跑协程 + 捕获 `KeyboardInterrupt`）。server 侧直接 `asyncio.create_task` + `task.cancel()`
- 别把「客户端断连自动取消」做成唯一的取消方式：用户点停止是一个**明确意图**，应该有显式请求；断连检测是补充，不是替代
- 本片不碰 HITL 审批挂起 —— 那是 L3，机制不同（挂起是存档等确认，取消是终止）

### 代码审查改了什么 (两轴各起了一个 sub-agent, 都是真跑出来的)

| 审查发现 | 处理 |
|---------|------|
| **取消失败后按钮永久卡死** (我新写的代码): 失败分支只报错、不复位, 于是按钮停在 disabled + 「正在停止…」, 而守卫 `if (... \|\| stopping) return` 挡住重按 —— **最需要停止按钮的时刻它正好死着** | 修: 失败时把按钮放回去。浏览器里用 mock 打了一个 500 复现并验修: 2553ms 按钮恢复可点 (那一刻输入框还锁着, 说明运行仍在跑), 运行继续到 5563ms 正常作答 |
| **任意 404 都被当成「刚好答完了」**: 页面静默忽略 404, 所以一个不带 `run_not_found` 的 404 (对面没有这条路由 / 版本不齐) 会被当成正常竞争 —— 停止按钮从此按不动且一句解释都没有 | 修: 只有 `404 + run_not_found` 才转 404, 别的一律 502。补了一条用例 (`test_a_404_without_the_expected_code_is_a_failure_not_a_race`) |

| `forward_cancel` 与 `open_upstream` 里「令牌 fail closed + 三个头」逐字重复两份 | 抽出 `_internal_token(who, action)` 与 `_service_headers(token, user_id, conversation_id)` —— 少带 `X-Conversation-Id` 的后果是**每次取消都失败**, 这种错只能靠"只写一份"来防 |
| `_not_running` 这名字读着像布尔判定, 实际返回文案 | 改名 `_not_running_message` |

### 与初稿的出入

1. **「补一个终局事件」不用补 —— 04 已经补了**。`runs.close_stream` 在任务被取消时会
   `emit_terminal(CANCELLED_CODE, ...)`, 04 的用例 (`test_a_cancelled_run_ends_with_cancelled`)
   早就断言过。所以本片在框架侧只做了「接上端点」这一件事; 那条用例改成从**真端点**触发
   (原先直接摸 `registry` 里的任务句柄), 因为客户端看到的东西由边界决定。
2. **业务侧真的只是配置**。`create_minimall_app` 交出的还是那两个插座, 取消端点复用了
   同一个 `MinimallContexts` —— 于是「只能取消自己那段会话里的运行」**零代码**成立
   (判据是 `thread_id` 里含买家)。ticket 里那句「如果 04 的接缝设计对了, 这里应该只是
   配置」得到了正面回答。
3. **「三种不在册」合并成一个回答 (首稿没定)**。已结束 / 没这个编号 / 不是你的运行,
   在取消那一刻是同一件事 (跑完即出册, 本层分不出来), 于是都是 404 + `run_not_found`,
   响应体除回显的编号外逐字相同。不选 403 的理由: 403 会确认「这个编号真实存在过」,
   那是一条能拿去枚举别人运行的情报。
4. **前端按钮的可见性绑在 `X-Run-Id` 上**。拿不到编号就不显示停止按钮 (按了也没用),
   为此 BFF 新增了把上游那个响应头转给浏览器 —— 这是首稿没写到的一小步。
5. **页面把 404 当正常竞争, 不打扰用户**。用户按停止的那一瞬它刚答完, 是每次都可能遇到
   的事, 不该弹一句「出错了」。

### 计划外但必须做的

1. **`run_id` 的形状校验 (32 位十六进制)**。它要拼进 URL 的**路径**: 一个带 `/` 或 `..`
   的编号能把一个攥着内部令牌与 `X-User-Id` 的请求指到同一台机器上的另一个端点去。
   卡形状比事后转义牢, 而且合法的编号只可能来自我们自己那条流。浏览器里也真验过:
   `../../admin/` → 400, 且一个请求都没发出去。
2. **BFF 得把 `X-Run-Id` 带给浏览器** (首稿默认了前端有编号, 没说它从哪来)。
3. **`ERROR_COPY` 加两条** (`run_not_found` / `invalid_run_id`) —— 这个项目的硬规矩是
   「凡是回到浏览器的 `error.message` 都必须是用户话术」。
4. **`httpx.InvalidURL` 在取消这条路上也要接住** (它不是 `HTTPError`)。06 在 `open_upstream`
   里踩过一次, 这次直接按同一条处理 (回 502 而不是让基地址写错冒成 500)。

### 明确不处理的

- **不写 ADR**: 取消端点的三条决定 (身份判据 / 三种不在册合并 / 200 只说"请求收到了")
  都写在框架的 docstring 与 `RunNotFoundError` 里了, 再加一份 ADR 就是第三份同样的说法。
- **不碰 HITL 挂起** (L3, 机制不同) 与**断连自动取消那条路** (04 已有, 本片没动)。
- **不给取消加"断线重试"**: 取消请求失败时页面只说一句人话, 不做自动重试 ——
  用户再按一次就是了, 而自动重试会让"到底停没停"变得难以解释。

### 遗留 (已知, 不在本片范围)

- 服务端在「客户端断连」时仍会把这次运行**取消掉**; 但「运行已经开始」这件事本身无法
  回滚 (模型那一次调用已经发出去/计过费)。这与 `CharAgent/docs/DESIGN.md` #13 的
  「双计费不给假账」是同一类事实, 不是本片引入的。
- 取消之后接着说的那一句是**新的一次运行**: 它有自己的 run_id、自己的 token 与墙钟预算。
