# 07 · 取消：浏览器上按「停止」，运行真的停下

**Status:** ready-for-agent

**Type:** task

**Blocked by:** 06

**上游:** `../PRD.md` §4.9（L1b）、`CharApp/docs/PLAN.md` §4、`CharAgent/docs/DESIGN.md` #18

## 做什么

一次运行跑到一半，用户在页面上按「停止」，它真的停下来 —— 四层切穿：框架端点 → 业务服务 → BFF → 前端按钮。

这一条是 L1b 里**唯一**跨越全部四层的功能，也是它值得单独成片的原因：任何一层没接，行为就不成立。

## 已经替你确认过的事实

| 事实 | 出处 |
|------|------|
| 取消语义已经定死：就是 `asyncio.Task.cancel()`，只是触发源从终端信号换成 HTTP 请求 | `client/app.py:293-294` |
| **框架在取消时不产终局事件**，注释写明「error(cancelled) 由 server 层负责」 | `agent/loop.py:349-351` |
| 取消是**协作式**的：落在下一个 `await`。同步工具跑在 `asyncio.to_thread` 里，取消停的是 await，**不是那个线程** | `tool/executor.py:171` |
| 取消之后 `ChatSession` 会把已完成的工作收进历史（`_reclaim_progress`），所以接着说一句「继续」就能接上 | `client/session.py:301-347` |
| 框架已有先例：取消中途工具，断言 <2s 且**零泄漏任务** | `tests/test_loop_guard.py:319-345` |

## 具体任务

### 1. 框架侧（`CharAgent/server/`）

- 取消端点：`POST runs/{id}/cancel`。run 登记表与 `run_id` 在 04 里已经立好，这里只是接上
- **补一个终局事件**：框架不产它，所以是本层的责任。理由不是「补个好看的结尾」，而是**SSE 流需要一个明确的终止信号** —— 否则前端只能靠超时或断连猜，重连陷阱（06 第 4 条）也收不干净
- 明确语义边界并记录：取消一个已结束的 run / 不存在的 run，各自返回什么

### 2. 业务侧

把取消端点从框架的接缝暴露出来 —— 如果 04 的接缝设计对了，这里应该只是配置，不是新逻辑。

### 3. BFF

转发取消请求到 CharApp 服务。**身份从 session 取**（与 06 同一条纪律）—— 不能让人取消别人的运行。

### 4. 前端

「停止」按钮 + 调取消接口 + 收到终局事件后收尾。

### 5. 取消之后能接着走

`ChatSession` 会把已落盘的进度收回历史（只做加法），所以用户接着说「继续」就是一次普通提问，模型看着历史自己接上 —— 这是框架已经做好的能力（`client/session.py:102-107`）。**要在页面上真的验一遍**，不只是框架测试里绿。

### 6. 写测试

## 验收

- [ ] 浏览器上按「停止」，正在跑的运行在 1-2 秒内停下，SSE 流有**干净的结尾**（不是静默断连）
- [ ] 停下之后说一句「继续」→ 接着走，**不重做已完成的步骤**
- [ ] 取消一个已经结束的 run → 不是 500
- [ ] 取消一个不存在的 run → 明确回应
- [ ] 客户端直接断开连接 → 服务端不泄漏任务（对齐框架 `test_loop_guard.py` 已有的断言方式）
- [ ] 取消**不影响**同一进程里其他买家的运行
- [ ] 不能取消别人的运行（身份从 session 取，不看参数）

## 备注

- **取消是协作式的**：对只读工具（本阶段）无所谓，但写操作阶段要重新考虑 —— 一个已经发出去的加购/下单请求不会因为 await 被取消而回滚。**这条要写进备注，别留到 L2 才想起来**
- 框架的 `KillSwitch` **不要用** —— 它是给终端 Ctrl-C 用的（同步跑协程 + 捕获 `KeyboardInterrupt`）。server 侧直接 `asyncio.create_task` + `task.cancel()`
- 别把「客户端断连自动取消」做成唯一的取消方式：用户点停止是一个**明确意图**，应该有显式请求；断连检测是补充，不是替代
- 本片不碰 HITL 审批挂起 —— 那是 L3，机制不同（挂起是存档等确认，取消是终止）
