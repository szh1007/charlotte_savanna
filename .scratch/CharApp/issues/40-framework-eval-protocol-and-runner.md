## 本片要做的五件

### 一、三个协议

放框架侧新包（名字在实施时定，倾 `CharAgent/eval/`）：

| 协议 | 形状（倾向） | 谁实现 |
|---|---|---|
| `EvalCase` | `id` / 题面 / 期望工具集 / 期望参数（可选）/ 元信息（场景分类等） | 业务（issue 42 从 YAML 加载） |
| `Judge` | `judge(case, facts) -> Verdict(ok, reason, detail)` | 业务（issue 42 的三个指标 + 回答合规） |
| `EvalSubject` | `async run_once(case) -> RunFacts` | 业务（装配一个会话、问一句、交回事实） |

**`EvalSubject` 是本片的关键接缝**：框架管循环（跑 N 题 × M 次、收集、判分、落报告），业务管"怎么造一个会话"与"怎么取事实"。挂起-恢复、载荷注入这些业务特有的动作全部留在业务侧（issue 43），框架一点都不用知道。

### 二、`RunFacts` 里给什么（**本片最核心的设计点**）

判据要同时喂饱两类问题：读轨迹的（工具选对没有）与读文本的（回答合规没有）。倾：

| 字段 | 内容 | 谁用 |
|---|---|---|
| `tool_calls` | 每次调用的 `tool_name` / `arguments` / `status` / `duration_ms`（按发生序） | 召回率、准确率、参数正确率 |
| `answer` | 最终回答文本（**没有 final 时是 `None`**，见 `outcome`） | 回答合规判据 |
| `outcome` | 三分类：`passed` / `truncated`（被预算截断）/ `suspended`（停在挂起） | 三分类结局 |
| `error` | 终局错误（`token_budget` / 其它），有才是 `truncated` | 同上 |
| `turns` / `tokens` / `elapsed_ms` | 运行成本与规模 | 报告的成本收益那一块 |
| `run_id` | 运行编号 | 回看与归因 |
| `config` | 本次跑用的配置快照（见第五条的第七块） | 报告头部 |

**三分类是硬要求**（L4 规划期定）：全挂组的 prompt 前缀更长、更容易撞上 60k token 预算 —— 若把截断算作"答错"，全挂组的分数会被压低，**裁剪组会显得更准，而那个差异来自前缀长度不是来自选择能力**。判据与报告都按三分类写。

### 三、跑批器

- 串行跑（`for case: for attempt in range(times)`），**先不做并发** —— 20 题 × 3 次在假商城下是分钟级
- 每题每轮用**独立的 subject**（题之间不共享会话与记录层，否则轨迹会串；假库不过滤 WHERE 那个坑见 issue 41）
- 每次跑完立刻调 `Judge`，结果进报告；judge 抛异常**不能中断整批**（记成一条 `judge_error` 继续）
- 真 API key 缺失时**启动期报错**，不静默跑一半

### 四、报告渲染

**JSON**（程序读，用来 diff 两次跑分）+ **Markdown**（人看，能直接贴进 README）。Markdown 的七块：

1. **头部配置快照** —— 跑分时间 / 模型名 / prompt 版本 / 两组各自的工具集大小与分类器 / 三道刹车（`max_turns` / `max_tokens` / `max_duration`）/ 压缩旋钮（阈值 / 保留轮数 / 工具结果截断）。**这一块不能省**：`.env` 今天把压缩阈值压到 30000、工具截断压到 800（框架默认 32000 / 2000），不记就说不清"这是哪套参数下的分"
2. **两组对照总表** —— 召回率 / 准确率 / 参数正确率 / 三分类结局分布 / 零调用样本数 / 挂起次数 / 平均轮数 / 平均 token / 平均耗时 / 总金额
3. **波动** —— 每组 3 次各自的数 + 极差（这是"为什么要跑 3 次"的正当性所在）
4. **逐题表** —— 题号 / 题面摘要 / 期望工具集 / 实际调用 / 命中情况 / 终局 / 轮数 / token / 耗时
5. **失败样本单列** —— badcase 回流的入口（题号 + 差在哪 + 实际调用 + 终局）
6. **差异归因**（两组对照时）—— A 对 B 错的题、B 对 A 错的题
7. **两类收益分开说** —— 准确率收益（**只在未截断的样本内比**）与成本收益（token 省了多少、截断少了多少）

### 五、`compare` 入口

读两份 JSON，出一张差异表（同一组的两轮之间、或两组之间）。**"这次改得比上次好"最终就是这张表** —— 它必须能显示波动范围，否则读者会把噪声当改进。

## 实施记录（2026-09-28）

**六件全部落地**，全部验收框可勾。与票据原文有 **七处出入**，都是实施时定的：

| 票据原文 | 实际做法 | 为什么 |
|---|---|---|
| `Judge` 返回 `Verdict(ok, reason, detail)` | `Judgment(ok, reason, metrics)` | ① `Verdict` 这个名字被 `CharAgent.hooks` 占了（放行 / 拒绝 / 要人批三种态），同名会在根门面撞车；② `detail` 装不下**池化** —— L4 的口径是「分子分母分别相加再相除」，那要求判据交出 `Metric(hit, total)` 这一对，自由文本汇不回来 |
| 三分类（`passed` / `truncated` / `suspended`） | **四分类**，多一个 `BROKEN` | 上游打断与跑批抛错总得有个去处。混进「截断」会让「裁剪之后截断少了多少」被上游抖动污染，混进「答错」更糟。三分类的**要害**（截断不算答错）一条不少，而 issue 42/45 要按四类分流 |
| `RunFacts` 九个字段 | 多一个 `cost` | §四第 2 块要求「总金额」，九个字段里没有它 —— 那是「没算」（None）与「零元」分得开的写法 |
| 配置快照当跑批器的参数（票面没说，但 §四第 1 块要它） | 当成 `RunFacts.config`，由**业务每跑交回来** | 只有装配会话的那一方知道这一跑到底用的什么参数；从外面另传一份，两份迟早漂开。同组里真出现两份不同的，报告会点名（`config_conflicts`） |
| 报告是单组的 | 一次可跑 **1–2 组** | §四第 2/6/7 块全是「两组对照」，单组报告表达不了。两组以上当场拒绝（对照是两两比） |
| §五只说 `compare` 出「一张差异表」 | 它还摆了**配置快照**与**波动** | 「改了 prompt 之后好没好」最要紧的是「这两份各是哪套参数」；波动那一条是票据 §五自己要求的（否则读者把噪声当改进） |
| （未提） | 框架 CLI：`python -m CharAgent.eval compare a.json b.json` | 「入口」的最直接读法；也是验收第 4 条的验收方式（真敲一遍） |

### 给 issue 42 / 44 / 45 的话

- **判据的形状**：`judge(case, facts) -> Judgment(ok, reason, metrics)`。要池化的量（召回率 / 准确率 / 参数正确率）**必须走 `metrics`**（`Metric(hit, total)`），`ok` 只进「通过数」那一路 —— 把比率提前算成浮点，汇总时就再也加不回来了。
- **终局是四类**：`completed` / `truncated` / `suspended` / `broken`。构造 `RunFacts` 时用 `run_outcome_of(result.outcome)`，别自己 if。
- **配置快照由业务交**（`RunFacts.config`）：§四第 1 块列的六样（模型名 / prompt 版本 / 工具集大小与分类器 / 三道刹车 / 压缩旋钮）框架不检查，交空报告就只印一句「没交配置快照」。
- **两组就是两个 `EvalGroup`**（各自的 `build_subject`），一次 `run` 交一份报告；想比两份文件走 `compare_files`。
