## 一、要解决的问题（Problem Statement）

### 从一个"没有客服的商城"说起

`app/minimall/` 是一个能跑的真实商城：能注册、能登录、能浏览商品、能加购物车、能下单、能用余额付款。但它只有一个网页界面 —— 买家想找商品，得自己在页面上点筛选器；想查订单，得点进订单页一页页翻。

### 从"一个没接过真实业务的框架"说起

`CharAgent/` 是一个从零手写的 agent 框架：能带工具一问一答、能中断续跑、能切换存储后端，有 756 个测试在跑。但它至今只接过**演示工具** —— 查当前时间、单位换算、统计文本、还有一个写死在代码里的假订单查询（它假设订单号是 14 位，而真实商城的订单号是 24 位）。

框架里有几处**预先留好的扩展点**，代码写得很完整，但从来没有过一个真实调用方：

- **挂载点（hooks）**：框架在 5 个固定时机"喊一声"，等插件来接。机制通了，但生产代码里注册的插件数量是 **0**。
- **审批挂起（pending）**：快照能停在"某个工具调用还没拿到结果"的半路，恢复路径也写好了。但没有任何代码会走到这条路径上。

**没人用过的接口，等于没设计过。** 一个没有真实调用方的扩展点，你无法判断它够不够用 —— 它可能看起来很美，一接真业务就发现少了东西。

### 三件事同时卡住

| 卡点 | 具体表现 |
|------|---------|
| 框架没被真实业务验证过 | 扩展点全是"预留"，不知道设计得对不对 |
| 商城没有智能客服 | 买家只能用鼠标点，不能用嘴问 |
| 两者之间零连接 | 框架不知道商城存在，商城不知道框架存在 |

## 二、要做什么（Solution）

### 一句话

**给 minimall 商城装一个能说人话的客服助手**；这个助手用 `CharAgent` 框架搭起来，而框架本身不知道"商城"是什么东西。

### 用起来是什么样

**第一阶段（命令行版）**：

```
你：有什么 2000 块以下的手机推荐吗
助手：我查到 3 款，第一款是……（调用真实商品接口，返回真实数据）

你：我最近的订单到哪了
助手：你最近一笔订单是 xxx，状态是"已付款"，还没发货。

你：我余额还有多少
助手：你的余额是 9500 元。
```

**第二阶段（网页版）**：

买家在 minimall 的页面上点一个按钮，弹出客服对话框，直接用已有的登录状态聊天。**多个买家同时用，各看各的数据**。

**后续阶段**：能加购物车、能下单、能取消、能退款（含管理员协商金额的部分退款）；下单前助手会问一句"确认吗"；开发者能查到"这次回答花了多少钱、模型当时看到了什么"；有一套评分题库能证明"这次改得比上次好"。

> **补记（2026-09-26，L3b 收口）**：那句"下单前问一句确认吗"的**实现方式定为框架级确认卡**（页面上一张只有「确认 / 取消」两个按钮的卡，见 §4.7 第三阶段与 issues 34–37）—— 不再由模型在对话里问。

### 为什么这么分两层

```
CharApp/    ← 业务应用：知道商品、订单、退款这些事
    ↓ 只能它依赖上面，不能反过来
CharAgent/  ← 通用框架：完全不知道任何业务
```

**依赖方向严格单向。** 框架代码里不出现 `minimall`、`商品`、`订单` 这些词。这样做的好处很实在：以后要做一个"代码助手"（读写文件、搜代码、跑命令），只需要再写一个业务层，框架一行不用改。

**这不是口号，是一条能跑的测试**：同一个框架，装配两个完全不同的业务（电商 + 一个跟电商毫无关系的假业务），都能跑通。

## 三、用户故事（User Stories）

### A. 买家 —— 只读问答（第一阶段就做）

1. 作为买家，我想用一句大白话问"有没有 2000 块以下的手机"，直接拿到符合条件的商品，这样我不用自己在页面上点一堆筛选条件。
2. 作为买家，我想问"这个商品还有货吗"，拿到**当前**库存数字，这样我不用反复刷新页面猜。
3. 作为买家，我想问"有什么值得买的"，拿到运营标记为精选的商品，这样我不用一个个翻。
4. 作为买家，我想问"都有哪些分类"，看到完整的分类树，这样我知道商城都卖什么。
5. 作为买家，我想问"我购物车里现在有什么"，看到购物车内容，这样我不用跳到购物车页面。
6. 作为买家，我想问"我最近买了什么"，看到我的订单列表，这样我不用一页页翻订单。
7. 作为买家，我想问"订单 20260918xxx 到哪了"，看到那一单的商品明细、收货地址、状态时间线，这样我不用点进去查。
8. 作为买家，我想问"我余额还有多少"，看到准确数字，这样我能决定买不买。
9. 作为买家，我想问"我有几个收货地址"，看到地址列表，这样我不用去个人中心。
10. 作为买家，我想在问完"推荐个手机"之后接着说"第二个多少钱"，助手能听懂"第二个"指的是上一轮的第 2 个商品，这样对话是连贯的，不是每句都从零开始。
11. 作为买家，我想在问答中途按 Ctrl-C 打断、之后说一句"继续"，助手能接着刚才的进度走而不重做已完成的步骤，这样我不怕手滑。

### B. 买家 —— 能改数据的操作（第二阶段）

12. 作为买家，我想说"把第二个加到购物车"，助手帮我加进去，这样我不用手动操作。
13. 作为买家，我想说"把购物车里的数量改成 3"，助手帮我改，这样我不用回页面点。
14. 作为买家，我想说"下单，寄到我家"，助手用我的默认地址下单。
15. 作为买家，我想在助手真的下单之前被问一句"确认下单吗，共 xxx 元"，这样我不会因为说错话把钱花掉。
16. 作为买家，我想说"帮我付了这单"，助手用我的支付密码完成支付。
17. 作为买家，我想说"我要退款"，助手帮我提交一笔退款申请。
18. 作为买家，我想问"我的退款处理到哪一步了"，看到退款进度。
19. 作为买家，我想说"这个商品和描述不符，我要投诉"，助手把我的投诉记下来。
20. 作为买家，我想在助手说"我查到 3 款商品"之后追问"那就第一个吧"，助手知道"第一个"指谁。

> **2026-09-21 范围修订**：故事 16（支付）与故事 19（投诉）**不做**，理由见 §4.5 与 §6。
> 其余故事（12–15、17、18、20）全部保留，另补一条故事 16 的替代：买家想取消自己已付款的订单时，
> 走自助取消（无需审批），由助手代为执行。

### C. 买家 —— 网页使用（第二阶段）

21. 作为买家，我想在 minimall 的页面上点一个按钮就打开客服对话框，不用另外打开一个网站。
22. 作为买家，我想用我已经登录的 minimall 账号直接用客服，不用再登录一次。
23. 作为买家，我想一边看商品页一边问助手，不用在两个页面之间来回切。
24. 作为买家 A，我想确认我**绝对**看不到买家 B 的订单 —— 哪怕我试着在对话框里问"查一下别人的订单"。
25. 作为买家，我想在两个不同设备上开客服时，对话历史各是各的，不串台。

### D. 框架开发者（本项目的作者）

26. 作为框架开发者，我想在新增一个业务接入点时**完全不用改** agent 主循环，这样框架的核心是稳定的。
27. 作为框架开发者，我想让"当前用户是谁"只出现在装配代码里，**永远不进工具的参数表**，这样模型根本没有机会伪造身份。
28. 作为框架开发者，我想用一条测试同时装配两个完全不同的业务都能跑通，这样"通用"是有证据的，不是我自称的。
29. 作为框架开发者，我想让框架的代码里不出现任何业务词（商城、商品、订单），这样分层不会随时间腐化。
30. 作为框架开发者，我想让"危险操作前拦截"挂在一个统一的点上，而不是散落在 17 个业务工具函数里各写一遍。
31. 作为框架开发者，我想让危险操作能被"暂停下来等人确认"，而不是靠 prompt 里求模型自觉。

### E. 业务开发者（同一个作者的另一顶帽子）

32. 作为业务开发者，我想只写"业务动作"（查商品、下单、退款），不用管 agent 循环、重试、快照、流式输出这些底层，这样我能专注在业务上。
33. 作为业务开发者，我想让业务代码全部待在 `CharApp/` 目录里，一点不污染框架。
34. 作为业务开发者，我想让工具的名字和说明写得清楚，这样模型能选对工具。
35. 作为业务开发者，我想在评估数据出来之后能判断"工具是不是给太多了"，而不是靠拍脑袋。
36. 作为业务开发者，我想让每个工具都写成异步的、不会阻塞其他工具的调用，这样多个查询能同时进行。

### F. 可观测与评估（第三、四阶段）

37. 作为开发者，我想在加一个新的可观测插件时不用动框架核心，通过挂载点接进去。
38. 作为开发者，我想让每次回答都能事后查到"模型当时看到了什么、调了哪些工具、花了多少钱"。
39. 作为开发者，我想让每次回答都记录"用的是哪一版提示词"，这样评估结果能归因到具体一版。
40. 作为开发者，我想有一套评分题库，能一键跑出分数，这样我能证明"这次改动比上次好"。
41. 作为开发者，我想对比"一次给模型 9 个工具"和"按场景动态给 4 个工具"哪种回答更准，用数据决定，而不是靠猜。
42. 作为开发者，我想让日志里**不出现**用户的敏感信息（密码、完整手机号），这样日志可以放心保留。

### G. 面试官 / 评审者（这个项目的真实观众）

43. 作为面试官，我想在五分钟内看出"框架 + 业务"两层结构清晰、依赖方向单一，这样我能判断作者真的懂分层。
44. 作为面试官，我想看到每个关键取舍都有记录和理由（为什么退款不动库存、为什么内部接口信任传过来的用户 ID、为什么"退款中"要挤进订单状态），这样我能判断作者是思考过的，而不是照着教程抄的。
45. 作为面试官，我想看到这套东西能真的跑起来（而不是只有代码和 PPT），这样我能相信它确实工作过。
46. 作为面试官，我想看到"预留的扩展点在被真实业务用过之后做了哪些修改"，这样我能判断作者有没有"设计—验证—修正"的完整经验。

## 四、实现决策（Implementation Decisions）

> 说明：以下每条都是本次设计讨论中**拍过板**的决定，附上当时的理由。凡是"为什么不用另一种做法"，都是真实比较过的。

### 4.1 代码怎么分层

**决定**：在仓库根目录下并列两个目录 —— 框架和业务应用。框架绝对不引用业务。

**理由**：如果业务代码塞进框架目录里，以后做第二个业务（代码助手）也要往同一个地方塞，框架会变成一个业务大杂烩，"通用框架"这个说法就崩了。

**约束**：以后框架要能被单独安装使用（需要给框架加一个包声明文件），这样"能被复用的框架"从说法变成事实。

### 4.2 身份（"我是谁"）怎么传

这是整个设计里最容易做错的一处，说细一点。

**问题**：助手要代表某个买家操作（查"我的"订单），所以工具必须知道"当前用户是谁"。但工具的**参数表会被序列化成文本发给模型看** —— 如果把"用户 ID"做成一个工具参数，模型就会看到它，甚至可能被诱导填别的值。

**决定**：用户 ID 不进工具的参数表。工具从"运行上下文"里拿它，而"运行上下文"由装配代码填写。

```
浏览器登录（唯一真正验证身份的地方）
   ↓ 拿到 user_id
Django 把 user_id 放进请求头转发给助手服务
   ↓
助手服务把 user_id 放进"运行上下文"
   ↓
工具从运行上下文取 user_id —— 模型看不见、也改不了
```

**结果**：**"诱导模型去查别人的订单"这条攻击路径根本不存在** —— 模型压根不知道有这么个东西。

**分阶段**：第一阶段（命令行）从命令行参数取用户 ID；第二阶段（网页）从 Django 转发的请求头取。**只有最前面"从哪取"这一小段会变，后面的代码一行不改。**

### 4.3 助手怎么访问商城的数据

**决定**：在商城应用里新增一组**专门给助手用的接口**（不是复用现有的买家网页接口，也不是直接读写数据库）。这组接口内部调用商城已有的业务函数。

**为什么不用直接读数据库**：会绕过商城已经写好的业务规则（比如下单时扣库存的加锁逻辑、缓存失效通知），助手会变成一个绕过规则的后门。

**为什么不用现有的买家接口**：那些接口是按网页需要设计的（分页、字段选择），助手要完成一次下单得凑五次调用才能拼齐。助手需要的是"粗粒度的业务动作"，不是"细粒度的数据接口"。

**这组接口的规则**：

- 用一个内部令牌认证（沿用项目里已经有的做法）；**没配置令牌时拒绝一切请求**（不给"忘了配置就默认放行"的机会）
- 需要用户身份的接口从请求头取用户 ID
- **商品数据直接查数据库，不走缓存**。原因：商城的商品详情缓存最长约 12 分钟，助手如果报"还剩 3 件"而那是 12 分钟前的数字，买家会当成事实。助手的请求量很小，直查数据库的代价可以接受。
  - 备注：如果以后商城能把缓存一致性解决好，这条可以改，验收测试里那条"改库存后立刻反映"就要同时改掉。

### 4.4 业务工具怎么设计

**第一批 9 个只读工具**（都是异步的，不阻塞彼此）：

| 分组 | 工具 | 做什么 |
|------|------|--------|
| 商品 | 搜索商品 | 按关键词搜，可带分类、价格区间、排序、页码 |
| 商品 | 查商品详情 | 按商品标识查详情，含库存 |
| 商品 | 查分类树 | 全部分类 |
| 商品 | 查精选商品 | 运营标记为精选的那些 |
| 购物车 | 查我的购物车 | 只读 |
| 订单 | 查我的订单列表 | 当前用户的订单 |
| 订单 | 查我的订单详情 | 按订单号 |
| 账户 | 查我的余额 | 当前用户的余额 |
| 账户 | 查我的地址 | 当前用户的收货地址 |

**命名约定**：涉及"我"的工具用 `my` 开头（如"查我的订单"）。这既是给模型的语言提示，也强化"身份不可指定"这件事。

**为什么一次性给 9 个而不是按场景给 4 个**：现在没有数据能判断 9 个是否太多。先全给，把"工具数量 vs 选择准确率"做成第四阶段的一个对照实验 —— 用数据决定，而不是提前优化一个想象中的问题。

**实现约束**：框架把同步的工具函数扔进线程池执行。业务工具如果写成同步的，会占满线程池让其他调用排队。所以业务工具必须写成异步的（这正好是框架难点清单里"阻塞 IO 陷阱"的真实案例）。

**为什么不用闭包直接包住用户 ID**：能跑，但没有统一形状 —— 17 个工具手工拼一遍，每个业务都要重写。框架提供一个"工具提供者"的统一约定（叫 `ToolProvider`），业务实现它即可。这也是第 28 条用户故事（一条测试装两个业务）能成立的前提。

### 4.5 售后域：先分清"退款"和"退货"

这四个词在设计里经常被混着用，但它们不是一回事。先把边界钉死：

| 术语 | 含义 | 本项目怎么做 |
|------|------|------------|
| **退款** | 钱退回买家，**不涉及货物寄回** | ✅ 做 |
| **退货退款** | 货要寄回、卖家签收后才退钱。需要退货地址、承运商、物流单号 | ❌ 不做 —— 商城连"物流单号"这个字段都没有，做这个等于新建一整套物流域 |
| **售后** | 退款、退货退款、换货、维修的总称 | 只作为领域的名字（命名空间），不建对应数据表 |
| **投诉** | 对商品或服务不满的表达，**不涉及钱** | ❌ 不做 —— 它是一个独立的 Django 模型，和退款没有状态上的关系，**对框架的扩展点没有任何新的验证价值**（2026-09-21 修订，原计划放第二批） |

**退款申请的完整设计**：

| 维度 | 决定 | 理由 |
|------|------|------|
| 能从哪些订单状态发起 | 已付款 / 已发货 / 已收货 / 已完成 | "待付款"还没扣钱，走"取消订单"就行，不需要退款。**无售后时限** —— `completed` 在商城里没有闭环语义（`complete_order` 只把状态推一步），凭空加限期是发明不存在的规则。**2026-09-22 修订**：付款之后**不再允许取消**，一律走退款（原来 `pending` / `paid` 两态都可取消）；判据从「订单处于什么状态」改成「**用户说的是哪个动词**」 |
| 退多少 | **管理员审批时输入金额**（协商金额，`≤` 订单总额） | 2026-09-21 修订（原为"全额"）。买家申请时**不带金额** —— 诉求是"退钱"，金额协商发生在对话框里；让模型有能力填金额等于给模型决定权，与 §4.2 相悖。**不按商品行分摊**（那需要子表、按行算钱、处理"退一件留一件"，本项目不做） |
| 状态流转 | `待处理 → 已批准 → 已退款`，或 `待处理 → 已驳回` | **"批准"和"钱到账"分开**。生产环境里批准和实际打款之间常隔着支付网关，而且这个中间态正好是"暂停等人工审批"机制的验证场。金额在**批准**时定，钱在**打款**时出 |
| 谁审批 | 管理员在商城后台点 | 商城**没有卖家角色**，只有管理员。**审批入口要新建** —— 2026-09-21 更正：原文"后台入口已经存在"不成立，`RefundRequest` 是新模型，`admin.py` 里现在零退款相关的东西 |
| 订单状态怎么变 | 申请 → 订单变**"退款中"**；打款 → **"已退款"**；驳回 → **恢复申请前的状态** | 2026-09-21 修订（原为"退款完成时订单变成已退款"）。"退款中"是必要的：一张正在退款流程里的订单若仍显示"已发货"，买家会以为还能收货。**恢复**靠申请时快照的 `order_status_before`，不靠时间戳推断 |
| 缺失的字段 | 订单表补一个"退款时间"（`refunded_at`，由**打款**那一步写） | 现有订单只有付款/发货/收货/取消四个时间戳，**恰好缺退款那一个**，不对称 |

**两个状态机由此耦合**：`RefundRequest.status`（4 值）与 `Order.status`（新增 `refunding` 取值）必须在
**申请 / 批准 / 打款 / 驳回**四个转换点上同步。这个耦合是有意选的（买家看订单列表要一眼看出"在退款"），
代价与替代方案记在 `CharApp/docs/adr/0004`。

**库存回滚以发货为界（2026-09-22 修订，原「退款一律不动库存」作废）**：货还没出去就回滚、
出去了就不回滚 —— 走取消还是走退款都一样。回滚发生在**打款那一步**（不在申请时）。
原来的写法是「取消回滚、退款不回滚」，于是同一张已付款订单走两条路会得到**不同的库存结果**，
服务函数的 docstring 专门为此解释那个不对称。改判之后判据统一，不对称消失。
代价照记：`paid` 的退款从申请到打款之间，那件货既没回库存也没发出去 —— 它被这一单占着，
别人买不到。本项目接受（商城没有真实仓储），但它正是「审批期间要不要预占库存」这个真实问题的起点。

**同一订单的重复申请**：同一时刻只允许**一个**进行中的申请（`requested` / `approved`）；
被驳回后**可以再提**（新的一条申请）。因此不能靠 `unique_together` 一条约束表达，要做成
应用层校验 + `select_for_update` 防并发双提。

**管理员备注（`admin_note`）**：批准与驳回都可填。驳回时它是"为什么被驳回"（故事 18 要靠它答），
批准时它写明协商结果（如"协商一致退 70 元"）—— 这正是部分退款场景里买家最需要看到的那句话。

**明确不做自动审批**：自动审批（比如"7 天内无理由自动通过"）看起来更智能，但它会把"暂停等人工确认"这个真实场景消掉 —— 而那正是框架里预留机制**仅有的两个验证场之一**（另一个是 L3 的助手代付：审批人是管理员，代付的确认人是买家本人）。人工审批不是妥协，是故意保留的验证场。

### 4.6 扩展点：从"只能看"升级为"能拦"

**现状**：框架在 5 个固定时机喊一声，插件只能在旁边观察（记录日志、统计花费）。工具相关的那个时机是**执行完之后**才喊。

**问题**：这样一来，"权限校验"、"危险操作拦截"、"下单前审批"**全都无处可挂**。插件唯一能影响流程的方式是偷偷改历史消息 —— 没法定点拦截，也没法暂停。

**决定**：新增一个"工具执行前"的挂载点，并让挂载点有返回值语义：

- 所有插件都返回"放行" → 工具照常执行
- 任何一个插件返回"拒绝 + 原因" → **跳过执行**，把原因当作工具的执行结果回填给模型

**为什么这么设计**：被拒绝的工具调用对模型来说就是一次"工具报错"，而框架**已经**保证"工具错误永远不抛异常、会转成模型看得懂的文字回填" —— 也就是说，这条通道是现成的，不用新建。

**为什么不做成完整的中间件链**（像某些成熟框架那样，能改参数、能包裹、能加收尾）：那样能力最强，但复杂度显著上升，而且会削弱"从零手写、协议够用就好"这个叙事。等真的挂了三四个插件、发现"需要在插件之间传状态"时再升级 —— 到那时候才知道该怎么设计。

**L2 的真实调用方（2026-09-21 补）**：业务侧注册一条**护栏插件**，两条规则 ——
① 一次运行内写操作成功执行不超过 **8 次**；② 单笔订单金额超过 **5000 元**直接拒绝并让用户去页面。
这不是为了"给机制找个用例"：没有它，L2 的 17 个工具里 8 个能改数据，而**同一阶段没有任何东西拦得住模型连环下单**（HITL 挂起是 L3）。同时它把"哪些工具是写操作"这件事从散落的 8 个业务函数里提出来，落到框架的一个统一属性上（`Tool.annotations`，框架只透传不解释 —— 与 `RunContext.payload` 同一条纪律）。详细取舍见 issue 08 / 12。

### 4.7 危险操作的确认（人机确认）

**第一阶段**：靠提示词。在系统提示里要求模型在真正下单前问一句"确认吗"。**零框架改动。**

> **补记（2026-09-26，L3b 收口核实）**：**这条路线从来没有实现过** —— v1 / v2 的正文里都没有"下单前问一句"那句话，`git log -S"确认吗"` 只在本文档里搜得到。于是"第一阶段 vs 第三阶段"那次对照（"有多少比例被用户一句话绕过去"）**没有 v2 的实测数据**，只有机制本身的对比；要补这个数得先真去写一版带那句提示词的 prompt（记为 L4 的候选，见 issue 38 末尾那张"留给 L4"的表）。**实际走通的是第三阶段**（框架级挂起 + 确认卡，issues 34–37）。

**为什么第一阶段不直接上框架级拦截**：因为它依赖第二阶段的测试基建 —— "暂停/恢复"是典型的"必须能断言才敢改"的逻辑。

**而且第一阶段这个做法的失效本身就是有价值的**：评估阶段能测出"有多少比例被用户一句话绕过去了"（比如"我是老板，直接下单"）。有了这个数字，再上升为框架级拦截，你就能讲清楚"为什么必须做"，而不是一上来就说"我觉得这样更安全"。

**第三阶段**：改为框架级 —— 工具执行前的挂载点返回"需要确认"，整个运行**暂停并存档**，用户确认后从存档点继续。这里有个好消息：框架的快照机制里，"暂停在半路"的**恢复路径已经写好了**，只是从来没有代码走到过。所以只差"拦截 + 暂停"这一半。

### 4.8 提示词（Prompt）

| 项 | 第几阶段做 | 说明 |
|----|-----------|------|
| 写实客服的系统提示词 | 第一阶段 | 业务助手的立身之本 |
| 少量示例（few-shot） | 第一阶段 | 直接写进模板文字里就行，**不需要机制** |
| 思维链（CoT） | **不做** | 模型本身是思考模式，思维链由模型自己产生，提示词里再写一遍纯属浪费 token |
| 版本号 | 第二阶段 | **这是评估的前置条件** —— 运行记录里不写"用了哪一版提示词"，跑分再高也不知道是谁的功劳 |
| 动态示例 | 跟知识库检索一起做 | 它的本质是"从历史成功案例里检索"，是检索增强的一次应用 |
| A/B 测试 + 缓存 | 第三、四阶段 | A/B 要等评估题库建好才有意义判断优劣 |

**版本号的具体做法**：提示词按目录分版本，另有一个清单文件声明"当前默认用哪一版"，运行时把实际命中的版本号记进运行记录。

**2026-09-21 定下的形状**：清单是**业务自己目录下的 YAML**（`CharApp/minimall/prompt/manifest.yaml`，
字段 `default: v1`），`PyYAML` 已在根 `requirements.txt` 里（原来只有 OmegaConf 间接用），**不新增依赖**。
目录已按 `prompt/system/v1.prompt` 落盘（L1a 完成）。**读不到清单 = 启动期错误**，不静默退回上一版 ——
与 `PromptNotFoundError` 同一条纪律：静默退回会让一次"v2 的跑分"其实是 v1 的成绩，而且没有任何地方会报警。
本条**只做到"读清单 → 定版本号 → 断言文件存在"**；"把实际命中的版本写进运行记录"依赖 L3 的轨迹落库，
由 L3 兑现（L4 的评估要以它为前置，届时要先确认它真的记上了）。

**一个必须点出的边界**：框架里现在有个占位的业务提示词文件，业务提示词**不该留在框架里**，要移到业务目录下。相应地，框架的提示词加载函数要支持"指定目录"，否则业务提示词没地方放。

### 4.9 阶段划分

| 阶段 | 名称 | 内容 | 验收标准 |
|------|------|------|---------|
| **L1a** | 能跑（命令行） | 框架的工具提供者约定；商城的 9 个只读接口；业务的 9 个只读工具 + 命令行入口 | 命令行里问"推荐个手机"、"我的订单到哪了"，拿到**真实**数据 |
| **L1b** | 能跑（网页、多用户） | 框架的 HTTP 服务层（流式输出 + 取消）；Django 转发层；商城网页上的客服对话框 | 浏览器打开客服页，多个买家各自登录、各自看到自己的数据 |
| **L2** | 可测 + 能改数据 | 工具执行前的拦截点（`before_tool_execute` + `Tool.annotations`）；提示词版本化（清单文件）；商城的写操作内部端点；17 个工具（+8 个写工具）；业务侧护栏插件；工具事件去字段化；会话历史接口；退款域整片（含协商金额的部分退款）；顺带修商城三处缺事务/锁的写路径 | 拦截行为能被自动化测试断言；下单与退款链路跑通（浏览器里下单 → 申请退款 → 管理员批准 70 元 → 打款 → 助手答得出退了 70） |
| **L2.5** | 会话治理（原计划外，用户要求的中间阶段） | 框架侧：**上下文压缩**（账本/视图分离、滚动摘要、工具结果截断、单请求 token 阈值）；框架侧：**会话记录与水合**（记录落库、重启后模型与前端都拿得回历史、会话列表端点、空闲淘汰）；业务侧接入（快照换 Postgres、两个入口都记）；前端左侧会话列表（新建 / 切换）；会话管理动作（重命名 / 删除 / 搜索 / 置顶） | 真机：聊几句 → **重启服务** → 前端历史还在且模型接着上文答；长对话触发压缩后**单请求 token 不再增长，而用户看到的历史一条不少**；左侧列表能新建、能切回 |
| **L3** | 可观测 + 人工确认 | 运行轨迹落库、成本记账、敏感信息脱敏；框架级的人工确认挂起；**助手代付**（用户本人在页面上输支付密码，走挂起-恢复，密码不进会话历史） | 能回答"当时它看到了什么、花了多少钱" |
| **L4** | 可评估 | 评分题库 + 自动跑分；提示词 A/B；**工具数量 A/B（17 个全挂 vs 按场景动态裁剪）** | 能证明"这次改得比上次好"，两个 A/B 有对照数据 |

**为什么第一阶段不能跳过命令行直接做网页**：网页会同时引入 HTTP 层、流式输出、Django 转发、前端渲染、跨进程错误传播五个新变量。如果"框架 → 工具 → 商城接口 → 数据库"这条链路本身还没验证过，出问题时你无法判断是哪一层坏了。命令行版本用最少的变量把链路跑通，网页版只加"传输"这一层。

**为什么退款申请排在第二阶段而不是更晚**：因为它是"人工确认"机制的真实素材。没有这个场景，第三阶段的框架级确认就没有东西可验。

### 4.10 信任模型（三层，只有一个真验证点）

| 边界 | 认证方式 | 说明 |
|------|---------|------|
| 浏览器 ↔ Django | **登录 Cookie** | **唯一真正验证"你是谁"的地方** |
| Django ↔ 助手服务 | 内部令牌 + 用户 ID | 同一个信任域内的服务间调用 |
| 助手服务 ↔ 商城接口 | 内部令牌 + 用户 ID | 同上 |

**这里有一个必须记录的取舍**：助手服务和商城接口之间，用户 ID 是"直接传过去"的，而不是签名的令牌。这意味着"任何拿到内部令牌的人都能冒充任意用户"。

**为什么还是这么选**：第一阶段只有本机单用户演示，为了这个引入令牌签发/验签/时钟偏移/密钥轮换，是在**为一个不存在的威胁做工程**。

**但必须记录**：这个决定满足"记录架构决策"的全部三个条件 —— 改认证契约要动所有接口（难回退）、面试官一定会问"为什么敢直接信任"（没有上下文时反直觉）、确实存在真实取舍。所以要写一份决策记录，内容包含**生产环境的正确做法**（用签名令牌，把用户 ID 放在签名载荷里）。

### 4.11 用户 ID 的会话隔离

**决定**：会话编号规则是 `业务:用户ID:对话ID`。

**理由**：框架的快照本来就按会话编号分区，只要编号里带上用户 ID，**多用户隔离是免费得到的**，不用额外设计。

### 4.12 插件放哪

**决定**：通用插件（运行轨迹、成本记账、脱敏）放框架目录；业务专属插件（商城的权限规则、FAQ 知识库）放业务目录。

**判断标准只有一条**：**这个插件换到"代码助手"那个业务还能用吗？** 能 → 框架；不能 → 业务。这条标准同时也是通用性测试要断言的东西。

### 4.13 运行轨迹存哪

**决定**：存进已有的 Postgres 数据库，一次运行一行，明细放在 JSON 字段里。

**为什么不用 JSON 文件**：评估阶段要按时间段、按工具、按用户做聚合统计（"上周工具调用成功率"），用 SQL 是唯一不别扭的做法。

**为什么不用现成的可观测平台**：这个项目的核心叙事是"从零手写"，接一个外部平台会让面试官分不清哪些是作者做的。

**为什么是一行而不是每个事件一行**：避免写入量放大。

## 五、测试决策（Testing Decisions）

### 什么算一个好测试

**只测外部行为，不测内部实现。** 具体说：

- ✅ 测"问了这句话，模型收到的是这些工具，工具被这样调用了，最后答的是这个"
- ✅ 测"没带令牌请求商城接口，被拒绝了"
- ✅ 测"买家 A 的令牌取不到买家 B 的订单"
- ❌ 测"某个私有方法的第三个参数是什么"
- ❌ 测"内部状态变量现在是几"

**理由**：内部实现会变，外部行为（对用户、对调用方的承诺）才是契约。

### 测试接缝（只有两个，都是现成的）

**接缝一：一次完整的问答**

从最高处切进去 —— 直接驱动"问一句"这个动作，用假模型（框架已有的 MockLLM，支持三种形态：固定回复、按脚本依次回复、录制回放）扮演模型，然后断言：

- 模型收到的工具清单一共有几个、分别叫什么
- 哪些工具被调用了、按什么顺序、传了什么参数（框架已有轨迹断言工具）
- 最终回答里包含了工具返回的数据

**这一个接缝同时覆盖三层**：框架的工具提供者约定、业务工具的组装、工具到商城接口的调用（商城的 HTTP 用 `respx` 拦下来）。

**先例**：框架现有 756 个测试大量使用这个接缝，`respx` 也已经是框架测试的依赖（用来测 HTTP 适配器）。

**接缝二：商城接口**

用 Django 的测试客户端直接打那 9 个接口，断言：

- 没有令牌 → 拒绝
- 令牌错了 → 拒绝
- **没有配置内部令牌 → 全部拒绝**（这条容易漏，要专门测）
- 买家 A 的请求取不到买家 B 的数据
- 改了库存之后立刻能读到新值（证明真的没走缓存）

**先例**：商城现有的接口测试（`app/minimall/tests/test_api.py`）就是这个写法。

### 各模块测什么

| 模块 | 测什么 | 接缝 |
|------|--------|------|
| 框架的工具提供者约定 | 提供一个假实现，能装配成一次完整问答；工具清单正确传入 | 接缝一 |
| 框架的通用性 | **同一套装配代码，装两个不同的业务（电商 + 一个跟电商无关的假业务）都能跑通** | 接缝一 |
| 框架的提示词加载 | 能指定业务目录加载业务提示词 | 单元测试 |
| 业务的 9 个工具 | 每个工具的参数校验、返回解析、错误处理 | 单元测试 + HTTP 拦截 |
| 业务的工具提供者 | 给定用户 ID，返回 9 个工具；**且这 9 个工具的参数表里不出现"用户 ID"** | 接缝一 |
| 业务的命令行入口 | 端到端跑一次真实问答 | 接缝一 |
| 商城接口 | 认证、隔离、不走缓存 | 接缝二 |

**特别注意「工具参数表里不出现用户 ID」这条要单独写一个测试** —— 它是 4.2 那条核心安全设计的守卫，不能靠"我记得"。写法：拿到工具列表后，遍历每个工具的参数定义，断言里面没有 `user_id` / `user` 这类字段。

## 六、不做什么（Out of Scope）

| 不做 | 原因 |
|------|------|
| **退货退款** | 需要退货地址、承运商、物流单号，商城一个字段都没有。做这个等于新建一整套物流域 |
| **按商品行分摊的部分退款** | 要按行选商品、按行算钱、处理"退一件留一件"，需要子表，复杂度翻倍且对求职作品零收益。**协商金额的部分退款要做** —— 它只是 `RefundRequest` 上一个 `amount` 字段，不涉及行结构（2026-09-21 修订） |
| **自动审批退款** | 会把"人工确认"这个唯一能验证框架挂起机制的场景消掉（见 4.5） |
| **投诉** | 一个独立的 Django 模型，与退款无状态耦合，**对框架的扩展点没有任何新的验证价值**（2026-09-21 修订，原计划放第二批） |
| **支付（助手代付）** | 支付密码必须由明文经手才能校验（`check_password`），而 §4.2 的核心纪律是"身份不进参数表、模型看不见也改不了"。这两条不可调和。正确的实现是框架级挂起（用户**本人**在页面上直接输入密码），归 L3（2026-09-21 修订，原计划放 L2） |
| **换货 / 维修** | 属于"售后"上位概念，本项目不涉及 |
| **卖家 / 商家角色** | 商城**根本不存在**这个角色，只有买家和管理员。不得假设其存在 |
| **真实支付网关** | 商城的余额是站内虚拟货币，注册送 10000，够用 |
| **多 agent 协作** | 框架难点清单里标为最低优先级。单 agent 挂 17 个工具都还没验证过，同时引入多 agent 是两个未知相乘 |
| **MCP / A2A / 多模态 / 代码执行** | 框架的扩展能力册，本轮不做 |
| **生产部署 / 多实例 / 限流熔断** | 本项目定位是求职作品，这些属于"能扛真实流量"，不是本项目目标 |
| **接外部可观测平台** | 会削弱"从零手写"的叙事（见 4.13） |
| **恢复已删除的历史文档** | 已定：以当前磁盘状态为基线，旧文档永久废弃不重建 |

## 七、补充说明（Further Notes）

### 7.1 这个项目的定位

**产出目标是求职作品。** 这个定位直接影响取舍：**"能演示、能讲清楚一个架构决策"比"运维体系完备"更重要**。所以本 spec 里有大量"为什么不做 X"的记录 —— 那些不是省略，是刻意保留的讲述素材。

### 7.2 已有的四条领域词汇必须先读

`CharApp/CONTEXT.md` 定义了本项目的一批术语，实现时**必须用其中的词，不要自创同义词**。最容易出错的三个：

- **退款** ≠ **退货退款**（前者不涉及寄回货物）
- **取消** ≠ **退款**（取消是买家自助、不需要审批；退款需要管理员批准）
- **买家 / 管理员** —— 商城**没有卖家角色**，别假设它存在

### 7.3 框架的现状（避免重复劳动）

- 框架已有约 1.4 万行非测试代码、700+ 测试，**核心循环、工具系统、模型适配、流式事件、重试、快照、数据层、命令行都已经完成**
- 难点清单里标记为最高优先级的 15 项，**13 项已完成**；明显欠账的是"提示词工程"（只到"文件化模板"）和"工具执行前的拦截点"（不存在）
- **不要重写任何已完成的组件。** 本 spec 要的是"在已有框架上加一个业务接入点"，不是"再造一个框架"

### 7.4 最需要小心的三处

1. **不要让框架知道业务的存在** —— 这是整个项目的核心卖点，一旦破例（比如框架里写一句 `if 业务 == "商城"`），卖点就没了。那条"两个业务共用一套装配"的测试就是防线。

2. **不要手写 17 个工具的闭包** —— 框架已经定了"工具提供者"这个统一约定，业务实现它就行。手写闭包能跑但每个业务都要重写一遍。

3. **工具必须是异步的** —— 框架把同步工具扔进线程池，9 个同步工具会互相排队。这是框架难点清单里"阻塞 IO 陷阱"的真实场景，不是教条。

### 7.5 拆成三个可并行/串行的执行单元

| # | 单元 | 依赖 | 能不能并行 |
|---|------|------|-----------|
| 01 | 框架侧：工具提供者约定 + 提示词目录参数 + 包声明 | 无 | 可与 02 并行 |
| 02 | 商城侧：9 个只读接口 + 认证 + 测试 | 无 | 可与 01 并行 |
| 03 | 业务侧：9 个工具 + 工具提供者 + 命令行入口 + 测试 | 依赖 01 和 02 | 必须等前两个 |

详见同目录下的 `issues/` 目录。

> 每片见对应 ticket。L2 的关键路径是 `09 → 10 → 11 → 12`，`08` 与 `09` 可并行、`13` 与 `11` 可并行。
