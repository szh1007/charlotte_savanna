## 0. 定位与判据

**目标**：把已有的四条经历打磨成「面试官追问不穿、自己能当场演示」的求职作品。

**求职条件（2026-09-30 定）**

| 项 | 值 |
|---|---|
| 目标岗位 | **业务 Agent 落地**（重业务链路 + 工具设计 + HITL + 评测），用 CharAgent 的运行时深度做差异化 |
| 投入 | 全职、每天 16 小时 —— **时间不是约束** |
| 面试形式 | 腾讯会议共享桌面（**自己操作演示**）/ 线下面谈 |
| 交付物 | 公开 GitHub 门户 + 一页纸架构图 / 讲述稿 |

**两条判据**（所有取舍按这两条裁）

1. **面试官能看见什么** —— 看不见的工作等于没做
2. **会不会被问穿** —— 已知会崩的必须先修；不做的必须落成「核实后不做」的判据，别留成沉默的缺席

## 2. 七个组

| 组 | 名称 | 内容 | 量级 |
|---|---|---|---|
| **0** | 清雷 | 三个项目里**已知会崩**、或表述与代码不符的地方 | 1.5–3 天 |
| **D** | 演示装置 | 一键启动 + 演示剧本（**提前到组 0 之后**，之后每次改动都走一遍） | 0.5–1 天 |
| **B** | 框架加固 | CharAgent 层：#38 结构化日志 · #15 工具超时 · #14 熔断 | 2.5–3 天 |
| **A** | 主线能力 | L5（RAG + 注入防护）· 长期记忆 · MCP client | 7–10 天 |
| **C** | RAG 补强 | rag_text2sql 评估与安全 · rag_knowledge 题库与消融 | 5–6 天 |
| **E** | 门户 | 四条经历的 README + 根 `README.md` / `CLAUDE.md` | 2 天 |
| **F** | 底稿 | #64 教学文档 · 多智能体原理底稿 | 1 天 |

**执行顺序**：`0 → D → B → A → C → E → F`

- **0 先做**：成本最低、确定性最高。只要没修，「面试官真跑 / 真看」就埋着雷。
- **D 提前**：演示装置要**随功能长**，最后一次性调试会很难；每次改动后走一遍等于持续回归。
- **B 排在 A 前**：三件全在框架层且都小，先把 CharAgent 稳定下来再往上叠 L5 与记忆，避免在同一个文件上反复改。
- **C 放 A 后**：它换了一条代码线，适合当主线之后的「换脑子」。
- **E 必须在所有技术补充之后**：否则门户要写两遍。
- **F 随时可插**：不依赖任何东西。

## 5. 明确不做（记录「不做」与记录「要做」同样重要）

| 不做 | 理由 |
|---|---|
| **多智能体实现** | 本项目没有多智能体的必要。改为写原理底稿（C21）应付面试考察 |
| **#64 无状态化 + graceful drain 实现** | 对面试时的技术与功能演示没有实质帮助。改为写教学文档（C20） |
| **#39 指标告警 / #40 版本化灰度回滚** | 报告里已有归因列与版本列，讲清「为什么不做到这一步」就够 |
| **Docker Compose / 公网部署** | 面试形式是自己操作共享桌面，不需要公网通道 |
| **charplot 补 LangGraph 高级能力** | checkpointer / HITL / 重试这三样在 CharAgent 里已**手写**做过；用框架再做一遍不加分，反而稀释「charplot 讲工程」的定位 |
| **AI 辅助开发说明** | 面试话术统一准备，不写进作品 |
| **演示形态设计（截图 / 录屏 / 一页纸之外的产物）** | 腾讯会议共享桌面自己操作即可 |
| **charplot 前端补测试 / #15 之外的 P2 项** | 边际收益低 |

## 6. 开放决策（2026-09-30 全部拍板）

> 沿用 `.scratch/CharApp/` 的纪律：这些**不能默默假设**。下表是结论与理由，切票的依据。
> 其中有几条是先查事实再拍的 —— 查出来的事实写在对应票据的「现状」节里。

### 6.1 作品集与流程层

| # | 决策 | 结论 |
|---|---|---|
| D1 | MCP 做哪一侧 | **两侧都做** —— 消费侧证框架抽象通用，暴露侧证业务能力可被任何 MCP 客户端调用（且可演示性极强） |
| D2 | #14 备份模型 | **切 `CLOSEAI`（另一家，真容灾）** —— 同 provider 另一档会一起挂，等于没切；且配了第二家才谈得上「价目表支持多 provider」 |
| D3 | 「RAG 工程」门面 | **各自 README + 根 README 一节串起来** —— 合并是讲述层面的事，不必强加在仓库结构上 |
| D4 | rag_text2sql golden set | **人工写问题 + 人工确认口径；L2 只做到「可执行率」** —— 用现有 SQL 反推会把当前缺陷固化成"正确答案" |

### 6.2 L5

| # | 决策 | 结论 |
|---|---|---|
| L5-D1 | 语料载体 | **新建一张轻表（政策 / FAQ 短文）+ Admin 手写 Markdown + 内部端点取**。抄 charplot 的「知识库 + 文档」两张表 + 上传解析不加分（那条链路已被证明两次） |
| L5-D2 | 向量库搬哪套 | **搬 `project/charplot/rag/` 五件套 + 重写 `retriever.py`** —— 形状同源（AI 侧服务 + Django 业务侧 + 内部端点），且有显式主键与「拒绝模型静默下载」两条纪律。`rag_knowledge` 那套搬不动（查询服务全绑 `QueryState`，取一件会把 Mongo/MinerU/LangGraph 一起带上） |
| L5-D3 | 两个本地模型的内存 | **服务启动时后台预热** —— 共享桌面演示时「第一问卡 30 秒」是致命的 |
| L5-D4 | 逐句引用走哪条通道 | **扩 `final` 事件的 payload（带引用数组）**，贯穿到 BFF 与前端两个正文写入口。新增事件类型会动 #4「终局事件恰好一个」的不变量，代价大得多 |

### 6.3 长期记忆

| # | 决策 | 结论 |
|---|---|---|
| MEM-D1 | 放框架层还是业务层 | **框架 `db/` 层加 `memories` 表与仓储（`db/README.md:142-149` 早已规划）+ 业务侧装配**。照 `redact/` 的分工模式：框架给表与协议，业务给内容 |
| MEM-D2 | 情景记忆存什么 | **存「提炼后的事实」，不存「每轮摘要」** —— 后者会与 `charagent_messages` 里 `hidden=True` 的摘要行双写 |
| MEM-D3 | 作用域 | **`(tenant_id, user_id)` 强制过滤**（#32 硬性安全要求，不靠「相信模型不乱看」） |

### 6.4 两处「直接定、不必问」的

- **`rag_knowledge` 扩多文档后 `must_hit` 允许 0~N 条，默认 1 条** —— 多命中要求会让指标变成全有全无，只给跨文档题开多命中。
- **MCP 暴露侧的信任边界**：本地演示 + 绑定单个固定 user_id + **写 ADR 说明边界**（不现在上真鉴权）—— ADR-0001 那句「什么时候必须还」的判据正是「信任域被拆开」，而 MCP 客户端不在浏览器 session 的信任域里，这次正好兑现一次。
