## 现状（2026-09-30 查证）

**这个项目最大的缺口是「零数字」。** README §7 自认评估体系**未落地**；`find *test*` 为空；知识库是玩具规模（**5 表 / 24 列 / 98 个列向量点 / 75 个取值文档 / 2 个指标**）；实际跑通过的问句只有两类（「华北销售总额」「iPhone 卖了多少台」）。

面试官只要问一句「召回率多少、SQL 正确率多少」，**目前没有任何数字可答**。而 Text2SQL 恰恰是最容易被当场验的题型。

**好消息**：README §7 那份设计是现成的、且写得不差 —— 本票**照它做，但砍掉一层**。

## 一、Golden set（30–50 题）

**标准答案从哪来（D4 的结论）**：**人工写问题 + 人工确认口径**。

**⚠️ 绝不能用「现在跑通的 SQL 反推」当标准答案** —— 那等于把当前实现的缺陷**固化成"正确答案"**，题库就永远测不出问题。题库的全部价值恰恰在于它**独立于实现**。

每题记：

| 字段 | 说明 |
|---|---|
| `question` | 自然语言问句 |
| `expected_tables` / `expected_columns` | L1 的 gold |
| `expected_metrics` | 该调哪个指标（没有就空） |
| `notes` | **口径说明** —— 比如「GMV 不含取消单」；这一栏是人工确认留下的痕迹 |

**覆盖面**（README §7 已列，照抄）：单表 / 多表 JOIN / 时间区间 / **相对时间**（「上个月」）/ 维度取值（「华北」）/ 指标别名 / **无指标的问题** / **歧义问题**。

> 最后一类特别值钱：**歧义题问的是「它有没有反问或承认不确定」**，而不是「答得对不对」—— 这类题能测出系统在不知道时的行为。放 2–3 道。

## 二、跑批器与报告

**L1 · Schema 召回**（规则判，全部题）
- 列精确率 / 召回率 · 表必命中率 · 指标命中率
- 数据源：图跑到 `filter_table` / `filter_metric` 之后的候选集（**读节点输出，不是读最终 SQL** —— 这样能把「召回错」与「生成错」分开定位）

**L2 · SQL 可执行率 EX**（规则判，全部题）
- 生成出来的 SQL 能不能在 dw 库里跑通
- **本票只做到这一层**

**L2 的 EEX（结果完全一致）只在前几道能手算的题上做** —— 30–50 题的规模上，逐题人工确认结果集的性价比不成立。**如实写进报告说"为什么只做几道"，比硬凑一个假数字好。**

**L3 · LLM-as-judge：不做。** 理由与 `CharApp/docs/adr/0021` 同源：引 judge 会把**非确定性引进判据里**，「这次比上次好」这句话本身就不再可复现。这次要证的两件事恰好都可规则化。

**打真模型 + 每题跑 N 次**（N=3），报告里给**臂内极差** —— 与 `CharApp/eval` 的报告形状对齐（JSON 给程序 diff，Markdown 给人看）。

---

## 三、稳定性

- 每题跑 N 次，报告同时给均值与极差（**一次跑出来的差不能当结论** —— 这是 L4 那次 A/B 的教训：「臂内极差为 0 不等于差是真的」）
- 逐节点快照：题目失败时能定位到是哪一层（召回 / 合并 / 过滤 / 生成 / 校验）
- 跑批时给 dw 库加只读事务 + LIMIT 保护（执行器的安全垫在 C16，这里先用起来）

## 开工前要定的 —— 已定（2026-10-05）

| # | 决策 | 结论与理由 |
|---|---|---|
| 1 | 跑批用的 dw 数据要不要造丰富 | **不动数据**。相对时间题只用有数据的窗口（「去年」=2025Q1）；「今年 / 上个月」按设计落在空窗口，如实记录空结果、不进 EEX。理由：扩数据要改本地样例库并重建索引，收益只在少数题的 EEX；而「可执行 + 空结果」本身就是有信息量的边界。 |
| 2 | 歧义题的判据怎么写 | **不设计歧义题**（用户决定）。理由：当前项目定位是简单问答统计，不搞复杂评估；且系统尚无澄清机制（§6.2-7），照票面建议判「有没有反问」只会是恒定 0。这条写进了报告的「不做什么与为什么」，不留沉默的缺席。 |

## 实施记录

**跑批**：真模型 `deepseek-v4-flash` × 39 题 × 3 次（=117 次问答），一键
`python -m app.eval.runner`。**落盘基线（2026-10-05 23:58 起跑, 32.6 分钟；
2026-10-06 00:50 复跑首轮超时的 2 题并回）**：

| 指标 | 数值 |
|---|---|
| **L1 列召回率** | **90.5%**（臂内平均极差 0.0pp） |
| **L2 SQL 可执行率（EX）** | **100%**（117/117） |
| 列精确率 / 表必命中率 / 指标命中率 | 97.4%（臂内极差 1.3pp）/ 82.1% / 100% |
| 召回@merge（诊断行） | 94.5% |
| 运行失败率 | **0%**（首轮 2 次 240s 超时, 复跑全部成功 —— 见下） |
| EEX（9 道手算题） | 100% |
| 生成 SQL 撞护栏被拒 | 0 次 |

跑批共三遍：第一遍在修正 AOV 声明之前（90.2% / 97.4%）；第二遍被代码评审的修复打断；
第三遍（起跑 2026-10-05 23:58）在 AOV 声明修正 + 评审修复之后。第一遍的 117 条 SQL 已
核对过 **0 条含行注释**，故「注释吞括号」那处 bug 未污染任何已发布的数字。

**首轮 2 次超时的根因与复跑（2026-10-06）**：

- 现场：两次都挂在 `recall_value` 的那次 LLM 调用上 —— 该节点两条日志一条未打出，而
  并行的列召回 / 指标召回都在几秒内完成（`logs/app.log` 时间窗核对）；超时那跑**没有产出
  SQL**（不是「SQL 跑不通」），两题其余跑次的 SQL 与结果都对（622 件 / 20 位客户，独立口径复核）
- 根因：**上游偶发挂起**。客户端读超时 600s、`max_retries=2`，240s 内既无异常也无重试记录
  —— 请求一直在飞；prompt 仅 1.6KB、期望输出是一个小 JSON，排除「生成太长」。探针实测该
  调用正常 2~20s（12 次全过），复跑同题 6 次全部 8.6~17.1s 通过
- 处置：新增 `--merge-into`（复跑指定题并回已落盘报告，其余题不重掷；`RunRecord.from_dict`
  + `records_from_report` 重建，附「报告→记录→报告」往返一致性用例），复跑 2 题 × 3 次
  全部成功并回基线 —— 报告头部留「复跑并回 + 上一版失败」一行，历史不进黑洞
- 真正的解法仍归 C16（超时 + 重试）：现在唯一的兜底是跑批器的 240s 上限，链路自身没有预算
- **一条未解释的观察**（如实留痕，不作为证据）：定位过程中有一次「6 连探针」超过 180s 未
  完成（该调用正常 1–2 分钟跑完 6 次）；输出被 Python 缓冲，指不出卡在第几次。它与「偶发
  挂起」一致，但单独看不足以作证 —— 上面的根因结论靠的是批次日志 + 客户端配置 + 复跑对照

**TDD 抓到的两个真 bug**（都补了回归用例）：

1. `wrap_limit` 误用「扫描用」的掩码函数拼要执行的 SQL：字符串字面量被整段抹掉，
   `WHERE region_name = '华北'` 在真库上语法报错 —— **`--check-gold` 自检当场抓住 12 道**，
   修复后 39/39 可执行
2. 禁词扫描没忽略大小写：小写 `select … into outfile` 能绕过后白名单形同虚设

**报告渲染层两次修正**（都发生在跑批之后，属「最后一米」）：逐题表把「指标块」(dict)
当数字传给 `_pct` 导致渲染崩（补渲染层用例）；逐题表极差读了不存在的键、恒显 `±0.00`，
N=1 时汇总又显 `0.0pp` 像「稳如泰山」—— 未知极差一律显 `n/a`。

**跑批读出来的结论**（写进报告「解读」节与 README §7.5）：

- 时间类（time_range / relative_time）表必命中率 20% / 25% **不是召回失败**：merge 阶段
  dim_date 已召回（79% / 73%），是 `filter_table` 把它裁掉、系统改走 `fact_order.date_id`
  直接取范围（逐 run 数：dim_date 分别缺 12/15、9/12 次，最终 SQL **0 次**引用它）
- **「两种时间写法等价」是量出来的**：time-01 / relative-01 开 EEX 直接比对结果集（通过）；
  另用独立口径 SQL 手工复核 6 道时间/相对时间题 × 3 次，结果全部一致
- 无指标列表题列精确率 79%：merge 会给涉及的表补主外键，过滤后仍留下未被使用的列
- 首轮 2 次失败全是 240s 超时、都卡在 `recall_value` 的 LLM 调用上（根因与复跑见上节）；
  复跑后运行失败率归零，EX 117/117 —— 全程没有任何「SQL 跑不通」，报告为此保留一行
  「只看产出 SQL 的 N 次」把「没跑完」与「SQL 跑不通」分开
- 117 次里模型没有生成过非只读语句（护栏 0 次命中 —— 0 次也是结论）

| 抓到的问题 | 怎么修的 |
|---|---|

| 常量 200 三写 / `_body` 与 `wrap_limit` 各写一遍分号剥离 / 逐 run 字段手抄 | 统一引 `MAX_ROWS_DEFAULT`；抽出 `_strip_trailing_semicolon`；加 `RunRecord.to_dict()`；`_per_case_block` 复用 `_block` |
| 测试里 `pytestmark_needs_meta_config` 易与 pytest 特殊名混淆 | 改名 `needs_meta_config` |

评审**未改**的判断项（记在这里，不留沉默）：`Spread.rng` / 逐题 `range` / 汇总 `avg_range`
