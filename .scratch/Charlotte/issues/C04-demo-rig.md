## 为什么提前到组 0 之后

面试要在**自己机器上当场跑**。现在同时要活着的有：MySQL + Redis + Postgres + Django(8000) + CharApp server(1007)，而 `sh/` 里**只有单个服务的脚本**，没有聚合入口。

`sh/charapp_backend.sh` 的注释里明写着一个雷：

> 换一台机器 / 换一个库要先建表（`cd CharAgent && alembic upgrade head`），否则第一次写记录或存快照时才会报错 —— **进程能起来，报错落在第一个买家的第一句问话上**。

这个装置**随功能长**（每加一块能力就往剧本里加一段），所以现在做；等到最后一次性调试会很难。

## 一、`sh/charapp_demo.sh`

一条命令做完：

1. **前置检查**：MySQL / Redis / Postgres 三个依赖是否活着（不活着就给一句能照着做的提示，**不要静默失败**）
2. **建表检查**：`CharAgent/alembic upgrade head` 是否已跑过（对齐 `alembic upgrade head` 的幂等性，跑一次确认）
3. **起服务**：Django(8000) + CharApp server(1007)，各自以后台进程起、日志落 `logs/`
4. **健康检查**：轮询到两个端口都活为止（带超时上限和明确的失败输出）
5. **打开客服页**：`start http://127.0.0.1:8000/minimall/...`
6. **打印演示账号与当前数据状态**（余额、未付款订单号）—— 省得当场翻数据库

**约束**：沿用仓库 `sh/` 的既有写法（`#!/usr/bin/env bash` + `set -euo pipefail`、Windows Git Bash 兼容、路径从 `BASH_SOURCE` 推根目录）。

**要记的数**：**冷启动计时** —— 从执行脚本到能提问，秒数写进 README。这个数决定面试时要不要提前把服务开着。

## 二、演示剧本（`sh/charapp_demo.md` 或客服页 README 一节）

**目标**：60–90 秒内走完一条**同时展示三件事**的路径 —— 工具调用真实、HITL 真实、副作用真实。

推荐路径（现状能力下）：

| 步 | 你说什么 | 演示什么 | 秒 |
|---|---|---|---|
| 1 | 「我的订单到哪了」 | 工具调用 + **查的是真库**（订单号是真的） | ~15 |
| 2 | 「帮我把这单付了」 | **挂起卡**弹出（只有密码框） | ~10 |
| 3 | 本人输密码 → 点确认 | 密码**不进模型**（可当场说） | ~10 |
| 4 | 订单变 `paid`、余额 19505 → 19406 | **副作用真的发生了** | ~15 |

**L5 做完后加一段**（C08–C10 落地时回填到本票）：问一个政策类问题 → 答案**逐句带引用** → 再问一个知识库里没有的 → 如实说不知道。

**每段都要有兜底动作**：模型慢 / 网络抖动 / 上游超时的时候你怎么办 —— 写清楚（换一种问法？切到预置的备用问句？直接讲代码？）。**腾讯会议共享桌面时等待会被放大**。

## 三、数据准备

演示走通需要一批**预设数据**：

- 买家账号余额充足
- 至少一笔**未付款订单**（用于演示代付）
- L5 之后还需要知识库已索引

**做法**：写成一个可重复执行的准备步骤（Django management command 或 `sh/` 里的一段），并且**每次演示前跑一遍**保证状态一致 —— 否则上一轮演示付掉的单会让下一轮卡住。

## 实施记录

**装置（`sh/charapp_demo.sh`）**

- 沿用 `sh/` 既有写法：`#!/usr/bin/env bash` + `set -euo pipefail`，根目录从 `BASH_SOURCE` 推。
- 解释器直接用仓库 `.venv`（没激活 venv 直跑脚本是这里最容易踩的坑，症状是一堆
  `ModuleNotFoundError`，看着像代码坏了）。
- 监听地址/端口跟着 `.env` 读（`CHARAPP_SERVER_HOST/PORT`），客服服务读哪两个值这里就读哪两个。
- **已活着的服务复用不重启**：跑第二遍不撞端口，是不是本轮起的写在输出里。
- 健康检查走 HTTP 而不是只看端口：Django 探 `/minimall/agent/`（未登录 302）、客服服务探
  `/openapi.json`（200）。**5xx 不算就绪**——进程活着但应用坏了正是最该报出来的那种失败。
  服务进程退出会立刻停手并摊出日志最后 20 行。
- `PYTHONIOENCODING=utf-8`：Windows 上 Python 默认跟系统码页（GBK），而 Git Bash 按 UTF-8
  读 —— 少这一条，`demo_prepare` 的中文在终端上是乱码（真机第一轮实撞）。
- `runserver --noreload`：演示装置要「起一次就定住」，自动重载会在演示中途重启，还会在
  `_status_.sh` 里多一个包装进程。
- `--no-open`：不开浏览器（只想把服务拉起来时用）。

**数据准备（`manage.py demo_prepare --user-id 10`）**

- 只做两件事：保证有一笔未付款订单（已有就复用**最新**那笔）、保证余额不低于下限（默认 1000）。
- 报「最新」那笔是**真机改的**：第一版报最早那笔，而剧本第二句「帮我把最近的那笔待付款
  订单付了」→ 助手照订单列表（新单在前）挑中的是最新那笔，两者对不上。
- 输出最后那句「当前: 余额 …」才是动手**之后**的准数（第一版把动手前的值打在了首行，
  演示前照着念会念错）。

**剧本（`sh/charapp_demo.md`，与装置脚本同名 —— 票据 §二 原文写的是 `sh/DEMO.md` 或
客服页 README 一节，落点按前者、名字跟装置对齐）**

- 第二句的推荐措辞由「帮我把这单付了」改成「帮我把**最近的那笔待付款**订单付了」——
  真机上账里有 4 笔待付款时，前者会让助手**反问是哪一笔**（它不猜，这是对的，但演示里
  白耗十几秒）。票据 §二 那张表是「推荐路径（现状能力下）」，这属于按真机结果调措辞。
- 兜底表里有两条是真机撞过才写的：助手反问「哪一笔」、以及付款被业务端点拒（400）。
