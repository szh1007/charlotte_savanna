## 一、检索工具

```python
@tool
async def search_knowledge(query: str) -> str:
    """查商城的政策与规则文档（退货/退款/运费/售后/支付/订单状态）。

    什么时候用: 买家问的是「规定是什么」—— 几天能退、运费谁出、超时怎么办。
    什么时候不用: 问的是他自己的单据（订单、余额、地址）用 get_my_* 那几个；
                 问商品本身用 search_products。
    """
```

- **`async def`**（对齐 #65：同步工具会占满线程池），内部把同步的模型推理丢进线程池
- **返回值必须带稳定标识**：`[1] 退货与退款政策\n<片段>…` —— 编号是 C10 的引用契约的基础，格式在本票**定死**
- 参数只有一个 `query`（模型自己组织检索词），描述里给 examples
- 挂进 `_BUILDERS` **末尾**（往后接），经由既有 `build_tools` 流到 `MinimallToolProvider.provide`

**一处容易被漏的连带改动**：`CharApp/tests/conftest.py` 的 `TOOL_NAMES` 是**工具名的权威清单**（去数字化之后，它是唯一权威）—— 新工具必须加进去，否则护栏与装配的用例会静默漏掉它。

（`ToolScope.TOOL_GROUPS` 是 issue 44 的 A/B 装置、生产入口不装 —— 要不要把这个新工具归组，看那时还跑不跑那组实验。）

## 二、prompt v5

新建 `CharApp/minimall/prompt/system/v5.prompt`（**不覆盖 v4** —— 旧版本是 A/B 的对照，manifest 的注释里写着 v2 不删的理由，同一条纪律）。

两处改动：

**① 新增一节「政策问题怎么答」**（放在「能力表」之后）：
> 买家问规定、政策、流程怎么走 —— **先查 `search_knowledge`，按查到的内容答**。
> 查不到就如实说不知道、并告诉他可以找人工；**不许凭印象编**。

**② 「术语」节不动。** 那里面是**系统的硬规则**（取消 vs 退款、库存以发货为界、本项目没有退货退款、余额是站内余额、下单≠付钱）—— 硬规则必须 100% 遵守，**不交给概率检索**。

> **这条边界要写进 ADR**：「可查的政策事实」进知识库，「必须无条件遵守的系统规则」留 prompt。两者的区别不是"长短"，是**错了的后果** —— 政策答偏了可以纠正，规则答错了会产生错误操作。

**③ 本票刻意不做的**：prompt 里**先不写引用规则**，工具返回的 `[n]` 编号**先不要求模型写进答复**。理由：C10 才打开引用通道，现在就要求引用会出现「模型写了 `[1]`、前端当纯文本显示」的中间态 —— 看起来像 bug，实际是半成品。**这个开关在 C10 打开。**

## 实施记录

**工具怎么拿到检索器（票面说"挂进 `_BUILDERS` 末尾"，实施时挂在了 `build_tools` 末尾）**：
`_BUILDERS` 那张表的形状是 `(client, user_id) -> Tool`，而知识检索既不要身份也不要
商城客户端，要的是**检索器** —— 与代付（多一份一次性凭据）同一个理由，它也在
`build_tools` 里单独接，接在最后（"加工具是往后接"这条没变）。`retriever` 是**必填
keyword**：忘了传该在装配处就炸，而不是静默少一个工具（少一个工具不会让任何既有用例
变红，只会让买家问政策时得到一句"我查不到"）。

**检索器走的是第三条通道**：身份与一次性凭据随**运行**进来（载荷 → 闭包），检索器随
**装配**进来（构造参数 → 闭包）—— 政策对谁都是同一份，没有"这次是谁"可言，也就不该
走载荷。三条通道各有各的守卫用例（schema 里搜不到身份 / 搜不到密码 / 检索词确实落到
传进来的那个检索器上）。

**`MinimallService.knowledge` 默认给一份配置而不是 None**：工具集该只有一种形状 ——
"这个进程有没有知识库"不该让模型看见的工具数量变来变去（那会让每一处"工具有几个"的
推理都要先问是哪种装配）。默认值就是 `config.py` 那套（本机 Milvus + modelscope 默认
路径），生产两个入口都从 `CHARAPP_*` 读；跑分 / 用例不传时拿到同一个形状，只是没人去
调那个工具就察觉不到区别。（`build_service` 的接线由 `test_server` 那条装配用例钉住：
env 里的 `CHARAPP_MODELSCOPE_ROOT` 必须出现在 `service.knowledge` 上。）

**两处既有"权威表"是被用例逼着补的**（不是我先想到的）：`redaction.TOOL_PHRASES`
（每个工具都要有页面话术，`test_redaction` 当场红了）与 `scoping.TOOL_GROUPS`
（六组并集必须正好是工具清单）。后者顺带给政策问题补了两条分类用例（`你们一般几点
发货` → knowledge 组；`退款要几天才能到账` → refund + knowledge 两组）。

**prompt v5 的第二处改动是 C08 交接的那条对齐**（票面只写了"新增一节"）：v4 的禁则
第 6 条写着"不承诺到货时间、不承诺退款何时到账 —— 这些都不在你能查到的数据里"，而
知识库上线之后这半句已经是**假话**（时效条文就在库里）。不改它，模型读到"不在数据里"
会把刚查到的时效重新堵回去。改成"发货与退款的时间**只念条文**，不加码、不承诺具体
时刻"，并把"他这一单明天能不能到"点出来（那个确实查不到）。术语节与示例段一个字没动
（v4 逐字可 diff，只有这两处）。

**引用规则**（`[1] [2]` 写进答复）：按票面**故意不做**。这条"不做"有一半的痕迹在
用例里（`test_prompt` 断 `"[1]" not in body`）—— C10 打开这个开关时它会红，那时该改
的就是它。

**实测的两条数字**（都是真模型 + 真 Milvus 跑出来的）：

- **命令行入口的第一次检索要等模型加载**：真机 20.7 秒（`搜索 22s`）。这是 C08 的
  预热只装在**服务进程**（`_serve`）里的结果 —— 命令行进程没有预热，第一次
  `search_knowledge` 现场把 bge-m3 + reranker 读进内存。第二次起 ~7 秒（精排是大头，
  见 C08）。**不给 CLI 加预热**：它是开发者工具，加了会把每次启动都拖慢十几秒。
- **空结果也照常"成功"**：检索没命中时工具返回的是一句带下一步的话（不是错误），
  于是页面上那一行是「政策查过了」而不是「政策没查到」—— 话术是照"调用成功"写的，
  不是照"查到东西"写的（`redaction.py` 里那句话有注释）。

**顺带记一条待办给 C10**：把「索引 + 一个政策问题」接进 `sh/charapp_demo.sh` /
`sh/charapp_demo.md`（C04 早就写明 L5 落地后回填那一段）—— 引用通道与演示剧本一起
写才顺，本票刻意没动演示装置。

上一轮查到的条文，不再重复检索** —— 那一跑它想着"我已经有 `[4] 运费与配送说明` 了"，
直接照上文答（答案是对的：免运费 / 48 小时 / 配送范围，外加一句"到货时间查不到"）。
对政策类问题这是可接受的（省一次 7 秒检索），但要知道它的推论：**改完文章重跑索引之后，
一段旧会话里的那几段仍是旧的**（模型看的是自己上下文里的文本）。演示或验收要问政策时，
新开一段会话最干净 —— 这一条也写进了 ADR-0026 的「代价与边界」。
