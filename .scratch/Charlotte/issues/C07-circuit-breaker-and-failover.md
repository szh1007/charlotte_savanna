## 现状

`retry/chat_model.py` 的 `RetryingChatModel` 用**组合包装**的方式给 `ChatModel` 加上了重试（#13 定下的「在哪切一刀」）。熔断是**同一层的另一个包装** —— 不需要动 `agent/loop.py` 一行。

**但两者的嵌套顺序是个真决策，先定下来再动手。**

---

## 一、嵌套顺序（本片的核心决策）

两个候选：

| 方案 | 行为 |
|---|---|
| **A** `Retrying(CircuitBreaker(Model))` | 熔断器看到**每一次物理调用** → 计数准确；熔断打开时抛**不可重试**错误 → 重试**立刻放弃**，不在退避里空转 |
| B `CircuitBreaker(Retrying(Model))` | 熔断器只看到**逻辑调用**的最终结果 → 内部重试 3 次失败才算 1 次 → 熔断器**反应迟钝** |

**选 A**，并靠 `retry/policy.py` 已有的 `is_retryable` 判据落地：熔断器打开时抛的异常**不声明 retryable**，重试层「未声明一律不重试」（#13 已定的规矩）会自动放弃。

> **这条要写进 ADR**：它满足三条判据（换个顺序是行为差异极大的改动 · 反直觉 · 有真实取舍）。ADR 里要写清楚为什么不是 B。

## 二、三态

| 态 | 判据 | 行为 |
|---|---|---|
| **关闭** | 默认 | 正常放行，滚动统计失败 |
| **打开** | 连续 N 次失败 / 或窗口内失败率超阈值 | **直接拒绝，不发出请求**；带冷却期 |
| **半开** | 冷却期到 | **只放行一个探测请求**；成功 → 关闭；失败 → 回到打开（冷却期可加长） |

**三个必须钉住的点**：

1. **打开期间必须真的不发请求** —— 否则「熔断」只是把错误换了个说法，下游照样被打
2. **半开只放行一个** —— 否则冷却期一到，积压的请求会同时涌出去（惊群），把刚缓过来的下游再打挂
3. **冷却期与阈值要可配**，且**注入时间源**（对齐 #13 与 #61 的 `sleep` / `time_source` 注入缝，让测试零真实等待）

## 三、failover

主模型熔断打开时切到备份模型：

- **切换要在轮内可见**：本轮的后续调用走备份，不要等下一轮
- **开/关要有痕迹**：切了几次、切到谁 —— 落到日志（C05 之后的）与 `runs` 的归因列
- **不产生假账**（对齐 #13 的「双计费不给假账」）：切到备份模型后，**用量与金额按实际调用的那个模型记** —— 两家的单价不一样，混着算就是假账
- 备份模型自己也要有熔断（否则它挂了就一起挂）

## 四、验收

- [ ] 用假 `ChatModel` 钉住：连续 N 次失败 → 进打开态 → **再调用时假模型计数不增加**（真的没发请求）
- [ ] 打开期间抛出的异常**不可重试** → `RetryingChatModel` 立刻放弃、不空转
- [ ] 冷却后进半开，**只有一个探测请求被放行**（用一个可控的假模型 + 并发发起多个调用验）
- [ ] 探测成功 → 关闭；探测失败 → 回打开
- [ ] failover：主模型打开后，后续调用走备份模型；`runs` 里记的是**实际模型**与对应的单价
- [ ] 时间源可注入 → 测试零真实等待
- [ ] `agent/loop.py` **零改动**（与 L1a 的同款纪律：加一层能力不需要动循环核心）
- [ ] 现有 1502 个用例全绿
