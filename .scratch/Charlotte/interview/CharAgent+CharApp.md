## 一、简历项目经历描述

**项目经历：从 0 手写的 AI Agent 运行时（CharAgent）＋ 电商智能客服落地（CharApp）**

> **一句话概括**：为彻底掌握 Agent 的每一个机制，**不依赖任何 LLM 框架**（无 LangChain / LangGraph，`pyproject.toml` 仅 8 项库级依赖，删任一项立即 import 报错），从 0 手写了 Agent 运行时 CharAgent —— agent loop、流式事件总线、断点续跑、重试/熔断、HITL 挂起-恢复、日志脱敏全部自实现；再以它为底座实现电商智能客服 CharApp，接入真实商城（Django + MySQL），22 个工具走真实业务链路（真下单、真扣款、真退款）。测试合计 2200+ 用例（框架 1739 + 业务 465，全离线可跑），31 条 ADR 记录每项取舍的代价与重评条件。

**核心亮点与难点：**

1. **手写 agent loop：把一次模型调用变成可靠的多轮工具循环** —— 并行工具调用（同一 assistant 消息的多条 `tool_calls` 并发执行、部分失败也回填，保住并行语义不退化）；错误自纠错（失败回填「可操作错误文本」而非 422，模型自己换参重试）；`finish_reason` 六态分流（length 截断走续写/精简、上游中断绝不当答案返回）；三种软限制（轮数 / token 预算 / 墙钟）+ kill switch 双层停机机制。

2. **流式事件总线做成状态机，而非日志** —— 九类事件 + 每 run 单调递增 `seq` + 四条硬不变量（`tool_result` 必须配对未闭合的 `tool_call`、有未闭合调用不得发终局事件、终局事件恰好一个……违反即抛错）；乱序在框架自检处暴露而不是画到用户屏幕上；`final.content` 是唯一权威值、`delta` 只作预览（截断拼合场景下前端用 `final` 覆盖缓冲）。真机实测增量渲染把长答复首字时间 **16.0s → 1.4s**。

3. **断点续跑 + HITL 挂起-恢复（生产级细节密度最高的一环）** —— 每 Turn 落一帧快照，内存 / Redis / Postgres 三实现，同一份契约断言跑三遍，能力差异先声明再使用；**挂起不建审批表**（一次工具调用的行状态就是审批单：`needs_approval` + `approved_by/at`），恢复只补做欠着的调用、已完成轮次一步不重跑、没有人的结论就报错绝不自动执行；幂等键取**三列** `(run_id, message_id, tool_call_id)`（上游每轮从 `call_0` 重新编号，少一列必撞）+ PG 持久化 —— 真机战绩：代付的恢复请求重放两次，**一分钱没多扣、工具一次没多跑**。

4. **上下文压缩：账本 / 视图分离** —— 历史 append-only 永不改写，每次调用前把账本投影成「system + 滚动摘要 + 最近 N 个提问」的视图，切点只落在提问处（绝不拆散 `assistant↔tool` 配对，否则上游直接 400）；压缩失败不切刀、只有上游报超窗口才允许硬裁。真机上抓出两个静态读码看不出的缺陷：① 投影与切刀合并会让视图隔轮失效、摘要白烧一半（八轮模拟 2 压 3 跳）；② 估算器坐标不一致（同一份内容按账本量高估一倍、按视图量低估 20 倍）。

5. **稳定性三件套：重试 / 熔断 / 主备切换** —— 只重瞬态（429 / 5xx / 超时），指数退避 + full jitter + 三个上限（次数 / 总耗时预判 / 单次封顶）；熔断三态由「计数 + 时钟」现算（无定时器、打开期间真的不发请求、半开只放一个探测）；嵌套顺序 `Retrying(Failover(主, 备))` —— 闸在内层才看得见每次物理调用，且跳闸那一跳当场改走**另一家厂商**的备份；成本按「谁服务记谁」逐模型归因。工具超时即**中断本次运行** —— 结果未知时不把决定权交回模型（避免同一动作被执行两遍）。

6. **安全三条可兑现的边界** —— ① 身份永不进工具函数签名：它在 wire schema 里搜不到，「诱导模型查他人订单」这条攻击路径**根本不存在**而不是被拦住（代付密码走同一条一次性载荷通道，schema 里永远没有这个参数）；② 日志**写之前**按字段类型结构化脱敏（不是正则碰运气），`thread/run/request` 三个 id 经 contextvars 贯穿，框架自己的异常栈也过同一出口；③ 注入防护四层纵深 + 政策知识库逐句引用溯源，并备有「投毒文档」演示用例。

7. **评估与 A/B：用数据说话** —— 评估集 20 题 6 场景、只走规则判分（刻意不引 LLM-as-judge，保住「这次比上次好」的可复现性）、只有「跑完」的跑次进分子分母；两组 A/B 落地为默认配置：prompt v3→v4 让回答合规 **85% → 100%**；工具按题裁剪 token **-37%** 而花费几乎不变（缓存让长前缀近免费）。过程中还抓出一处被证伪的装置假设 ——「只裁不拒是假的」：裁剪后模型仍调得到被裁工具，A/B 前提一度当场失效。

**工程质量与个人能力点**：31 条 ADR 每条都记录决策 / 代价 / 被否替代方案 /「什么时候该重新看这条决定」；一条硬纪律「加业务能力不许改 loop 核心」由工具超时、熔断、长期记忆、MCP 四批纯加法验证；MockLLM 三形态（固定 / 脚本化 / 录制回放）+ respx 假商城 + 快照与契约测试让 2200+ 用例零外部依赖；一条命令的演示装置（含依赖检查 → 建表 → 起双服务 → 健康检查 → 数据准备）冷启动 29 秒即可提问。

## 二、对话记录

### Q1 项目整体介绍

**面试官**：你这个 charagent + charapp 主要做的是什么，先简单介绍一下你的这个项目

**我**：这个项目一句话概括：**一个不依赖任何 LLM 框架、从 0 手写的 Agent 运行时（CharAgent），加上它真刀真枪的业务落地 —— 一个接真实商城的电商智能客服（CharApp）**。

先说动机。我在用 LangChain / LangGraph 做过几个项目之后有一个感受：框架能让人很快把东西搭出来，但很多机制是黑盒 —— 上下文什么时候被压、断了怎么续上、重试和熔断谁包着谁，出了问题只能猜。所以我想反过来做一遍：卸掉所有框架，从 0 写一个 agent 运行时，逼着每个机制都回答清楚「为什么这么设计、替代方案被否在哪」。`pyproject.toml` 里必装依赖只有 8 项，而且每一项都是框架真正 import 到的库，没有 LangChain —— 这就是「零框架依赖」这句话的证据。

框架侧，核心是这么几块：手写的 agent loop —— 并行工具调用、错误自纠错、循环防护、截断处理；流式事件总线，它不是一个日志而是一个状态机，九类事件、每 run 单调递增的 seq、四条硬不变量，违反当场抛错；快照与断点续跑，内存 / Redis / Postgres 三个实现；稳定层是重试退避、三态熔断加主备切换；再往上还有 HITL 挂起-恢复、上下文压缩、日志脱敏与结构化日志。

业务侧是把框架接到一个真实商城上：22 个工具，从查商品、查订单，到加购、下单、申请退款、代付，全部走真实业务链路 —— 真库、真扣款、真状态机。另外还有 RAG 政策知识库带逐句引用、注入防护四层、长期记忆；以及一套评估体系 —— 20 题 6 个场景，跑过 prompt 和工具数量两组 A/B，报告都随仓库提交。

规模上：框架 1739 个用例、业务 465 个，全部离线可跑；31 条 ADR 记录了每个决策的代价、被否掉的替代方案和「什么时候该回来看这条决定」；演示装置一条命令，冷启动半分钟以内就能提问。

最后补一句我最想强调的设计约束：**加业务能力不许改 agent loop 核心**。工具超时、熔断、长期记忆、MCP 接入这四批功能全是纯加法，一行都没碰循环 —— 我的判断标准是，如果加一个业务接入点需要改循环本体，那就说明接缝设计失败了。

### Q2 工具调用的设计

**面试官**：说说你是怎么设计工具调用的

**我**：工具这块我是分四层设计的，从「模型看到的」到「真正执行的」依次收口：

**第一层，工具怎么长出来 —— 声明。** 用 `@tool` 装饰器把一个普通函数注册成 `Tool` 对象，装饰完返回的是 Tool 而不是包装函数，也没有全局注册表 —— 调用方显式收集成列表传给 loop，工具的来源和去向都在装配处一眼可见。参数 schema 是自动生成的，默认走 pydantic 引擎：函数签名上的 `Annotated[type, Field(description=..., pattern=..., examples=...)]` 直接生成 JSON Schema。这里有个原则是**约束写进 schema 比写在说明里有效** —— 比如订单号写成 `^\d{24}$`，模型填错当场被拦，而不是白跑一趟再回一个错。工具描述取 docstring 首段，标准是「写给一个没见过这个系统的初级工程师看」：什么时候用、什么时候不用、返回什么。

另外工具上有一个 `annotations` 的挂位，业务可以在那里打标记 —— 比如我的商城工具里写工具都打 `{writes: True}`。但框架**只透传不解释**这个标记：它不进模型的 schema，也不参与任何框架逻辑，只是让护栏插件能认出「这是一次写操作」。框架一旦认了某个业务键名，换个业务就得改框架，这条线我们守得很死。

**第二层，一次调用怎么跑 —— 执行链。** `execute_tool` 是一条固定的链：解析 arguments → 参数校验 → 调用 → 结果文本化，中间任何一步失败都**不抛异常**，而是变成 `ToolExecution(ok=False, error=...)`。这是整个设计里最要紧的一条：工具失败不是运行失败，是喂给模型的**一条可操作的错误文本**，模型看懂了下一轮自己换参数重试 —— 这就是错误自纠错的底子。所以我从来不甩一个 422 让模型猜，错误文案里必须写清「哪个参数不对、应该长什么样、可用参数有哪些」。

**第三层，多个工具怎么并行 —— 编排。** 同一轮 assistant 消息里的多条 `tool_calls` 用 `gather` 并发执行，结果**按调用顺序**回填。这里有个不能破的结构：并行的标志就是「多个 tool_calls 在同一个 assistant 消息里」—— 如果为了图省事把并行结果拆成多个顺序轮次回填，模型看到的历史就变成「一次只调一个工具」，后续会**退化成串行调用**，能力直接掉一档。所以并行语义是保真的，回填和回放都得保住这个形状。

**第四层，工具怎么进到一次运行 —— 接缝与裁决。** 工具的装配走 `ToolProvider` 接缝：`async def provide(context) -> Sequence[Tool]`。这里是我认为整个项目最重要的一条安全设计：**身份不进工具的参数表**。`user_id` 由装配时用闭包裹进每个工具，模型的 schema 里根本没有这个参数 —— 所以「诱导模型查别人的订单」这条攻击路径是**根本不存在**，而不是被拦住。有一条测试会把所有工具序列化后在 schema 文本里搜身份键和支付密码，断言搜不到。

执行前还有一个裁决点：`before_tool_execute` 钩子上，插件可以放行、拒绝、或者要求人工确认。三个刻意的设计：拒绝优先于挂起、且不看插件注册顺序（顺序是装配的偶然事实，靠它的话一个会超预算的操作会先弹确认卡、用户输完密码才被拒）；裁决插件自己抛异常按**拒绝**处理（fail closed）—— 一个悄悄失效的护栏比没有护栏更危险；被拒绝的调用照样回填一条失败结果给模型，而不是让运行崩掉。

最后是两个「跑起来才知道」的细节：一是**超时**，`asyncio.timeout` 包住调用，协程工具是真的被取消，但同步工具在线程池里**掐不掉** —— 只能放弃等待，日志如实记一条「线程还在跑」，对有副作用的工具这意味着副作用仍可能发生；而且超时的结果是**未知**的，所以 loop 直接中断本次运行，不把决定权交回模型，避免同一个动作做两遍。二是**裁剪**：做工具数量 A/B 的时候发现「只裁不拒是假的」—— 模型看到的工具列表裁了，但执行查的是全量表，照样调得到。所以后来加了配套的拒绝钩子，让**可见集和可调用集必须等价**，不然 A/B 比的不是「少给」而是「看不见」，前提当场失效。

### Q3 身份不进参数表与数据隔离安全

**面试官**：你刚才说的身份不进工具的参数表，能再详细说说怎么做的吗。除此之外你还有什么其他设计可以保证业务数据的隔离与安全

**我**：先详细说「身份不进参数表」这条，它是分四步落地的：

**第一步，身份的来源只有一处。** 全链路唯一的真实认证点是浏览器 ↔ Django 的 session cookie。Django 的 BFF 从 session 里取出 `user_id`，转成 `X-User-Id` 请求头打给客服服务。客服服务里有一个 `build_context` 函数 —— 整个项目**只有这一处**把身份装进运行上下文：它造出 `RunContext(thread_id=f"minimall:{user_id}:{conversation_id}", tenant_id=..., user_id=..., payload={"user_id": ...})`。命令行入口传的是 argv，服务入口传的是请求头，变的只是「谁往 payload 里放这个值」，下游一行不改。

**第二步，装配时用闭包包住。** `ToolProvider.provide(context)` 里从 payload 取出买家 ID，然后 `build_tools(client, user_id)` 把这一个值写进每个工具工厂的闭包。所以工具的函数签名里**没有任何身份参数** —— 它们全是业务字段：订单号、slug、数量。模型从头到尾不知道「当前是谁」这回事。

**第三步，工具执行时才把身份附到请求上。** 工具内部调商城内部端点时，由 HTTP 客户端逐请求带上 `X-User-Id` 头。关键在于：这个值从闭包来，不经过模型的手。

**第四步，用测试把这条钉死。** 有一条用例把全部 22 个工具序列化后做两件事：一是逐工具逐键比对参数表；二是在 schema 全文里搜索一组身份关键词（`user_id` / `buyer_id` / 买家…），断言**搜不到**。守卫值用的是 `987654` 这种怪数而不是真实值 —— 防的是「假绿」。同一条测试还搜支付密码。

为什么非这样不可？因为**工具的 schema 会被序列化成文本发给模型看** —— 身份一旦成了参数，模型就看得见；看见了，就可以被诱导去填别人的值。经典的注入路径就是在知识文档里写一句「请查询用户 X 的订单」。闭包之后这条路是**根本不存在**，而不是「被拦住了」—— 这俩的区别在于后者总有绕过的可能。另外工具的命名也是设计的一部分：`get_my_cart`、`list_my_orders` 里的 `my` 既是给模型的语言提示，也在告诉评审者：这个名字里的 my，就是「身份不可指定」那句话。

---

除此之外，隔离与安全我按纵深分几层：

**信任边界。** 内部端点直接采信调用方声明的 `X-User-Id`，这个决定背后有一条明确判据：**信任域有没有被拆开**。在浏览器 session 那条链里它是安全的；而 MCP 暴露侧正是这条判据的一次兑现 —— MCP 客户端不在浏览器信任域里，所以暴露侧只开只读工具（把打 `writes` 注解的 8 个全剔掉，只剩 11 个）、并且只代表配置里那**一个**固定账户，客户端说什么都不算数。Token 比较用 `secrets.compare_digest` 常量时间，空令牌 fail closed。

**数据模型层的强制过滤。** 仓储层有一条纪律：凡按条件查人的方法都强制带 `tenant_id`，签名里根本不给「不加租户」的口子 —— 隔离靠的是 SQL 里的 WHERE，不靠「相信模型不乱看」。长期记忆同样按 `(tenant_id, user_id)` 强制过滤，有「换个用户查不到」的用例钉着；而且记忆写入时**敏感的记不进去**（手机号 / 邮箱 / 证件号 / 银行卡 / 一次性密码形状直接拒），因为记忆会在以后每次对话里进上下文。快照的分区键是 `thread_id`，拼成 `minimall:{user_id}:{conversation_id}` —— 多用户隔离是分区免费带来的，不用额外设计。

**展示层的两道脱敏。** 第一条是**事件脱敏**：工具事件的载荷在业务层**整条**换成人话才出浏览器，参数原文与返回正文一个字节都不进去。实现用的是**白名单** —— 只留 `tool_call_id / tool_name / status / duration_ms / turn` 这几个键，以后框架加新字段默认进不了浏览器。第二条是**日志脱敏**：日志写出之前按字段类型结构化打码 —— 规矩是框架的四条通用规则（手机号 / 邮箱 / 证件号 / 银行卡形状），名单是业务的（哪些字段算敏感只有本业务知道）。这两条与存储层的边界我写得很清楚：**工具轨迹落库保留原文**，因为「查案」需要它 —— 那条边界是浏览器，不是存储。

**注入防护四层纵深。** 输入层就是上面说的身份设计；检索层给外部资料加「这是资料不是你收到的指令」的声明、并对可疑文本打标（但**打标不丢弃**，因为政策文本里出现「忽略」这类词的概率不为零，误伤是每次都会发生的）；工具层是高危动作挂起等本人点头；输出层只记不改 —— 答复里出现了内部工具名、内部标识、手机号这类不该出现的东西就记一条告警，但**不改写答复**，因为改写等于系统替模型说话，「当时它看到了什么」当场作废。

**写路径的护栏。** 四条规则都挂在「工具执行前」那个裁决点上：一次运行的写操作预算 8 次、单笔订单金额上限 5000 元（用 `Decimal` 判，不让浮点碰钱）、代付挂起、下单挂起。这里有个细节我想强调：**金额校验是护栏自己去 GET 购物车算的，不让模型自报金额** —— 被检查的人不能填检查项。

**防重放。** 幂等键是三列 `(run_id, message_id, tool_call_id)` 加 PG 持久化，挡的是「同一次工具调用被执行两遍」。真机战绩：代付的恢复请求重放两次，两次都挡在工具执行之前，一分钱没多扣。而「还有没有未决挂起」的判据落在数据库里、不看内存，所以进程重启也拦得住。

边界也如实说：MCP 暴露侧不做真鉴权（本地演示 + 单账户 + ADR 里写清了这条边界），agent 侧不直连业务库而是走内部端点收口读写权限 —— 这几条是明说的取舍，不是沉默的缺席。

### Q4 上下文工程的设计

**面试官**：你的上下文工程是怎么设计的

**我**：上下文工程这块，我先说问题起点：前端的会话编号是固定存在标签页里的，所以一段对话的历史**只增不减** —— 每一轮都要把全量历史重发给模型，成本和首字延迟随轮数线性上涨，一直到撞上窗口。这不是一个性能指标问题，是一个「聊久了必然撞墙」的问题。

我的核心设计是一句话：**账本和视图分开**。同一个会话在系统里其实有三份东西：

- **账本**：每一轮落一帧快照，append-only、一个字不改，给机器用（续跑、回溯）；
- **视图**：每次模型调用**前现算**一份，内容是「身份说明 + 压缩摘要 + 最近 N 个完整提问」，给模型用；
- **记录**：一条消息一行，给人看的那份，**永不压缩**。

压缩只发生在这三份里的第二份 —— 它是一层**投影**，算完就丢，不落地。这个选择有三个理由：第一，落盘的仍然是全量，所以断点续跑、回溯、快照表格看到的永远是完整过程，压缩掉的只是「这一次请求送什么」；第二，「恢复不重跑」的前提是「做过的事都在历史里」，原地删历史就等于把那个前提拆了；第三，投影是**纯函数** —— 同样的账本加同样的参数，出来的视图一样，好测也好解释。

具体压法是三件套，从省得多到省得细：

1. **窗口裁剪**，保留单位就是**提问** —— 切点只落在提问的位置上。这一点很关键：上游对消息配对的要求是硬的，`assistant(tool_calls)` 后面必须紧跟它的 `tool` 消息，切在中间直接 400。切在提问上，被裁掉的那段和保留的那段各自都是完整对话。
2. **工具结果截断** —— 留着但已经很旧的工具正文截到一个上限。工具返回往往是大头，截它比再丢一个提问划算，骨架（调过什么、结论是什么）都还在。注意「正在回答的那个提问」之后的内容不截 —— 模型正拿着这份结果答这一句，截了就是答非所问。
3. **滚动摘要** —— 被裁掉的那段压成一段摘要，而且下一次压缩时**连上一条摘要一起重压**。这一条是从 Anthropic 那份 compaction 文档里学来又自己踩实的：只压新掉的那段的话，更早的信息会被逐次稀释，几轮之后就消失了。

加上四条硬不变量：绝不拆散 assistant 与它的 tool 消息、第 0 条 system 永不裁、至少保留最近一个完整提问、裁完仍是合法 wire 序列 —— 违反了就是 400，所以这些不是「建议」是「纪律」。

然后是触发机制，这里有我踩得最深的一块。触发靠**估算**（字符启发式 + 一个从上游真实 input_tokens 反推出来的固定开销项），估算超过阈值才压，压完要落到「阈值 × 水位线比例」以下才停手 —— 水位线是**滞回**，只按下限压的话下一次调用立刻又超线，于是每次调用都压一次，摘要那一次调用也就每次都花钱。另外还有三道闸：投影得真超阈值；压完得**真的变小**（账本小的时候摘要那条可能比裁掉的还大）；还得**够本** —— 花一次摘要调用只省几百 token 不划算。

这里有两个真机抓出来、静态读码看不出来的缺陷，我觉得是这块最值得讲的：

**第一个，投影和切刀曾经是合成一句话的。** 原来的代码是「不超阈值就原样返回」，而那个「原样」是**全量账本** —— 于是压过之后每隔一轮视图就失效一次：账本把估算顶回大值，再下一轮又切一刀、又烧一次摘要。八轮模拟里出现了「2 压 3 跳、4 压 5 跳」这种规律性震荡，一半的轮次请求跳回全量、摘要调用白烧一半。修法是把两件事拆开：**投影每一轮都做**（摘要替换掉它覆盖过的那段），阈值只管「要不要再切一刀」。分开之后滞回自己就长出来了 —— 因为投影才是真正发出去的东西，它因为上一刀推过切点而变小。

**第二个，估算器的坐标曾经是错的。** 原来的锚估算器隐含一个前提：「拿它量的列表一定是账本那条 append-only 线的延伸」。压缩上线的那一天这个前提就破了 —— 送出去的有时是视图。最小复现很极端：同一份内容，按视图量出 415，真实是 8000，**低估 20 倍**；账本被量成 13291，而它自己的启发式只有 6520，**高估一倍**。后果是水位线试算严重偏低 → 误判「已经压到位了」→ 提前停手，压缩永远做不彻底，而且**不报错不告警**。修法是换成「启发式 + 固定开销校准」：校准项 = 真实 input_tokens − 那把尺子量的启发式，于是**任何一份列表都走同一条算式**。顺带协议也改了：回灌真实用量时收的是「那一次**真发出去的列表**」，不是「账本有几条」。

还有三个细节值得一提：

- **摘要那一次调用被钉死 `thinking=False`**。真机实测发现不关思考的话，推理会把 max_tokens 先吃光、正文为空，框架按「摘要失败」降级 —— 表现是「摘要这一步在生产里从没生效过」，库里九帧只有两帧带摘要。摘要是机械压缩，思考在这里买不到什么，所以我把关思考写死成常量而不是参数：「要生效就得每一家都记得关」正是它漏掉整片功能的原因。
- **摘要失败本轮不切刀**。切点一旦推进，[covers, cut) 那段的原文就既不在摘要里、也不在视图里 —— 凭空消失。所以失败就退到「只投影」。**唯一允许丢信息的是紧急压缩** —— 上游明确报「输入超窗口」时才走的那一档：不问阈值、不问水位线、摘要失败也照裁，代价是把丢掉的那段显式声明为「有意放弃」。
- **诊断值随帧记录**：每一轮会记估算偏差（估算 vs 上游真实 input_tokens）和缓存命中率。后者尤其重要 —— 压缩会**换掉前缀**，KV-cache 命中率会掉，所以这条曲线是「压缩花掉的钱」最直接的证据。

最后说分工与边界：它和 LoopGuard 是两个数各算各的 —— guard 是**运行级刹车**（这次运行别烧太多，直接停），压缩是**单请求治理**（别让这一次请求变大，压完继续）。压掉的信息也没有丢：旧帧还在快照里，`list_history` 可回溯；而真正的「长期记忆 + 按需检索」是另一个组件，边界写得很清楚，免得把「上下文里看不见」误当成「已经不存在了」。

### Q5 滚动摘要流程举例

**面试官**：能简单举例讲讲滚动摘要的流程吗

**我**：用一个具体的时间线来走一遍。假设账本长这样（简化成关键几轮）：

```
第 0 条  system  身份说明
第 1-6 条  问 1 ~ 答 2（中间夹着工具往返）
第 7-10 条 问 3 ~ 答 4
第 11-14 条 问 5 ~ 答 6
```

**第一次压缩。** 估算超阈值，触发。步骤是：

1. 定切点 —— 保留最近 N 个**提问**；假设 N=2，切点落在「问 3」的位置（第 7 条），于是问 1、问 2 那两轮要被裁掉。
2. 取材料 —— 要压的内容是 `history[1:7]`，也就是问 1 到答 2 的原文。此刻还没有上一条摘要，`previous = None`。
3. 调一次模型 —— 把材料交给摘要模型，产出**摘要 S1**。
4. 记账 —— `summary_covers = 7`，意思是「摘要覆盖到账本第 7 条为止」。
5. 此后的视图是：`[system, S1, 问 3, 答 3, 问 4, 答 4]` —— 账本一个字没动。

**继续聊，又超阈值了，第二次压缩。** 这时切点推进到第 11 条（问 5）。关键的差别在这两步：

- **材料的起点不是第 1 条，而是 `summary_covers`** —— 也就是 `history[7:11]`，问 3 到答 4 的原文。上次已经压进摘要的那段，不重复喂。
- **`previous` 传的是 S1** —— 摘要模型拿到的是「上一版摘要 + 这次新裁掉的原文」**一起**，产出**新摘要 S2**。然后 `summary_covers` 推进到 11，视图变成 `[system, S2, 问 5, 答 5, 问 6, 答 6]`。

**这就是「滚动」两个字的意思。** 如果只压新掉的那段、不带旧摘要，会发生什么？第二次压缩时 S1 被丢掉，换成一个只关于「问 3~答 4」的 S2 —— 问 1、问 2 的信息就没了。每一次压缩都稀释一次，几轮之后最早的对话就被逐次洗没了。带上旧摘要，问 1 的信息就顺着 `S1 → S2 → S3` 这条链一路保住，代价是摘要本身随对话缓慢增长（所以它有自己的长度预算，我这边是 1024）。

配套还有三个细节：

- **摘要的输入也有上界**（默认 8000 token）。材料超了就从最旧的那端砍，但**不静默** —— 会记一条 warning：「最旧的 N 条没进摘要」。这是配置驱动的代价，说了才叫代价，不说就是事故。
- **摘要被长度截断的不当摘要用**。因为滚动摘要本来就随对话增长，一旦开始撞上限，往后每一轮都是半截，而下一轮还拿这个半截当 previous 继续重压 —— 信息会逐次损失而且没有任何告警。所以判据里有一条：`finish_reason=length` 直接按「失败」处理，本轮不切刀，下次再试。
- **滚动跨运行也成立**。摘要和「压到第几条」这两个字段是**随快照存**的，所以我下一段运行接着聊时会把它们一起递回去 —— 不递的话，每段运行都会把同一段旧历史重压一遍，内容不会错，但白花一次摘要调用。

一句话总结：摘要不是「每段对话各拍一张照片」，而是**把老照片和新拍的一张叠在一起洗成新的一张** —— 旧信息始终在画面里，只是不断被重新编码。也正因为这样，「真正丢信息」只留给了紧急压缩那一档 —— 它是整条链路上唯一被允许丢东西的地方，而且丢掉的段会被显式标记成「有意放弃」。

### Q6 摘要输入上界的具体裁剪

**面试官**：你刚说的摘要的输入有商社（上界），材料吵了（超了）就从最旧的那端砍，具体怎么砍

**我**：具体是 `cap_summary_material` 这个函数在做，逻辑很短，但有个方向性的选择：

**它从最新的那条倒着往回收。** 代码是遍历 `reversed(dropped)`：从材料里**最近**的一条开始，逐条加进来，累计量一超上限就停、把前面更旧的全部丢掉。理由是相关性随距离衰减 —— 越旧的越该被压成摘要（它们本来就是因为旧才被裁的），最近那几轮留着更值。所以砍的时候，砍掉的是**最旧的那端**。

**尺子量的是「渲染后的文本」。** 每条消息在计数之前，先按摘要视角渲染成文本（工具正文按 `tool_limit` 先截一刀），再用估算器估 token —— 也就是说，量的是「摘要模型实际会看到的样子」，而不是 wire 里的原始长度。这一点决定了估算是大致对得上的：比如一条工具返回在 wire 里很长，但渲染时本来就截过了，不会虚占额度。

**一个边界：至少留一条。** 停止条件是「已经收了至少一条、且再加就超限」，所以就算第一条自己就超限，它也会被留下 —— 一条都不留等于没材料可压。副作用是「一条超长消息」的场合上界会失效一次，但换来的是**消息永远不会被切碎**：摘要材料的最小单位就是一条完整消息，不把一条消息切成两半。

**砍掉之后会发生什么，这才是这条设计的核心。** 被砍掉的那几条**没进摘要**，而切点（`summary_covers`）照旧推进到切点位置 —— 意思是它们既不在摘要里、也不在后面的视图里，**就此丢了**。我把它当作一个**明说的代价**来处理，而不是「顺手丢掉」：

- 一是**不静默**：会记一条 warning，写清「摘要材料超过输入上界（X token），最旧的 N 条没进摘要」，N 由函数返回的长度差算出来。
- 二是**不退回切点**。这是我在写这块时专门想过的：不把切点退回去、让这几条继续留在视图里？那样下一轮的投影就会把「已经进过摘要」的那段又拉回来 —— `covers` 和切点分了家，视图会在相邻两轮之间**跳变**，正是前面说的那条视图震荡缺陷的翻版。所以宁可让这几条真的丢，也不让视图失去稳定性。

**定位上，它是一道配置旋钮**（默认 8000 token，0 表示不截），和「把摘要整个关掉、只做硬截断」是同一类选择 —— 都是用户选的，不是框架偷偷做的。LangChain 的 `trim_tokens_to_summarize` 默认 4000，是同一条规矩。所以真要「一条都不丢」，就是把这个值调大或设 0，代价是那一次摘要调用的输入变贵；而这个取舍的边界，我记在 ADR 里了。

### Q7 summary_covers 与 dropped 的区别

**面试官**：你刚才介绍的两个参数 summary_covers 和 dropped 感觉没有区别啊 —— summary_covers 指的是摘要覆盖到的位置，dropped 指的是丢弃的内容，二者在滚动摘要的过程中感觉作用上重复了呀

**我**：你的直觉是对的 —— **在一次「切了刀」的压缩里，这两个数确实恰好携带同一条信息**：`dropped = cut - 1`、`summary_covers = cut`，差的那个 1 就是永不裁的第 0 条 system。所以单看那一次动作，说它们重复不为过。

但它们不是同一个东西，因为它们回答的是两个不同的问题：**`summary_covers` 回答「边界在哪」**（账本坐标，一个绝对位置），**`dropped` 回答「这一刀多长」**（本次动作的计数，一个增量）。三个地方能让它们分家：

**第一，不切刀的那些轮。** 这是最直接的证据。投影是**每一轮都做**的 —— 一旦压过一次，后面每一轮的视图都带着摘要（`[system, 摘要, history[covers:]]`），但 `dropped = 0`，因为这一轮根本没砍。此刻 `covers` 还是那个值（比如 11，表示前 11 条已经不在视图里），`dropped` 是 0。如果只有 `dropped` 这一个数，这段运行看起来「什么都没压」，可视图里明明躺着一条取代了 11 条消息的摘要。这也是我修「视图隔轮震荡」那个缺陷时想明白的：投影和切刀是两件事，所以「边界」和「刀长」也必须是两个数。

**第二，跨运行。** `summary_covers` 是**状态** —— 它随快照存（帧 v4 起），第二段运行从快照读回来就是 11。而 `dropped` 是那一次动作的**观察值**，事件发完就没了。所以恢复之后，这一段的第一轮就是典型的「covers = 11 而 dropped = 0」。

**第三，最本质的一条：`covers` 甚至不总是「摘要」的覆盖点。** 当摘要被配置关掉、只做硬截断时，`summary` 是 `None`，但 `covers` 照样推进到切点 —— 因为它的严格语义其实是「**账本第 0 到 covers-1 条已经不在视图里了**」，摘要只是达成这个状态的主要方式，不是唯一方式。所以它的本名更接近「投影切点」，只是绝大多数时候它由摘要填上。

反过来看能不能只留一个：只留 `dropped` 的话，要恢复位置就得把它累加 —— 而那个累加值必须跨运行保存，保存下来就还是 `covers`，白绕一圈；只留 `covers` 的话，`dropped` 理论上可推（本轮 covers 减上轮 covers），但发射事件的地方就得为此回查旧状态 —— 而 `CompiledView` 是一次投影的**自描述产物**，事件与帧的观察值直接取它的字段，两个消费者（快照要位置、事件要动作）各取所需，不必让谁去减谁。

打个比方就是：一个是**播放位置**，一个是**这一次快进了多少**。快进的那一下两者恰好对得上，但暂停的时候位置还在、快进量是 0 —— 它们不能合并。

### Q8 确认：位置与动作的区分

**面试官**：哦哦所以 cover 是一个投影从哪里开始看的一个状态值，drop 是每次如果有切刀的动作，表示本次压缩切掉了几条

**我**：对，就是这个理解。归一下类会更清楚：**`summary_covers` 是这批字段里唯一的状态**（账本上的一个位置，进快照、跨运行存活），而 `dropped` 是**动作的度量**（这一次压了多少，随事件发出去就结束）。

顺着这个分类再补一个细节：`CompiledView` 里和 `dropped` 同族的还有两个 —— `truncated`（这次截短了几条老工具结果）和 `reasoning_cleared`（这次清了几条老思维链）。它们仨是同一类：都只描述「本次动作」，都不进任何状态。而且这三个计数合起来还承担一个判据 —— 框架靠它们决定**要不要发 `context_compacted` 事件**：三个都是 0（没超阈值、没得裁、或者被 `clear_at_least` 挡下）就不发，因为「什么都没动」不该在前端留一条「压缩过」的痕迹。而 `summary_covers` 管的是另外两件事：下一轮投影从哪条开始拼，以及恢复时从快照里读到「这条边界线画在哪」。

一句话收束：**covers 是「画在哪」，dropped 是「这次画了多长」** —— 线画下之后一直在，笔动不动是另一回事。

### Q9 记忆模块的设计

**面试官**：好的，你项目的上下文工程设计我懂了，那再跟我讲讲你的记忆模块是怎么设计的

**我**：记忆这块我是分四层问题来做的：**存什么、谁决定写、怎么取、怎么收场**。

**先说定位和边界。** 上下文压缩解决的是「这一段对话怎么装进窗口」，但有一类信息它天然装不下 —— 跨会话还成立的东西：用户说过「以后都寄到公司」、他对花生过敏、上次退过一次款。这些跟这段对话没关系，但下一段对话里用得上。所以我把记忆的边界划得很清楚，和另外三样东西分开：**记录**回答「这段对话里发生了什么」、**快照**是给模型的全量账本、**知识库**是政策（对谁都是同一份），而**记忆**是「每个买家自己的一份、跨对话仍然成立的一句话」。还有一条业务纪律：商城的实时数据不当记忆用 —— 订单、余额、地址每次现查，记忆里的不算最新。

**存什么：一句话事实 + 两种行为。** 表是 `charagent_memories`，一条一行：内容就是一句提炼后的事实（上限 200 字，长过这个数的多半是原文或摘要，那是别的东西该管的），带 `(tenant_id, user_id)` 归属、种类、来源线索。种类上我落地了**两种行为**：`episodic`（发生过的事）和 `semantic`（偏好与事实）是**累积型**，多条并存；`style`（回答风格）和 `nickname`（称呼）是**替换型** —— 同一时刻只留最新一条。这里有个我想强调的设计：替换型在仓储层自动软删旧值，**模型不需要知道「要先删再写」** —— 它改了主意就直接记新的。不因为实现细节给模型多加工序。

另外三个存储决定：来源字段（哪段对话、哪次运行来的）**刻意不挂外键** —— 记忆的本性就是比产生它的对话活得久，挂外键要么被级联删掉、要么被置空，两个都不对，所以它只是溯源线索；删除用**软删**（行留着审计可查，检索不再返回）；时间字段里留了 `last_used_at`。

**谁决定写：模型自己，而且走工具。** 这是我做的一个明确取舍，代号 #33：不在每轮开头把记忆批量注入上下文，而是给模型三个工具 —— `remember` / `recall` / `forget`。理由有两条：一是**规则抽不出「这句话以后还用得上」**，而模型知道；二是工具形态让「模型主动记了一笔」出现在轨迹里 —— 记了什么、什么时候记的，可查。代价是「写多了污染、写少了没用」，但我**不靠 prompt 求它节制**，靠仓储层的容量上限加衰减淘汰兜住。

**怎么取：全量 + 衰减排序 + 编号。** `recall` 取回活记忆，按时间衰减排序 —— `recency_score = 0.5 ** (age_days / half_life_days)`，半衰期 30 天，所以新的在前。每条带一个 8 位的编号；`forget` 就按编号删。这里有个刻意的克制：**`forget` 不做内容模糊匹配** —— 模糊匹配需要相似度判断，判错就是删错行，代价远大于让模型多看一眼编号照抄；编号前缀命中多条时也直接拒绝，让它多抄几位。`recall` 也不带 `query` 参数：每条用户的记忆有容量上限（默认 50 条），全量返回就够 —— 带 query 就需要向量检索，而那是**记忆量大到「列不完」时才成立的优化**，我把子集化的三层演进（top-K → 使用时间进分值 → 语义检索）写成了计划，但没有提前做。

**怎么收场：容量 + 衰减淘汰。** 每 `(租户, 买家)` 的活记忆超上限，就按同一个衰减口径把分值最低的软删。这里有一条设计纪律：**取回和淘汰共用同一个排序口径**（分值、写入时刻、编号三个键）—— 两处各抄一份，迟早会漂成一个「取回的」和「扔掉的」不是同一把尺。参数上我保持诚实：容量 50、半衰期 30 天这两个数是**拍的**，注释里明写了「没有真实使用数据支撑，写在这里是为了复盘时一眼看见哪些数是拍的」。

**最后是安全，这里有三道。** 第一道是**归属强制过滤**：检索永远带 `(tenant_id, user_id)` 的 WHERE，「换个用户查不到」有用例钉着 —— 这条与「谁能看到谁的会话」是同一对键、同一条边界；也因此记忆是业务侧唯一身份不来自 `payload` 的一族工具，直接用框架运行上下文里那两个字段。第二道是**敏感值拒写，而不是打码** —— 这是和日志脱敏正好相反的分工：日志是「打码之后照写」，记忆是「拒绝写入」，因为记忆会在以后**每一次对话里喂给模型读**，手机号、邮箱、证件号、银行卡、一次性密码这类值不该长期留在里面。复用的是脱敏那四条规则的正则加一个「6 位数字」形状，拒写文案三个要点：说清**没写**（别让它以为记上了）、给出替代做法（这些值现查就有）、劝住重试。第三道是装配层的隔离：命令行和网页用不同的租户键，我调试时聊出来的东西不会污染买家在网页上的记忆。

边界也如实说：召回目前是全量返回，**没有做语义检索**；程序性记忆（行为模式）明确没做；还有一个已知错配 —— 跑分线刻意不装记忆工具（跨题的状态会污染可复现性），而 v8 提示词里写着「先 recall」，影响有界但记在案。

### Q10 短期记忆（分点）

**面试官**：太乱了，先说短期记忆，分点解释

**我**：好，重来 —— 先说短期记忆，也就是「模型在这一次对话里能记住的东西」。

**一、它是什么、存在哪。** 短期记忆就是这段对话的消息历史，载体是一份 OpenAI 兼容的 wire 消息列表（dict 直通，不引入中间消息模型）。它的结构是：第 0 条是身份说明（system），然后是「用户提问 → assistant 回复（可能带 tool_calls）→ tool 回填」这种轮次，assistant 的思维链也回填在同一条消息里。整个项目里「消息历史」只有这一种形状，从 loop 到快照到落库都用它。

**二、生命周期以「会话」为界。** 会话编号是 `thread_id`，一份历史跟着一个会话走；会话里可以问很多次，**每一次提问是一次独立的运行（run）**，但历史是跨 run 累积的 —— 这次运行结束时 loop 把最新的历史交回会话，下次提问接着用。所以「运行」是预算、护栏、成本的单位，「会话」是记忆的单位。

**三、同一份历史有两种表示。** 给**模型**的那份是「账本 → 投影 → 视图」：账本 append-only 一字不改，每次调用前投影出视图（system + 摘要 + 最近若干轮）。给**人**的那份是记录表：一条消息一行，**永不压缩**。压缩只动「这一次请求送什么」，两种落地的表示都不动。

**四、持久化：每 Turn 一帧快照。** 历史不是只活在内存里 —— 每一轮结束落一帧快照，按 `thread_id` 分区，append-only。这一份是给机器用的：断点续跑、回溯、time-travel 都靠它。同一段会话的帧用 `parent_id` 串成一条链。

**五、进程重启怎么办：水合。** 内存里的历史进程一死就没了，但快照还在。重启后第一次提问时做一次**水合**：从最新一帧快照把历史读回内存，然后正常接着聊。这里有个专门抠过的细节 —— 快照如果停在「工具调用还没有结果」的半路上（进程死在工具执行中间），水合会补一条「本次服务中断、这一步结果未知」的 tool 回填，**绝不重放**那次调用。理由是：说「没执行」是撒谎（它可能已经生效了），而丢掉那半截会把模型推向重发写操作。

**六、内存里的会话只是缓存。** 这一点是和水合配对的：会话登记表可以按空闲 TTL（半小时）淘汰登记项，淘汰之后下一次提问重新装配、由水合把历史接回来。也就是说，「淘汰」这件事的正当性**来自**水合 —— 两件事一起才成立，缺一个就不敢做。

**七、上限治理分两个数。** 短期记忆不能无限长，管它的是两道闸：**运行级**是 LoopGuard（轮数 / token 预算 / 墙钟，到点就停），**单请求级**是压缩（账本投影成视图，让发出去的那一份不随会话线性增长）。前者是「这次别烧太多」，后者是「这一次请求别变大」，各算各的。

短期记忆的边界就到这 —— 它记的是**这段对话**里发生了什么。跨对话还成立的东西（偏好、长期事实）是另一个组件，落独立的表和工具，要听那部分我接着讲。

### Q11 长期记忆（分点）

**面试官**：再讲一下长期记忆

**我**：长期记忆我按同样方式分点讲：

**一、它是什么。** 长期记忆存的是**跨对话仍然成立的一句话事实** —— 「以后都寄到公司」「对花生过敏」「上周退过一次款」。它和另外三样东西的边界我划得很清楚：**记录**回答「这段对话里发生了什么」、**快照**是给模型的全量账本、**知识库**是政策（对谁都是同一份），而记忆是**每个买家自己的一份**。还有一条业务纪律：商城的实时数据不当记忆用 —— 订单、余额、地址每次现查，记忆里的不算最新。

**二、存什么。** 表是 `charagent_memories`，一条一行：内容（上限 200 字 —— 长过这个数的多半是原文或摘要，那是别的东西该管的）、`(tenant_id, user_id)` 归属、种类、来源线索、三个时间戳。四个刻意的决定：来源字段（哪段对话、哪次运行）**不挂外键** —— 记忆比产生它的对话活得久，挂外键要么被级联删掉要么被置空，两个都不对，它只是溯源线索；存**提炼后的事实**，不存原文也不存每轮摘要（后者会和记录表里的摘要行双写）；删除用**软删**（行留着审计可查，检索不再返回）；归属两列 NOT NULL。

**三、两种行为。** `episodic`（发生过的事）和 `semantic`（偏好与事实）是**累积型** —— 多条并存；`style`（回答风格）和 `nickname`（称呼）是**替换型** —— 同一时刻只留最新一条。替换在仓储层自动软删旧值，**模型不需要知道「先删再写」**，改了主意直接记新的即可 —— 不因为实现细节给模型多加工序。

**四、谁决定写：模型自己。** 这是 #33 的一个明确取舍 —— 不在每轮开头把记忆批量注入上下文，而是给模型三个工具让它自己判断。两条理由：一是**规则抽不出「这句话以后还用得上」**，而模型知道；二是工具形态让「模型主动记了一笔」出现在轨迹里，可查。代价是「写多了污染、写少了没用」，但我**不靠 prompt 求它节制**，靠仓储层的容量上限加衰减淘汰兜住。

**五、三个工具。**
- `remember(content, kind)` —— 身份不进参数表（与业务工具同一条纪律，`tenant/user/thread` 全在闭包里）；写入记来源：`source_thread_id` 从闭包来、`source_run_id` 从日志上下文读（它到执行期才存在）；重复内容不会产生两条（按租户+用户+内容去重）。
- `recall()` —— 取回活记忆，按时间衰减排序（新的在前），每条带种类、时间、**编号**；取回后顺手刷一下 `last_used_at`，但现在只记账、不进排序。
- `forget(memory_id)` —— 按编号删，而编号是模型从 recall 结果里照抄的 8 位前缀。这里有个刻意的克制：**不做内容模糊匹配** —— 模糊匹配要相似度判断，判错就是删错行，代价远大于让模型多看一眼编号；前缀命中多条时也直接拒绝，让它多抄几位。

**六、怎么收场：容量 + 衰减。** 每个 `(租户, 买家)` 的活记忆有上限（默认 50 条），超了按衰减分值把最低的软删。衰减用指数曲线：`0.5 的 (年龄/半衰期) 次方`，半衰期 30 天。这里有一条设计纪律：**取回和淘汰共用同一个排序口径**（分值、写入时刻、编号三个键）—— 两处各抄一份，迟早会漂成「取回的」和「扔掉的」不是同一把尺。参数我保持诚实：容量和半衰期这两个数是**拍的**，注释里写明「没有真实使用数据支撑」。

**七、安全三道闸。** 第一，**归属强制过滤**：检索永远带 `(tenant_id, user_id)` 的 WHERE，「换个用户查不到」有用例钉着 —— 这也让记忆成为业务侧唯一身份不来自 `payload` 的一族工具，直接用运行上下文里那两个字段。第二，**敏感值拒写而不是打码** —— 和日志脱敏正好相反：日志是「打码后照写」，记忆是「拒绝写入」，因为记忆会在以后**每一次对话里喂给模型读**；复用脱敏的四条规则加一个「6 位数字」形状，拒写的文案说清没写、给替代做法（现查就有）、劝住重试。第三，**装配层隔离**：命令行和网页用不同的租户键，我调试时聊出来的东西不会污染买家网页上的记忆。

**八、边界与欠账。** 召回目前是**全量返回**，没有做语义检索 —— 我判断子集化是「记忆量大到列不完」时才成立的优化，所以把三层演进（top-K → 使用时间进分值 → 语义检索）写成了计划但没提前做；程序性记忆（行为模式）明确不做。还有一个已知错配如实记着：跑分线刻意不装记忆工具（跨题状态会污染可复现性），而最新版提示词里写着「先 recall」—— 影响有界，但记在案。

### Q12 如何确保敏感值一定拒写

**面试官**：你怎么确保敏感值一定能拒绝写入？

**我**：**先说结论：不能确保。** 它是**形状识别，不是语义判断** —— 这点我在模块文档里就写明了，面试官问到这里我更应该说清楚它挡不住什么。

**第一，它实际挡的是什么。** `remember` 工具入口上有一道校验，内容是五类形状的正则：手机号（11 位）、邮箱、身份证、银行卡，外加一条「6 位数字」（支付密码和验证码在这系统里都是这个形状 —— 这条是我在脱敏那四条之外**多加的**，因为记忆和日志的消费方式不同，日志打完码就结束，记忆会被反复读进上下文）。命中任意一条就**拒绝写入**，并把拒绝原因回给模型。这道校验的边界用的是 `(?<!\d)` / `(?!\d)` 顾盼而不是 `\b` —— 中文里 `\b` 不可靠（汉字在 re 里也算 `\w`），而这两组顾盼缺一不可：少了它，一个 24 位订单号会被拆出一个 6 位子串、误报成验证码。

**第二，它挡不住什么，我能数出来。** 把数字拆开写（「一三八开头，后面是 0003」）、用空格或横杠分隔、写成中文数字、编码变形 —— 都绕得过去。所以这道闸的真实保证只有一句：**这类形状的值，不会通过 `remember` 这个正门、以原样被写进记忆表**。它不保证「任何语义上敏感的信息都进不去」。

**第三，那为什么这个设计仍然成立。** 三个理由：

- **写入路径唯一**。记忆只有 `remember` 一个写入方 —— 没有别的 API、没有每轮自动摘要落库、没有旁路。所以只需要守住这一道门，不存在「这道拦了那道漏了」的问题。这一点比规则多严更重要。
- **它是 fail closed 的**：命中就拒，绝不静默通过或打码。顺带说，**为什么是「拒写」而不是像日志那样「打码后照写」** —— 因为打码会制造一个更坏的假象：记了一条被打码的记忆，内容已经没用了还占着容量，而且模型以为自己记上了。拒写加一条明确的错误文案（说清没写、给出替代做法「这些值现查就有」、劝住重试），模型当场知道，并且能在答复里如实告诉用户。
- **误拒的代价有界**。规则取的是「形状像就拒」，宁可误伤。误伤的代价是模型换一条路（用工具现查），而不是用户办不成事。

**第四，为什么不再上更重的手段。** 一个选项是引语义模型来判敏感 —— 我不做，理由两条：一是那等于把一个分类器塞进写入路径，它的误判率只是把假阴性换成假阳性，并不保证正确；二是记忆写入的场景本来是「模型提炼一句以后有用的事实」，正常内容不该被语义审查拖慢。另一条边界：输出层已经有一道独立的泄漏扫描（答复里出现手机号、邮箱这类就记告警），它管的是「说出去」，和「记下来」是两道不同的闸 —— 我不指望其中任何一道去补另一道。

**第五，漏了之后的兜底。** 就算真有一条绕过去了，它落在表里也是可管理状态：记忆按 `(租户, 买家)` 隔离、软删可清、有 `forget` 工具让用户明说「忘掉那个」、容量上限加衰减淘汰保证它不会无限累积。也就是说，「拒写」不是唯一防线，是**在唯一入口上把最容易发生的形态挡住**，剩下的靠可删、可查、有上限兜底。

所以这条设计我的自我评价是：它是一个**明确知道自己边界的形状闸**，不是一个「一定能拦住」的承诺 —— 我把它当纵深的一层来用，而不是当一堵墙。

### Q13 中断类型盘点

**面试官**：好的记忆模块我懂了。那你再讲讲 HITL、断点续跑、幂等键这类中断的设计 —— 先说说你项目中有哪些中断类型的设计，除了我上面的三个，还有其他的吗

**我**：好 —— 这个问题值得先把盘子铺开：中断在这个项目里**不是一个机制，是一组机制**。我按「谁打断、打断之后怎么办」把它拆成四块，您点名的三个在后面两块里。

**第一块：谁在让运行停下来（打断源，五个）。**

1. **模型自己停** —— 它读完历史决定不再调工具，正常收尾（`finished`）。这是唯一一种「不算意外」的停。
2. **框架刹车停**（软限制）—— 轮数 / token 预算 / 墙钟三种上限，判定时机是**每轮收尾、准备发起下一次模型决策之前**。刻意做成「跑完当前这轮再停」，这样历史永远是完整的，不会留下「调了工具却没结果」的半截对话。
3. **外部即时打断（kill switch）** —— 对运行中的任务调 `task.cancel()`，在任意 await 点立即生效。三个入口都接上了：HTTP 的取消端点、CLI 的 Ctrl-C、还有**客户端断连**（SSE 流的 finally 里主动取消）。它与软限制的分工是「任意时刻立刻断」vs「这一轮结束再说」，而且 `CancelledError` 一路不吞、不重试 —— 用户按了停止，插件和重试层都不许挡。
4. **上游打断** —— 服务端没把这次生成跑完（资源不足 / 被中断），内容可能只是半截，**绝不能当答案返回**，如实上报 `server_interrupted`；重放决策不归它，归重试层。
5. **框架主动停：工具超时** —— 这是我最想强调的一条。工具超时不是「工具说不行」，是**结果未知**（可能已经生效了）——所以不把决定权交回模型，直接中断本次运行，避免同一个动作做两遍。而且「中断优先于挂起」：同一批里如果既有超时、又有要人批的调用，一条都不挂，因为结果没弄清前确认卡没有意义。

**第二块：打断之后怎么办（出路，四种）。**

6. **继续跑：重试** —— 只重瞬态（429 / 5xx / 网络），指数退避加抖动，三个上限（次数 / 总耗时 / 单次封顶）。
7. **换条路跑：熔断 + 主备** —— 上游连续失败就跳闸，这一跳当场改走备份模型（另一家厂商）；两家都开着就是 `CircuitOpenError`，**不可重试**，立刻放弃、不在退避里空转。
8. **停在这里，等着再继续** —— 这就是您点的**断点续跑**（每 Turn 落一帧快照、换起点接着跑、已完成的不重跑）和 **HITL 挂起-恢复**（停半路等人给结论，从存档点只补做欠的那条）。
9. **到此为止，不回头** —— 两条：截断重试超限就放弃（`truncation_limit`）；还有一条容易被忽略的：**增量渲染「吐过字就不再重发」** —— 一旦已经把半截答复推给用户，重试和换家都停，半截如实交出去。重发整条请求会让用户看到「半截 + 从头再来」，比「半截 + 一句说明」糟得多。

**第三块：防「同一件事做两遍」（防重）。**

10. **幂等键** —— 您点的第三个。三列键 `(run_id, message_id, tool_call_id)` 加 PG 持久化，挡的是「同一次工具调用被执行两遍」，直接服务对象就是 HITL 的恢复端点。
11. 另外两条同族的：**超时即中断**（结果未知就不继续，上面第 5 条）、**水合不重放**（进程重启后把历史读回来，撞上「工具没结果」的半路只补一条「结果未知」，绝不重放写操作）。

**第四块：拒绝开始（准入层，容易被漏掉但也是中断设计）。**

12. **同一会话不并发** —— 会话在忙时，新的请求直接 409 拒绝，而不是排队或打断；**会话有未决挂起时也拒绝新提问** —— 而这条判据落在数据库里（`needs_approval` 且未批准），所以进程重启也拦得住。

盘完这一圈，我的整体判断是：这四个块其实是**同一条纪律的四个面** —— 「**不确定的东西不许往前走**」。上游给的半截不确定，就上报不采用；工具的结果不确定，就中断不继续；人还没给结论，就停住不自动执行；同一动作做过没有不确定，就用幂等键挡住重复。

您点名的 HITL、断点续跑、幂等键是第 8 和第 10 条 —— 要从哪个深入？

### Q14 HITL 与断点续跑流程详解

**面试官**：详细说明一下 HITL & 断点续跑的流程，两个听起来应该很像那就一起讲讲吧，举例讲解，能直观看到整个流程是怎么跑的

**我**：先给一句总纲，这样两个概念就分开了：**断点续跑是底座，HITL 是架在这个底座上的一个应用**。快照机制本身不关心为什么停（进程死了、人按了停止、还是等人批准），它只管「停在哪儿、从哪儿继续」；HITL 在这之上多加了「凭什么继续」——必须有人给一个结论。下面用一个真实场景把两个一起走一遍：买家说「帮我把这单付了」。

**第一段：跑到挂起点。**

1. 买家在客服页说这句话 → Django BFF 转发 → `POST /runs` 到客服服务。服务认证后组装运行上下文（`thread_id` 是「minimall:买家id:对话id」），装配会话 —— 记住这一刻：**支付密码还不在任何人手里**，工具闭包是空手装的。
2. 记录员先建一行运行账（`charagent_runs`，状态 running），拿到 `run_id`。然后 loop 开跑。
3. **Turn 1**：模型决策 → 要调 `pay_my_order(订单号)`。框架先发 `tool_call` 事件，然后**在执行前**把那条 assistant 消息和这次调用先落库（状态 `pending`）—— 这一步是刻意前置的：执行中被硬杀，库里也看得出它正要调什么。
4. 执行前走到裁决点：业务护栏认出这是 `pay_my_order`，返回 `Decision.requires_approval(prompt="付款需要您本人输入支付密码", needs=("payment_password",))`。于是**这条调用不执行**。
5. 关键的一步：那条调用**不回填结果** —— 它的结果就那么欠着，这正是「挂起」的形状（后面恢复就是靠这个形状把欠账找出来的）。loop 把「谁在等人批」记进状态，本次运行以 `SUSPENDED` 收尾。
6. **Turn 收尾落帧**：这一帧里有两样东西 —— 完整历史（含那条欠着的 assistant 消息），和一句「这一帧是一次挂起点，欠着哪一条调用」。帧上 `parent_id` 指向前一帧，来源标成「挂起」。同时记录层把那条工具调用推进成 `needs_approval`，并且把**给用户看的那句话和还缺什么**（`approval_prompt` / `approval_needs`）写在这一行上 —— 刷新页面重建确认卡就靠它。
7. 终局事件发 `approval_required`（它是三类终局事件之一，事件流到此为止）。前端渲染出带密码框的确认卡。运行行状态是 `waiting_user` —— **挂起不算运行结束**。

**中间：等人。** 这段可能几分钟、也可能隔天，所以我把「等待」设计成不依赖任何内存：
- 进程重启、会话被空闲淘汰，都没关系 —— 未决挂起的判据是**查库**（`status = needs_approval 且未批准`），不在内存里；
- 期间这段会话不许新提问（返回 409）—— 这也是查库判的；
- 恢复沿用**同一个运行编号** —— 它是这次运行的第二段，不是新的一次运行。

**第二段：恢复。**

8. 买家输密码、点确认 → `POST /runs/{run_id}/resume`，请求体是 `{"decision": "approve", "data": {"payment_password": ...}}`。
9. 服务端**先认领幂等键再动别的**：键是 `resume:{run_id}:{message_id}:{tool_call_id}` 三列拼的。抢到才继续；抢不到就按状态回一个明确的 409。您双击第二下，就死在这一步 —— 幂等键挡的正是这个，恢复是 HTTP 端点，重放不是理论风险。
10. 然后**重新装配会话**。这一步不能省：密码是在「构造工具」那一刻裹进闭包的，旧会话是空手装的。装配时 `data` 并进运行载荷（只增不覆盖，防止客户端顶掉身份键）。
11. `session.resume()` 读最新快照，再按帧里的**身份说明引用**（名字 + 正文哈希）读盘把正文补回历史 —— 然后进 `loop.resume()`：
    - 计数器**接续**（轮数、token 预算跨断点仍然算数）；
    - 从头扫历史，找出「带 tool_calls 的 assistant 后面缺 tool 消息」的那批 —— 就是欠着的那条付款；
    - **没有人的结论在这里直接报错** —— 这是「绝不自动执行」的落点，命令行那个 `--resume` 撞上挂起点会被拦住，而不是悄悄把付款执行掉；
    - 有结论（批准）→ 只补做这一条，**前面的轮次一步都不重跑，也不重问模型一次**（那一轮的决策早就做过了）。工具真的执行：带身份头 + 密码打商城的付款端点，真扣款；回填结果、落一帧（来源标成「欠账补做」）。
    - 顺便说个细节：**批准的豁免范围很窄** —— 它只抵消「需人工确认」这一种裁决；护栏的其他拒绝照常生效（挂起期间世界可能变了，那些规矩不该因为人点过一次确认就放行）。
12. 循环继续：下一次模型决策读到付款结果 → 组织答复「已为您付款，余额还剩 X」→ 正常收尾，运行行结账（金额、用量、状态 finished），幂等键置成 completed。前端看到的第二条流事件序号**从 1 重来**（每次 resume 是一次新的流）。

**最后把两者的异同点收一下，四个对比：**

| | 断点续跑（底座） | HITL（应用） |
|---|---|---|
| 停的原因 | 进程死了 / 人主动停 —— 没有等待对象 | **等一个特定的人给一个特定的结论** |
| 恢复的凭据 | 有存档就能跑 | 存档 + **人的结论**，缺结论报错 |
| 谁触发那帧 | 普通轮 / 分叉 | 多一个「挂起」来源标签，帧里记着欠谁 |
| 额外的闸 | 无 | **幂等键**（因为恢复是 HTTP 端点，会被重放） |

而它们共用的那条纪律是同一句话：**「做过的事都在历史里，所以绝不重做」**——普通续跑不重跑已完成的轮次，HITL 恢复不重跑前面、只补欠的那一条。真机战绩也在这条线上：同一个恢复请求重放两次，两次都被挡在工具执行之前，**一分钱没多扣、工具一次没多跑**。

### Q15 关键节点精简版

**面试官**：说的优点（有点）复杂，简单几句话概括关键节点

**我**：好，压缩成五步：

1. **拦**：模型要调高危工具（比如付款）→ 护栏在「执行前」那个点拦下，说「这得本人点头」→ 工具**不执行**。
2. **存**：进度落一帧快照，帧里记着「欠着哪条调用」；同时把「要给用户看的那句话 + 还缺什么」写进那条工具调用行；发一个 `approval_required` 事件，前端弹确认卡。**挂起不算运行结束**，之后进程重启、会话淘汰都不影响。
3. **等**：等人。未决状态的判据在数据库里，不在内存 —— 所以隔天回来、刷新页面，卡片都重建得出来。
4. **续**：人给结论 → 恢复端点。**先用幂等键挡住重复请求**（恢复是 HTTP 端点，双击就得防住），再读存档、重新装配会话（支付密码这一刻才进工具闭包），然后**只补做欠的那一条**：批准就真执行、拒绝就把原因当结果回填 —— **前面的轮次一步不重跑，也不重问模型一次**。
5. **走**：模型接着读结果答话，正常收尾。

一句话版本：**停半路 → 存档等人 → 人点头后从存档点只补欠的那一条，其余一律不重做** —— 断点续跑是这套「从哪儿继续」的底座，HITL 在它上面加了「必须有人给结论」和「幂等键防重放」两条。

### Q16 幂等键的设计与防重放演示

**面试官**：ok，那幂等键是怎么设计的呢，是如何防止重放的呢，举实际的例子演示一下过程

**我**：幂等键我拆成三块讲：**键长什么样、状态怎么流转、以及重放现场怎么挡住**。

**一、键：三列拼一个字符串。** 格式是 `resume:{run_id}:{message_id}:{tool_call_id}`。为什么必须三列 —— 上游（DeepSeek 那类接口）每一轮都从 `call_0` 重新编号，所以一个 run 里会出现好几个 `call_0`，单列必撞；加上 `run_id` 只解决了跨运行，同一个运行的多轮之间还会撞。真正唯一的身份是「**哪条 assistant 消息发起的这次调用**」，所以是这三列。落库是一张 `charagent_idempotency_keys` 表，键本身是主键。

**二、状态机与三个动作。** 存储协议的形状和「挂号看病」一样，三个动作：

- `claim`（认领）—— 动作执行**前**拿号；拿到执行权、撞车被挡、或直接拿回结果，三种答复；
- `complete`（登记完成）—— 动作成功后把结果记上；
- `release`（释放）—— 动作失败就把号放回去，否则这把键永远卡在「在途」，后续合法重试全被挡住。

底层就两种状态：`in_progress`（有人在办）和 `completed`（办完了，结果在这行里）。

**三、重放现场。** 举个例子：买家点「确认付款」，网络卡了一下，他以为没点上，又点了一次 —— 两个 `POST /runs/{id}/resume` 先后到达（或者几乎同时）。

**第一下：**
1. 服务先 `claim(键)`。实现是**一条 SQL**：`INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE 已过期 RETURNING key`。表里没这个键 → 插入成功 → 拿到执行权，状态 `in_progress`，返回 CLAIMED。
2. 拿到才继续往下：重装会话 → 读存档 → 补做那条付款 —— **工具真的执行、真的扣款**。
3. 动作成功 → `complete(键, 结果)` → 那行变 `completed`，结果写进 `result` 列。

**第二下，分两种到达时机：**
- **第一次还没跑完就到了**：`claim` 撞上已存在的键，那条 UPDATE 因为「没过期」不满足条件、不返回行 → 服务读一下状态 → `in_progress` → 回 409「正在处理中」。**工具一次都没多跑。**
- **第一次跑完之后才到**：`claim` 撞上 `completed` 的行 → 直接拿到「已完成 + 结果」 → 回 409「已经处理过了」。

两条路的结果一样：**第二下被挡在装配和工具执行之前，一分钱没多扣**。这就是真机战绩的原型 —— 同一个恢复请求重放两次，工具一次没多跑。

**四、为什么这么设计，两个关键判断。**

1. **判据落在数据库的主键冲突上，不是应用层「先查后插」**。「先查后插」有并发窗口：两个请求可能同时查到「不存在」，然后都去插。`ON CONFLICT` 的原子性由数据库保证 —— **谁先插进去谁拿到执行权**，这和运行表上 `request_id` 的唯一约束是同一条理由：唯一约束才是真正不会漏的那道闸。
2. **claim 排在装配之前**。顺序是刻意的：抢到键才去重装会话、执行恢复；抢不到的直接返回，连工具闭包都不装 —— 挡得越早越好。

**五、几个边角，都如实说。**

- **时间维度**：`expires_at` 为空表示永不过期（本项目的默认）；配了 TTL 的，过期后这把键可以重新认领 —— 那时它描述的就是新一次操作了（那一行会被整行改写）。有个配置闸：TTL 填 0 或负数在构造期直接报错，因为那等于「认领完立刻能重新认领」，这把锁就等于不存在。
- **release 的语义**：只删 `in_progress` 的行。已完成的结果**不能被后来的失败抹掉** —— 这是幂等语义的核心。
- **一个已知边界**：没做 owner 校验 —— 同一把键过期后被重新认领时，前一手的 `complete` 有可能写进后来那一手的行。要挡它得在键上带「谁认领的」身份，那是 Redis 版该带的东西；而本项目 TTL 默认永不过期、且一次工具调用远短于任何合理 TTL，所以这个窗口留在边界里、写进了文档。

一句话总结：**幂等键就是给「有副作用的那一次动作」发一张一次性凭证 —— 认领是原子性的（数据库主键冲突），办完记结果、失败要释放，重复请求在动手之前就被挡下**。

### Q18 agent loop 的设计与关键节点

**面试官**：聊聊你对 agent loop 的设计和理解，有哪些关键节点

**我**：先说我对 agent loop 最本质的理解：**模型是"无状态的一次调用者"—— 它自己不会执行任何东西**。所谓 agent loop，就是替它跑腿的那段循环，核心只有三件事在空转：把完整历史交给模型 → 执行模型要求的工具 → 把结果放回历史 → 再交给模型。它让"一次模型调用"变成了"多轮工具循环"。这里有个容易被忽略的点：**中间没有"用户再提问"** —— 每一轮模型看到的输入是「用户最初那一句 + 之前所有轮次的一切」，新增信息几乎全部来自工具返回。所以 loop 的工程质量，基本决定了 agent 的可靠性上限。

**按一轮的生命周期，我把关键节点分成五个关口：**

**关口一：刹车判定。** 每轮开始前先过 guard 三种软限制（轮数 / token 预算 / 墙钟）。这里最要紧的设计是**判定时机** —— 只在"上一轮的事都办完了、准备问模型下一轮"时才判。这样任何时候停下来，历史都是完整的（不会留下"调了工具没结果"的半截对话），kill switch 那种随时打断是它的另一极。

**关口二：模型决策。** 一次 `generate` 调用，前后各挂一个 hook，并且这里是**上下文的投影点** —— 配了压缩策略时，送给模型的是从账本投影出的视图，账本一字不动。响应回来记两笔账：一笔总量（给预算判定，也是唯一能和供应商对账的数）、一笔分解（输入/输出/思维链/缓存命中，给成本归因），两笔取自同一个 usage 所以必然对得上。思维链在这里走**旁路**：单独成事件给前端折叠展示，不混进正文，但它同样回填 wire 历史。

**关口三：分派 —— 按 `finish_reason` 分流，这是 loop 里最像"交通枢纽"的地方。** 六个取值四条路：

- `tool_calls` → **工具轮**：先发调用事件，再**并行**执行（同一消息里的多条调用一起跑），最后按调用顺序回填。顺序回填这点是刻意的 —— 并发下事件序列必须确定，回填顺序和历史结构也必须一致。
- `length`（截断）→ **绝不能当答案返回**。两条策略：续写（保留已写前缀接着写）或精简（丢掉不完整内容重答）；重试次数超限就放弃。最终答案跨多条消息时，由框架拼合好交给调用方 —— 调用方不需要自己从历史里抠。
- 上游中断（资源不足 / 被中断）→ 内容可能是半截，**如实上报，不当答案**；重放决策归重试层，不归这一层。
- `stop` 及其他 → 自然终止，拼合正文收尾。

**关口四：轮次收尾 —— 这里有一个刻意的顺序。** 每轮结束做三件事，顺序是：先把这一轮新增的消息和工具调用事实**交给记录层**（这条是"降级"的路：写不进去只记日志、收尾还会补），再**落快照帧**（这条失败要**上抛** —— 存档是可靠性基线，悄悄吞掉会变成"以为存上了"的事故），最后触发 `after_turn` 钩子。降级的那件先做、上抛的那件后做 —— 插件晚一步收到通知没关系，快照晚一步存就可能永远丢了。

**关口五：终局 —— 单一出口。** 终局事件（`final` / `error` / `approval_required`）从 `LoopResult` 派生，**恰好一个**，而且事件流与返回值不会各说各话（同一份 outcome、content、耗时）。

**另外有三条"设计层"的判断，我觉得比节点本身更值得说：**

**第一，并行不增加轮数。** "一次模型决策"是一个 turn —— 模型一次要求并行调 3 个工具，3 个并发跑完一起回填，仍然只算一轮。这是概念上的划线：轮数是"模型决策了几次"，不是"调了几个工具"。而且并行结构**必须保真**：并行的标志就是"多个 tool_calls 在同一个 assistant 消息里"，如果为了图省事把结果拆成多个顺序轮次回填，模型看到的历史就退化成"一次只调一个工具"，后续会跟着退化成串行 —— 这个结构一破不可逆。

**第二，文本边界要判三次。** 工具轮里模型写的正文是**过程叙述**（「让我先查一下订单」），它不能混进最终答案 —— 所以工具轮一到，之前拼合的正文档位就清掉；终止轮的正文才算答案；截断轮是例外（它的正文是答案素材，不当过程叙述）。这三条判错的后果很具体：要么最终答复里混进"让我先查一下"，要么把已作废的半截推给用户。

**第三，循环核心不许为业务改。** 我给自己定的硬约束是：加业务能力不许改 loop 本体。业务接入只有三个接缝 —— 工具装配走 `ToolProvider`、运行中介入走六个 hook 点、身份和业务数据走 `RunContext.payload`。后来加的工具超时、熔断主备、长期记忆、MCP 接入四批功能**全是纯加法**，一行没碰循环；此后只改过确实动到循环语义的几批（压缩、会话记录、挂起、增量渲染）。我的检验标准是：**如果加一个业务接入点需要改循环核心，那就说明接缝设计失败了** —— 这条约束也是这个项目最核心的方法论。

### Q19 agent loop 的状态机

**面试官**：你的 agent loop 的状态机是什么样的

**我**：这个问题问得好，因为这里有个容易混的点：**loop 本体其实不是一个"状态机"** —— 它就是一个 `while not done` 循环，配一个收场原因枚举。真正的状态机有三个，分属三个层次，它们管的东西完全不同：

**一、事件状态机 —— 管「一次运行内，推给前端的事件序列合不合法」（秒级）。**

这是我在 `stream/bus.py` 里手写的，状态只有两样：**未闭合的工具调用集合**和**是否已终局**。九类事件在它里面只走一条主序列：

```
[thinking] → (tool_call → tool_result)+ → [thinking] → ... → final | error | approval_required
```

四条不变量，违反当场抛错：

1. `seq` 每 run 从 1 起单调递增（前端断线续拉靠它）；
2. `tool_result` 必须匹配一条**未闭合**的 `tool_call`；同一个 id 在闭合前不得重复开启（只约束未闭合期间 —— 真实上游的 `call_0` 是逐轮重置的，跨轮复用是正常的）；
3. 还有未闭合的调用时**不得发终局事件** —— 唯一例外是 `approval_required`，因为「有一条故意没回填」正是它在说的事；
4. 三类终局（`final` / `error` / `approval_required`）之后不得再发任何事件，且**恰好一个**。

另外三类事件是**旁路**：`reasoning`（思维链）、`answer_delta`（正文增量）、`context_compacted`（压缩提示）—— 它们不参与工具配对，随时可发，但同样受「终局之后闭嘴」约束。

为什么把它做成状态机而不是日志？因为**事件流是前端渲染的唯一依据** —— 乱序等于把 bug 直接画到用户屏幕上：`tool_result` 先于 `tool_call` 会让界面出现「凭空回来的工具结果」，`final` 之后又来事件会让界面在给出答案后继续跳。这些约束和 wire 历史的配对约束（tool 消息必须紧跟带 tool_calls 的 assistant）是同一条规则在两条通道上的体现。**在这里拦下是框架自检，比让错误流到前端强。**

**二、运行状态机 —— 管「这次运行的生命周期走到了哪」（跨 run，天级）。**

八态：`created / running / waiting_tool / waiting_user / retrying / failed / finished / cancelled`。合法迁移写成一张表（终态没有出边）。

这里面我最想讲的是**为什么要有 `waiting_tool` / `waiting_user` / `retrying` 这些"没动静"的档** —— 因为它们对用户的含义完全不同：「等工具返回」是秒级的、不用管；「等用户给结论」是**一天都可能**、需要前端弹卡片；「在重试」是系统在自救。如果只有 running 一档，这三种状态在运维视角里长得一模一样。

两个配套的设计：一是 `SETTLEABLE_RUN_STATUSES` 是「终态 ∪ waiting_user」—— 决定 `finished_at` 写不写，因为**挂起要写运行行的收尾信息、但不算结束**；二是状态迁移用**乐观锁** —— `try_transition` 是一条带 `WHERE status = from_status` 的 UPDATE，「抢到的那个人负责」，防止两个并发动作把状态反复横跳。

**三、工具调用行状态机 —— 管「单条调用现在是什么状态」（最细粒度）。**

六态：`pending / succeeded / failed / cancelled / needs_approval`。L3b 的挂起就落在这一行上（`needs_approval` + `approved_by/at`），整个 HITL「挂起不建审批表」的决定，就是**把审批的载体从一张新表挪到了这条调用行上**。

**第四个，loop 自己的「收场原因」枚举。** 循环体不建模状态，但每次结束都会产出一个 `LoopOutcome`，八种：`finished` / `max_turns` / `token_budget` / `time_limit` / `truncation_limit` / `server_interrupted` / `interrupted` / `suspended`。它回答的不是「现在在哪」，而是「**为什么停**」—— 这个枚举是三个状态机之间的**枢纽**。

**最后说三者怎么接起来，这里有个依赖方向的处理。** `agent/` 层不 import `db/`（否则会成环），所以映射表放在 db 侧：`RUN_STATUS_FOR_OUTCOME` 把 loop 的 outcome 翻成运行状态（注意几条口径：刹车停和截断放弃记 **finished** ——「跑完了但没给答案」不算失败；上游中断与工具超时记 **failed**；挂起记 **waiting_user**），`TOOL_CALL_STATUS_FOR_OUTCOME` 同理。**框架侧只定义自己的词汇，存储侧负责翻译** —— 换一个记录后端，只要它认这两张表，loop 一行不用改。

一句话收束：**事件状态机管「这次说得对不对」，运行状态机管「这件事办到哪了」，工具行状态机管「这一条动作成没成」** —— 三层各管一个时间尺度，用「收场原因」这个枚举串起来。

### Q20 状态机精简版

**面试官**：简单列举，不要说得这么复杂

**我**：三个状态机，分三层，别混：

**一、事件状态机**（秒级，一次运行内）—— 管「推给前端的事件序列合不合法」。五条规则：seq 单调递增；`tool_result` 必须配对未闭合的 `tool_call`；工具没回填完不发终局；终局（final / error / approval_required）**恰好一个**；终局之后不再发。违反当场抛错。

**二、运行状态机**（跨运行）—— 管「这次运行走到哪了」。八态：
`created / running / waiting_tool / waiting_user / retrying / failed / finished / cancelled`
合法迁移一张表，终态没有出边；迁移用乐观锁（`WHERE status = 原状态`）。

**三、工具调用行状态机**（最细粒度）—— 管「这一条调用成没成」。六态：
`pending / succeeded / failed / cancelled / needs_approval`
HITL 的挂起就落在这一行上。

loop 本体不是状态机，就是个 `while not done` 循环，出口产一个「收场原因」枚举（finished / max_turns / token_budget / time_limit / truncation_limit / server_interrupted / interrupted / suspended）—— 它是前两个状态机之间的枢纽：**收场原因 → 运行状态**的映射表在 db 侧，框架不认存储词汇。

一句话：**事件机管这次说得对不对，运行机管这件事办到哪了，工具行管这一条动作成没成。**

### Q21 CharApp 如何对接 CharAgent（模块划分）

**面试官**：charapp 是怎么使用、对接 charagent 的，分哪些模块

**我**：CharApp 的对接原则一句话：**框架给插座，业务插插头** —— 框架定义了若干个接缝（都是 Protocol，不要求继承），业务侧每个模块就负责插好其中一个。依赖方向严格单向：框架不 import 任何业务代码（有测试钉住）。

按模块过一遍，每个说清「职责 + 挂在哪个接缝上」：

**1. 配置与传输层**
- `config.py` —— 全项目**唯一读环境变量**的地方（`CHARAPP_*` 段：内部令牌、服务地址、压缩五旋钮、知识库配置等）。
- `minimall/client.py` —— 商城内部端点的异步 HTTP 客户端，业务侧唯一一处「怎么跟商城说话」。身份（`X-User-Id`）逐请求给，但它从闭包来、不从模型来。

**2. 工具层**
- `tools.py` —— 19 个业务工具的工厂（`build_tools`），身份在装配时裹进闭包。
- `provider.py` —— **接缝①：`ToolProvider`**。`provide(context)` 一次交出全部 22 个工具（19 业务 + 框架给的 3 个记忆工具）；从 payload 取身份、把一次性凭据挑进闭包。

**3. 治理层（全部挂在框架的 hook / 出口上）**
- `guardrail.py` —— **接缝②：`BEFORE_TOOL_EXECUTE` 裁决点**。四条规则（写预算 8 次 / 单笔 5000 上限 / 代付挂起 / 下单挂起）。
- `scoping.py` —— 也是 hook：`BEFORE_TURN` 原地裁剪可见工具 + `BEFORE_TOOL_EXECUTE` 拒绝范围外调用（跑分 A/B 装置，生产不装）。
- `injection.py` —— 注入防护的第 2 / 4 层：检索侧给资料加声明与打标；输出侧包一层**事件出口**做泄漏扫描。
- `redaction.py` / `log_redaction.py` —— 两条脱敏路：前者包事件出口（工具事件整条换人话）；后者给框架的日志脱敏提供**字段名单**。

**4. RAG 层（`knowledge/`）**
- 一条完整链路：文档 → 切分 → bge-m3 向量化 → Milvus 混合检索 → rerank → 检索工具。
- `citations.py` + `history_citations.py` —— 逐句引用：检索工具领编号、`ON_TOOL_EXECUTED` 钩子收原料、`final` 出口挂着引用交付，历史那一半从记录表回填。

**5. 装配层 —— 这是对接的核心文件**
- `service.py` —— 两个入口共用的全部装配，`session_for()` 是**唯一一处装会话的地方**：造提示词 → 工具 → hook 注册（裁剪 → 护栏）→ 压缩成对零件 → `ChatSession` → 三层出口包装。它还管身份来源的唯一入口 `build_context()`（CLI 传 argv、服务传请求头）。
- 用到的框架零件：`ChatSession`（会话）、`TrimAndSummarize + CalibratedTokenCounter`（压缩）、`LoopGuard`（三道刹车）、`PostgresCheckpointSaver`（快照）、`ConversationRecorder`（记账）、`load_prompt`（提示词按版本文件加载）。

**6. 入口层（三个，互不替代）**
- `server.py` —— **接缝③：框架的 `create_app`**，业务只实现两个插座（ContextProvider 做认证 + SessionProvider 转交 `session_for`）；HTTP + SSE 全链路由框架出。
- `cli.py` —— 命令行入口，与 server 共用 `service.py`，差别只在「身份从哪来、话怎么说出去」。
- `mcp_server.py` —— **暴露侧**：把同一套工具以 MCP 协议开出去，只开只读 11 个、绑定单个账户。

**7. 评估层（`eval/`）**
- `fixtures.py`（respx 假商城）+ `golden.py`（20 题 6 场景）+ `harness.py`（跑分环境）+ `judges.py`（规则判据）+ `subject.py`（被测对象）+ `run.py`（入口）—— 跑在框架的 `EvalRunner` 协议上。

如果画一张对接图，就是：**框架的每个接缝 ← 业务的一个模块**：`ToolProvider` ← provider、`hooks` ← guardrail / scoping / citations、`event_sink` ← 三层包装（脱敏 / 引用 / 审计）、`create_app` ← server、`RunRecorder` ← 记账、`CheckpointSaver` ← Postgres —— 而 `service.py` 是把这些插头**一次性插好**的那个装配台。

### Q22 MCP 两侧设计

**面试官**：你的 charagent 和 charapp 的 mcp 是怎么设计的，可以做到以下吗：1. charagent 的 mcp 服务可以接入所有外部第三方的 mcp 吗（包括你自研的 charapp 的 mcp 服务）2. charapp 的 mcp 协议可以被其他 agent 接入使用吗

**我**：**两条都能 —— 而且这正是设计时的意图：两侧都做**（一侧证明框架抽象通用，一侧证明业务能力可以开给任何 agent 客户端）。两边共用同一个协议、同一套工具定义。

**一、消费侧：CharAgent 接外部 MCP。**

接法是：配一张 server 表 → 每一台起一个 `McpClient` → 列工具 → 转成框架的 Tool → 交给同一个 `ToolProvider` 插座。几个为「通用性」专门做的设计：

- **配置直接兼容 Claude Desktop / Code 的 `mcpServers` 格式**，而且只读我们用得上的五个键（command / args / env / cwd / tool_prefix / call_timeout），**不认识的键一律跳过** —— 所以能直接抄别人家的配置来用，不用改写。
- **工具转换是按协议做的，不认是谁家实现**：任何 MCP server 的 `tools/list` 结果都转成框架工具；名字可加前缀；`tools/call` 返回 `isError=true` 时转成「可操作错误」走框架同一条错误通道；MCP 自己的 annotations（readOnlyHint 这类）**不搬** —— 那是它的词汇表，不是我们的。
- **重名仲裁 fail fast**：同一台 server 内部重名（那是它的 bug）、跨 server 撞名（给两条出路：配 `tool_prefix` 或别连它）—— 都当场报错。为什么不合并或让后来者赢？那最坏：模型以为调的是这台、实际打到那台，是「静默地错」。
- **实测过的**：接过一个自制的 demo server、跑过 MCP 参考实现的试接脚本，以及 —— 最有说服力的一条 —— **用自己的客户端接自己的服务端**：CharApp 侧有一条测试用**真子进程 + 真 HTTP 假商城**验证「框架 `McpToolProvider` → CharApp 的 MCP server → 商城」整条链路真的通。

**诚实的边界**：传输只做了 **stdio** 这一种（Streamable HTTP / SSE 没做）；MCP 三类能力里只用了 **tools**（resources / prompts / sampling 没接）。所以「所有第三方 MCP」要加一个限定：**stdio 传输的、tools 能力为主的那些**。这是设计储备里明确记着的边界，不是遗漏。

**二、暴露侧：CharApp 的 MCP 开给别的 agent。**

它实现的是**标准 MCP 协议（stdio）**，所以任何 MCP 客户端都能接 —— Claude Desktop、Claude Code、别的 agent 框架都行。仓库根已经放了一份 `.mcp.json` 配置，也就是说我自己平时就用 Claude Code 直接接它做验证。

三个刻意的设计：

- **工具定义与助手完全同源**：照抄 `build_tools` 那套（说明、schema、闭包身份逐字相同），只按 `writes` 注解剔掉 8 个写工具 → 开出去 **11 个只读**。所以「助手能用的工具」和「MCP 开出去的工具」不会漂。
- **执行走框架同一条链**：`call_tool` 里调的是 `execute_tool` —— 参数校验、超时、错误文案与助手逐字一样。接出去的工具和助手的工具**行为一致**。
- **用低层的 MCP `Server`，不用 FastMCP**：因为我们的工具 schema **已经是** wire JSON Schema，低层可以原样递出去；FastMCP 会从函数签名再猜一遍、还附送它自己的 outputSchema，多一层翻译就多一层漂。

**信任边界是明说的**（ADR-0030）：暴露侧**只读 11 个工具 + 只代表配置里那一个固定账户** —— 客户端说什么身份都不算数，因为 MCP 客户端不在浏览器 session 那条信任域里。这就是 ADR-0001 那句「信任域被拆开时必须还」的判据的一次实际兑现：**不做真鉴权是记录在案的取舍，不是忘了做**。

所以回到您两个问题：**一，能接 —— 带 stdio 和 tools 这两个限定；二，能被接 —— 只读单账户这个边界写进 ADR 了。**

### Q23 Skill 的理解与设计落地

**面试官**：你的整个项目中没有设计 skill 模块，你能先讲讲 skill 在 agent 中是怎么应用的吗？具体到 charagent 和 charapp，你会怎么设计

**我**：先说我对 Skill 的理解，再说具体到这两个项目我会怎么设计。

**一、Skill 是什么 —— 用一句话和三个已有概念划开。**

**MCP 提供「连接」（怎么调到工具），Skill 提供「知识」（怎么做好某类任务）**，两者互补不替代。它和我项目里已有的一堆东西的分工：

| 概念 | 回答的问题 | 例子 |
|---|---|---|
| 工具 | **能不能做**（动作） | `request_refund` |
| **Skill** | **怎么做**（流程/知识） | 「处理退款请求的完整步骤」 |
| 知识库（RAG） | 事实是什么（条文） | 「7 天无理由」的原文 |
| 记忆 | 这个人是谁（个人事实） | 「他偏好货到付款」 |
| 系统提示词 | 永远适用的规矩 | 身份、禁则 |

关键判断：**Skill 要接管的是系统提示词里「有一串固定步骤、但只有特定场景才用得上」的那部分** —— 它写在提示词里是每轮都付费、却很少被用到。

**二、它的工作机制：三级渐进披露。**

这是 Skill 设计的精髓，每一级解决「成本」和「能力」的矛盾：

- **L1：名字 + 描述** —— 总是加载，成本几十个 token。它的作用不是"使用"，是**路由**：模型看着菜单决定"这个任务该不该用某个 skill"。所以 description 是索引本身 —— 描述写得不好，skill 就等于不存在。
- **L2：正文** —— 只有模型决定用了才加载。一段几千字的流程知识，用到时才花这个钱。
- **L3：附带资源** —— 正文里引用的文件/模板/脚本，真正需要某一份时才读。

对应到业界实现（Anthropic 的 Agent Skills）：一个 skill 就是一个文件夹，`SKILL.md` 带 frontmatter 的 name / description，加可选附带文件；模型先看 L1，需要时主动去读 L2/L3。

**三、落到 CharAgent：怎么不改 loop 一行把它做出来。**

我的设计是**两段式**，全部落在现有接缝上：

1. **L1 索引进提示词** —— 扫描 `skills/` 目录，把每个 skill 的 name + description 拼成一段索引，跟着身份说明一起装配。这一步不需要任何新机制：我的 `prompt` 包本来就是「按名加载 + 变量渲染」，业务把索引当变量渲进去就行。
2. **L2/L3 走工具** —— 框架加一个 `skill` 包，给出两个东西：`SkillRegistry`（扫描目录、读元数据）和 `build_skill_tools(registry)` —— 产出一个 `load_skill(name)` 工具（返回正文）和一个 `read_skill_file(name, path)`（读附带资源）。**它们就是普通工具**：`@tool` 装饰器、schema 自动生成、超时、错误语义，全部复用。

这样做的三个理由：**一是零新机制** —— 没有新的事件类型、没有新的循环分支，因此不可能碰 `agent/loop.py`；**二是可观测** —— 加载 skill 是一次工具调用，轨迹里看得见「模型用了哪个 skill」；**三是框架给机制、业务给内容** —— 与脱敏、记忆、评估同一条分工：框架管扫描/加载/注入的形状，业务管写哪些 skill。

顺手说一个必须守的纪律：**skill 只是知识，不改权限**。它教"怎么做"，但护栏那条闸不受它影响 —— 否则 skill 就成了绕过护栏的暗道（一个被注入的 skill 内容如果能让模型绕过人工确认，那这套机制就白设计了）。

**四、落到 CharApp：具体该拆什么。**

现在 v8 提示词里有几节已经露出了"skill 的形状"：政策问答流程、长期记忆的使用方式、代付/下单的确认话术。随着场景变多，可以拆成：

- `refund-flow` —— 退款全流程（怎么判断订单能不能退、走申请还是走取消、时效怎么解释）；
- `order-troubleshoot` —— 订单异常排查（没收到货 / 状态不对 / 金额不对，各自的步骤）；
- `payment-help` —— 付款相关（余额不足怎么办、代付为什么要密码、失败了怎么引导）。

装配上就是：`CharApp/minimall/skills/` 目录 + 一个启用清单；`service.session_for` 里把索引拼进提示词、把两个 skill 工具装进工具集 —— 与其他 22 个工具同一个插座，一行不用改框架。

**五、为什么现在没做 —— 判断和触发条件。**

判据很直接：**当前复杂度还没到**。22 个工具、8 个场景的提示词，加上压缩机制在管窗口，常驻成本还没有显形。Skill 的收益要在「某类任务的长流程开始成群出现」时才兑现 —— 比如支持多种售后类型、每种商品品类一套流程，那时候提示词要么膨胀到离谱、要么开始互相干扰，就该搬。所以我把它的设计记在难点地图里（#51），实现标成不做 —— 和"多智能体不实现、写原理底稿"是同一条原则：**记录「不做」与记录「要做」同样重要**。真要做的时候，上面那两段式就是路径。

### Q24 最难的经历与收获

**面试官**：好，面试到尾声了，最后一个问题 —— 你觉得你在做 charagent + charapp 的项目中，遇到过的最难的事是什么，你是怎么解决的，你有什么收获

**我**：**最难的不是某个功能写不出来，而是"静默失效"** —— 写不出来的东西可以查文档、看源码；静默失效不一样：它不报错、不告警、日志干净、逐行读代码每句都对，但它在真机上隔一轮咬你一口。我在这个项目里抓到的三个最值钱的缺陷，全是这一类。

**最典型的一个：上下文压缩的"视图隔轮失效"。**

现象是这样冒出来的：我在真机上模拟八轮长对话，观察每一轮实际发出去的请求大小，发现一个规律性震荡 —— **第 2 轮压了、第 3 轮跳回全量；第 4 轮压了、第 5 轮又跳回去**。也就是说一半的轮次请求是超标的全量，而摘要那一次调用 **白烧一半**。

难在哪？第一，它**每隔一轮才现形一次**，看一眼某轮的代码永远是对的；第二，它不报错 —— 压缩"看起来在工作"，只是钱多花了、效果没到位；第三，根因藏在一个非常自然的写法里：我最初把「投影」和「切刀」合成了一句话 —— 「不超阈值就原样返回」。而那句"原样"是**全量账本**：于是压完的那一轮，下一轮把账本拿去估算（账本只增不减、永远超线）→ 判定"要再压" → 又切一刀。**每两轮循环一次。**

我是怎么找到它的？靠两样东西：一是**给每一轮都记观察值** —— 这一轮真的发出去的是什么、估算多少、省了多少，全部落进快照帧的 metadata；二是一个**八轮最小复现脚本**，把"每隔一轮"的规律逼出来。找到根因之后，修法反而很简单：**把两件事拆开** —— 投影每一轮都做（摘要替换掉它覆盖过的那段），阈值只管「要不要**再切一刀**」。拆开之后，滞回自己就长出来了 —— 因为投影才是真正发出去的东西，它因为上一刀推过切点而变小。

**同一主题的第二个案例：估算器坐标不一致。** 我的估算器原来是"锚 + 增量"，隐含一个前提 —— 「拿它量的列表一定是账本那条线的延伸」。压缩上线的那一天，这个前提就破了（有时量的是视图）。最小复现很极端：同一份内容，按视图量出 415、真实 8000，**低估 20 倍**；账本被量成 13291、而它自己的启发式只有 6520，**高估一倍**。它的后果也是静默的：水位线试算偏低 → 误判"压到位了" → 提前停手，压缩永远做不彻底、还不报错。修法是换成"启发式 + 固定开销校准"，让**任何一份列表都走同一条算式**。

**还有一个不是缺陷、但更打脸的：A/B 装置的"只裁不拒"。** 做工具数量 A/B 时我发现：从可见列表里裁掉工具之后，模型**照样调得到** —— 因为执行查的是全量工具表，和当轮给它的列表无关。这意味着两臂比的根本不是"少给"，而是"看不见"，整个对照的**前提当场失效**。这件事教会我的是：**验证「你测的是你以为的东西」，要先于相信任何数据。**

**这三件事给我的收获，我归纳成四条：**

1. **给系统装仪表，比多写一个功能重要。** 估算偏差、缓存命中率、每轮耗时、每一帧的来源 —— 这些诊断值我是当基础设施在做的。没有 `estimate_drift` 这个字段，第二个案例到今天还藏着。
2. **真机验收是最后一道测试，而且必须在流程里有位置。** 这三个缺陷全部在单测的覆盖之外 —— 单测测得了确定性的东西，测不了"每隔一轮"这种时序耦合。所以我在每个阶段的收口都放了一次真机走查，而不是只跑 pytest 绿了就算完。
3. **每修一个静默缺陷，必须把它钉成测试或装置** —— 视图震荡修完有用例守着，裁剪问题修完变成了「可见集必须等于可调集」这条被测试钉住的规则。不然同一个坑会换个面貌回来。
4. **最深的一条：这些全都不是编码错误，是概念边界没划干净。**「投影」和「切刀」是两件事、「账本坐标」和「视图坐标」是两个空间、「可见」和「可调用」是两件事 —— 边界划不干净，代码写得再对也是错的。这也是为什么我后来越来越重视写 ADR：**每条决策记录的不是"我选了 A"，而是"A 和 B 的边界在哪、什么条件下该回来重看"**。

如果要用一句话收尾：这个项目给我最大的改变是 —— 我从"会用 agent"变成了"**知道 agent 会在哪里悄悄错，以及怎么设计让它自己说出来**"。前一半靠学，后一半只能靠真机一遍遍跑出来。
