## 一、简历项目经历描述

**项目经历：RAG 方向双项目（LangGraph 工业级知识库问答 + RAG Text2SQL 数据查询智能体）**

> **一句话概括**：两个从 0 搭建的 LangGraph RAG 生产级链路：一个是垂直领域知识库问答（离线加载图 + 在线查询图），一个是自然语言转 SQL 的数据查询智能体。二者都自建了 golden set 量化评估闭环（分层指标 + 消融对照 + 报告落盘），关键设计均以实测数字为准绳而非默认值；两端合计约 350 个全离线用例（141 + 208）。

**项目一 · 工业级 RAG 知识库问答（LangGraph 双图 / Milvus / BGE-M3 / bge-reranker-v2-m3）**

> 加载图 7 节点建索引，查询图 7 节点在线问答：**主体识别 → 三路并行召回 → RRF → 精排 → 流式溯源回答**。83 题基线最终层召回 0.8434 / 必命中 0.9136 / MRR@1 0.8916。

- **主体识别即检索入口，也是最大瓶颈**：LLM 抽取文档主体名并建独立向量集合，检索时以 `item_name in [...]` 硬过滤缩小范围（避免多文档同义内容互相污染）。全称 vs 简称的差异靠规则归一化处理——实测「中华人民共和国数据安全法」与「数据安全法」相似度 0.701、阈值 0.70、错误候选能到 0.68，分数区间太薄判不住；问题没点名主体时改走**内容兜底**（全库 chunk 召回反推所属文档），阈值 0.65 是扫出来的（0.70 只接住 50% 的题，0.65 接住 86%）。入口通过率 **29/79 → 68/79**。
- **三路并行召回 + 分层融合**：向量 / HyDE / 联网三路并行执行；RRF（k=60、双路 0.5 权重、按 chunk_id 去重累加）只融前两路，联网结果在精排层才并入并给中性先验——它没有 RRF 先验，按比例缩会被系统性降权。
- **精排不做一票否决**：reranker 打分与 RRF 先验加权融合，先验归一化用「除以最大值」而非 min-max（min-max 会把小候选池的跨度撑满，精排再准也翻不了盘）；按批内最长候选向上取窗口档位（1024/2048），**超窗口截断而非 LLM 压缩**（截断确定，压缩稿与评测标注的原文对不上）。
- **分块是召回的地基**：多级标题切分 + 标题栈给每块记祖先链并回填正文首行——聚合型问题（"快速开始包含哪些步骤"）这一块正文里没有那四个字，实测排到全文档第 23 名，补上路径后第 1；另处理 HTML 表格整块保留（超长按行切且每片自闭合）、MinerU 伪标题、碎片跨节吸收。
- **评估口径先行**：83 题 / 15 篇法规语料 / 138 chunk，4 层分层指标；**精确率只报最终层**（前几层分母是人为召回池）；**必命中率是门槛**（捞到任意一条即过，未标注记 null 出分母）；交付条数按扫参取 top-1（1 条 0.922/0.870 vs 2 条 0.507/0.916）。
- **精排开/关消融**：同批题同参数两臂两趟，精排净赚 **+2.4pp**（召回 0.8434 vs 0.8193），代价 **+18 秒/题**（P50 21.4s vs 3.3s）——用 18 秒换 2.4 个点，值不值按场景算。为让两臂之差可归因，把 HyDE 的 LLM 生成**逐题冻结重放**（存的是真实那次生成，题目改了自动判失效），主体识别走真实链路、不注入预期答案。
- **性能定位**：从节点日志反解逐节点 P50/P95——精排占整链路 **~85%**（15.8s/题，检索本身毫秒级）；线上 TTFT P50 51.5s 的根因查清是**联网结果也进了精排池**（池子从 10 条涨到 10+N，还把窗口顶到高档，同一趟精排 P50 50.3s）。
- **韧性**：单路召回失败/为空降级为"这一路没贡献"而非整链 500；三路全空返回固定"不知道"文案而不叫模型硬编；Milvus 混合检索失败统一返回空列表而非 None。参数跟着语料走——文档标题片打折系数在换语料后重扫，发现有害即改回 1.0。

**项目二 · RAG Text2SQL 数据查询智能体（LangGraph 单图 12 节点 / Qdrant + Elasticsearch / MySQL 双库）**

> 自然语言 → SQL：**关键词抽取 → 三级召回（列/指标/取值）→ 合并补齐 → LLM 过滤 → 生成 → 校验 → 校正 → 执行**。39 题 × 3 次：**列召回率 90.5%、SQL 可执行率 100%（117/117）、失败率 0%**。

- **元数据三级语义索引（声明式建模）**：一份 `yaml` 声明表/字段/指标，一次构建写三处——meta 库（类型 + 取值示例 + 主外键角色）、Qdrant（列与指标各按 name/description/alias 建多个向量点，检索后按业务 id 去重）、ES（`sync` 列全量 distinct 值，ik_max_word）。列/指标阈值分开（0.6 / 0.7），指标描述更短更易漏。
- **Schema Linking 的补齐策略**：指标 → 关联列（回查 meta 库）、取值 → 所属列（并把命中值追加进列的 examples）、每张涉及的表补主外键（保证 JOIN 可行）；再由 LLM **只在候选范围内**裁剪表与字段（JSON 输出 + 代码双向裁剪）。
- **执行护栏（模型生成的 SQL 直连数据库，最重要的一处工程）**：① 语句级只读白名单——只放行单条 SELECT/WITH，扫描前屏蔽字符串字面量与惰性注释，且实测出三个必须写对的细节：`/*!...*/` 是可执行注释不能屏蔽、`--` 后不跟空白不是注释、`;` 多语句必须挡（asyncmy 默认开 MULTI_STATEMENTS，实测 `SELECT 1; SELECT 2` 两条都执行）；② LIMIT 在**文本层**补齐/收紧（默认 200 / 上限 1000），刻意不用派生表包裹——实测包裹会把两表同名列的合法 JOIN 变成 1060 语法错，补的 LIMIT 另起一行以免被行尾注释吞掉；③ 数据库侧兜底——连接建立即 `SET SESSION TRANSACTION READ ONLY` + `max_execution_time`，写操作报 1792、慢查询报 3024 且**连接仍可用**（校正节点能接着走）。拒绝理由写成给模型看的**可操作文本**，校正节点有机会自己改对；护栏落在一处执行咽喉，图内两个节点与跑批器共用同一份实现。
- **评估体系（L1/L2 分层 + 人工口径）**：golden set 39 题 7 类，问题人工写、口径人工确认，**绝不用系统跑通的 SQL 反推**（那等于把当前缺陷固化成"正确答案"）；L1 读**过滤后的候选集**而非最终 SQL，并留一行「召回@merge」做诊断——时间类题表必命中只有 20%/25%，两行一比即知丢在**过滤**而非召回（dim_date 缺 12/15 次、最终 SQL 0 次引用它），再用 EEX 与独立口径 SQL 实测两种写法结果一致；EX 把"没跑完"与"SQL 跑不通"拆成两个数读，每题 3 次并给臂内极差。
- **性能优化：批量嵌入 + 带上限并发**：三路召回节点从"逐关键词串行"（N 个关键词 = 2N 个 RTT）改成一次批量嵌入 + Semaphore 限并发（默认 4），P50 **−37%/−46%/−55%**；先验证据是 117 组召回 id **集合全部一致**（耗时变快但结果被换掉，那是改坏了）。A/B 用**冻结的关键词扩展结果重放**——真 LLM 档抖动可达 20 秒，会把几百毫秒的优化整个淹掉；微基准另证"再提并发无意义，剩下的大头是嵌入推理本身"。
- **工程韧性**：LLM 调用给预算（60s 超时 + max_retries=2 交 SDK 只重瞬态）——由"跑批 117 次里 2 次卡在上游挂起、SDK 默认读超时 600s 形同没有预算"这件实测事故催生；数据库语句只在**连接失效**时重试一次（语句错该走校正节点）；单题超时/抛错隔离进报告并继续整批；失败题复跑可 `--merge-into` 并回基线，不让其余 37 题重掷。

### Q1 主流 RAG 架构与我的理解

**面试官**：你有了解当前主流的一些 RAG 架构设计吗，这些架构对比传统的朴素 RAG 上都有哪些改进？结合我上面的问题讲讲你对于 RAG 的理解。

**我**：了解，而且我是按"它在链路的哪个环节动手"来记的，不是按名词记。我先给判断，再展开，最后落到我自己做过的部分。

**一、Naive RAG 的短板，就是所有演进的方向。** 朴素 RAG 是「切块 → 向量化 → Top-K → 拼 Prompt → 生成」，它的三个硬伤很明确：① 索引侧——固定字数切块，语义会被从中间截断；② 检索侧——只靠单路 embedding 相似度，专有名词 / 编码类查询天然不敏感，搜不到就没辙；③ 检索后与生成侧——搜到垃圾也不过滤，模型照样"照着错的书抄"，链路里没有任何"判断"环节。把这三点拆开看，所有改进方案都能归位：**要么给链路加"更多的路"（召回广度），要么加"判断"（质检、反思、路由）**，代价一律是延迟、成本、或新的误判来源。

**二、按环节归类（我会背的是这张表，不是 16 个名字）**

| 动哪里 | 方案 | 解决什么 | 代价 / 前提 |
|---|---|---|---|
| 切块 / 索引 | 语义分块、Parent-Child、多模态 | 语义完整；小块检索精度 + 大块上下文；图文不丢 | 逐句编码贵；索引量翻倍；VLM 成本 |
| 查询前 / 查询 | Adaptive 路由、Multi-Query、HyDE、Agentic | 简单问题别跑全套；口语化问法覆盖；短问题对齐长文档；自主选工具 | 分类器误判；延迟与改写跑偏；Agent 不可控 |
| 检索 | Hybrid Search、Reranking | 语义 + 精确术语兼得；粗回收广度、精排保精度 | 维护双索引；精排延迟 |
| 检索后 | CRAG | 低相关不硬答，回退 Web | 多一次 LLM 判定 |
| 生成侧 | Self-RAG、Speculative | 支撑性校验防幻觉；并行草稿降延迟 | 评审成本最高；一致性风险 |
| 数据形态 | GraphRAG、Text-to-SQL | 跨文档多跳；聚合 / 排序 / 筛选类问题向量无解 | 图谱构建贵；SQL 有注入面 |

补一句我自己的理解：**RRF 之所以是生产标配，是因为它只用 rank 不用 score**——不同检索器的分数量纲本来就不可比，用名次融合绕开了归一化问题。同一个坑我在精排融合时也踩过：rerank 分和 RRF 分不同量级，不归一化就相加等于没融合，而归一化用「除以最大值」而不是 min-max——min-max 会把小候选池的跨度撑满，精排再准也翻不了盘。

**三、落到我项目里：哪些我做了，哪些我知道但没做。**
- **做了**：Hybrid Search 我是用 BGE-M3 的稠密+稀疏双向量 + Milvus WeightedRanker 落地的（chunks 偏稠密 0.7/0.3），RRF 用于融合"普通检索"和"HyDE"两条路；查询侧有改写 + HyDE；检索后有精排 + 动态截断；Text2SQL 那套就是第 12 种，并且我按"绝不允许模型生成的 SQL 直接执行"补了三层护栏（只读白名单 + LIMIT 收敛 + 只读事务兜底）。
- **有实测结论、不靠背名词**：精排不是无脑加——我做过开/关消融，净赚 2.4 个点，代价是每题多 18 秒；更关键的是我查出线上首字延迟 51 秒的根因是**联网结果也进了精排池**，池子变大、窗口档位被顶高。这正好说明 CRAG 那类"低相关才回退 Web"的设计不是啰嗦，是必要的条件约束——我把 Web 做成了常开的一路，代价立刻显形。
- **没做、如实说**：GraphRAG 的多跳、Adaptive 的完整路由（我的 Text2SQL 里歧义问题还是硬生成，没有澄清分支）、Self-RAG 式的生成侧复核。生成侧我是刻意退了一步的：质量校验我做成"落盘报告 + 人工判读"，不引 LLM-as-judge——judge 会把非确定性带进判据，"这次比上次好"就不可复现了。

**四、我对 RAG 的理解，三句话：**
1. **RAG 的本质是"把生成约束在可核验的证据上"**，不是"装个向量库"。所以引用溯源不是锦上添花，它和检索质量是同一件事的两面。
2. **链路是漏斗，上游决定上限**：召回决定天花板、融合决定顺序、精排决定交付、生成只决定表达。我的 83 题评测里最终层召回 0.84，而精排净赚只有 2.4 个点——瓶颈从来不在最后一步。
3. **工程上比"选哪个架构"更重要的是"能被量化、能降级"**：任何一层出问题都不能变成 500（我项目里单路召回失败降级为"这一路没贡献"），任何一次调参都要有前后对照的数字（冻结随机源、臂内极差、报告落盘）。这也是我不赞成"上来就 Multi-Agent + GraphRAG + 多模态全家桶"的原因——复杂度是要用实测收益来还的。

**面试官**：rag_knowledge 中具体分为哪些节点，每个节点具体是什么作用，按顺序、分点、简单精炼的概括一下。

|---|---|---|
| 1 | `_08 node_item_name_confirm` | 入口：取最近 10 条历史 → LLM 改写问题 + 提取主体名（指代消解）→ 主体名去 `item_name` 集合检索确认（≥0.70 确定 / ≥0.60 候选）→ 没确认出来走内容兜底反推主体；**路由决策就发生在这里** |
| 2 | `_09_1 node_search_embedding` | 第一路：改写问题向量化 → 稠密/稀疏混合检索（0.7/0.3），`item_name in [...]` 硬过滤，取 Top10 |
| 3 | `_09_2 node_search_embedding_hyde` | 第二路：LLM 生成假设性答案 → 「问题 + 假设答案」拼接向量化后同样检索 |
| 4 | `_09_3 node_web_search` | 第三路：Tavily 联网搜索（过滤 score ≤ 0.5），补充本地库覆盖不到的内容 |
| 5 | `_10 node_rrf` | 融合：**只融前两路**（各 0.5 权重，k=60，按 chunk_id 去重累加）取 Top5；联网那份只是穿过它 |
| 6 | `_11 node_rerank` | 精排：RRF + 联网合并成统一结构 → 按批内最长选窗口档位 → reranker 打分 → 与 RRF 先验加权融合 → 按"相对头部的累计衰减"动态截断，交付 top-1 |
| 7 | `_12 node_answer_output` | 作答：组装「参考内容 + 置信度 + 来源 + 历史 + 主体」prompt → 生成（流式则 SSE 逐字推）→ 提取命中块里的图片 URL → 回答存 MongoDB |

**三、两条结构上必须说清的点：**
- **`_08` 的路由是三分支**：有确定主体 → 三路（2/3/4）作为**并行边**同时跑，都汇到 `_10`；只有候选主体 → 直接跳到 `_12` 输出候选列表；没有主体 → 输出"未检测到主体"。
- **`_09_1` ~ `_09_3` 每一路都套了失败隔离**：单路抛异常或返回空，降级成"这一路没有贡献"，另外两路不受影响；三路全空时 `_12` 返回固定的"没找到相关资料"文案，不叫模型硬编。

### Q3 rag_knowledge 各节点如何保证召回率与精确率

**面试官**：详细讲解每个节点分别怎么保证最终的召回率 / 精确率。

**我**：先立一个框架，不然后面每个节点看着都像在堆参数：**召回率的上限在加载侧就定死了**（库里没有的东西，查询侧再强也捞不回来），**查询侧则是"前三层保召回、后三层保精确"的漏斗**。我按这个分工逐个说。

#### 加载图（决定召回天花板）

**`_01 entry`｜文件识别**
- 保召回：先把"源文档能不能进库"卡清楚——支持的类型才放行，避免半截索引。这也是排查手册里的第 9、10 条：**源文档本身不全 / 知识库覆盖不够，是召回率低的第一大来源**，所以入口不做任何静默吞掉。

**`_02 pdf_to_md`｜MinerU 解析**
- 保召回：轮询必须等到 `state=done` 才下载；解压后找不到 md、任务 failed 一律抛错——**绝不静默产出一份空文档**（空文档进了库，表现是"搜不到"而不是"报错"，更查）。
- 细节：轮询期间 5xx 和网络异常只记日志继续轮，4xx 才终止——避免把"解析中"误判成失败。

**`_03 md_img`｜图片语义化**
- 保召回：图片本身不可检索，用 VL 模型把图意写成文字塞回 md，让"接线怎么接""外观什么样"这类问题有文本可命中。
- 保精确：摘要时带图片前后 100 字上下文做约束（否则 VL 可能把错误"事实"注入 chunk，这是我排查表里明确列的风险项）。

**`_04 document_split`｜分块（对召回/精确影响最大的一个节点）**
- 保召回：按多级标题切 → 块内语义单一，向量更纯；**标题栈 + 祖先链回填正文首行**——问"快速开始包含哪些步骤"时，§5.2 那块正文里根本没有"快速开始"四个字，实测在 24 条候选里排第 23，补上 `## 5. 快速开始 > ### 5.2 环境变量` 后排第 1，这是"聚合题"的重灾区；小块合并（<400 并回，上限 1000），太小的块零召回；表格整块保留、超长按行切且**每片自闭合**——MinerU 把整表压成一行，硬切会出 `。</td><td>` 残片（实测 18/131 个 chunk 带残渣）。
- 保精确：跨节合并只吸收"正文 < 80 字的碎片"——放宽会把正常小节吞掉，一个块混两个主题，谁的问题都匹配不好（实测 106 块里 32 块含两个以上章节标题，就是放宽的产物）；伪标题识别（`## a 按 (Foil Save)…`）当内容行——否则每个操作步骤自成 section、标题退化成 `## a`；顺序上，路径拼接**必须排在切分/合并之后**，因为那几个判据依赖"正文首行是标题行"。

**`_05 item_name_recognition`｜主体识别**
- 保召回 + 保精确的双效设计：识出的主体名既写进每个 chunk、又拼进 embedding 文本（`item_name_content`），让主体信息参与语义匹配；检索时以它做硬过滤，避免多文档同内容互相污染。
- 兜底：LLM 识别失败降级用 `file_title`——**绝不能写空串**，否则该文档从主体链路整体消失。

**`_06 bge_embedding`**
- 保召回：一次产出稠密 + 稀疏两路（BGE-M3），稀疏那路就是后面混合检索里的"精确术语"能力来源。
- 保精确：原生 L2 归一化（稠密 IP ≈ COSINE，量级一致）；batch=5 分批，失败可定位。

**`_07 import_milvus`**
- 保召回与精确都要的一条：**先按 `file_title` 删旧再插**——重传幂等，避免重复块挤占 Top-K 名额（既浪费召回位，又拉低精确）。
- 索引选型：稠密走 HNSW（M=64 / efConstruction=100，精度优于 IVF），稀疏走倒排 + DAAT_MAXSCORE。

#### 查询图

**`_08 item_name_confirm`｜入口，召回最大瓶颈也是最大杠杆**
- 保召回的四重链：① LLM 抽取（prompt 明确"多个专有名称全抽""没有就返回空，宁可空也别挑一个词凑"）；② 向量确认（0.4 稠密 / 0.6 **偏稀疏**——主体名是短串，字面重合比语义更可靠）；③ **规则归一化**（削「中华人民共和国」前缀/书名号/空格）——实测「中华人民共和国数据安全法」相似度 0.701、阈值 0.70、错误候选能到 0.68，分数区间薄得判不住，而"差一个前缀"是确定的事实，就交给规则；④ **内容兜底**：问题没点名主体时，拿问题去全库 chunk 召回反推它属于哪份文档，阈值 0.65（实测 0.70 只接住 50% 的题，0.65 接住 86%）。这一整套把入口通过率从 29/79 提到 68/79。
- 保精确：候选区间（0.60~0.70）**不硬检索**，直接把候选列表作为答案输出——宁可不答，也不把问题塞给可能不对的文档。

**`_09_1 / _09_2 / _09_3`｜三路并行召回**
- `_09_1` 普通检索：混合权重 **0.7 稠密 / 0.3 稀疏**（偏语义），召回池取 20 条再截 10——"召回多、精排少"的漏斗（此前召回/融合/精排共用 5，精排只能在 5 条里挑 3 条，等于白排）。`expr` 的值用统一转义函数拼，不依赖 Python `repr` 挑引号的"碰巧"。
- `_09_2` HyDE：先让 LLM 写一段假设答案，用「问题 + 假设答案」拼接向量检索——补的是"问得短、文档写得长"的语义空间差。它天然可能跑偏，所以定位是**并行的一路而非唯一一路**：编错了还有 RRF 和精排兜。
- `_09_3` 联网：补"库里根本没有"的召回缺口；只留 score > 0.5 的结果。
- 三者共同的一条：每路套失败隔离——单路挂/空降级成"这一路没贡献"，不拖累另外两路、不 500。

**`_10 rrf`｜融合**
- 保召回：两路命中合成一个池，单路漏的靠另一路捞。
- 保精确：**只用 rank 不用 score**（跨检索器分数量纲本来就不可比，这正是 RRF 的通用价值）；按 chunk_id 去重累加 = 被两路同时命中的块分数更高，相当于一致性投票；只送 10 条进精排，控制池子的噪声与延迟。

**`_11 rerank`｜精确率的主力**
- cross-encoder 对 (query, doc) 联合打分，比双塔准；但**不与 RRF 先验做取舍平衡就是"一票否决"**，所以做加权融合，reranker 打偏时 RRF 先验（实测 MRR@1≈0.70）能把顺序拽回来。
- 归一化用"除以最大值"而非 min-max——min-max 会把小候选池的跨度撑满，精排再准也翻不了盘。
- 超窗口**截断而非 LLM 压缩**：压缩稿和评测标注的原文对不上，而且每次压出来还不一样；截断是确定的。
- 动态截断判据是"相对第 1 名的累计衰减"，不是相邻两点落差（0.8/0.7/0.6/0.5 那样缓慢下滑，相邻判据永远不触发）；且下限不能等于上限（曾经都=8，等于前 8 条无条件保留，0.95 掉到 0.05 也照原样返回——这个坑有回归用例钉着）。
- 交付条数定 top-1 是**量出来的**：1 条 0.922/0.870 vs 2 条 0.507/0.916，法条问答的答案基本落在单条条文里，多带一条只换回约 5 个点召回、精确砍半。

**`_12 answer_output`｜作答（守"最后一公里的精确"）**
- prompt 明确"尽量基于参考内容作答、不要编造"，参考内容带标题/来源/置信度/链接（可核验）。
- 一路都没召回到 → 返回**写死的"没找到资料"文案**，不叫模型硬编。
- 历史里的助手回答只截前 50 字，防稀释当前问题与规则（这是精确率的隐性保护）。

#### 三条横切设计

1. **降级不报错**：单路失败 → 空贡献；两路全空 → 精排跳过；三路全空 → 固定文案。任何一层都不把"检索不到"变成 500。
2. **参数跟着语料走**：文档标题片打折系数在上一版语料上是 0.7，换成法规语料后重扫发现有害，改回 1.0——**没有全局最优的参数，只有当前语料下量出来的最优**。
3. **每一条都能量化验证**：4 层分层指标（普通检索 / HyDE / RRF / 最终重排）就是为了让"是哪一层拖了后腿"可定位；精排开/关消融净赚 2.4 个点、代价每题 18 秒，这笔账是有数可算的。

### Q4 节点参数是怎么定下来的

**面试官**：你都是怎么确定节点中的各个参数的。

**我**：参数我不是"扫一遍网格搜索"定出来的，也不是拍的。我按**参数的来源**把它们分三类，每类的定法不一样——这比逐个报数字更能说明问题。

**一、结构性参数：靠"这一层在链路里的职责"推，不扫。** 这类参数扫是没意义的，因为它改的是漏斗形状，不是刻度：
- **召回池与精排池的关系**：一开始召回 / RRF / 精排共用 Top-5，等于精排只能在 5 条里挑 3 条，**它就没有腾挪空间了**。所以我改成 召回 20 → 截 10 进 RRF → 10 条进精排。"召回多、精排少"是有腾挪空间的漏斗，这是结构判断，不是调参。
- **混合检索权重**：chunks 用 0.7 稠密 / 0.3 稀疏，因为这一路是以语义召回为主、稀疏兜精确术语；主体名确认反过来用 0.4 / 0.6 偏稀疏，因为**主体名是短串，字面重合比语义更可靠**。权重跟着"这一路存的是什么"走。
- **RRF 双路 0.5/0.5**：两路定位等价（都是本地检索），等权就是默认。

**二、经验阈值：先扫分布，分布分不开就换机制（这条最重要）。** 相似度类阈值我从来不"拍一个数就上"，而是先看**正负样本的分布区间**，能分开才用阈值：
- 主体确认定 0.70，是拿名称测试集扫出来的上界 / 候选区间；
- 但扫的过程暴露了一件更关键的事：**「中华人民共和国数据安全法」vs 用户说的「数据安全法」相似度只有 0.701，而错误候选能到 0.68**——正负样本间隔不到 0.02，阈值根本承担不了这个判断。所以我的结论不是"调阈值"，而是**换机制**：把"差一个前缀"这种**确定的事实**交给规则（归一化削前缀），相似度只用来分辨真正不同的文档。这是我在这个项目里最想讲的一条方法论：**阈值只该处理"不确定"，确定的东西用规则判，别让模型去猜。**
- 内容兜底的 0.65 是另一条真实取舍：0.70 只接住 50% 的题但接住的都对；0.65 接住 86%，代价是 14% 可能分给一份相近文档。我选 0.65，理由有二：口语化提问是真实用户的主要问法，不能大半挡在检索门外；而分错文档时的兜底是**检索仍按内容排序**，相近文档的块只会排后面，不会直接毁掉答案。
- Tavily 的 score > 0.5（严格大于、0.5 整被滤掉）这种边界我写的是回归用例——阈值本身是经验值，但**边界行为必须被钉住**，否则哪次重构就漂了。

**三、性能 / 成本参数：靠微基准和逐节点耗时反解。**
- **精排窗口 1024 / 2048**：先是发现旧窗口 512 导致 67% 的候选被压缩，为此还加了一次 LLM 压缩——而压缩稿和评测标注的原文对不上、每次跑还不一样，等于把不确定性引进了打分。于是把窗口开到 2048 去掉压缩环。档位分两档是因为 attention 是平方复杂度：按**批内最长候选**向上取档，短批不用按 2048 pad。三处上限（最高档 == 配置上限 == 模型加载的 max_length）必须对齐，否则"压到 A 却被模型按 B 截掉"，这个有断言用例钉着。
- **embedding batch=5、历史 10 条、主体识别取前 5 chunk / 2000 字、改写 ≤100 字、HyDE ≤300 字**：这一族全是"够用就好 + 防稀释"——判据是别让历史 / 上下文稀释当前问题与规则。主体识别只用文档开头是因为**判定主体不需要读完全文**，多读只增加 token 和噪声。

**四、真扫参的只有少数几个，但扫的纪律比数字值钱。** 真正做了对照扫描的是**交付条数**和**文档标题片折扣**：
- **交付条数 top-1**：同一排序上截前 k 条，1 条 0.922/0.870、2 条 0.507/0.916、3 条 0.342/0.928，并算了一条"第 k 条真是答案的概率"（第 2 条约 1/3、第 3 条约 1/6）。结论：多带一条只换回约 5 个点召回，精确砍半，所以交付收敛到 1 条。
- **文档标题片折扣 0.7 → 1.0**：0.7 是上一版语料（4 份项目说明文档）扫出来的，换 15 篇法规语料后**重扫发现打折反而有害**（0.870/0.818 对 0.922/0.870），改回 1.0。这条我总结成一句话：**参数跟着语料走，换语料必须重扫——这比任何单个取值都重要。**

扫描本身有三条纪律，不然数字不可信：
1. **一次只动一个变量，并且冻住随机源**：HyDE 那一路的 LLM 生成逐题冻结重放（存的是它真实生成的那一次，题目改了自动判失效）。不冻的话同一题两次跑候选池都不同，两臂之差就归因不到精排头上。
2. **两臂各跑两趟，先看臂内极差再看两臂之差**：差必须明显大于臂内极差才算数。我这边实测两趟**逐位相同**，说明链路里已经没有随机源（embedding、Milvus、rerank 都是确定性的），所以差是干净的。反过来说，"极差为 0"我从不读成"系统很稳"，那只是当前采样设置的产物。
3. **口径随数字走**：报告里写死语料版本、K 值（MRR@K 的 K 跟着交付条数走）、冻结方式。跨题库的数字我从不直接比——这份基线之前的每一轮都因语料或分块变更作废过。

**五、两条收尾的工程习惯。**
- **机制和档位分离**：融合旋钮（`RERANK_FUSION_ALPHA`，0=纯精排、1=纯 RRF）、精排开关（`ENABLE_RERANK`）、标题片系数，我都是**保留结构、只调档位**，不把没选中的那一支删掉。因为分块质量一改，结论可能反转，留着才能重测——精排开关的注释里就写着这句话。
- **测试钉机制，不钉实时值**：融合 / 断崖那几个用例用 autouse fixture 把参数钉死，否则我一改线上配置，用例就跟着挂——那是被调参绑架的测试，不是回归。

一句话总结：**结构性参数靠职责推，经验阈值先看分布、分不开就换机制，性能参数靠基准反解，能扫的少数几个按"冻结随机源 + 臂内极差 + 口径随行"的纪律扫；而所有参数都留在配置里，因为它们只对当前语料最优。**

### Q5 调参过程中遇到的问题与取舍

**面试官**：你在测试运行调参数的过程中，有遇到什么问题，你都是怎么解决或者取舍的。

**我**：调参过程中真正花时间的，很少是"参数本身该取几"，而是**尺子不准、或者改了参数行为悄悄坏掉**。我按问题类型讲，每类挑一个最典型的。

**一、最贵的一类：尺子本身是错的 —— 先修度量，再谈调参。**

**实例：评测把答案喂给了被测环节。** 早期评测跑主体识别时，我把题库里的 `expected_item_names` 直接注入了 state，于是那一层**根本没跑**，报告里"主体命中率 1.0"是构造出来的数。照这个数字去调阈值，调的全是空气。后来改成只给原始问题、走真实链路，认不出就如实记全 0。

**取舍是要认账的**：改完数字从 1.0 掉到真实的 0.9259，报表变难看了，一度还暴露了"79 道题里 57 道卡在主体识别"这种难看的现实。但只有真数字才能指导优化——也正是那次难看，才有了后面的简称归一化 + 内容兜底，把入口通过率从 29/79 提到 68/79。我的原则是：**指标异常好看时，第一反应是查尺子，而不是庆祝。**

同一类里还有个更隐蔽的：HyDE 的 LLM 生成我做冻结重放时，抓取那一趟那个函数名正被 patch 成"回调本模块"，如果按名字去模块上取函数就会自己调自己（实测 RecursionError），而这异常被这一路的失败隔离**吞掉**，表现为静默降级成空召回——没有报错，只是数字悄悄变差。修法是 import 期先把真实函数引用拿住，并放一个"被按名字取到就露馅"的假函数钉在用例里。**这条教训是：降级必须配 `exc_info=True` 的 error 日志，否则"降级"和"真的没内容"从日志上分不开。**

**二、第二类：阈值承担了它承担不了的判断 —— 换机制，不是调数值。**

调主体确认阈值时发现的：库里是「中华人民共和国数据安全法」，用户说「数据安全法」，相似度 **0.701**；而**错误候选能到 0.68**——正负样本间隔不到 0.02，我把阈值在 0.65~0.72 之间怎么挪都有一边要错。这时正确的动作不是继续扫参，而是判断"**这个判断本身就不该交给相似度**"：差一个前缀是**确定的事实**，交给规则；相似度只用来分辨真正不同的文档。

同类的还有两处：**必命中率**原来算"命中数/标注数"，结果同一条链路标 1 条时 1.0、标 3 条时 0.33——数字随标注习惯变、不可比，改成门槛口径（捞到任意一条即过），没标注的题记 null 出分母；**交付条数**从"断崖动态决定"改成量出来的 top-1（1 条 0.922/0.870 vs 2 条 0.507/0.916）。

**三、第三类：改了参数，行为悄悄坏掉（没有异常的那种）。** 这类是调参最耗时的部分，因为它们**不报错，只是结果失真**：
- **护栏的 LIMIT 最初用外层派生表包裹**，结果把两表同名列的合法 JOIN 变成 1060 语法错——我本来只是想加个上限，却把"能跑的 SQL"改成"跑不了"，这个代价比没有上限大得多。改成文本层只改数字。
- 补的 LIMIT 贴在同一行，被行尾 `-- 注释` 一起注释掉，等于没加 → 必须另起一行。
- 掩码（屏蔽字面量 / 注释）只能用于**扫描**，我一度拿掩码后的文本去拼要执行的 SQL，`WHERE province = '广东省'` 的取值被抹成空白，"成功执行但语义变了"——这个是题库自检当场抓出 12 道题的。
- 分块器两个真 bug 同源：`parent_title` 补齐排在合并之后（判据恒为 None，**合并从来没生效过**）；分隔符列表少了末尾的 `""` 兜底（无分隔符文本整段返回，实测产物里有 793/1403 字符的块）。

**共同解法是同一套**：给产物做"体检"（把 chunks 备份成 JSON 看块长分布、找 HTML 残渣、数碎块占比），再用回归用例把判据钉死——比如用 spy 断言"进合并前每块都有 parent_title"，用 `'x'*1400` 断言不会整段返回。

**四、第四类：成本和收益的账 —— 量清楚，然后如实取舍。**

**精排**：消融数据是净赚 2.4 个点，代价是每题多花 18 秒（P50 21.4s vs 3.3s）。我没有据此删掉精排，因为离线批处理和在线问答的账不一样。**更值钱的是顺着这条线查清了线上首字延迟 51 秒的根因**：不是检索、不是作答，是我把联网结果也放进了精排池——池子从 10 条涨到 10+N，联网文档更长还把窗口档位顶到高档，同一趟精排 P50 到了 50.3 秒。

**取舍我做得比较克制**：只把线索如实记进文档（联网要么不进精排、要么先按自己的分数截一道），**没有顺手改**——因为动它得先补一条"联网进池值不值"的对照实验，跟精排开关一套做法。先改代码后补证据，是最容易把结论做反的。

**LLM 预算**这条更典型：跑批 117 次里 2 次 240 秒超时，日志显示两条都没打出来、请求一直在飞——根因是 SDK 默认读超时 600 秒，等于**没有预算**。修法不是把跑批超时从 240 调大（那只是把问题藏起来），而是给调用立预算（60s + 只重瞬态的重试），顺带把整套执行护栏立起来。复跑时用 `--merge-into` 只把那 2 题并回基线，**其余 37 题不重掷**——否则基线就不是"只改该改的地方"了。

**五、第五类：测量方法自己被干扰。**

**优化召回节点的并发时差点被 LLM 抖动骗了**：如果按"整节点耗时"做前后对照，那次关键词扩展调用正常 1.5~5 秒、上游偶发挂起能飙到 20 秒以上，几百毫秒的优化会被完全淹没；更糟的是两趟输入本来不同（词表都是现生成的），摆在一起甚至能得出反向结论——真被这么读过一次，那份报告已经移出仓库了。修法是**冻结关键词扩展结果重放**，只量"嵌入 + 检索"，真 LLM 那一档保留但报告里写明"不能做 A/B"。

还有一条纪律是**先看结果有没有被换掉，再看省了多少**：优化后 117 组召回 id 集合全部一致，才敢说"P50 降 37%~55%"是优化而不是改坏。

最后一个是心态上的取舍：**"臂内极差为 0"我从不读成"系统很稳"**——那只是 temperature=0 的产物，是"当前离线没有随机源"的证明，不是稳定性的证明。所以我也不引 LLM-as-judge 进判据（它会把非确定性重新引回来，"这次比上次好"就不可复现），生成质量宁可落盘报告加人工判读。

**如果只留一条经验**：调参出问题时，我按"**尺子 → 机制 → 数值**"的顺序怀疑——先查度量本身对不对，再查这个判断该不该由这个参数承担，最后才是调数值。这个顺序我在这个项目里验证过太多次了。

### Q6 rag_text2sql 的节点划分与召回/精确设计

**面试官**：rag_text2sql 中具体分为哪些节点，每个节点具体是什么作用，按顺序、分点、简单精炼的概括一下；然后再详细讲解每个节点分别怎么保证最终的召回率 / 精确率。

**我**：rag_text2sql 是**单图 12 个节点 / 9 个逻辑阶段**：关键词 → 三路召回（列/指标/取值）→ 合并补齐 → 过滤（表 / 指标）→ 补上下文 → 生成 → 校验 → 校正 → 执行。先给节点表，再逐节点讲它守的是召回还是精确。

#### 一、节点一览（按执行顺序）

| 顺序 | 节点 | 作用 |
|---|---|---|
| 1 | `extract_keywords` | jieba 关键词抽取（topK=20 + 词性白名单），并把**完整问题**也并入关键词，避免分词丢语义 |
| 2 | `recall_column` | 列召回：LLM 扩展"列级业务字段名" → 批量嵌入 → Qdrant 列集合检索（阈值 0.6），按业务 id 去重 |
| 3 | `recall_metric` | 指标召回：LLM 扩展度量概念与同义词（成交额≈GMV）→ Qdrant 指标集合检索（阈值 0.7） |
| 4 | `recall_value` | 取值召回：LLM 扩展取值候选 → ES 对 value 字段做 ik 分词 match，按文档 id 去重 |
| 5 | `merge_retrieve` | 合并三路并补齐：指标→关联列、取值→所属列（值还回填进列的 examples）、每张表补主外键，组装「表→字段」树与指标 |
| 6 | `filter_table` | LLM 只在候选范围内裁剪表与字段（输出 JSON），代码按结果双向裁剪 |
| 7 | `filter_metric` | LLM 裁剪指标，**允许返回空**（没度量诉求就不选） |
| 8 | `pad_context` | 注入当前日期 / 星期 / 季度 + dw 库版本与方言 |
| 9 | `generate_sql` | 基于召回 schema 生成 SQL（约束：只用真实字段 / 只读 / 单条 / 无 markdown 围栏） |
| 10 | `validate_sql` | **真实执行一次**校验（不取结果），失败写 `error` → 条件路由 |
| 11 | `correct_sql` | 错误驱动的最小修复（带错误原文 + 原 SQL + 全部上下文） |
| 12 | `execute_sql` | 执行并 SSE 推 `{"result": [...]}`；失败必须推 error 事件 |

结构上两个要点：**2/3/4 是三条并行边**，都汇到 5；**6/7 也是并行**，都汇到 8；`validate_sql` 是唯一有条件路由的节点（通过 → 执行，失败 → 校正，校正后直接执行，**只有一轮**）。

#### 二、逐节点：守召回还是守精确

**① `extract_keywords` — 守召回的第一道**
- 保召回：词性白名单（名词/地名/机构/专有名词/动名词/英文等）保证抽出的是有信息量的词；最关键的一条是**把完整问题也塞进关键词列表**——分词一定会丢语义（"统计华北地区的销售总额"被切开后，整体表达就没了），用原始 query 托底。
- 保精确：白名单本身是剪枝，把无意义的虚词挡在检索之外。
- 如实说的缺口：白名单里没有时间词 / 数词词性，"最近三个月""去年"容易丢——目前靠"完整 query 并入"缓解。它是确定性的（无模型），所以做延迟 A/B 时不用冻它——**冻结只针对那几处真 LLM 调用**。

**② `recall_column` — 召回的主力，精确靠去重**
- 保召回：LLM 做的是"Schema 推断"而不是同义词改写——问题带时间/人群/状态语义，就必须补出对应字段名，把口语翻译成业务字段语；然后每个关键词向量化检索（阈值 0.6，默认 top10）。
- 保精确：这个集合里**一个字段被建了多个向量点**（name / description / 每条 alias 各一个，payload 相同、id 随机），所以同一字段会被多次命中——按业务 id 去重、"先到先得"。
- **性能与正确性的取舍**：C18 从"逐关键词串行"改成一次批量嵌入 + 带上限并发，P50 −37%；判据是**召回 id 集合 117 组全一致**（快了但结果被换掉，那是改坏）。顺序必须保持，因为顺序决定"同一字段被多个关键词命中时留哪一份"。
- 阈值取 0.6 偏宽是有意的：**后面还有 LLM 过滤当闸门**，这里宁多勿漏——两层分工，不该在召回层就把阈值卡死。

**③ `recall_metric` — 口径的守门人**
- 保召回：同一套扩展手法，补的是"度量目标 + 同义词"（问"成交额"要能命中 GMV）。
- 保精确：阈值**比列路更严（0.7）**——指标是"口径"，误召回会把错的计算口径带进 SQL，代价比多召一列大得多；而指标描述文本短、更容易虚高命中，所以两路阈值分开定。
- 两个踩过的坑：一是指标库本身只有 2 个（GMV/AOV），"卖了多少台"这类问题**召不到指标不是阈值问题、是知识覆盖问题**；二是 AOV 的 `relevant_columns` 曾误声明成 `order_quantity`（与它自己"平均订单金额"的描述不符），修正后必须**重建索引**才生效——声明和描述打架会直接误导后续补齐。

**④ `recall_value` — 补"字面枚举"这一路**
- 保召回：它解决的是列向量天生的盲区——列描述里不会有 "iphone" 这种具体值，但用户的问法往往就是。所以取值单独建 ES 索引（`sync: true` 的维度列全量 distinct 值，ik_max_word），LLM 扩展出取值候选后直接 match。
- 保精确：按文档体里的 `id` 去重（ES 侧刻意不传 `_id`，让 ES 自动生成，去重靠业务字段）。
- **性能**：这一路没有嵌入（ES 直接吃关键词），C18 只把逐关键词的 await 换成带上限并发，P50 −55%（22ms → 10ms）——**它是三路里最快的，因为省掉了嵌入那一大块**。

**⑤ `merge_retrieve` — 一个纯"防漏"的节点**
- 保召回（这一层几乎全在补召回）：① **指标 → 关联列**：召回到的指标，其 `relevant_columns` 里没被召回就按 id 回 meta 库补——缺了指标计算列，SQL 就是"无米下锅"；② **取值 → 所属列**：命中了取值但列没被召回，补列，并把该值**追加进列的 examples**，给生成阶段更多线索；③ **每张涉及的表补主外键**：这是跨表 JOIN 能成立的前提。
- 顺序上有个真 bug（已修 + 有回归用例）：补列必须排在"examples 回填"**之前**——回填要读 `map[col_id]`，而补进来的字段此刻才进 map；顺序反了这条兜底**写了从未生效过**（一走就 KeyError，日志里 0 次失败恰恰是"根本没走到"的证据）。
- 它同时是评估上的基准点：报告里的「召回@merge」这一行读的就是这里的候选集，和"过滤后"一比，就知道列是丢在召回还是丢在过滤。

**⑥ `filter_table` — 精确的主力，也是召回最容易被误伤的地方**
- 保精确：prompt 立了几条硬规则——只能从候选中选（禁新增、禁改名）、每张选中的表至少留一个字段、字段的取舍唯一标准是"本次查询**实际用到**"、明显不用的必须剔除；代码拿到 JSON 后**双向裁剪**。
- 保召回：规则里反向保住了三类"容易被模型顺手删掉、但删了就答不出"的字段——时间/人群/状态这类语义字段、用于消歧的字段（禁止留给后续阶段补救）、**与业务相关的主外键**（同时要求与业务无关的主外键必须去掉，防止无脑全留）。
- 实测结论（这条我很想讲）：时间类题的表必命中率只有 20%/25%，我排查下来**不是召回失败**——merge 阶段 dim_date 的召回率是 79%/73%，是过滤把它裁掉、系统改走 `fact_order.date_id` 直接取范围（dim_date 缺 12/15 次，但最终 SQL **0 次**引用它）。这两条题我用了两种独立证据确认两种写法结果一致（EEX 直比结果集 + 不经过任何节点的独立口径 SQL 手工复核）。**这里的取舍是：我没有为了把表必命中率刷好看去改过滤规则**，而是把这个"策略差异"如实写进了报告和口径说明。
- 如实说的缺口：过滤结果与关键词 / 合并结果之间**没有交叉校验回退**，理论上模型可能删掉必需列或编造字段（生成 prompt 里禁止但代码没回检）；过滤前也缺一道"规则保底剪枝"。

**⑦ `filter_metric` — 允许留空的裁剪**
- 保精确：只保留真正有度量诉求的指标，**允许返回 `[]`**——这条比看上去重要：题库里有一类"无指标列表题"（纯筛选列表，不需要任何聚合），如果被迫带一个指标下去，生成的口径就会被带偏。
- 它与 `filter_table` 并行跑、各自只动自己那半份状态（一个裁表/列、一个裁指标），互不干扰。

**⑧ `pad_context` — 让时间基准存在**
- **间接保召回 / 精确**：至少把"今天是什么日期、哪个季度、dw 是什么版本方言"注入生成 prompt——没有它，"今年""上个月"连换算基准都没有；方言注入是防模型写出方言不支持的语法。
- 如实说的缺口：相对时间（去年/最近三个月）**没有显式解析节点**，时间语义是裸交给 LLM 的，dim_date 与事实表的关联方式也没显式注入——所以时间类题的"走哪条关联路径"是模型自由选择的结果，这是我最想补的一个节点。

**⑨ `generate_sql` — 精确靠约束，不靠运气**
- 保精确：六条硬约束写进 prompt——只能用候选里真实存在的表和字段、有指标定义就严格遵循口径不得重解释、只读、语法必须符合指定方言与版本、默认单条 SQL、输出纯文本（禁 markdown 围栏，围栏会污染后续校验和展示）。
- 上下文全部用 yaml 结构化注入（表/字段/指标/日期/方言）——对模型好对齐，对我好人工核对。
- 需要点明的因果：生成阶段出现"编造字段"，根因通常在**过滤/合并那一层**（该给的列没给到位），不是生成本身的错。所以我把"过滤输出与召回结果交叉校验"列为改进项，而不是继续加 prompt 禁令。

**⑩ `validate_sql` — 用"真跑一遍"换确定性**
- 保精确 + 保安全：它做的不是语法检查而是**真实执行一次**——只有执行过才能确认方言、函数、字段名真的存在；执行前先过护栏（只读白名单 + LIMIT 收敛），被拒的理由是可操作文本、回填给校正节点。
- 失败处理：异常原文透传进 `error`（不包装成"执行失败"四个字），条件路由据此分流。
- 如实说的边界：校验只查"能不能执行"，**不查语义**（丢了 WHERE、忘了 GROUP BY 照样通过）——所以 L2 可执行率不等于正确率，这一点我写在报告里，并且没引 LLM-as-judge 去补。

**⑪ `correct_sql` — 一轮修复，且有约束**
- 保精确：错误驱动的最小修复——注入错误原文、原 SQL、全部上下文，prompt 强制**保持原业务语义与结构稳定**，防"越修越错"（把 JOIN 改掉、把聚合口径换掉那种）。
- 和护栏的配合值得讲：护栏的拒绝理由我特意写成了给模型看的可操作文本（"只允许单条 SELECT/WITH，当前以 DROP 开头，请改成…"），于是**护栏既拦住了危险，又成了校正的输入**，而不是把整图变成失败。
- 如实说的缺口：只有一轮、无循环上限与兜底；除零类运行时错误目前靠模型自觉，没在 prompt 里强制 NULLIF。

**⑫ `execute_sql` — 交付，且失败必须说话**
- 保精确（交付层）：执行结果以行列表推送、前端渲染表格；执行同样过护栏。
- 一条被修过的真问题：这个节点是**链路终点**，失败时如果不推 error 事件，前端既收不到 `result` 也收不到 `error`，最后一个步骤永远停在 running——用户看到的是"一直转圈"而不是"失败了"。修完有专门的回归用例钉着（成功推 result、失败推 error、错误原文透传）。
- 与评估解耦：跑批器判 EX 是**自己重跑一遍最终 SQL**，不复用图内那次的执行结果——判据只有一条"能不能跑通"，两边互不污染。

#### 三、横切的设计（回答"整体怎么保证"）

1. **三级索引决定召回上限**：列的 name/description/alias 多向量点（同一字段多点命中 → 召回率天然更高）、取值入 ES（补字面枚举）、指标入库（补口径）。
2. **阈值两路分工**：列宽（0.6，后面有 LLM 过滤当闸门）、指标严（0.7，口径错代价大）——这是"两层分工"的思路，不在单层求最优。
3. **召回宽、过滤严、生成受约束**：整个漏斗的方向是"前面宁多勿漏、后面宁缺勿滥"，并且中间那一层（过滤）不做"兜底保留"。
4. **评估上能定位**：L1 读的是**过滤后的候选集**（不是最终 SQL），外加一行"召回@merge"做诊断——"列是丢在召回还是丢在过滤"这个问题，报告里两行一比就有答案。

### Q7 rag_knowledge 没设计好的地方与改进方向

**面试官**：你觉得 rag_knowledge 中，你有哪些没有设计好的，或者可以改进的点，说说你的想法。

**我**：分四类说，因为"没设计好"和"没做完"和"刻意不做"是三种性质，我不想混为一谈。

#### 一、真正该算设计缺陷的（三处，我认）

**1）精排池没有准入策略——这是我认为最该改的一处。**
根因很具体：我把联网结果直接并进了精排池（`_merge_rrf_and_web`），而精排的窗口档位是**按整批最长候选向上取**的。后果是双重的：池子从 10 条涨到 10+N，而且联网文档更长，把整批顶到高档位。实测线上 rerank P50 = 50.3 秒、TTFT P50 = 51.5 秒——**用户等的 51 秒里，绝大部分是"精排在给不相干的联网结果打分"**，这两条数字已经查清、也写进文档了，但优化我没动手。
为什么没动手我要说清楚：动它得先补一条"联网结果进精排池值不值"的对照实验（跟精排开/关那套同样做法），否则改完是好是坏没有证据。**先改代码后补证据，是我在这个项目里最不想犯的错。**
改法两条路：联网结果不进精排、或者进池前先按它自己的分数截一道。另外"窗口档位全批共享"这件事本身也值得改——一条长文档拖慢一整批，可以按长度分桶打分。

**2）入口节点没有失败兜底，这是我 C02 修漏的一处，而且不对称得很刺眼。**
三路召回（`_09_1/2/3`）我都套了失败隔离：单路异常降级成"这一路没贡献"，不拖累别人、不 500。但**最上游的 `_08 主体确认节点自己没有这层保护**——它的 LLM 改写 + 主体提取是 JSON 模式解析，解析失败直接抛异常，整图失败。也就是说：越靠上游、影响面越大的节点，我反而没给它兜底；而下游三条支路各自都有。这是设计上的不一致，不是遗漏细节。改法很便宜：改写 / 提取失败时降级——用原始问题当 `rewritten_query`、主体走内容兜底那条路继续，而不是整链断掉。

**3）参数全散在代码常量里，没有配置层。**
阈值、TopK、权重、窗口档位都是 `config.py` 里的模块级常量，改一个数要改代码 + 重启。副作用在测试里也能看到——我不得不写 autouse fixture 把常量钉死，否则"改线上配置会把测试改挂"。同一个仓库里 rag_text2sql 那边我用的是 OmegaConf + dataclass 的结构化配置，两边做法不一致，这是我的问题。当然这里有个真实的两难：这些参数**必须随语料重扫**（标题片折扣从 0.7 改成 1.0 就是例子），所以它们要"可调"，但每次调都必须配一次评估——配置层应该设计成"参数 + 语料版本号 + 上次评估报告"绑在一起，光加个 yaml 是不够的。

#### 二、知道要做但没做完（欠交付）

**4）引用溯源差最后一公里。** 后端其实够了：命中块的 `title / parent_title / score / url` 都在，prompt 里也让模型输出 `[参考来源]` 区块；但前端按纯文本渲染，**链接不可点**，引用也没有结构化返回（没做成"答案里的第 3 句来自哪个 chunk"的高亮跳转）。可核验性是 RAG 最值钱的承诺之一，我这块只做了一半，是我最想补的"便宜大件"。

**5）候选主体（0.60~0.70）的交互闭环没有。** 后端逻辑都留了（`confirm` / `candidate` 两个列表、候选分支会输出候选名），前端没做"点击确认后二次检索"。结果是：**主体稍有犹豫就直接降级成"我没听懂"**，明明离答案只差用户点一下。这是产品级的半成品。

**6）增量索引与文档管理缺失。** 现在是全量重传、按 `file_title` 删旧插新；改一篇文档要重跑整篇，没有版本感知、没有上架/下架、解析走 BackgroundTasks 重启就丢。更实际的痛点是它连带出的：**chunk_id 是 Milvus 自增主键，一重切就全失效，题库必须重建**——我后来用"题库源存文本片段、id 现解析"绕开了人工重标，但绕开的是标注成本，不是重建成本。

**7）没有任何缓存。** 相同问题反复跑全套（含一次 LLM 改写 + 一次 HyDE 生成 + 精排）。模型加载做了单例，但问题级 / 答案级缓存没做。对一个"句子越短、成本越高"的链路，这一块空着挺浪费的。

#### 三、有意取舍，但我知道代价在哪

**8）生成质量完全不量化**（faithfulness / answer_relevancy 不做）。理由我说过：引 LLM-as-judge 会把非确定性带进判据。但我得承认代价——**检索指标好看不等于答案好用**，我现在只能靠报告 + 人工判读，出了"资料对、答得偏"的问题，我的评测体系接不住。

**9）HyDE 的假设答案是冻结的**——为了消融实验干净，我把那次采样的好坏一起固化了。这是"评测口径的取舍反噬到线上质量"的典型：如果 HyDE 那次生成质量差，我在报告里也看不出来，因为每次重放都是同一份。

**10）精确率只报最终层。** 前几层的分母是我自己设的召回池大小，报出来是"池子多大分之一"，没有信息量——所以我不报。但这等于**我在前几层没有可信的"准"读数**，要比较不同召回策略的"准不准"，得先设计一个非人为的分母口径，这件事我没做。

**11）几组权重是"按职责推的"，没扫过**：混合检索 0.7/0.3、RRF 0.5/0.5、主体名确认 0.4/0.6。我坚持"结构性参数靠职责推"的立场，但**主体名那一组值得扫**，因为它是全链路最大的瓶颈，0.4/0.6 是我拍的"短串靠字面"，没有分布证据。

#### 四、天花板，不是"没做好"，是要换方案

**12）多跳与跨文档对比是结构性弱项。** 纯向量 RAG 的答案必须落在某一条 chunk 里；题库里那 3 道多跳题、4 道跨文档题，架构上就支持不了。要解只有两条路：GraphRAG（实体关系 + 社区摘要，成本高）或多查询分解 + 逐子问题检索再合并。

**13）交付 top-1 对聚合类是"结构性伤害"。** 交付条数是我扫参扫出来的（法条答案基本落在单条条文里），但这个结论是**全局平均**——对多跳/跨文档题，答案天然散在多条。所以正确的形态不是"全局一个数"，而是**按题型分流**（这也正好接上我想补的意图路由节点）。把这两件事合起来看，我认为**下一个大版本的方向是"意图路由 + 按题型决定检索策略与交付条数"**，而不是继续在单链路上抠参数。

#### 如果只改三件

1. **精排池准入 + 窗口分桶**（救线上 51 秒延迟，且顺手可能提质量——因为不相干的联网结果本来就在抢名次）；
2. **入口节点补失败兜底**（不对称的脆弱点，改动最小、收益最直接）；
3. **引用结构化 + 前端可点**（把"可核验"这个承诺补齐，成本低）。

前两件是设计问题，第三件是完成度问题——**类别不同，但都指向同一件事：我在这条链路上"能跑通"已经做得比较透了，接下来该做的是"出错时怎么体面地退化"和"结果怎么让人核验"。**

### Q8 六项技术选型的理由

**面试官**：rag_knowledge 向量数据库为什么选 Milvus；为什么用 MongoDB 存储聊天记录（而不是其他数据库）；为什么嵌入模型选择 bge-m3 + 精排模型 bge-reranker-v2-m3；rag_text2sql 向量数据库为什么选 Qdrant；为什么用 ES 存储表的取值数据；为什么嵌入模型选择 bge-large-zh-v1.5。

**我**：六个问题我按「我的判据 → 为什么不选另一个 → 代价」这个统一格式答，因为它们其实共享同一条原则：**选型看的是"这一路检索的语义是什么"**，不是看库本身谁更强。

#### 一、rag_knowledge 为什么用 Milvus

**判据：它一次调用就能满足我这三件刚需。** ① **稠密 + 稀疏双向量**：BGE-M3 一次编码就输出稠密和稀疏两路，我需要同时存、同时在一次检索里用；Milvus 原生支持 `SPARSE_FLOAT_VECTOR` + 倒排索引（我用 DAAT_MAXSCORE / IP），并且 `hybrid_search` 直接把两路的 ANN 请求 + `WeightedRanker(0.7, 0.3, norm_score=True)` 融合一起做完。② **标量过滤与向量检索同查询**：`expr="item_name in [...]"` 是硬过滤，必须"先过滤再取 top-k"，否则别的文档会把名额挤占掉——这是 pre-filter，不是查完再筛。③ **索引可选型**：稠密走 HNSW（M=64/efConstruction=100/COSINE，精度优先），稀疏走倒排，两个集合（chunks / item_name）用同一套模式。

**为什么不选别的**：Qdrant 现在也有稀疏向量和混合，pgvector 更省运维，但当时我要的是"混合检索开箱即用、不用自己拼双索引 + 自己写融合"，Milvus 这条路是现成的；而且它是生产向的（分布式、持久化、多种索引），我把它当"接得住更大语料"的选择。

**代价我要认**：① 部署最重（etcd/minio 那套依赖），而它一挂整条链路就停——这也是我"索引手工全量重建"痛点的直接来源；② 就我这个语料量（138 个 chunk）而言，它属于重炮打蚊子。所以如果重做，我会认真比一次 Qdrant。

#### 二、rag_knowledge 为什么用 MongoDB 存聊天记录

**判据：这份数据的形状和访问模式都指向文档库。** ① **形状是"每轮一条、结构还在长"**：`item_names`、`image_urls` 是数组，`rewritten_query` 是我后期加的字段——文档库加字段零迁移，关系库每加一列要写迁移。② **访问模式只有两种**：按 `session_id` 取最近 10 条、按 session 清空——一个 key 下的有序列表，不需要 join、不需要事务、不需要复杂查询。③ **对话历史是"记录"，要可查可审**（我有 history 的 GET/DELETE 接口），不是纯粹的瞬时状态。

**为什么不选别的**：Redis 更快、存"最近 N 条"天然合适，但它的定位是缓存，不适合当历史记录的唯一存储；MySQL 完全能做，但要为数组字段拆表或塞 JSON 列，加字段就得迁移，为一份对话历史不值当。

**代价我要认**：为它单引一个数据库，就是多一份运维和一份故障面——如果这是一个已经有 MySQL 的项目，我很可能直接加张表，不会为聊天记录引入新组件。另外现在历史只承担"短期记录 + 指代消解的原料"，没做摘要压缩，也没做长程记忆。

#### 三、rag_knowledge 为什么用 BGE-M3 + bge-reranker-v2-m3

**BGE-M3 的判据是"省一套东西、多一分能力"**：① 一次编码同出稠密 + 稀疏，我不用同时维护"embedding 模型 + BM25 分词器"，也不用担心两路的文本预处理不一致；② 它那路稀疏是**模型学出来的词权重**（SPLADE 思路），比传统 BM25 多一点语义泛化，但保留了字面命中的敏感度——这正是我的 `item_name` 那一路最需要的（短串、专有名词，我用 0.4/0.6 偏稀疏就是基于这个）；③ 中文与长输入都稳（8192 token），且模型原生 L2 归一化，稠密走 COSINE/IP 不会量级打架。

**精排选 v2-m3 的判据是"同族 + 我量过"**：与 embedding 同源同族，语义空间 / 训练语料一致，联调少踩坑；它是多语言 cross-encoder，中文长文本表现好；而最终定它的依据是**实测净赚 2.4 个点**——不是"它应该好"，是我扫过。

**代价我也量化了**：这套组合重。本地 CPU 上精排占整链路 85% 的时间（评测 15.8s/题，线上 50s）。所以我把两件事做成结构：窗口档位按批内最长自适应（1024/2048，attention 是平方复杂度）＋ `ENABLE_RERANK` 开关保留——**哪天换模型（蒸馏/量化/GPU），能立刻拿数字重谈这笔账**。另外 M3 本身还能出 ColBERT 多向量，我没启用：多向量会把索引体积和检索复杂度抬一个台阶，当前双路已经够用，这是有意识的"不用"而不是"不知道"。

#### 四、rag_text2sql 为什么用 Qdrant

**判据：这个项目要的是"轻 + 阈值 + payload 即业务对象"。** ① **轻**：元数据索引只有 24 个字段 ≈ 98 个向量点，单二进制起一个就完事，不需要 etcd/minio 那套——同一份仓库里两个项目用两个库，差别就来自"语料规模与检索复杂度差了一个数量级"。② **`score_threshold` 是内建能力**：我这两路（列 0.6 / 指标 0.7）就是"带阈值过滤的最近邻"，Qdrant 一次调用直接支持，Milvus 侧要自己后过滤。③ **payload 直接存业务结构**：整个 `ColumnInfoQdrant` 作为 payload，检索回来 `ColumnInfoQdrant(**point.payload)` 就是业务对象，省掉回查关系库那一步——我把它当"带语义索引的 KV 库"用。④ **重建成本极低**：98 个点先删后建是秒级，所以"改配置就重建索引"在我的链路里是廉价动作。

**为什么不选 Milvus**：这里**不需要**稀疏 / 混合（列名与指标名是短文本，稠密 + 阈值就够），也不需要分布式——Milvus 的部署成本对这份小索引是纯负担。

**诚实说一句**：这个项目的向量检索**没有做混合/稀疏**（我列在改进项里：列向量追加 examples 典型值 + BM25 稀疏双路）。这是"我没用"，不是"Qdrant 不能"。

#### 五、rag_text2sql 为什么用 ES 存字段取值

**判据：这一路要的是字面 / 分词命中，不是语义匹配。** 取值是**枚举与实体**（省份、品牌、类别、客户名），用户说的是"华北""华为""iphone"。这类数据的正确答案是**精确或分词命中**，用向量反而会引入"语义相近但取值不同"的误召回——"江苏/江西"、"华为/荣耀"在向量空间里都很近，但在 WHERE 条件里是**互斥的取值**。枚举数据用倒排索引是最自然的形态。

② **中文分词粒度**：中文枚举值没有空格，"华北地区"要能被"华北"命中，就必须有中文分词器，`ik_max_word` 给最细粒度，插件生态成熟。③ **量级匹配**：全量 distinct 值（上限 10 万）正是倒排索引的主场，term 查是毫秒级。④ **语义角色**：它命中之后由 merge 补列、最终变成 SQL 里的过滤条件——它的用途是"筛"，不是"排相关"。

**为什么不选别的**：MySQL 的 `LIKE '%关键词%'` 在 10 万取值上无法用索引、只能全表扫，而且不能分词；MySQL 的 ngram 全文索引理论可行，但 parser 配置与中文效果都不如 ik。

**要认的两点**：① mapping 里只有 `value` 是 text，检索只做 `match: {value: ...}`，**没做 `multi_match` + `column_name` boost**，一个取值出现在多列时会全召回，靠后面的合并和 LLM 过滤去筛；② ES 侧我刻意不传 `_id`（让 ES 自动生成），去重靠文档体的业务 id——代价是重建只能"先删索引再建"（全量重建），换来的是不会因为 id 冲突静默覆盖。

#### 六、rag_text2sql 为什么用 bge-large-zh-v1.5

**判据：任务是"纯中文短文本"，而且它是被调用最频繁的组件。** ① 索引和查询都是**短中文短语**（列名/描述/别名、指标名、口语化关键词），bge-large-zh 是中文单语模型，在这个形态上是当时最稳的开源选择之一，1024 维够表达。② **不需要多语言**——没有跨语言需求，选多语言模型（比如 M3 那种体量）是纯浪费：这一路"每个关键词一次嵌入 + 一批关键词并发嵌入"，是整条链路里调用最频繁的一环，**轻**就是它的核心指标。③ 我也**不需要它出稀疏向量**（取值走 ES，列/指标是短文本），所以更没必要上 M3。④ 它 CPU 上跑得动、批量收益明显（微基准：1 条 110ms / 8 条 336ms，逐条 4 次要 504ms）——这是 C18"批量嵌入 + 带上限并发"能成立的前提。

**代价与前提**：阈值（0.6/0.7）是**在这个模型的分数分布上调出来的**，换模型必须重扫阈值——这是绑定关系。而且如果哪天要做混合检索，就得换能出稀疏的模型或者外挂 BM25，那时这个选型会被重新考虑。

另外一个踩过的坑值得提：本地服务是"OpenAI 兼容"但不是真 OpenAI——TEI 不接受 tiktoken 的 token ID，所以 `check_embedding_ctx_length` 必须关掉走原始文本。**兼容接口不等于等价语义，参数要对齐。**

#### 一句话收束

六个选型如果要归到一条原则上：**先问"这一路检索的语义是什么"，再选组件**——要混合与过滤的走 Milvus + M3，要短中文语义索引的走 Qdrant + bge-large-zh，要字面枚举的走 ES，要"每轮一条、结构会长"的记录就走文档库。反过来，我每个选型都能说出**代价**在哪，这也是我不敢说"选得都对"的原因：Milvus 的重、Mongo 多引一个组件、reranker 的 18 秒、bge-large-zh 换模型就要重扫阈值——这些都是账，只是我算过之后决定付。

### Q9 选型理由精简版

**面试官**：简短概括一下，不需要说的这么详细。

**我**：好，六个问题各两三句：

1. **rag_knowledge 用 Milvus**：要的是"稠密+稀疏混合检索 + 标量过滤"一次调用做完（`hybrid_search` + `WeightedRanker` + `expr` 硬过滤），BGE-M3 的双向量能直接存、直接检。代价是部署最重，语料量小的话属于重炮打蚊子。
2. **rag_knowledge 用 MongoDB 存聊天**：这份数据是"每轮一条、字段还在长"（item_names / image_urls 都是数组），访问只有"按 session 取最近 10 条 / 清空"两种。文档库加字段零迁移；Redis 定位是缓存不适合当记录，MySQL 要为数组拆表或迁移，为一份历史不值当。
3. **用 BGE-M3 + bge-reranker-v2-m3**：M3 一次编码同出稠密+稀疏，我不用再单独维护一套 BM25，且稀疏那路对专有名词 / 短串敏感——正好是主体名那一路要的。精排选同族多语言的 v2-m3，最终定它是**实测净赚 2.4 个点**。代价是重：精排占链路 85% 时间，所以窗口档位自适应 + 保留开关。
4. **rag_text2sql 用 Qdrant**：索引极小（24 字段 ≈ 98 个向量点）、要"带阈值过滤的最近邻"、payload 直接存业务对象检索回来就是结构体，单二进制零依赖。这里不需要稀疏/混合，Milvus 那套部署是纯负担。
5. **用 ES 存字段取值**：取值是**枚举**（省份、品牌），要的是字面/分词命中而不是语义——"江苏/江西"向量上极近但在 WHERE 里互斥。ik_max_word 解决中文粒度，10 万级取值正是倒排索引主场。
6. **用 bge-large-zh-v1.5**：纯中文短文本任务，不需要多语言、也不需要它出稀疏，那就要"轻"——这一路是调用最频繁的组件，CPU 跑得动、批量收益明显（8 条 336ms vs 逐条 4 条 504ms）。前提是阈值 0.6/0.7 绑在这个模型上，换模型必须重扫。

**一句话共性**：先看这一路检索的语义（混合 / 语义 / 字面 / 记录），再选组件；两个项目用两套库不是随手，是因为元数据规模差了一个数量级。
