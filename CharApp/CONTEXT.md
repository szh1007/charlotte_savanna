# CharApp — 电商智能客服

基于 `CharAgent` 通用 agent 框架构建的业务应用集合。当前只有一个上下文 `minimall` (包 `CharApp/minimall/`), 对接 `app/minimall` 的商城数据。

## Language

### 售后域（AfterSale）

**退款（Refund）**：
钱退回买家，不涉及货物寄回。`RefundRequest` 只表达退款。
**是否回滚库存以发货为界**：货还没出去就回滚，出去了就不回滚 —— 与走取消还是走退款无关。
_Avoid_：售后、退货 —— 三者含义不同，不可互换

**退货退款（Return & Refund）**：
货物寄回并经卖家签收后，钱才退回买家。需要退货地址、承运商、物流单号。
_Avoid_：退款 —— 本项目未实现退货退款，且 minimall 无任何物流字段

**售后（AfterSale）**：
退款、退货退款、换货、维修的上位概念。
_Avoid_：客服、工单 —— 本项目只用它作域名词（命名空间），不建对应模型

**投诉（Complaint）**：
买家对商品或服务不满的表达，不涉及资金流转。
**不实施**（2026-09-21 决定）—— 保留此词只为消歧：它不是售后、也不是退款。
_Avoid_：售后 —— 投诉与退款无状态耦合，是两个独立模型

### 角色

**买家（Buyer）**：
持有 `django.contrib.auth.User` 的注册用户，通过 `Profile` 持有余额，是唯一能发起下单与退款的角色。
_Avoid_：用户、客户

**管理员（Staff）**：
`User.is_staff=True` 的账号，只能在 Django Admin 中操作（含审批退款、发货）。
_Avoid_：卖家、商家 —— **本项目不存在卖家角色**，不得假设其存在

### 交易

**余额（Balance）**：
`Profile.balance`，买家预存的可支付金额，注册时赠送 10000。支付与充值都只在此字段上增减。
_Avoid_：钱包、账户余额

**支付密码（Payment Password）**：
6 位数字，与登录密码分离，仅在支付与充值时校验。
**助手可以代付，但密码由用户本人在页面上输入**（2026-09-24 决定，**推翻** 2026-09-21 的「助手不代付」）。
当初那条的推理只对了一半：校验确实需要明文经手，但它与「身份不进工具参数表」**并不冲突** ——
密码走**一次性载荷**，与 `user_id` 完全同一条路，永不进模型看得见的任何地方（见 ADR-0015）。
_Avoid_：交易密码

**取消（Cancel）**：
买家单方终止订单。**只有未付款（`pending`）能取消**；付款之后一律走退款。
取消即刻生效、回滚库存。
_Avoid_：退款 —— 取消不需要审批，退款需要

**退款申请（RefundRequest）**：
买家对已支付订单发起的退款请求。状态机 `requested → approved → refunded`，或 `requested → rejected`。
**退多少由管理员在批准时定**（协商金额，不超过订单总额）；买家申请时不带金额。
同一订单同一时刻只允许一个进行中的申请；被驳回后可以再提。
**要不要回滚库存看申请时发没发货**（见「退款」词条）；退款流程进行中的订单不允许发货。
_Avoid_：退款单、售后单

**退款中（Refunding）**：
订单在退款流程进行中的状态。申请退款即进入，打款后变「已退款」，被驳回则**恢复申请前的状态**。
_Avoid_：申请中、处理中 —— 它描述的是**订单**的状态，不是退款申请的状态（后者叫 `requested`）

### 集成

**内部端点（Agent Endpoint）**：
`app/minimall/views_agent.py` 暴露给 CharApp 的粗粒度业务动作，以 `X-Internal-Token` 认证。
_Avoid_：管理 API、内部 API —— 它是「面向 agent 的业务动作」，不是用户面接口的镜像

**CharAgent**：
通用 agent 框架，对业务零知识 —— 不 import 任何 `CharApp` / Django / minimall 代码。
_Avoid_：把业务代码放进 CharAgent

**CharApp**：
基于 CharAgent 构建的业务应用。依赖方向严格单向 `CharApp → CharAgent`。

### 会话运行时（Chat Runtime）

**会话（Conversation）**：
一段连续的对话，也是数据隔离与快照分区的最小单位。
框架侧叫 `thread`（`thread_id`），业务侧叫 `conversation_id`，前端叫「对话框」—— 三处指的是同一个东西。
_Avoid_：进程、连接 —— 会话的生命周期与任何进程无关（进程重启后它还在）

**运行（Run）**：
会话里的一次问答：从一次提问，到一次答复终止。
**预算、护栏、成本都按运行算**（写操作上限、token 预算、耗时上限），所以「这一次」与「这一整段」要分清。
**挂起不算运行结束**（2026-09-24 补）：一次运行可以被**挂起**，等待期可能很长（几分钟到隔天），
而它仍然没有终止 —— 恢复沿用同一个运行编号（`loop_id` 与 `run_id` 都不变）。
所以**运行耗时与成本口径要排除挂起等待期**：`runs` 那一行的时间跨度会横跨它，
真实耗时按工具调用行的时间戳算。
_Avoid_：会话 —— 「会话级预算」与「运行级预算」不是同一件事

**用量（Usage）**：
一次运行消耗的 token 数：一个总量 + 五个分量（未命中缓存的输入 / 命中缓存的输入 /
输出 / 输出里的推理 / 其余）。
分量**全部可空**：没上报与「报了零」是两回事 —— 前者是「不知道」，后者是「确实是零」。
_Avoid_：花费、成本 —— 那是钱，见下条

**运行金额（Run Cost）**：
一次运行花了多少钱：**运行收尾那一刻**按当时那一版价目表算好，写死在运行行里，事后不重算。
`NULL` = 那一刻没算出来（原因记在明细里：没配价 / 缺哪一档 / 日历过期），`0` = 真的花了 0 元。
_Avoid_：用量 —— 一个是 token 数，一个是钱；换一版价目表金额不变（用量不变）

**峰价 / 谷价（Peak / Valley）**：
同一档 token 在两个时段的两套单价。判据是**运行的开始时刻**：落在供应商的忙碌时段
（工作日 9–12 与 14–18，按北京时间）算峰，其余算谷；工作日按中国日历 —— 法定节假日不算、
**调休上班的周末算**（2026-09-25 是周五休息日、2026-09-20 是周日工作日，都是真数据）。
_Avoid_：高峰（那是流量概念）；按运行结束时刻判 —— 跨过 12 点的那一趟整趟按开始时刻算

**价目表（Price Table）**：
部署侧给的「模型 → 单价」配置，默认空 —— 没配价就没有金额（**不是 0**）。
用两套价（峰谷）就必须同时给时区与峰时段：不给会拿一套默认规则静默算错钱，所以那里直接报错。
_Avoid_：把它当运行数据 —— 它是部署事实，随供应商调价而变

**快照（Checkpoint）**：
会话的**账本**：每一轮落一帧、只追加不改写，用来断点续跑与回溯。
它记的是**给模型看**的那份消息（含工具往返与推理链），不是给人看的。
**身份说明按引用记**（名字 + 正文哈希），正文的唯一定义在提示词文件里 —— 配置不逐帧抄。
_Avoid_：记录 —— 两者形状与用途都不同（见下条）

**记录（Transcript）**：
会话的**给人看的**版本：一条消息一行，每行标着要不要展示给前端。
**只有它永不压缩** —— 用户刷新后看到的、在左侧列表点开的那份，就是它。
_Avoid_：快照 —— 它是给模型的**全量账本**（只追加不改写），压缩动的是「上下文视图」，账本与记录两份都不动（见 ADR-0008）

**工具轨迹（Tool Call Trace）**：
一次运行里**每一次工具调用**的留痕，一次调用一行：工具名、模型填的参数、结果、耗时、状态。
（PLAN 与票据里也写「工具调用轨迹」，是同一件事 —— 本表这一个是权威写法。）
落 `charagent_tool_calls`，由记录层在执行前后各写一次（2026-09-25 落地，见 ADR-0016）。
**它与「记录」是两份**：记录是给人看的对话（说了什么），轨迹是给排查看的动作（做了什么、
成没成、花了多久）。**参数与结果保留原文**（订单号、地址、余额都进库）—— ADR-0003 那句
「原文不出本进程」管的是**展示层**（不进浏览器），存储层不留原文就查不了案。
**状态是一门状态机的取值**（`pending` / `succeeded` / `failed` / `needs_approval`），
L3b 的挂起态也落在这一行上（见「挂起」词条）。
_Avoid_：与「记录」混为一谈 —— 一个记「说了什么」，一个记「做了什么」
_Avoid_：把 `trace` 入口的输出当日志 —— 日志写完就打码，轨迹按 ADR-0016 留原文

**身份说明（Identity Prompt）**：
会话历史第 0 条 `role: system` 消息，说明「你是谁」—— 由提示词文件（一版一个文件）渲染而来。
**模型对自己的身份没有内省能力**，这条不给就会从语料里续写一个最像的，所以必须由会话给。
_Avoid_：系统提示词 —— 框架里「提示词」指文件本身（还有摘要指令、工具描述等），身份说明只是其中一份

**上下文视图（Context View）**：
这次运行**实际发给模型**的那份消息：身份说明 + 压缩摘要 + 最近若干轮完整对话。
它与账本（快照）**不是同一份**：越聊越短的是它，账本一直长。
**它的第 0 条就是账本的第 0 条**，所以「身份说明按引用记」这条规矩对两份都成立（记的是同一个引用）。
**压缩摘要（Summary）**：上下文视图里替代「更早那些轮」的那条消息，由模型自己生成、滚动更新。
**压缩降级（Compaction Fallback）**：摘要没能生成出来时，这一轮**不切刀** —— 一条消息都不丢，退到「只投影」。摘要失败不算压缩失败，只是「这一次压得不狠」。
**紧急压缩（Emergency Compaction）**：上游明确说输入超出窗口时才走的那一档 —— 不问阈值也不问水位线，裁到只剩最近一个提问。**它是整条链路上唯一「允许丢信息」的地方**：丢掉的段在账本里记成「有意放弃」。平时的压缩只丢「已经进过摘要」的那段。
_Avoid_：把上下文视图当成「历史」—— 用户看到的历史（记录）永远比它全
_Avoid_：把「压缩」一律读成「丢信息」—— 平时那道只丢已经压进摘要的，真正会丢的只有紧急那一档

**置顶（Pin）**：
用户把一段会话钉在列表最前，**最近钉的排在更前面**。
记的是**时刻**（`pinned_at`）不是布尔：布尔说不清「谁先钉的」，而排序要靠这个。
_Avoid_：把置顶当成"收藏"—— 它只影响列表顺序，不改会话本身任何东西

**删除（Delete，软删）**：
用户语义上的「删除」= **从我的列表里消失**；数据一条不动（行、消息、运行、快照都还在）。
**这是有意的**：运行表上挂着成本记账、快照里是「模型为什么忘了」的唯一线索，真删会把它们一起带走（外键 CASCADE）。
_Avoid_：把「删除」当成「数据没了」—— 库里查得到，只是不再列出来；真删是将来某个清理动作的事，本阶段不做

**会话搜索（Conversation Search）**：
在会话列表里按**标题**找一段对话：大小写不敏感，`%` 与 `_` 按字面当字符，只在当前
(租户, 买家) **还看得见**的会话里找（删掉的不算）。
**只搜标题，不搜消息正文**（2026-09-23 决定，见 ADR-0010）—— 搜出来的每一条，标题上
都看得见那个词。搜的是**完整标题**（上限 100），不是列表上截到 20 字那一行，所以
「搜到了、而那一行的可见部分里没有这个词」是正常的。
_Avoid_：消息搜索 —— 一个答「哪段对话」、一个答「哪句话」；把正文卷进会话搜索，就得
连相关性排序与命中位置一起做（否则顺序说不通），那是另一个量级的功能

**日志脱敏（Log Redaction）**：
日志**写出去之前**先把敏感值换成认不出来的样子（2026-09-25 落地，见 ADR-0019）。
**规矩是框架的**（手机号 11 位 / 邮箱 / 身份证 / 银行卡这四种形状跨业务），
**名单是业务的**（哪个字段算敏感只有本业务知道，写在 `minimall/log_redaction.py`）。
两半分开: 有结构的数据按**字段名**打（`redact_fields`），一整句话按**形状**认（`redact_text`）。
**打不出来的如实留着** —— 订单号那种「本项目自己发的编号」不猜（猜错了会误伤真数据），
未识别的自由文本逐字放过，不假装兜住了。
_Avoid_：与「事件脱敏」混为一谈（见下条）—— 一个整条不留，一个留下打码后的样子

**事件脱敏（Event Redaction）**：
工具事件的载荷在业务这一层**整条**换成人话（2026-09-21 起，ADR-0003）：参数原文与
返回正文一个字节都不进浏览器。管的是**展示层**；模型自己在答复或思维链里复述的值
不在此列（那是它的话）。
_Avoid_：与「日志脱敏」混为一谈 —— 那一条管的是**留痕**（日志 / 落盘），两条路各修各的

### 人工确认（HITL）

**挂起（Suspension）**：
一次运行**停在半路**：模型已经决定要调某个工具，但那个动作被认为需要用户本人确认，
于是**先不执行**，把当前进度连同那条欠着的调用一起存档，等人给结论。
**它是"等着别人给结论"，不是"当场有结论"** —— 后者叫**拒绝**（框架里是 `Decision.reject`，
工具不跑、原因当场作为失败文本回填给模型，模型立刻换个说法接着答）。
_Avoid_：拒绝 —— 两者的区别不在"允许不允许"，在"这个结论由谁、在哪一刻给"

**恢复（Resume）**：
用户给出结论后，从**存档点**接着跑 —— **只补做那条欠着的调用**，前面的轮次一步都不重跑。
**恢复沿用同一个运行编号**（`loop_id` 与 `run_id` 都不变），所以它是一次运行的第二段，
不是新的一次运行。
**拒绝也要恢复**：把拒绝原因当**工具结果**回填，模型据此继续 —— 这与"当场拒绝"是两条路，
别混。
_Avoid_：重跑、重试 —— 恢复靠存档，不靠重来

**确认人（Approver）**：
点下那个确认的人。本项目的两个场景里都是**买家本人**（代付与下单前确认），
而退款审批的审批人是**管理员** —— 那条走 Django Admin，**不经过挂起机制**（L2 已完成）。
_Avoid_：审批人 —— 本项目的「审批」只指"决定一笔退款"，与挂起不是同一条链

**一次性载荷（One-shot Payload）**：
恢复时才注入的一份数据，**只活这一次运行**，用完即弃。现在唯一的用途是**支付密码**。
它与 `user_id` 走完全同一条路（运行时载荷），因此**永不进模型的 wire schema、永不进消息、
永不进工具参数与结果的落库原文**（见 ADR-0015）。
_Avoid_：工具参数 —— 参数是**模型填的**且会落库，载荷是**运行时注入的**且不落库

**审批单（Approval）**：
**不建**（2026-09-24 决定，见 ADR-0014）。挂起的全部状态由「那次工具调用的一行」
（`status = needs_approval` + `approved_by` / `approved_at`）与快照里的挂起记录表达。
保留此词只为消歧：一次挂起**不是**一张有自己生命周期的单据 —— 没有审批单列表、
没有多级审批、没有审批意见。
_Avoid_：挂起 —— 一个是"要批的那件事"，一个是"这件事的状态"；本项目只有后者
