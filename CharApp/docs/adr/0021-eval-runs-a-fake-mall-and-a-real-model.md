# 评估打真模型、跑假商城、只走规则判；结局四种，其中三种不算数

**Status:** accepted（2026-09-29）

## 决定

L4 的评估（`CharApp/eval/`）建在四件东西上，每一件都对应一个**要量的变量**：

1. **打真模型**。`EvalSubject` 每一跑现造一个模型；跑分这条线上 `MockLLM` 只用来
   验装置（离线用例），不用来出数据。
2. **跑假商城**。商城那套内部端点由 respx 拦下来回样本（`eval/fixtures.py`），
   快照在内存、记录落内存假库 —— 跑分**不依赖 Django、不依赖 MySQL、不依赖 Redis**。
3. **判据只走规则**。那套判据（工具选择 / 参数 / 答复 / 回答合规 / markdown 强调 /
   护栏）都是纯函数，不引 LLM-judge；同一份事实喂两次结论一定一样。
4. **结局分档**：`COMPLETED`（跑完，进判据的分子分母）之外还有 `TRUNCATED` /
   `SUSPENDED` / `BROKEN` 三种 —— **它们如实计数、单独成列，但不进任何判据的分母**。

## 为什么需要它

**真模型**：L4 要回答的两个问题（「少给工具会不会选得更准」、「换一版提示词会不会更
合规」）都是**模型行为**的问题。MockLLM 是脚本化的 —— 你写什么它演什么，测不出这两件
事。所以非确定性不是一个要消除的噪声，它**就是被测对象**（对策是每题跑 3 次 + 报波动
极差，而不是换成假模型）。

**假商城**：真商城有三个问题。① **写操作真的改库** —— 同一道题跑第二遍时，购物车、
订单、余额都不是第一遍的样子，两组数据不可比（这是评估的地基，不是优化）。
② 每一跑都要一个起着的 Django + MySQL + Redis。③ 末了还得清库，而清库本身会出错。
假商城的代价是**样本可能与真契约漂开** —— 所以样本一律照 `serializers_agent.py` 抄
（金额是 2 位小数字符串、状态给 code + 中文 label），且 `tests/test_eval_fixtures.py`
守着「样本里的敏感值清单与 `log_redaction.LOG_FIELDS` 名字对得上」。

**规则判**：这次要证的两件事恰好都可规则化（工具选择读轨迹、输出合规搜文本），而
LLM-judge 会把一个非确定性的东西引进**判据**里 —— 那时「这次比上次好」这句话本身也
不可复现了。

**结局分档**：全挂那一组的前缀更长、更容易撞上 60k token 预算。把截断算成「答错」，
裁剪组的准确率会**虚高** —— 而那个差值来自前缀长度，不是选择能力。挂起与坏掉同理：
前者是「等人点头」（L3b 的确认链路），后者是装置的锅，都不该记在模型头上。

## 代价与边界

- **假商城不挡真模型这件事不是自明的，是修出来的**（issue 44 冒烟时真撞上过两次）：
  假商城拦的是 httpx 这条通道，模型的请求也走它。respx 默认拦在 **httpcore** 那一层，
  连**系统代理转发**一起接管 —— 本机走代理出网时地址被拼成 `Invalid port:
  '7890api.deepseek.com:443'`；改成 `using=「httpx」`（拦在 httpx 那一层）之后，没匹配上的
  请求才走**没被动过的真传输**。另外 `assert_all_mocked=False` **不是**放行（它对没匹
  配上的请求自动合成一个空的 200），放行要显式挂一条「把请求原样返回」的兜底路由
  （`fixtures.pass_through_the_rest`，注册在最后）。两处都在 `fixtures.py` 里钉着用例。
- **假库有三处脾气**（见 `eval/harness.py` 的模块 docstring）：不过滤 `WHERE`、不排序、
  不校验外键。跑分器在三处补上（自己按 `run_id` 筛、按发起时间排序、不依赖外键），
  于是同一个方法在真假两个库上给出同一个结果。
- **规则判拿不到「过程类」的东西**：语气、说服力、有没有把话说到点上，这些判不了。
  要量它们得先接受一个有非确定性的判据，那是另一条路。
- **分母会变小**：截断 / 挂起 / 坏掉越多，进判据的跑次越少。报告因此**分开列**——
  终局分布与判据分母是两处（第 2 块），平均轮数 / token / 耗时数的是**全部**跑次
  （没跑完的也花了钱）。
- **一跑的开销是真金白银**：一趟 120 跑约 10 分钟、约 ¥0.1。跑真模型意味着实验有预算，
  这也是一条「先手工检查触发能力、再开跑」的理由（否则可能花钱测出一个「没测到」）。

## 考虑过的替代方案

- **真商城上跑**：数据隔离与状态污染要重做一遍，而且每跑都要起 Django + MySQL + Redis；
  L3 已经有一条**真机验收**的线（issue 38），两条线分工不同 —— 那条验「能不能用」，
  这条量「用了多好」。
- **上 LLM-judge**：判据会变得不可复现，而这正是评估要避免的。真需要判「过程类」质量时
  再说，那时它该是**另一个**判据，不替换现有的规则判据。
- **只分通过 / 不通过**：截断会污染两组对比（见上），而「截断」这件事本身有信息量
  （前缀长度是这次 A/B 的自变量之一）。

## 什么时候该重新看这条决定

- **题集里出现判不了的过程类问题**（语气 / 策略 / 多轮说服）→ 那时再讨论要不要引 judge，
  以及它在报告里怎么与规则判据分开；
- **假商城的样本与真契约漂开**（改内部端点返回形状时）→ 样本要跟着改，且**两个 A/B 的
  数据会全部作废**（读数变了），这条要写进改动那一片的验收里；
- **要跑的评价规模上一个量级**（几百跑以上）→ 时间与钱都变，届时再考虑并发与抽样。
