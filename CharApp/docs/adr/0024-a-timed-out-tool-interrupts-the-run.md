# 工具超时即中断本次运行 —— 结果未知时不把决定权交回模型

**Status:** accepted（2026-10-04）

**改判 `0023` 的第 3 条**（超时之后回填什么、让模型接着决策）；其余各条（分层取值、
同步工具「不再等它」、`CancelledError` 不吞、模型层与 run 层不动）原样保留。

## 决定

1. **任何**工具调用超时（框架那道闸放弃等待）都**中断本次运行**：这一批跑完就收场，
   `outcome=interrupted`，终局事件 `error(code="interrupted")` —— 不再发起下一次模型
   决策，也没有答复。前端据此显示「已中断」（给用户的话术见 BFF 的 `ERROR_COPY`）。
2. **不区分读写、不加工具级开关**。框架不认识业务注解 `writes`（有一条防漂移用例扫
   源码守着），而「读超时」与「写超时」在框架眼里是同一件事：这次调用的**结果未知**。
   与其引入第二套标记让业务把「这是写工具」再声明一遍，不如统一按「结果未知就不继续」
   处理 —— 行为上最接近 Claude Code（工具中断即结束这次运行）。
3. **回填照做，但它不再是「给模型的下一步」**：那条 tool 消息仍进历史（wire 必须配对：
   带 `tool_calls` 的 assistant 后面必须有 tool 消息），文案如实写「结果未知、不要直接
   重试、先核实」—— 它写给的是**日后读到这段历史的人与模型**（下一轮提问、显式
   resume、复盘），不是本轮的下一步决策。同一批里未执行的兄弟调用（要人批的那些）
   也一律回填：未闭合的 `tool_call` 会让终局事件发不出去（`stream/bus.py` 的状态机）。
4. **中断优先于挂起**：同一批里既有「需人工确认」又有超时，一条都不挂 —— 结果没弄清前，
   确认卡没有意义。要批的那条按失败回填，文案明确说「本次运行已经中断」。
5. **只认框架那道闸**：工具自己抛的内置 `TimeoutError` 仍是普通意外异常（回填通用内部
   错误文案，运行照旧，有现成用例钉着）；而 `ToolTimeoutError` 这个类型本身就是「结果
   未知」的声明 —— 工具作者照着它抛，也算。
6. **恢复段同样生效**：HITL 批准后补做的那条超时（多半正是付款），第二段就地中断，
   不再问模型。

**落地**：`tool/executor.py`（`ToolExecution.timed_out`）· `agent/loop.py`
（`_handle_tool_turn` / `_complete_pending_turn` 的中断判定与「中断优先于挂起」）·
`agent/utils/types.py`（`LoopOutcome.INTERRUPTED`）· `agent/utils/messages.py`
（`RUN_INTERRUPTED_TEXT`：同批未执行调用的回填）· 三张映射表（`db/state.py` → `failed`
· `eval/utils/types.py` → `broken` · `client/render.py` → 中文短语）· BFF 的
`ERROR_COPY["interrupted"]`。

## 为什么需要它

- **改判的是 `0023` 第 3 条**：它当时的答案是「回填一句带『不要直接重试』的可操作文案，
  同一动作的重放交给 ADR-0017 的幂等键」。这套答案有一个洞：**模型换一次调用是全新的
  动作**，幂等键只管同一次动作的重放（0023 自己写明了这句）；而「不要直接重试」是一句
  **请求**，不是一道闸 —— 模型完全可能再发一次。
- **超时的结果是未知的**：协程工具被取消，但它可能已经把请求发了出去；同步工具的线程
  本来就还在跑（0023 第 2 条）。既然连「有没有生效」都不知道，让模型基于这份历史继续
  决策就是把风险敞着。停下、让人核实，是这里唯一可控的动作。
- **为什么值得一条 ADR**：**难回退** —— 改了所有工具超时的收场方式与事件契约；
  **有真实取舍** —— 只读工具也失去了「超时后换个方式继续」这条自纠错路径；
  **反直觉** —— `0023` 刚记下的「回填可操作文案」在这里被收窄，读旧文的人会以为
  超时仍是「模型自己看着办」。

## 代价与边界

- **「中断」不是「立即停」，也不是取消**：同一批的兄弟调用在超时之前就开了，`gather`
  会等它们跑完 —— 它们的副作用照常发生，回填与事件也照常产出。「取消兄弟」是另一族
  能力（见 #18），本 ADR 不做。
- **同步工具那条线程仍会跑到自己返回**（与 0023 第 2 条同一件事）：页面已经显示中断，
  副作用仍可能稍后发生；日志里那条 `thread_still_running` 是唯一的线索。
- **只读工具也一起中断**：它们本可以「换个方式再查」，现在没有了。这是统一的代价，
  判它值 —— 框架分不出读写，而分错的代价（重复写）比少一次自纠错重。
- **显式 resume 不被拦**：从那一帧接着跑是**人的决定**（命令行 `--resume` / 会话层
  `resume`），模型仍可能在下一段换参数重发那一次调用。目前没有闸，记在这里。
- **库里分不出两种中断**：`runs.status` 只有 `failed`（与上游中断同族），要细分得查最后
  一帧的 `metadata.outcome`（`interrupted`）或那条 tool 调用的文本；`charagent_tool_calls`
  也没有超时的专门状态（记 `failed` + 文本，文本有稳定前缀可匹配）。要不要加列是独立决定。
- **事件契约不加字段**：前端从终局那帧 `error(code=interrupted)` 加前一条 `tool_result`
  的两样事实就能重建现场，不必扩载荷。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 工具级开关（`@tool(interrupt_on_timeout=True)`，默认关） | 要让业务给每个写工具再声明一次「它会写」—— 而业务已经有一份 `writes` 注解给护栏用了，两份标记迟早对不上；框架又明令不许读那份注解（防漂移用例）。维护「两份声明焊死」的纪律，换来的只是让只读工具保留自纠错 |
| 同一个开关、默认开（只读工具显式关掉） | 安全默认更好，但所有现存工具（含演示工具）的行为都要跟着翻转，C06 刚钉的那批用例要反过来写；而「默认全中断」正是本 ADR 选的那条，不必再加一个开关 |
| 框架把 `writes` 注解升格成一等公民（认这个键） | 破坏「框架不认识业务词汇」这条线（换个业务就得改框架），并推翻一条专门为此写的防漂移用例 |
| 判据交给装配处的回调 / 策略对象 | 机制更重（新构造参数、新缝），而真实差异是一个布尔值；等真出现「有的工具想继续」再说 |
| 超时后用子进程隔离 / 真杀工具 | 过重，属 #24 沙箱那一族；本 ADR 的「线程还在跑」这条边界在那边才会消失 |
| 仍回填文案让模型继续（维持 0023） | 结果未知时把决定权交回模型，赌它「听话」；一次重复写就够把收益抹平 |

## 什么时候该重新看这条决定

- **若真机上中断得太频繁**（正常提问被只读超时打断）：先看是不是某个下游在慢 —— 那该修
  下游或让工具自己设超时；若确认「只读工具也该继续」有真实样本，再回来谈工具级开关。
- **若业务工具改走子进程 / 沙箱执行**（#24）：子进程能真杀，超时可以从「放弃等待」升级成
  「真的杀掉」，本 ADR 与 0023 一起重看。
- **若出现「中断之后人没跟进」的真实事故**：那时要补的是产品层的跟进机制（把
  `runs.status=failed` 加那条 tool 文本变成一条待办），不是把中断改回去。
