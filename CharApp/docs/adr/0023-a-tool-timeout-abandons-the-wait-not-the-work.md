# 工具超时是「不再等它」，不是「它停了」—— 分层超时补上工具那一层

**Status:** accepted（2026-10-03）

## 决定

`DESIGN.md` §② #15 的三层超时里，缺的只有中间那一层；这次补上它，并如实定下它的边界：

1. **工具层由框架给**：`tool/executor.py` 的调用那一步套一层 `asyncio.timeout`，默认
   **30 秒**（`tool/utils/config.py` 的 `DEFAULT_TOOL_TIMEOUT_SECONDS`），单个工具可用
   `@tool(timeout=...)` 覆盖（**keyword-only**，既有构造签名一个字没动）。取值是
   `DESIGN` 里 10-30 秒那一段的**上界**：给「工具自带的超时」让路 —— 一个自己设限的
   工具（典型形态是经一个带超时的 HTTP client 出门）总比框架先响，它给的话更准（哪个
   下游慢 / 什么错）；框架这一层是**兜底**，只管那些自己不设限的工具。它又必须明显小于
   模型层（60 秒）与 run 层（业务配的 90 秒），否则一次卡住的工具会把整轮预算吃光。
   **不给「不设超时」这个选项** —— 本片的起因就是「工具卡住就永远卡住」。
2. **超时的语义分两条路，且如实承认**：协程工具到点被 `cancel`，它是真的停了；**同步工具
   跑在线程池里，超时掐不掉线程** —— 只能不再等它，线程会跑到函数自己返回。于是同步那条
   路在日志里记一条 `thread_still_running`（结构化字段 + 一句话），**对有副作用的工具，
   这意味着副作用仍可能发生**。
3. **回填给模型的话带两层**：说清「超过 N 秒没回来，已放弃等待」，并给出可行动作
   （换个方式达成目的 / 调整参数再试），外加一句**「若这个操作会改动数据，不要直接重试
   —— 它可能已经生效」**。超时**不**伪装成「工具返回了空结果」（那会让模型以为查到了空
   数据）。
   **2026-10-04 改判（见 `0024`）**：这一条只成立了一天 —— 超时意味着结果未知，把决定权
   交回模型就有重复写操作的风险，于是改为**任何工具超时都中断本次运行**。回填仍在（tool
   消息必须配对：未闭合的调用会让终局事件发不出去），但文案只陈述事实（结果未知 / 不要
   直接重试 / 先核实），**不再是「给模型的下一步」**。
4. **两条边界不能被这道闸带走**：① **工具自己抛的 `TimeoutError`（socket / 连接池超时）
   不算框架超时** —— 用 `asyncio.Timeout.expired()` 认自己那一次，其余原样上抛，走「意外
   异常」那条回填路；② **`CancelledError` 照旧不被吞**（属 `BaseException`），kill switch
   在工具执行中照样即时打断，也不重试（#3 / #13 已定的规矩）。
5. **模型层与 run 层不动**：60 秒早就在 `model/client_httpx.py` / `client_sdk.py` 的构造
   参数上（这次补了一条把它钉住的用例），run 层是 `agent/guard.py` 的墙钟预算 —— 它的语义
   是「**这一轮结束后才判**」（#3），与单次调用超时不是一回事，别混。

## 为什么需要它

- **缺的层是实证的**：三层里模型 60 秒与 run 预算本来就在，`execute_tool` 那一层没有超时、
  没有循环、没有取消 —— 模型发起的工具调用一旦卡住就**永远卡住**，整轮不会结束。
- **「取消」在同步工具上做不到**，这不是实现偷懒：`asyncio.to_thread` 的线程没有取消点，
  Python 也没有安全的线程中断（`PyThreadState_SetAsyncExc` 之类不讲武德）。三个选项里
  **子进程隔离**能真杀但过重（本阶段不做，属 #24 的沙箱那一族），**要求业务全写成 `async def`**
  只是把问题推给工具作者（框架仍要处理同步工具）。剩下那条就是**如实承认**。
- **为什么值得一条 ADR**（三条都满足）：**难回退** —— 超时值一旦进了各业务的工具注册处，
  改它是一次影响面很大的行为变更；**反直觉** —— 「超时了但活儿还在跑」是多数人不会预期的
  语义，尤其对有副作用的工具；**有真实取舍** —— 放弃等待换整轮不卡死，代价写在上面第 2 条。
- **「结果未知」有现成的一半答案**：写操作超时之后的重试风险，靠两处兜 —— 模型的回填文案
  点名「不要直接重试」，以及 ADR-0017 的幂等键（HITL 恢复那条路上的重放已经挡得住）。这不
  等于「副作用一定不重复」：**模型换一次调用是全新的动作**，幂等键只管同一次动作的重放。
  这一层诚实留在边界里。
  **2026-10-04 补记**：那「一半答案」里的回填文案被换成了一道闸 —— 任何工具超时都中断本次
  运行（`0024`），模型不再有「要不要重试」这一步。幂等键的边界（只管同一动作的重放）不变。

## 代价与边界

- **同步工具的超时是「不再等它」**（与第 2 条同一件事，这里说它的代价）：那次调用的输出被
  丢弃，而副作用可能已经发生；`duration_ms` 记的是**放弃等待的那一刻**，不是函数真实耗时。
  日志里那条 `thread_still_running` 是唯一能看出「它还在跑」的线索。
- **kill switch 撞上同步工具时同理**，且今天**没有**对应的日志（本片只覆盖超时那条路）：
  线程在 run 被取消后照样跑到自己返回。要补的话是 #18 的活，不是这一片。
- **默认值只对「自己不设限」的工具起作用**：业务工具多半有自己的超时（本项目的 18 个工具
  经一个 10 秒的 HTTP client 出门），于是框架这一层在正常路径上**看不见** —— 它是兜底，
  不是主防线（那 10 秒是逐阶段的：连接 / 读 / 写 / 池各 10 秒，「慢滴流」响应可以越过它，
  框架这层正好兜住这一类）。**没有给任何工具单独放宽**（付款那类也一样）：放宽与否在真实
  链路里换不来差别（内层先生效），多一个数字只会多一处要维护的判断。
- **一次卡住的工具仍在吃 run 的预算**：30 秒的上限只保证「单次不会永远挂」，不保证「整轮
  很快结束」—— 同一轮里多个卡住的工具可以叠（并行时尤其），最终收场的是 run 层。分层就是
  这个意思：**每一层管自己那一段**。
- **`asyncio.timeout` 认的是自己那一次取消**：它靠 `Task.uncancel()` 的计数把「外部 kill
  switch」与「自己到点」分开，所以外部取消不会被转成超时（有一条用例钉着）。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 要求所有业务工具写成 `async def` | 只是把问题推给工具作者，框架仍要处理同步工具（演示工具、裸查库、第三方同步 SDK 都是同步的） |
| 同步工具用子进程隔离（能真杀） | 过重：跨进程传参 / 序列化 / 环境一致性都是新成本，属 #24 沙箱那一族，本阶段不做 |
| 超时值放环境变量（全局遥控） | 真实差异是**工具级**的（查库 vs 调外部 API），一个全局数字按不住；要全局改就在装配处给每个工具传同一个值，不必多一层隐式配置 |
| 不设缺省值，要求每个工具必须显式给 | 忘了给 = 回到「永远卡住」；缺省值在这里是安全网，而不变量应该有个好默认 |
| 超时也伪装成一次成功的空结果 | 模型会以为「查到了，没有数据」，与 #2 的「可操作错误」正面冲突 |
| 给同步工具的超时也记成「已取消」 | 那是**假话**（线程没停）。日志说的是「不再等它」，UI/轨迹看到的是同一件事：结果未知 |

## 什么时候该重新看这条决定

- **若真机上出现「工具还在跑、run 已经收场」造成的脏数据**（同一单被处理两次）：那时该补的是
  **工具自己的幂等**（服务端把「同一动作」认出来），而不是把超时调大 —— 调大只是把窗口推后。
  **2026-10-04 部分提前发生了**：不是脏数据，而是「模型可能自己重试」这条风险被提前堵上 ——
  超时即中断本次运行（`0024`）。工具自己的幂等仍是另一半：中断挡不住「人核实之前又发一次」，
  也挡不住显式 resume 之后模型换参数重发。
- **若某个工具真的需要跑过 30 秒**（长导出 / 长检索）：先问它能不能异步化成任务（#20），
  不能才给它一个显式 `timeout=`，并在 run 预算里给它留位。
- **若业务工具改走子进程 / 沙箱执行**（#24）：那时「取消不掉」这条边界消失，超时可以从
  「放弃等待」升级成「真的杀掉」，本 ADR 改为 superseded。
- **若 kill switch 那条路也要留下同样的痕迹**（第「代价与边界」第二条）：那时把这条日志抽成
  两处共用的一段，别抄第二份。
