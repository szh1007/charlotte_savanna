# 代付的密码走一次性载荷，永不进模型看得见的地方

**Status:** accepted（2026-09-24）

## 决定

"助手代付"是**助手发起、用户本人完成**的动作。支付密码的完整通路是：

```
用户在客服页面上输密码（Django 页面，session 校验 —— 唯一的真验证点）
  → Django BFF POST /api/minimall/agent/runs/{run_id}/resume
        body: {decision: "approve", data: {"payment_password": "..."}}
  → CharApp POST /runs/{run_id}/resume（同一个 body）
  → 恢复前把 data 塞进本次运行的 RunContext.payload
  → MinimallToolProvider.provide(ctx) 从 ctx.payload 取出，闭包捕获
  → pay_my_order 工具内部取用（async def + httpx）
```

> **上面第二行那条路径与 body 是当时的草稿，2026-09-26 由 issue 36 改成现在这样**：
> 浏览器打的是 `POST /minimall/agent/resume/`，body 里**有 `tool_call_id` 没有 `run_id`**。
> 正文保留原样以看思路，改动与理由见文末「补记」。

**密码只在这一个 run 的这一次恢复里活着** —— `provide` 每次运行造一批新工具，闭包天然是一次性的，恢复结束它就没了。

## 为什么：三个"永不"

| # | 保证 | 靠什么成立 |
|---|------|-----------|
| 1 | 密码**不进 messages** | 模型从头到尾没看见它。它不在任何一条消息里，只在恢复那一刻的 `payload` 里 |
| 2 | 密码**不进 `charagent_tool_calls.arguments`** | 那一列装的是**模型填的参数**（原样 JSON）。模型给的是 `{"order_no": "..."}`，密码是运行时注入的 —— 两件事在结构上就不在同一个地方 |
| 3 | 密码**不进 `charagent_tool_calls.result`** | 工具返回的是"支付成功"或"支付密码不正确"，原文不回填 |

**并且 `pay_my_order` 的工具 schema 里永远不出现 `payment_password` 这个参数。** 这一条是三个"永不"的**前提**而不是同义反复：只要它出现在 wire schema 里，模型就会自己编一个填进去，而编出来的值会走 `arguments` 落库 —— 于是 #2 当场失效，还附赠一条"模型以为自己知道密码"的假象。

这条与 `PLAN.md` §1 记的那条纪律是**同一个形状**：`user_id` 走 `RunContext.payload` 而永不进工具的函数签名，所以永不出现在 wire schema 里，"诱导模型查他人订单"这条路径天然不存在。密码是第二个走这条路的**运行时凭据**，机制不用新造。

## 为什么必须是"用户本人"而不是"助手代付"

`Profile.check_payment_password()` 要**明文经手**（`check_password(raw, hash)`）。这意味着密码必须在某个进程里以明文存在一瞬 —— 无法回避。能做的是**让那一瞬尽可能短、尽可能少的组件经手**：

- 不经过模型（模型只看得到"要付这一单"）
- 不经过快照与记录表（它们存的是给模型看/给人看的历史，里面没有密码）
- 不经过 `arguments`（那是落库的模型输出）

`CONTEXT.md` 的「支付密码」词条原本写着"助手不代付（2026-09-21 决定）—— 校验需要明文经手，与「身份不进工具参数表」不可调和"。**不可调和是真的，结论不是**：把密码放在**参数表之外**的载荷里，两条纪律就不打架了。本 ADR 是那个词条的重写依据。

## 代价与边界

- **密码错 = 本次代付失败收场，不自动重试。** 密码是一次性的（`payload` 随这次恢复一起消失），自动重试等于拿同一个错密码撞第二次，只会烧掉业务侧护栏那 8 次写预算。正确行为是让用户重新说一次"付"，**重新走一遍挂起**（也就重新输一次密码）。这条要写死在工具的返回文案里。
- **`data` 的归属必须无歧义**，所以配合 ADR-0014 那条边界：**一次挂起只挂一条需审批的调用**。
- **BFF 与 CharApp 的 HTTP body 里有明文密码。** 这在信任域内（`X-Internal-Token` 同一域，与 `X-User-Id` 走同一条边界），但它意味着**请求日志绝不能记 body**。落进 issue 36 的验收：构造一次代付，在两侧的应用日志里搜不到密码原文。
- **没有"免密支付"这种便捷口子**，也不做"记住密码 X 分钟"。一个"演示时跳过密码"的开关是安全反模式，与 ADR-0003 拒绝"演示开关"是同一条理由。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 密码做成 `pay_my_order(order_no, payment_password)` 的第二个参数 | 最直观，也最错：它进 wire schema → 模型会编值 → 编的值进 `arguments` 落库。而且"身份不进参数表"这条纪律会当场破一个口子，先例一开就没法讲清楚边界在哪 |
| Django 侧自己校验密码、自己扣款，CharApp 只收到"已确认"信号 | 支付动作就绕过了 agent —— 而 HITL 的恢复路径正是"**补做那条欠着的工具调用**"，绕过等于把这条路径空掉，挂起机制失去唯一的真实场景 |
| 密码存在会话里（恢复时再取） | 一个长活的东西比一个一次性载荷难守得多：它要定义生命周期、要防泄漏、要处理"会话被软删了密码还在"。而它换来的只是"不用重输" |
| 用户确认时不输密码，改为在商城页面付 | 那就不是代付了 —— 助手只能说"请你去订单页付款"，HITL 也就没有第二个验证场（PRD §4.5 明说验证场只有两个） |

## 补记（2026-09-26，issue 36 / 37 落地之后）

**BFF 那一跳的真实形状与上面那张图略有出入**（issue 36 的改判，正文保留原样以看思路）：

- **路径与 body**：浏览器打的是 `POST /minimall/agent/resume/`，body 是
  `{conversation_id, decision, tool_call_id, data}` —— **`run_id` 不在 body 里**。理由是框架里
  有**两个**运行编号：页面上那个（`X-Run-Id`）是**这一次 HTTP 请求**的进程内编号，而恢复端点
  要的是**记录层那一行**，带错了换来的是一次 404（"已经处理过了"，而用户什么都没做）。于是
  "哪一次运行"由唯一知道答案的那一方回答：**BFF 现问一句 `/history`**，再拿它去恢复；顺手
  用 `tool_call_id` 校验"这张卡还是不是同一张"。
- **`data` 只转发 `needs` 里点过名的键**（`views_bff.py` 的 `one_shot_payload`）。不这么做的话，
  浏览器能往这份载荷里塞任意键 —— 而框架会把它并进运行上下文，**身份（`user_id`）就在里面**：
  一次"改个字段"就能让工具去动别人的数据。这一层因此是这条通路的最后一道门。
- **框架侧合并成"只增不覆盖"**：`{**data, **context.payload}`（原本是 `{**payload, **data}`）——
  一次性的东西只该**补上缺的那些**，已有的键（谁 / 哪一段会话）一律以本次运行为准。

**真机给这条决定的三条背书**（issue 38，全链路真服务，买家 `savanna`）：

1. 密码**原文**在会话消息 / 轨迹的 `arguments` 与 `result` / 快照帧 / 两侧日志四处**一处都没有**
   （全库 53 列扫下来，`payment_password` 这个名字**只**出现在 `charagent_tool_calls.approval_needs`
   那一列 —— 那是"要问什么"的机器可读清单，前端据此渲染那个框，**不是值**）；
2. `pay_my_order` 那一行的 `arguments` 就是 `{"order_no": "202609261603140000102499"}`，
   **没有第二个参数**；
3. 同一个 `resume` 重放两次：两次都**被挡在工具执行之前**，一分钱没多扣、工具一次没多跑。

## 什么时候该重新看这条决定

- **若支付改成"一次确认、多次扣款"**（比如一键付清所有待付款订单）：一次性载荷的归属假设就破了。
- **若接入真实支付网关**（现在余额是站内虚拟货币）：网关的令牌化流程通常要求密码只在它自己的页面里输入，那时"密码经 CharApp 一段"这条要重新论证。
- **若 BFF 与 CharApp 之间不再是同一信任域**（见 ADR-0001 的"什么时候必须还"）：明文密码在 HTTP body 里这件事比明文 `X-User-Id` 更严重，它是内部 JWT / mTLS 那条路的又一个理由。
