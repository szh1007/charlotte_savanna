# 浏览器 → BFF 用 POST + fetch 读流，不用 EventSource

**Status:** accepted（2026-09-21，修订 PLAN §4.3 与 issue 06 §3/§4 的原决定）

## 决定

客服页面向 Django BFF 发问走 **`POST /minimall/agent/chat/`**（JSON 请求体 + `X-CSRFToken`），响应用 **`fetch` + `ReadableStream` 手写读 SSE 帧**。

被否掉的是原计划（PLAN §4.3、issue 06）：`EventSource` 发 GET、问句走 query 参数。

链路本身没变（浏览器 → BFF → 助手服务 → 商城），换的只是浏览器与 BFF 之间的那一跳长什么样。

## 为什么改

原计划选 `EventSource` 的理由是「浏览器原生、零构建、免费送帧解析」，这条仍然成立。它被换掉是因为它的约束与这个端点的**性质**撞上了：这个端点有副作用 —— 真跑一次模型、真花钱、真往会话里写东西。

`EventSource` 的三条约束逐条撞在这上面：

1. **只能发 GET，也带不了自定义头。** 认证因此只能靠 cookie（这是优点，用户故事 22 要的「用已有登录状态」正是这么来的），但代价是**没有任何显式的跨站防护**：GET 不过 Django 的 CSRF 检查，只剩 `SameSite=Lax` 这一层，而 Lax 只管**子资源**请求，**顶层导航照样带 cookie**。也就是说，任何用户访问的网站上写一句
   `location = 'http://127.0.0.1:8000/minimall/agent/chat/?message=…'`
   就能让登录用户**真跑一次模型**（真花钱），而且不需要点击。切换后 POST + CSRF 令牌把这条路彻底堵死（实测：无令牌的 POST → 403，未打到下游）。
2. **问句只能进 URL。** 于是每一句都落进访问日志（订单号、地址、余额跟着一起进去），也留在浏览器历史里。这与项目自己的规范（日志不记录敏感信息）直接冲突。改走请求体之后，日志里只剩 URL 本身。
3. **浏览器读不到非 200 响应的正文。** 于是「连不上助手服务」「上游拒绝」只能**假装 200、往流里塞一帧 error**，把状态码这一层信息丢掉。换成 `fetch` 之后，这些失败可以回真状态码（502/503）+ `{"error": {"code", "message"}}`，前端照样显示同一句人话。

顺带清掉一套补丁：`EventSource` 在**任何一次流结束之后都会自动重连**（正常答完也一样），那是在重放用户那句话、再计一次费。原先为此加了两道口子（客户端 `close()` + 服务端拒绝带 `Last-Event-ID` 的请求 → 409）。换成 `fetch` 之后没有自动重连这回事，两道口子连同它们的测试一起删掉了。

## 代价（说清，否则这条 ADR 就是自我辩护）

- **不能再靠浏览器把帧解析白送**（`EventSource` 干的就是这件事）。补法是**用现成的库**，不是自己写：`eventsource-parser` 的 `EventSourceParserStream`（`TextDecoderStream` + 切帧 + 字段解析一条管道），CDN 引入、版本钉死，与 base 模板里的 htmx / Alpine 同一个来源。页面自己只剩胶水（发什么请求、六类事件画成什么样，约 8 行）。
- 代价因此变成**一条 CDN 依赖**（多一个外部资源、多一个要跟的版本），而不是三十行协议代码 —— 这笔交换是划算的：那段代码里的坑（跨 chunk 的半个帧、**一个汉字被 TCP 切成两半**时的增量解码）别人已经踩过并维护着了。
- 失去「用浏览器原生能力」这个更好讲的取舍（「为什么用 EventSource」比「为什么用 fetch + 解析库」更好回答）。作为交换，换 POST 在**语义上是对的**：有副作用的操作本来就不该是 GET。

## 考虑过的替代方案

- **保留 GET，加一个一次性 token 进 query 校验** —— 能挡住跨站触发（query 里的令牌攻击者猜不到），约 30 分钟。否：它只解决了第 1 条，问句仍然进日志（第 2 条），错误仍然只能走流里说（第 3 条），而且这个端点在语义上仍然是「用 GET 干有副作用的事」——一份审计过不去的账。
- **`@microsoft/fetch-event-source`（一把梭：fetch + POST + 头 + 解析全包）** —— 否。少写十来行，但要多一个「忘了在 `onerror` 里 throw 就会自动重连」的隐形约定（对 POST 跑模型来说就是「答完再跑一遍、再计一次费」，正是这条 ADR 上面在解决的问题），而且它的 ESM 里是无扩展名的相对导入，浏览器直接吃不了，得走会重打包的 CDN。
- **让浏览器直连助手服务**（省掉 BFF 这一跳） —— 否。助手服务的身份设计是「信任转发方声明的 `X-User-Id`」（ADR 0001），直连等于把「我是谁」的决定权交给浏览器；而且内部令牌必须下发到浏览器，那串令牌还能打开商城那 9 个内部端点。见 `views_bff.py` 模块 docstring 与 PRD §4.10。
- **上 WebSocket** —— 否。为一次问答引入双向协议与另一套后端接线，收益不如代价；PRD 也没要求。
- **把 `EventSource` 与 `fetch` 两条路都留着** —— 否。两套传输 = 两套错误处理 + 两套测试，且只有一条会被真正使用。

## 什么时候该重新看这条决定

- 如果前端引入构建链（npm + 打包），库就可以进 `node_modules`、版本由 lockfile 管，CDN 那一跳的顾虑消失 —— 这条决定会更划算，不是更不划算。
- 如果将来要支持「断线续推」（框架的 SSE 层目前明确不支持，见 `CharAgent/server/sse.py`），那要在**服务端**补续推能力，与浏览器这侧用哪种客户端无关。
- 本决定**不影响**助手服务与框架：BFF 打上游仍然是 `POST /runs` + 三个头 + SSE，上游契约一字未动。

## 修订记录

- **2026-09-21（当天）**：初稿的「代价」写的是「前端必须自己写帧解析（约 30 行）」，并把它当成这条决定的主要代价。**那个前提是错的** —— 写它的当时默认了「前端零依赖」，而实际约束只有「零构建」：CDN 上的现成库一直是允许的（htmx / Alpine 就是这么来的）。改成 `eventsource-parser` 之后，那段协议代码从页面里消失，代价变成一条 CDN 依赖。其余部分（为什么离开 `EventSource`、CSRF、问句不进日志、错误回真状态码）不受影响。
- **2026-09-21（同日，换库时顺带核出的一处规范差异，不用改代码）**：BFF 的 `iter_frames` 会原样转发「上游没按帧收尾」的那半截帧（服务端只搬字节，不替上游补协议），而库按 SSE 规范**丢弃**它 —— 浏览器的 `EventSource` 也是这么做的（规范：流在中途结束、没等到最后的空行，那一个事件不派发）。也就是说，手写那一版「把尾帧也发出去」其实是**不合规范**的宽容。我们的服务端永远补上收尾的空行，所以这条只在上游畸形时才可见，而那时丢掉半截才对。
