# 摘要失败就不切刀；只有上游报超限才允许硬截断

**Status:** accepted（2026-09-23）

## 决定

压缩这条路上有三层，每一层「丢不丢信息」的态度都写死：

| 层 | 触发 | 切刀 | 丢信息 |
|---|---|---|---|
| **正常** | 投影后超阈值，且摘要成功 | ✓ | 只丢**摘要覆盖过**的那段（它进了摘要） |
| **摘要失败** | 同上，但摘要报错 / 没模型 / 正文为空 / 被 `length` 截断 | ✗（退到只投影） | **一条都不丢** |
| **紧急** | 上游明确回报输入超窗口（`ModelErrorKind.CONTEXT_OVERFLOW`） | ✓✓（不问阈值也不问水位线，裁到只剩最近 1 个提问） | `[covers, cut)` 那段**显式声明为有意放弃** |

配套两处：
- `summarize=False`（**配置选择**，不是失败）语义不变：硬截断是用户选的，`summary_covers` 跟着切点推进，账目自洽。
- 新增 `CompactionPolicy.emergency()`；loop 在 `_decide` 里捕获 `is_context_overflow`，调它一次、**只重发一次**。`ModelStatusError` 新增 `kind`，判据（错误正文里的几种写法）**只写在解析层一处**（`model/parse.py` 的 `classify_error`）。

## 为什么需要它：修之前，「降级」会静默吞掉对话

原实现在摘要失败时叫「降级为纯裁剪」—— 听起来无害，实测却会凭空丢信息（2026-09-23 复现，账本 17 条、`summarize=True`、摘要不可用）：

```
轮1: dropped=14 / summary_covers=0 / summary=None / 视图 3 条
     → history[1:15] 那 14 条**既不在摘要里，也不在视图里**
轮2: dropped=16   → 每轮只看得见最后一个问答，且永远没有摘要
```

根因是**账目与视图各走各的**：`summary_covers` 不推进（账目对），而 `_view(cut=cut)` 的切点照推（视图错）。于是 `apply` docstring 里明写的那条不变量 —— 「投影只丢**摘要已经覆盖过**的那一段，否则信息就凭空没了」—— 在这条路径上被破坏了。

而且触发条件是**活的**：`summarize=True` 且摘要失败。其中最常见的一种（思考把 `max_tokens` 吃光、正文为空）在 2026-09-23 的真机上正是「摘要这一步从没生效过」的原因。测试 `test_a_failed_summary_does_not_advance_summary_covers` 只钉了账目那一半（covers），**没钉视图那一半（cut）**—— 测试与实现共享同一个盲区。

第三层（紧急）是补上的另一半：在此之前 400 被判「永久错误」直接上抛，**这一轮就废了**；而估算不准是常态，DeepAgents 的 `ContextOverflowError` fallback 就是为这件事存在的。

## 代价与边界

- **摘要持续失败时，压缩等于完全失效** —— 账本会一直涨到撞窗口。这是有意的：与其静默丢，不如涨到**上游明确说超了**，再由 `emergency()` 兜住。两条是配套的：一条守住平时的信息完整，一条守住极端情况下的「这一次请求还能不能发出去」。
- **紧急路径允许丢，代价记在账目上**：`summary_covers` 推进到切点 —— 那一段被显式声明为「有意放弃」。这是整条链路上「允许丢」的唯一凭据，事后查帧能看出是哪一轮做的这个决定（`view.emergency`）。
- **降级不再进事件流**。修之前失败会发一条带 `warning` 的 `context_compacted`；现在失败 = 没压 = 没有「压缩过了」的痕迹（前端那行灰字说的是进度，不是诊断）。留痕改挂在 `metadata.view.warning` 上，事后查帧一样答得出来。
- **超限识别靠字符串**（`context_length_exceeded` / `maximum context length` 等几种写法），这是这份设计里唯一一处「猜」。它的边界写死在 `parse.classify_error` 一处，加一种上游写法就是加一行；认不出来时 `kind` 记 `unknown`，行为退化成「照旧上抛」—— 保守的那一侧。
- **只重发一次**。再超就是真的压不动（或窗口小得离谱），如实抛给上层，不把这一轮拖成重试循环。
- **还有第二种「允许丢」，它由配置驱动**：`summary_input_limit` 削掉的那部分材料没进过摘要，而切点照旧推进 —— 它们就此丢了（2026-09-24 代码审查定性）。它可认（与 `summarize=False` 的硬截断同类：用户设了上界，就是接受了这个代价），但**不能静默** —— 现在会记一句 `warning`。**不能**用「把切点退回去」来躲：那会让下一轮的投影把**已经进过摘要**的段又拉回来（covers 与切点分家），视图在相邻两轮之间跳变 —— 正是 ticket 23 修过的同一类振荡。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 失败时把 `summary_covers` 也推上去（承认那段被放弃） | 把「静默丢信息」合法化了 —— 丢的可能是几天前确认过的订单号，而用户看到的只是「模型突然不记得了」 |
| 失败时降级成「纯裁剪模式」（等价 `summarize=False`） | 与上一条是同一件事，只是换了说法。配置选择与意外失败必须分开：前者用户点了头，后者没有 |
| 摘要失败就把异常抛出去 | 一次网络抖动让用户这句问不出来 —— 而摘要只是「压得更好看」，不是这条链路成立的必需件 |
| 失败后本轮不再尝试，等下一轮 | 现在就是这个行为（不切刀 → 下一轮 `before` 仍超线 → 再试），不必额外加标记 |
| 阈值调到「压不动也不超窗口」，靠不压来兜底 | 阈值是按业务账单定的，改它等于把「省 token」与「防超限」两件事混成一个旋钮 |
| `emergency` 复用 `apply` 加一个 `emergency=True` 参数 | 会让 `apply` 里多一条「这次要不要留情面」的分支，而它的两条纪律（不变量 / 降级）本来就是相反的。分成两个方法之后，各自能把自己的纪律写清楚 |
| 只在 loop 层重试（把超限标成可重试错误） | 重试层拿不到压缩策略，改不动 messages —— 重发还是同一份超限的请求 |

## 什么时候该重新看这条决定

- **若 `warning` 在真机上长期非空**（摘要持续失败）：那是摘要那条调用的参数问题（`max_tokens` / 思考开关 / 模型能力），不是这条决策的问题 —— 但它会让压缩长期不生效，值得单开一片。
- **若上游给出结构化的错误码**（而不是把话写在 message 里）：`classify_error` 的字符串表可以删掉，判据换成读那个码。
- **若将来接上非 DeepSeek 的端点**：`context_length_exceeded` 那几种写法要照那家的文档补一遍 —— 补的是同一张表，不是新逻辑。
- **若「帧的保留期策略」开始做**（`checkpoint/postgres.py` 里明写「属后续阶段」）：那时要重新评估「原始内容还在不在」这件事 —— 紧急路径丢掉的段，能不能从旧帧里找回来。
