# 被引用的那一段可以进浏览器 —— 修订 0003 的一条边界

**Status:** accepted（2026-10-04）

**修订 `0003`（工具事件在业务侧脱敏）**：那一条立的是「工具的参数原文与返回正文
一个字节都不进浏览器」，为的是防内部实现与原始数据泄漏。这一条在它上面**开一个
口子**，并且把口子的边界写死 —— 不写这一条，半年后读代码的人会以为
`citations` 是漏洞。

## 决定

1. **放行的是「这条答复引用到的那些段」**：`final` 事件的载荷多一个 `citations`
   数组，每项 `{n, title, snippet}` —— `snippet` 是**服务端**从检索回来的正文里
   截的前 200 字。交付前过一道**机械**的过滤：扫答复正文里出现了哪几个 `[n]`，
   只带那几个（不解释它们指什么 —— 那仍然由服务端那份表说了算）。完整工具返回、
   参数原文（检索词）、以及**检索到但没被引用**的段落，照旧不出本进程。有一条
   否定断言守着：响应体里搜得着被引用那一段，搜不着另一段（检索到但没引用）的
   标题、搜不着摘录之外的那一截、也搜不着检索词 —— 直播的 SSE 与 `/history`
   两个响应都扫。
2. **不新增事件类型**：引用是终局答复的一部分，扩 `final` 的载荷即可 —— `#4`
   那条「终局事件恰好一个」的不变量一个字不动。新增一类事件则要动它（状态机、
   BFF 的终局集合、前端的分发、历史接口的对应块），代价大得多。
3. **引用是业务的话术，不是框架的能力**：谁被引用、怎么编号、摘要多长，全在
   `CharApp/minimall/knowledge/citations.py`。框架只多了一个可选插座
   （`create_app(message_extras=...)`）：读历史时按行下标把业务字段并进消息，
   框架**不认识** `citations` 是什么。
4. **编号是「这段对话」的累加序号**（不是「这一次调用」的）：一次检索返回五段就
   占五个号，下一次接着往下数。于是同一个 `[n]` 在这段对话里只指一段 —— 模型在它
   的上下文里看到的也是同一套号，"服务端按号回指"才成立。恢复一段旧会话时，
   编号与引用都从记录表里回读续上（进程重启也不会从 `[1]` 重数）。
5. **直播与历史共用一份实现**：两边都拿**同一段文本**（直播：工具刚返回的内容，
   经 `ON_TOOL_EXECUTED` 钩子收下；历史：`charagent_tool_calls.result` 里落库的
   那一份）喂给**同一个解析函数**。于是"刷新之后引用还在"不是两套算法碰巧一致，
   而是同一份输入走同一个函数（有一条用例把两条路的结果逐字比对）。

## 为什么需要它

- **没有它，逐句引用只能靠前端去啃工具事件** —— 而 ADR-0003 明文规定那条路不通
  （工具结果原文不进浏览器），事件里的 `summary` 又是截断到 200 字符的另一份东西。
  在 0003 上开一个**有名字、有边界、有测试**的口子，比让下一个人偷偷放宽 0003 强。
- **口子的两端都可控**：进来的是业务自己写的摘要（服务端截的，不是模型生成的措辞），
  出去的是语料文本（政策文档，公开且可控），而买家私有数据（订单、余额、地址）
  从来没有进过知识库（ADR-0026 划的边界）。
- **它同时解决了一个反直觉的问题**：刷新页面之后引用凭什么还在？答案不是"再查一次"
  （检索结果可能变了），而是"从记录里回读模型当时看到的那段文本" —— 这正是
  「账本与视图分开」那条纪律在引用上的兑现。

## 代价与边界

- **历史那条路会解析自己写出去的格式**（`[n] 标题` + 正文）。这是有意的取舍：
  另存一份结构化数据要动 `charagent_messages` 的 schema（alembic + 仓储 + 记录层
  四处），而落库的那段文本**就是模型当时看到的那一份**，拿它当唯一依据最不容易漂。
  两条纪律守着它：解析要求编号**连续**才认新段（正文里出现 `[9] …` 不会被当成段落
  边界；理论上"正好是下一个号"的行首仍会被误判 —— 当前六篇语料里 `^[` 出现 0 次，
  风险有界，真出现时改的是写出去的那一侧），以及写格式的那一侧（`formatting.py`）
  与读它的这一侧各有用例。
- **编号撞车时留先出现的那一条**并记一条 warning：只有"编号没有连续累加"的会话
  （进程重启且回读失败）才可能撞。猜一个回指不如留个可查的痕迹。
- **读历史是 N+1 条查询**：每个 run 一次 `list_for_run`（仓库层没有"按会话取全部
  工具调用"的口子，而业务不写 SQL 是既定纪律）。演示量级（几十轮）无感；真嫌慢时
  该动的是仓库层。
- **过滤只认"号"，不认"意思"**：服务端扫答复正文只看出现了哪几个 `[n]`，至于那个
  号指哪一段、写得对不对，一律以服务端那份引用表为准（模型编的号不在表里，前端
  原样当文本显示）。这条分工让"引用表是权威"与"别多发段落"两件事都成立。
- **引用可以来自更早的轮次**：账是按会话累加的，某一条答复引用了上一轮查到的
  `[4]`，`[4]` 就得在这条答复的载荷里（模型上下文里一直有它）。于是 `citations`
  是"这段会话到这一轮为止"那本账的**子集**，不是"本轮检索结果"的子集。
- **载荷随对话变长**：每段 200 字 × 引用条数。政策语料只有 6 篇，可忽略；语料涨到
  几百篇时要重新想（比如只带这一条答复可能用到的那些号）。
- **没配记录库时只有直播那一半**（历史回读无从谈起），与 `/history` 两个来源
  二选一是同一条：那种装配下刷新页面本来就没有历史。
- **不改变 0003 的其余部分**：工具事件的 `arguments` / `summary` / `error` 照旧
  换成中文短语；这条只对 `final` 生效，且只加一个业务字段。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|---|---|
| 前端从 `tool_result` 事件里拿引用 | 正是 0003 挡住的那条路（工具返回原文不进浏览器），而且事件里那份是截断到 200 字符的 `summary`，与检索返回不是一回事 |
| 新增一类 `citations` 事件 | 要动 `#4`「终局事件恰好一个」的不变量（状态机 / BFF 终局集合 / 前端分发 / 历史对应块四处），换来的是同一件事 |
| `charagent_messages` 加一列 `citations` (JSONB) | 动 schema / alembic / 仓储 / 记录层四处，而且框架要存一份它不认识的数据；回读落库文本这条路已经够准（有测试逐字比对） |
| 前端自己解析正文里的 `[n]` 并从历史接口另拿一份来源表 | 两处各解析一遍正文 = 两处各自漂；而且"编号以服务端为准"那条（模型写错号时原样显示）会被绕过 |
| 引用卡片只在**直播**时有（历史不补） | 刷新页面就没了 —— 那正是这一片要修的东西 |
| 摘要给整段（不截断） | 那是"把工具返回发给前端"的另一种写法；200 字是"够看清答的是哪一条"的最小值 |

## 什么时候该重新看这条决定

- **知识库里开始出现买家私有数据**（订单、地址、账号）：那时 `snippet` 的放行要
  重新判 —— 现在敢放，前提是知识库只装公开的政策语料（ADR-0026）。
- **`citations` 让载荷明显变大**（语料涨到几百篇 / 对话很长）：改成只带"这一条答复
  可能用到的号"需要服务端解析答复正文，那要先把"不解析模型的话"这条放松。
- **来源卡片要做得更多**（打开原文、跳到知识库页面）：那时该有稳定的来源标识
  （slug / chunk 主键），而它们现在**没有**进载荷（历史回读拿不到 slug）——
  要么把标识塞进工具返回格式（模型也看得见），要么加库列。
- **出现第二种"需要引用"的检索源**（商品、网页）：`SEARCH_TOOL_NAME` 那一处判断
  与"每次检索占一段连续号"的约定要一起重看。
