# 吐过字就不再重发 —— 重试与换家都停，半截如实交出去

**Status:** accepted（2026-10-05）

**补 `0017` 与 `0025` 的交界处**：那两条讲的是「失败了怎么再试一次」（`0017`）与
「这家真的挂了就换一家」（`0025`）—— 两者都是**整条重发**。这一条说的是那两种兜底
在**增量已经吐出去之后**必须停手：用户的屏幕上已经有半截字，重发收不回它。
[`0025`](./0025-the-breaker-sits-inside-retry-and-the-backup-is-another-vendor.md) 决定
「谁先谁后」，这一条决定「什么时候连兜底也不做」—— 是同一件事的两面。

## 决定

1. **判据是「这一跳有没有把增量交给调用方」**（任一通道：正文 `on_delta` 或思维链
   `on_reasoning_delta`）。置位之后，这一跳**不再重发**：
   - 异常路径：瞬态错误（429 / 5xx / 连接断开 / 超时）也不再来第二遍（`0017` 的
     异常判据在这道闸后面失效）；
   - 响应路径：「上游中断」（`insufficient_system_resource`，`0017` 指引"稍后重试"）
     原样返回，由 loop 按既有契约上报 `SERVER_INTERRUPTED`；
   - 熔断层：**换槽也停**（`0025` 的"跳闸当场改走备份"在吐过字之后不做）——
     换家 = 用另一家把整条请求重发，与重试是同一种重发。
2. **闸的位是「每次调用各自的」**：`RetryingChatModel` 与 `FailoverChatModel` 各拿
   一个（`retry/delta_gate.py` 的 `DeltaGate`）。外层那一趟若在内层换过家，外层看到
   的是「这一趟有没有吐过字」；内层换槽前若已经吐过字，它先停 —— 于是"换家之后
   再吐一遍"这条路径根本走不到。**只有没吐过字的尝试才会进入下一次尝试**，所以
   那个位单调、不必每轮清零。
3. **回调自己抛错也算吐过字**：文本已经交到调用方手里了（先置位再 `await`），
   重发同样会重复。
4. **簿记与从前一致**：吐过字的那次失败**照记**——熔断闸按 `0025` 的规矩数它一次
   失败（它确实失败了），`on_retry` 的记录单也照发（吐字之前那些失败尝试一条不少）。
   闸只管「要不要把这一跳转给别人 / 再发一遍」，不管「这次失败算不算数」。
5. **失败之后：保留半截 + 一行说明**（共同定案，前端与业务层各自落地）——框架把
   异常如实上抛（异常路径）或把中断响应原样交出（响应路径），loop 照既有规矩发
   `error` 终局事件；已画出的半截**不清屏**。清屏等于让用户刚读的字白读，而"没答完"
   必须说清，否则读者会以为那就是全文。
6. **只对「挂了增量回调的调用」生效**：非流式调用、以及没挂回调的流式调用（跑分、
   CLI、摘要那类内部调用）行为与从前**逐字一致** —— 这条闸的位永远是 `False`，
   判据函数原样转发给 `0017` 的那份 `is_retryable`。

**落地**：`retry/delta_gate.py`（`DeltaGate`：转发两个回调 + 记「有没有吐过字」）·
`retry/chat_model.py`（异常判据与响应判据各接一道闸）· `retry/failover.py`（`record_failure`
照记，吐过字则不换槽）· `agent/loop.py`（`stream=True` 时挂两个回调 → `bus.emit`
`answer_delta` / `reasoning`）· 业务侧的开关：`CharApp/minimall/config.py`（`CHARAPP_STREAM`）·
`CharApp/minimall/service.py`（`MinimallService.stream` + `session_for` 透传）·
`CharApp/minimall/server.py`（服务入口显式打开）· `client/session.py`（`ChatSession(stream=)`）·
`.env.example`（`CHARAPP_STREAM` 与「录制回放必须关掉它」）· 用例：
`tests/test_retry_chat_model.py`（吐字后断流只发一次请求 / 中断不重试 / 吐字前照旧重试的两条对照）、
`tests/test_retry_failover.py`（跳闸不换槽 + 组装形状）、`CharApp/tests/test_server.py`
（开关两态 + env → 零件 → 事件）。

## 为什么需要它

- **「半截 + 从头再来」比「半截 + 一句说明」糟得多**：重发会把完整答案再吐一遍，
  用户的屏幕上出现「前半句没了 → 后半句接在旧半截后面」这种拼接；收尾那句说明反而
  是最轻的补救。
- **重发还白烧一次钱**：中断响应那条路径上，被丢弃的那次**已经计费**（`0017` 的
  `on_retry` 记录单记的就是它）—— 而它换不回任何东西，因为半截已经不可收回。
- **值得一条 ADR 的原因**：三条判据都占 —— **难回退**（改回来要动重试策略与熔断
  切换时机）；**不看会疑惑**（读 `retry/chat_model.py` 的人一定会问"这里为什么不
  重试"）；**有真权衡**（放弃一部分"本来能救"的失败，换观感与不重复计费）。

## 代价与边界

- **吐过字之后的瞬态失败不再兜底**：极端情形（刚吐两个字就断连）下，一次本来能靠
  重试救回来的运行就此失败。这是有意的取舍：能救的那种失败绝大多数发生在**首字之前**
  （连接建立、首包），那时这道闸还没置位，`0017` 的重试原样生效。
- **对「上游中断」也不重试**：那条指引（"稍后重试"）在**没有输出**时仍然有效 ——
  本闸不管那种调用；只有已经吐过字的才原样返回。
- **半截的展示归前端**（C28）：框架只保证「不重发 + 半截事件已经发出去」，页面上
  「保留 + 说明」是渲染层的事（`error` 事件到达时不清空答复区）。
- **不做「遍数覆盖」**：让前端按"这是第几遍"覆盖缓冲（见替代方案 A）—— D 落地之后
  它用不上，留作将来（真机上若"吐字后失败"频繁到影响观感，它是首选补救）。
- **闸是进程内的**：与 `0025` 的闸同一性质（多实例部署下各进程各管各的）。
- **录制回放那条线不吃这条**：样本是非流式的（请求体里 `"stream": false`），
  `MockLLM.replay` 不看 stream 参数；而 `RecordingChatModel` 要求非流式的
  `response.raw` —— 录样本时**必须把增量渲染关掉**（`.env.example` 里写着）。
- **不算「吐过字」的东西**：工具调用分片（`tool_calls` 的 arguments 增量）不经这两条
  回调；「过程叙述被搬进过程行」发生在前端（C28），对服务端来说它一样是"已经交出去了"。

## 考虑过的替代方案

四条备选（A–D）里 **D 就是本 ADR 的决定**（判据只挂"有没有交出去"这一个事实，
不需要新增事件字段，也不牺牲首字之前的兜底）；下表是被否掉的那三条与两条边角做法：

| 方案 | 为什么否掉 |
|------|-----------|
| **A. 前端按"遍数"覆盖**（重发时给事件带个遍数，前端认出新的一遍就整体覆盖） | 事件契约里没有"遍数"这个概念，要新增一维状态；而且第二遍的字会先盖掉第一遍再被写回来，观感是闪烁。更根本的是：服务端明明知道"重发会重复"，却把这个判断推给前端 |
| **B. 服务端扣住不发**（等这一跳确定成功再成批吐） | 那就不是增量渲染了 —— TTFT 回到原样，这一批（C26–C29）的目的整个丢掉；扣住的那份缓冲还要无界增长 |
| **C. 流式一律不重试**（只看"这次调用是不是流式"） | 把"首字之前"那些本来能救的抖动一起放弃：连接没建立、首包没来时的失败与从前的失败没有区别（没有半截问题），重试它们既不重复也不伤观感 —— 白白多一次失败收场 |
| 重试时发一个"清屏"事件让前端把半截擦掉 | 用户读过的字凭空消失，比"半截 + 说明"更糟；而且"擦掉再写一遍"仍然花两次钱 |
| 让调用方自己决定"这一跳失败要不要重发"（把判据挂在业务侧） | 重试与熔断都在框架里，业务看不见"这一跳"；而且这是模型层的通用语义（谁用框架都该是这个行为），不是某个业务的偏好 |

## 什么时候该重新看这条决定

- **若"吐字之后失败"在真机上频繁到影响观感**（日志里数 `ModelConnectionError` 之后
  跟着 `SERVER_INTERRUPTED` 的运行占比）：先怀疑网络与上游，再考虑 A 方案（前端按
  遍数覆盖）作为补救 —— D 的取舍本身不必推翻。
- **若上游将来支持"从某个 offset 续写"**（同一请求带着已产出的前缀继续）：那时
  "重发"可以不必重吐，这道闸可以放宽成"续写而不是重发"。
- **若增量消费口不止一个**（比如同时推给多个前端 / 落一份到别处）：闸的判据
  （"交给调用方"）要跟着想清楚是哪一个口。
