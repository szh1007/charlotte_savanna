# 「退款中」做成订单状态的一个取值，接受两个状态机耦合

**Status:** accepted（2026-09-21）

## 决定

`Order.Status` 新增 `REFUNDING = "refunding", "退款中"`：

- 买家**申请退款** → 订单置 `refunding`
- 管理员**打款** → 订单置 `refunded`（同时写 `refunded_at`）
- 管理员**驳回** → 订单**恢复申请前的状态**

「恢复」靠 `RefundRequest` 上申请那一刻快照的 `order_status_before`，**不靠时间戳推断**。

## 为什么需要它

买家看自己的订单列表时，一张正在退款流程里的订单如果仍显示「已发货」，会以为还能收货；显示「已取消」又不对（取消是买家单方终止、即刻退钱，与退款是两回事，见 `CONTEXT.md`）。**订单状态得能表达「这笔钱正在退」这个事实。**

而且 PRD 早就开了这个头：`Order.Status.REFUNDED`（已退款）从建表起就在枚举里，只是从没有代码写过它。加 `refunding` 是**同一思路的延伸**，不是新发明 —— 原来只在「退款完成」那一刻联动，现在延伸到「退款进行中」。

## 代价：两个状态机由此耦合

`RefundRequest.status`（`requested` / `approved` / `rejected` / `refunded`）与 `Order.status` 必须在**四个转换点**上同步：

| 动作 | `RefundRequest.status` | `Order.status` |
|------|----------------------|----------------|
| 买家申请 | → `requested` | → `refunding` |
| 管理员批准（填金额） | → `approved` | 不变（仍是 `refunding`） |
| 管理员打款 | → `refunded` | → `refunded` + `refunded_at` |
| 管理员驳回 | → `rejected` | → **恢复 `order_status_before`** |

**任何一处漏了就是数据不一致。** 这个耦合是有意选的，代价用一条**把四个转换全钉住**的测试来兜 —— 而不是靠读代码时的注意力。

两个附带结论，都写进服务函数的 docstring：

- **`refunding` 自动挡住了不该发生的事**：`cancel_order` 只认 `pending` / `paid`，Admin 发货 action 只认 `paid`，`receive_order` 只认 `shipped` —— 退款中的订单自动不能被取消 / 发货 / 收货，三个地方一行都不用改。
- **驳回必须"恢复"而不是"推到某个终点"**：驳回意味着「这笔退款不成立」，订单应当继续正常流转（该发货发货、该收货收货）。把它推到 `cancelled` 是错的 —— 取消是买家终止订单，驳回不是。

## 考虑过的替代方案

- **`Order` 上加一个独立的 `refund_state` 字段**（`null` / `requesting` / `approved`），订单 `status` 完全不动。工程上更干净：两个状态机不耦合，驳回只要把 `refund_state` 置空，也不需要 `order_status_before` 快照。**否掉的理由**：订单的展示状态变成两个维度的组合（`shipped` + `requesting` 该显示成什么？），组合数是乘积，每个消费方（订单列表、详情页、DRF 序列化器、Admin）都要自己拼一遍。而实际会出现的组合只有寥寥几个 —— 用一个枚举值表达反而更直白。
- **不加状态，买家侧展示时联合查询 `RefundRequest`** —— 本质同上，且订单列表要多一次 join 才能显示对。
- **驳回时不恢复，让订单停在 `refunding`** —— 否。订单会卡死：既不能再取消（`refunding` 不在 `cancel_order` 的白名单里），也不能再申请退款（那一单的退款已被驳回），买家只能看着一个永远不动的状态。
- **驳回时推到 `cancelled`** —— 否。见上：取消与退款是两件不同的事，把驳回说成取消是误导买家。

## 什么时候该重新看这条决定

- **如果退款流程再加状态**（比如「审核中」→「处理中」→「已批准」），订单状态**不该跟着膨胀** —— 那时该把订单侧收敛成一个「是否在退款中」的标记位，而不是继续往 `Status` 里加枚举值。现在只加一个是因为流程只有四步；加到第三个就该换模型了。
- **如果订单状态将来变成事件溯源、或者加了状态历史表**，`order_status_before` 这个快照字段就可以退场 —— 历史表里本来就有。当前不加历史表，是因为 `RefundRequest` 本身就是这条流水（谁申请、何时批、何时打款、何时驳），再加一张表是把同一件事记两遍。
- 本条**不影响** `REFUNDED` 的既有语义，也不影响 `cancelled` —— 三个都是终态，互不转化。
