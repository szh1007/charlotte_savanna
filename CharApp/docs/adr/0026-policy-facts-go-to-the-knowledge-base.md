# 政策事实进知识库，硬规则留在提示词 —— 判据是「答错了会怎样」

**Status:** accepted（2026-10-04）

**补 `0005` 与 L5 的交界处**：`0005` 讲的是「身份说明是参考、成本是归因」；
这一条讲**知识从哪来** —— 哪些内容可以交给概率检索，哪些必须每次都在上下文里。
它与 `0002`（浏览器 → BFF 用 POST）这类传输决定无关，与 `0015`（一次性凭据）
有一点是共通的：**判据都落在「错了会怎样」，不落在「哪种写法更整齐」**。

## 决定

1. **按「答错的后果」划边界，不按长短、新旧或体量划**：

   | 进知识库（可查的政策事实） | 留在提示词术语节（必须无条件遵守） |
   |---|---|
   | 受理窗口（付款后到确认收货 15 天内） | 取消与退款的区别（哪个动词走哪条路） |
   | 审批与打款时效、受理时间段 | 库存回滚以发货为界 |
   | 运费谁承担（本项目：全站免运费） | 下单不等于付钱、付钱不等于发货 |
   | 余额能不能提现 / 能不能转让 | 「我的」工具查的是谁的数据（身份不进参数表） |
   | 八个订单状态各自的含义 | 退款金额由管理员协商，助手不问买家「想退多少」 |
   | 商品与库存的实时性说明 | |

   **判据一句话**：政策答偏了可以纠正、可以道歉、可以改语料；规则答错了会产生
   **错误操作**（把该退款的单取消掉、把没付钱的单说成已付款）。前者交给检索，
   后者每次都在上下文里 —— 它不需要"被检索到"，因为它必须永远在场。

2. **载体是一张轻表**（`app/minimall/models.py` 的 `KnowledgeArticle`：title /
   slug / category / content(Markdown) / is_active / sort_order）。不建「知识库 +
   文档」两张、不做上传解析 —— 那条链路在 `charplot` 与 `rag_knowledge` 里已经
   证明过两次，第三次不加分；政策是短文，管理员在 Admin 里手写 Markdown 就够。

3. **摄取是「读端点 → 切分 → 向量化 → 全量重建」的一条手工命令**
   （`python -m CharApp.minimall.knowledge.index`）：Django 侧给一条
   `X-Internal-Token` 的内部端点（直查库、不走 Redis 缓存），CharApp 侧把它切分、
   向量化（bge-m3 稠密+稀疏）、`drop + create + insert` 进 Milvus 的
   `ca_knowledge`。**不做自动触发**：内容变更的频率是「管理员改一篇文章」，
   挂在保存动作上要处理异步与失败重试，那是另一件事；代价是"改完忘了跑"，
   由 Admin 保存提示兜住。

4. **内容一致性是纪律，也是测试**：语料里的事实必须与**代码真正执行的行为**一致
   （顺序按 `services.py` 写、金额与状态按 `serializers_agent.py` 写）。一个已经
   兑现的例子：订单总额不含运费（`create_order` 只累加明细小计），所以运费那篇写
   的是「全站免运费」，而不是编一个满额包邮的门槛。Django 侧有一组语料形状测试
   （slug 唯一可做主键、分类是模型选项、正文够长且有小节标题、正文不自带一级标题）。

5. **检索是补充，不是替换**：术语节一个字不动。C09 的 v5 只新增一节「政策问题
   先查 `search_knowledge`」，并在其中写明**查不到就如实说不知道**。

**落地**：`app/minimall/models.py` + `migrations/0019_knowledgearticle.py`（知识表）·
`app/minimall/knowledge_corpus.py`（六篇语料）+ `management/commands/seed_knowledge.py`
（装库，默认不覆盖）· `app/minimall/views_agent.py` + `urls_agent.py` +
`serializers_agent.py`（内部端点）· `CharApp/minimall/knowledge/`（documents /
chunking / embeddings / rerank / milvus / query_rewrite / retriever / index /
prewarm）· `CharApp/minimall/config.py`（`KnowledgeConfig`）·
`CharApp/minimall/server.py`（启动预热）· 提示词那半边在 C09（v5 新增「政策问题
先查」一节）。

## 为什么需要它

三条判据都占：

- **难回退**：它决定了两处内容的归属，而归属一旦漂了（规则被写进知识库），症状是
  「助手大部分时候对、偶尔把不该做的事做了」—— 那比整条链路不可用更难查。
- **反直觉**：同样是「政策」，为什么「几天能退」进库、「取消还是退款」不进？
  直觉会说"都是规则，放一起吧"，而这条判据给出的答案是按**后果**分。没有 ADR，
  下一个人（包括半年后的我们）会顺手把术语节里的内容"整理"进知识库。
- **有真实取舍**：两处维护（改政策要重跑索引）+ 一条检索链路（两个本地模型常驻
  内存）换来的是"政策可更新、可溯源、可扩量"，而硬规则那一半继续用最笨也最可靠
  的办法 —— 每次都写进系统提示。

## 代价与边界

- **政策事实不保证被检索到**：与术语节不同，它要经过「改写 → 向量化 → 混合检索 →
  精排」，可能召回失败。验收上这条是显式的：知识库里没有的政策，助手必须如实说
  不知道（C09 的 prompt 与 C10 的引用都在守它）。**别把"必须永远生效"的内容放进来**。
- **两处维护**：改完内容要在 Admin 里保存、再跑一次索引；Admin 的保存提示与
  seed 命令的输出里都写着这句话。**索引是手工的**（第 3 条），这是本阶段的最小
  选择，不是长期形态。
- **一致性没有编译期检查**：语料测试只守形状（slug / 分类 / 结构），守不了
  「48 小时是不是真的 48 小时」—— 那要靠评审与真机核对。已知的一处待办：
  提示词里「不许诺到账/发货时间」那条与知识库里的时效条款需要在 v5 里对齐
  （政策写的是"安排发货的时限"，不是对买家的承诺）。
- **常驻内存与检索耗时（2026-10-04 实测，本机 CPU fp32）**：
  - 两个本地模型常驻 RSS 约 **3.4GB**（bge-m3 + bge-reranker-v2-m3）；
    预热 7~8 秒（服务启动后台做，见 `knowledge/prewarm.py`）。
  - 两个模型**必须串行加载**：并行会撞 transformers/accelerate 的全局态竞态
    （`init_empty_weights` 期间另一个线程可能在装权重），症状是第一次推理抛
    `Cannot copy out of meta tensor`，且时好时坏。实测复现后改串行。
  - 单次检索：embed_query 约 0.22 秒；混合检索约 0.07 秒；
    **精排约 1.1 秒/对**（逐对前向）。所以召回量默认 **10**（不是 charplot 的 20），
    语料涨大时要动这个旋钮，或者把 reranker 留空走「降级不精排」。
- **同一个会话里，模型可能复用上一轮查到的条文**（2026-10-04 真机）：提示词说的是
  「先去查」，而上下文里已经有条文时它会直接用（那一次它想的是"我已经有 `[4]
  运费与配送说明` 了"）。对政策问题这是可接受的（省一次 7 秒检索），但推论要记住：
  **改完文章重跑索引之后，旧会话里那几段仍是旧的** —— 模型看的是自己上下文里的
  文本，不是向量库。演示或验收前新开一段会话最干净。
- **语料规模决定了 rerank 的价值**：当前 6 篇短文、每条召回都几乎是整库，
  精排的排序收益看不出来；它的价值要等语料涨到几十篇才体现。留着它是因为
  「检索链路该有什么」比「现在够不够用」更重要 —— 而它是可关的。
- **单集合、无软删**：`ca_knowledge` 一个 collection，下架靠全量重建的
  **物理剔除**（不是软删标记）—— 代价是每次重建都要重新向量化全部语料
  （6 篇 22 秒，含模型加载），换来的是"索引里没有第二个状态"。
- **切分参数按来源类型查表**（当前只有 `article`：Markdown 分隔符 + 500/50），
  与 charplot 按文件扩展名查表同一形状 —— 将来加「商品说明」这类来源时新增一行，
  不动切分逻辑。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|---|---|
| 政策全部塞进提示词（不建知识库） | 每问必带、改一次要重启；而且把"可查的事实"变成"模型必须记住的负担" —— 提示词越长，术语节的硬规则越容易被稀释（L4 的 A/B 已经量过前缀长度的影响） |
| 硬规则也进知识库（只留一句"以知识库为准"） | 违反第 1 条的判据：规则必须 100% 遵守，而检索是概率的。最坏情况不是"答得不好"，是"把不该做的做了" |
| 微调 / 长上下文（`DESIGN` #45 的三选一） | 微调：知识更新要重训，且本项目要的是"可溯源"；长上下文：语料会涨、每问必带整库不划算。RAG 是三者里唯一同时满足"更新便宜 + 可引用"的 |
| 拿商品表当语料（`Product.description`） | 现状核查过：本机只有 5 条商品，`description` 就是商品名重复一遍，没有可用正文（issue C08 的「现状」节） |
| 知识库 + 文档两张表 + 上传解析 | 那条链路在 charplot 与 rag_knowledge 已各做一遍；L5 的定位是最小可演示，第三次不加分 |
| `auto_id` 主键（`rag_knowledge` 的形） | 外部对不上 chunk 编号，只能回查；显式主键 `{slug}-{序号}` 让引用可反解来源（C10 要用） |
| 索引自动触发（挂 Admin 保存 / 定时任务） | 本阶段语料变更极低频，而自动触发要处理异步、失败重试与并发重建；手工一条命令 + Admin 提示是当下最小的可靠形态 |
| rerank 也并行/常驻多 worker | 先解决"有没有"（当前 CPU 逐对 ~1.1 秒）；真嫌慢时的旋钮是召回量、模型开关或换更小的 reranker，不是并发（并发在 CPU 上只抢线程） |

## 什么时候该重新看这条决定

- **语料涨到几十篇 / 多主题**：召回量、切分参数、精排价值都要重算；那时也该有
  RAG 评估（命中率 / MRR，`DESIGN` #48）来回答"检索到底变好没有"。
- **出现「规则被答偏」的 case**：第一反应是把那条规则挪回术语节，并回看是不是
  第 1 条的边界被写松了 —— 不要用"在知识库里也写了"来兜底。
- **政策改动变频繁**（比如运营每天改价保条款）：手工索引就该升级成自动触发，
  那时要处理的是并发重建与失败重试（不是几行 if）。
- **要按分类过滤检索**（政策 / 配送 / 售后）：`category` 已经随 chunk 进了
  Milvus，加一个 filter 即可 —— 但先问"单参数工具是不是更好调"（C09 的取舍）。
- **换 embedding 模型**：向量空间不兼容，必须全量 re-embedding（`DESIGN` #47 的
  那条），`CHARAPP_EMBEDDING_DIM` 与 collection 一起重建。
