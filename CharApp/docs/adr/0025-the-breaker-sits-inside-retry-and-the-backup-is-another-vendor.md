# 熔断包在重试里，备份换另一家 —— 切了谁，账就按谁记

**Status:** accepted（2026-10-04）

**补 `0017` 与 `0023` 的交界处**：那两条讲的是「失败了怎么再试一次」，这一条讲
「试了还是不行的这家，暂时别再打它」以及「换一家之后账怎么记」。`0023` 与 `0024`
关于工具超时的决定不受影响（那是工具层的事，这里是模型层）。

**与 [`0029`](./0029-once-a-delta-is-out-the-request-is-not-resent.md) 互指**（2026-10-05 补）：
那一条讲的是**什么时候连"重试"与"换家"都不做** —— 增量已经吐出去之后
（`delta_gate.py` 的吐字闸）。两条合起来才是完整的收场规则：没有输出时按这一条的
次序兜底（先重试、跳闸才换家），有输出之后一律停手、半截如实交出去。

## 决定

1. **嵌套顺序：`RetryingChatModel(FailoverChatModel(主, 备))`** —— 熔断闸在**里面**，
   重试在**外面**。闸看得见每一次物理调用（每次重试都数得到），计数才准；反过来套
   （熔断在外、重试在内）则「重试 3 次全挂」在熔断器眼里只是 1 次失败，闸要过很久才跳。
   打开时抛的异常**不声明 `retryable`**，重试层按 `0017` 的既有规矩立刻放弃，
   不在退避里空转。
2. **三态（关闭 / 打开 / 半开）只数「这家自己的账」**：默认判据就是 `0017` 那份
   `is_retryable`（429 / 5xx / 连接失败 / 超时）。参数错这类 4xx **不算** —— 换个模型
   发同样的请求一样会错，为它熔断毫无意义（那种失败原样上抛）。一次成功把连续计数
   清零（「连续」二字落在实处）。
3. **打开期间真的不发请求**：闸的裁决在调用**之前**（`acquire()` 不通就抛
   `CircuitOpenError`，一个字节都不发出去）；**半开只放一个探测**（占位与状态检查之间
   没有 `await`，于是「只放一个」是原子的）—— 否则冷却到点，积压的请求会一起涌出去
   把刚缓过来的下游再打挂。被取消的调用**归还探测位**、不计成功也不计失败（取消是
   调用方的决定，不是上游的病；不还的话那个模型再也放不出请求）。
   **迟到的结论一律不参与**：一次调用发出去之后，别的调用可能已经把闸拨开了 —— 它在
   上一次打开**之前**走出去、在那之后才回来。那种失败只归探测位、不记账：记了会再跳
   一次闸，把冷却期从头再数（刚被前一批失败拨开的闸，因为一个更早的失败多关一整个
   冷却期，并发一多就被无限推后）；同理迟到的成功也不能拿来合闸（一个旧结论推翻一串
   新证据）。判据是「闸不关着、而这次调用又不是那个探测」—— 半开探测位只有一个，
   剩下的只可能是跳闸之前发出去的那一次。
4. **切换发生在两个时刻**：① 每次发请求前按「主 → 备」挑一个还放行的；② **刚跳闸
   的那一跳当场改走备份**（同一跳之内，不等重试层退避）。第二条不可省：默认阈值 3
   正好等于默认重试次数 3 —— 只做第一条的话，「闸开」与「重试认输」是同一刻，备份
   永远等不到出场机会。两家都不能用时抛 `CircuitOpenError`（**不可重试**），它继承
   `ModelError`，于是 CLI / server / 业务降级那几条既有路径原样接住（对上层来说
   「熔断」与「模型挂了」是同一件事：这条路走不通）。
5. **备份是另一家（CLOSEAI，OpenAI 兼容端点），不是同一家的另一档**：同 provider
   换档在同源故障时会一起挂，等于没切。三样变量（`CLOSEAI_API_KEY` /
   `CLOSEAI_BASE_URL` / `CLOSEAI_CHAT_MODEL`）**齐全才算配了备份**，少一样就当没配
   —— 备份是加固，不是启动前提（只想跑主模型的人不必有第二家的 key）。
6. **账目：谁服务谁记**。运行层开一本「服务台账」（`contextvars` 作用域，按运行 /
   asyncio 任务隔离），模型层每拿到一次**成功的响应**记一个名字（失败的那几次产出
   0 个 token，不上账），收尾时记录员读它写 `runs.model`：一个模型服务过就记它
   （价目表按名查，于是**熔断切过去的那些运行按备份的单价记账**）；一趟里两家都用过
   （主模型先答过话、后来才跳闸）记**组合名**（`主+备`）。
7. **一趟里换过家时，金额按各家分别算再相加**（2026-10-04 补，本 ADR 初版这里是
   「金额留空」）。依据是模型层盖在响应上的那个名字：每次成功返回时
   `response.model = 服务方`（价目表的键，**不是**上游回显的那个 —— 回显说的是上游
   自己是谁，还可能带版本号），于是记录员顺着 `LoopResult.turns` 就能把每一轮的用量
   归到各家头上（`db/recorder.py` 的 `_usage_by_model` → `db/cost.py` 的
   `cost_of_split`）：各查各的价、各判各的峰谷、各推各的缺档，最后相加。明细里每一
   行都带着归属（`model`），屏幕上因此是**每家一行算式** —— 把一个人家答的用量按另
   一家的单价乘，读的人会得出一个与金额不同的数。
   **跨段也拆得开**（HITL 续跑的第二段手里只有本段的轮：快照里没有每轮的响应，
   `CheckpointState` 只存消息与计数器）—— 靠的是运行行上的那一列 `usage_by_model`：
   每一段收尾时把自己那一段的逐模型用量**并进去**（按模型名相加），于是第二段拿到的
   是整趟的拆账。三个口径写死：① 它是**整份覆盖**（记录员先合并好再交出去），与金额
   那两列「算不出来就不动」的规矩不同；② **只在归并结果与运行行那几列对得上时才
   写** —— 写一半进去会让下一段在脏数据上继续合，那比「这一趟没有金额」糟得多；
   ③ 对不上就退回单模型那条路（组合名查不到价 → 金额留空并写明原因），并把前一段
   已经写下那笔金额**作废**（`void_cost`）：它是另一套单价算的，留着比没有更糟。
   **同一趟运行分两段写同一行时，名字在记录员那里再合一次**（HITL：挂起 → 人确认 →
   续跑，两段可能落在不同模型上）：`runs.model` 是**一趟运行**的归因，不是某一段的，
   后一段直接覆盖前一段会让行上写着一个名字、金额却按它的单价算了**整趟**的 token。
   合并规则只有一条（`model/utils/config.py` 的 `join_model_names`：去重、按首次出场、
   两边都可能是已经拼过的名字）。
7. **状态是进程内的，加一层不动循环**：两个闸跟着包装对象走（同一进程里跨运行累积，
   正是它该有的样子）；`agent/loop.py` 一行未改（与 `0017` 的同款纪律：加一层模型
   能力不必动循环核心）。

**落地**：`retry/circuit.py`（`CircuitBreaker` + `CircuitPolicy`：三态闸与它的规矩本）·
`retry/failover.py`（主备包装）· `retry/serving.py`（服务台账）·
`retry/utils/{types,errors}.py`（`CircuitState` / `ModelSwitch` / `CircuitOpenError`）·
`client/app.py`（装配 + `fallback_model_from_env` + 终端那行切换提示）·
`client/session.py`（每段运行开一本台账，收尾按它记模型名）·
`model/utils/config.py`（`join_model_names` / `MODEL_NAME_SEPARATOR`：模型名怎么合）·
`db/recorder.py`（逐模型用量 `_usage_by_model` / `_merged_usage` + 跨段合名 +
`void_cost`）· `db/schema.py` + `alembic/versions/0006_run_usage_by_model.py`

`db/cost.py`（`ModelUsage` / `cost_of_split` / 每行带 `model` 与 `derived`）·
`db/repositories/runs.py`（`void_cost`：把已有金额作废）· `client/trace.py`
（拆账那趟每家一行算式）· `.env.example`（备份端点 + 价目表加一条）。

## 为什么需要它

- **`0017` 只解决了「再试一次」，没解决「这家真的挂了」**：重试三次全失败之后，运行
  照旧以异常收场；下一次提问又从头重试 —— 每一次都要等满退避，用户看到的是「一直慢
  然后失败」，而挂掉的那家被反复地打。熔断解决的正是这一段：**先别打了，换一家**。
- **不换家的代价是一次整段不可用**：单模型部署下，上游一挂就是「整个助手挂」；而
  这里换的是**另一家**，同源故障（同一家的限流 / 同一家的机房）不会再一起带走。
- **为什么值得一条 ADR**：三条判据都占 —— **难回退**（改的是模型层的收场方式与运行
  行的记账口径）；**反直觉**（`retry/` 里多出来的那个包装为什么必须在重试**里面**，
  以及「闸一开就立刻切」为什么不能等重试层）；**有真实取舍**（多付一家 key 与价目表，
  换来的是「闸开之前那几次失败」仍然真实发生过、必须如实上账）。

## 代价与边界

- **闸是进程内的**：多实例部署下每个进程各有一份闸（这个进程认为「这家挂了」不代表
  那个进程也认为）—— 跨实例共享闸状态属 #21（分布式锁那一族），本 ADR 不做。单进程
  的 server / CLI 是当前唯一的部署形态，够用。
- **仍算不出来的只有一种现实情形：那一列是 NULL** —— 也就是「升级前建的运行行、升级
  之后才续跑」（升级后新落的账不会有这个问题，那一列是每一段收尾时写的）。它退回
  「金额留空 + 写明原因 + 作废旧金额」，而且**不把半份写回列里**（免得下一段在缺了
  一半的账上继续合）。判据是最后一道闸：归并结果必须与运行行那几列逐个对得上。
- **两道兜底不是「情形」**（列出来是为了说清代码里为什么有那两个分支）：某一段没有
  任何带 usage 的响应（真发生的话是上游没回 usage —— 那时五列本来就是 None，理由报的
  是「上游没上报分量」，比「没配价」更准）；以及那一列读不懂（只由本框架写、形状固定，
  现实中只有「将来形状变了」或「有人手改过」两途 —— 读不懂就当没有，理由是收尾这条
  路上少一笔金额，比让整轮记不上账轻）。
- **逐模型那几份是「按响应归并」的，不是「按调用时刻归并」的**：一行 `runs.model`
  说得清「两家都用过」，却说不清「各占多少」—— 那件事由每轮响应上的名字 + 那一列说。
- **跑过上下文压缩的运行拆不开**：摘要那一次调用的用量也计进了运行行那几列，却**不属于
  任何一轮**（它不出现在 `LoopResult.turns` 里）—— 拆出来的和比运行行小，那道闸会拒
  （金额留空 + 写明原因）。要覆盖它得让「逐模型用量」也把这类非轮次调用算进去（比如
  让服务台账记用量），记在「什么时候该重新看」里；真机上暂未遇到（要长会话才会压）。
- **判据只比输入与输出，不比缓存那两档**（2026-10-05 真机实测）：后者曾经是各家上报
  口径不同的地方（DeepSeek 两档都给、OpenAI 兼容那家只给命中），拿它当闸会让「一家报
  一家不报」的组合永远验不过 —— 而那正是这一列要服务的场景。
- **未命中那一档改在解析层补齐**（同一天，同一个根因）：上游只给「输入总量 + 命中」时，
  `model/parse.py` 立刻做一次减法补上 `cache_miss_tokens` —— 补在这里, 下游三处
  （逐轮累加 -> 运行行那五列 / `runs.usage_by_model` / 金额折算）看到的就是**同一份完整的
  账**。改之前只有金额那一步会推, 于是真机上出现过「输入 7468 / 未命中 1000 / 命中 6233」
  那种行（金额按 1235 收费、账上只记了一半）；`db/cost.py` 里同样的推导保留作老数据与
  非常规来源的兜底。
- **那一列是派生数据**：它记的东西理论上能从「每轮响应 + 五列」重算出来，落库只是
  因为跨段的第二段手里没有第一段的轮。所以它不进 `RunFacts`（那不是运行行的账目列），
  而是收尾那一刻合并、验证、再写。
- **失败尝试的用量不在运行行的账里**：被重试丢弃的那次响应（`insufficient_system_resource`，
  **已经计费**）由 `0017` 的 `on_retry` 交回调用方挂预算；它不属于「这次运行产出了
  多少 token」，两个口径本来就分开。
- **「切过去」不等于「主模型不再被碰」**：冷却到点会放一个探测回主模型（这正是半开的
  意思），探测成功就切回来 —— 一趟很长的运行可能两头都用过（于是记组合名）。
- **两侧共用一套阈值与判据**：不给备份单独配一套（谁也不会给备份设不同的阈值）；真要
  各自一套，接口是现成的（`failure_threshold` / `cooldown_seconds` / `counts_as_failure`
  都在构造参数上），只是当前没这个需求。
- **默认值**：连续 3 次失败开闸 / 冷却 30 秒 / 半开 1 个探测（`CircuitBreaker` 的默认
  参数，装配处可覆盖）。它们只是默认，不是契约。
- **不重试到「这一家恢复」**：切过去之后就一直用备份，直到冷却期允许探测 —— 没有
  「探测某一家更快恢复」这类调度，也不做冷却期递增（探测失败只是从头再数）。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| `CircuitBreaker(RetryingChatModel(主))`（闸在重试外面） | 闸只看得到逻辑调用的最终结果：重试 3 次全挂才算 1 次失败，阈值 3 意味着 9 次真实失败才跳闸；而「点开重试的那一层」也是错的 —— 闸的职责是「数这家欠了多少账」，那件事只有物理调用层数的准 |
| 主模型一失败就切备份（不熔断） | 把每次抖动都甩给备份：429 本来等半秒重试就好（`0017` 的主场），却要换一家更贵 / 风格不同的模型去答，还测不出「这家到底好没好」 |
| 熔断器只做状态机、切换交给外层的策略对象 | 多一层要装配的东西，而真实差异只有一个「主 → 备」的次序；等出现「三家以上 / 按权重分流」再说 |
| **借道 `total_cost_detail`** 记逐模型用量（不加列） | 段 1 若是混用，它算出来的 `lines` 本来就逐行带着 model 与 tokens，第二段读回来即可 —— 省一次迁移。否掉：那列说的是「这笔钱怎么算的」，把「哪家产出了多少」塞进去，下一个人（包括半年后的我们）得先绕过这个弯才读得懂；而且它只对「段 1 算出了金额」的行有效（gap 行没有 lines） |
| 把段 2 的账目改成**本段增量** + 金额改成**累加** | 也能得到「两段各算各的再相加」，但要改 `runs.settle` 的核心口径（ticket 28 明写「重算不是累加」），而且**重放会加两次**（同一次 run 的 resume 可能被点两次）—— 重算语义下同一份累计值算出来还是同一个数，天然幂等。否掉 |
| 闸状态放 Redis，多实例共享 | 属 #21 的题目；现在部署形态是单进程（CLI / 单实例 server），先不引入跨进程状态与它的超时 / 续租问题 |
| 探测失败就让冷却期翻倍（退避式冷却） | 有用但非必需：连续失败已经由「探测」这一层隔开（一次探测失败 = 再等 30 秒），而递增会引入「冷却多久才是头」的新配置面。真出现「下游恢复很慢」的样本再加 |
| 备份用同一家的另一档模型 | 同源故障（那家的限流 / 那只机房）会把两个一起带走，等于没切；省下的只是一套 key，丢的正是这个功能存在的理由 |
| 让框架认业务注解决定「这个模型重要不重要」 | 框架不认识业务词汇（有防漂移用例扫源码守着），而「谁先谁后」是**装配**的事：`build_model` 一行就说明白，不必让框架去猜 |

## 什么时候该重新看这条决定

- **若那一列开始频繁「凑不齐」**（日志与金额留空的运行里反复出现同一个原因）：先
  查是哪一段的轮不全（模型层改过盖章？快照换了实现？），而不是放宽那条判据 ——
  「宁可没有金额，不给错的钱」是这条线不可动的那一半。
- **若哪天要把「各模型分别花了多少」拿去做别的**（成本看板 / 配额）：那一列就是现成
  的数据源，但**别在查询侧拿它重算历史金额** —— 金额按 ADR-0018 是收尾那一刻的价目
  表算死的，重算会与账单对不上。
- **若部署形态变成多实例**（#21 上桌）：闸状态与「哪家是主」都要重新想 —— 至少要让
  各实例的闸有一致的判据来源。
- **若接入第三家 / 开始按成本分流**：`FailoverChatModel` 的「主 → 备」次序要升级成
  一个候选集合（现在的接口里 `_slots` 已是元组，扩展点在），那时这条决定里「切换时机」
  的两条仍成立，变的是「挑谁」。
- **若阈值 / 冷却的默认值在真机上明显不合适**（要么太灵敏要么太迟钝）：先把 .env 与
  装配处的值调一遍并记下样本，再回来改默认值 —— 默认值是该被真实数据推着走的。
