# 压缩的估算改成「启发式 + 固定开销校准」；触发判据量的是投影，不是账本

**Status:** accepted（2026-09-23）

## 决定

两件事一起定，因为它们是同一条故障链的两端（那条链叫「估算到底准不准」）：

1. **`AnchorTokenCounter` 退役，换成 `CalibratedTokenCounter`**（`CharAgent/agent/compaction.py`）。不再记「锚 + 增量」，改记一个从上游真实用量反推回来的常量：`overhead = 真实 input_tokens - estimate(那次真发出去的列表)`，于是 `count(任何列表) = estimate(列表) + overhead`。协议跟着改一处：`TokenCounter.note_usage(usage, *, sent)` 收的是**那一份真发出去的列表**（从前收的是「账本有几条」）。
2. **触发判据改量「这一轮的投影」，不再量账本**：`apply` 里的 `before` 从 `count(history)` 换成 `count(projected)`。

## 为什么需要它：原来那个锚，坐标在源头就是错的

锚式的隐含前提是「拿它量的列表一定是账本那条 append-only 线的延伸」。压缩把「送出去的」从账本里分出来之后，这个前提**在压缩上线的那一天就破了**，而它造成的两个方向的错各自都很极端（2026-09-23 最小复现，注入 `input_tokens=8000`、锚定 4 条）：

| 调用 | 结果 | 真实情况 | 错向 |
|------|------|---------|------|
| `count(同一份视图)` | **415** | 8000 | 走了「更短的列表」守卫 → 整根锚丢掉，退回裸启发式，**低估 20 倍** |
| `count(账本 17 条)` | **13,291** | 账本自己的启发式只有 6,520 | 把「视图的真实量」当成「账本前 4 条的贡献」，又加了一遍账本尾部，**高估一倍** |

两个错各自伤到不同的判定：阈值判定（走账本）偏高 → 压得更早，方向还算安全；而**水位线试算（走视图）严重偏低 → 误判「已经压到位了」→ 提前停手**。后者不报错、不告警，只是压缩永远做不彻底。

第 2 件事不是附带修改，而是**必须跟着改的那一半**：原来的滞回靠「锚落到小值」提供 —— 压完那一轮发的是小视图，上游回的真实用量小，于是下一轮的估算落在阈值以下，不再压。锚一退役，这条机制就没了，而账本 append-only 只增不减，拿它判的话**压完一次就永远超线**，于是每轮都切一刀、每轮都烧一次摘要调用。判据改成投影之后滞回自己就长出来了：投影才是真正要发出去的东西，它因为上一刀已经推过切点而变小。

## 代价与边界

- **失去「用真实用量修正启发式比例偏差」的能力**。那个能力本来就是假的（见上表的第二个错），但也要认下：估算里从此留着比例型偏差（中文实际约 1.3 token/字，启发式按 1 算）。它对**相对判定**（阈值、水位线）影响小，因为它是比例项；真分词器接上之后连这一项也没有了。
- **`overhead` 随列表大小轻微漂移**：它是「真实 − 估算」的差，比例偏差会被它吸收一部分。换来的是**任何一份列表都走同一条算式**，而不是「有时精确、有时错得很远」。
- **校准项可以是负的**（启发式高估时）：如实照着调，不夹到 0 —— 夹了等于假装「启发式从不高估」，于是估算永远偏大、压缩压得比该压的更勤。
- **协议变了**：`note_usage` 的签名换了一个参数。它是框架内部 SPI，业务侧的消费者只有 CharApp 一个（`build_compaction_for`），改起来是「改一处 + 改测试」。
- **凡是量「省了多少」的地方，基线都必须是投影，不是账本**。这一条比它看起来重要：`clear_at_least` 那道门第一版就写错了（拿账本当基线），而账本里含着**上一次已经裁掉的段** —— 它们在投影里根本不出现，于是被**重复计**成这一次的节省。压过一次之后这道门就形同虚设，每轮都照切照烧一次摘要（2026-09-24 代码审查抓出来的）。同一个道理也约束 `saved_tokens` 的口径（它一直是「账本 − 视图」，那是**相对量**，不是「这次省了多少」）。
- **判据换了之后，`saved_tokens` 的口径也要跟上**：它一直是「账本 − 视图」（同一把字符启发式量出来的相对量），这一条没变；变的是 `estimated_tokens` 所在的算式。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 拆两个方法：`count_ledger()` 保锚、`count_view()` 用校准 | 保下来的那点锚精度只在「视图 == 账本」时成立，而那正是压缩上线后不成立的那一半。留一个「有时对有时错」的方法，比一个「一直大致对」的方法难解释得多 |
| 锚改记**视图**（记 `(锚, 视图条数, 摘要指纹)`） | 摘要一重压指纹就失效，退化成校准；多维护一个指纹，只换来「不重压的那些轮更准」 |
| 保留旧签名，让 `note_usage` 自己判断那次发的是哪一份 | 这个信息在 `count()` 被调用时已经丢了 —— 调用方（loop）知道，估算器不知道。硬猜等于把缺陷 1 换个地方重演 |
| 上真分词器（tiktoken / DeepSeek 自己的 tokenizer） | 与既有取舍相反（`utils/messages.py` 写明「中文分词器算中文同样不准，多一个依赖只换来假精度」）；且 DeepSeek 的 tokenizer 不保证开放 |
| 阈值量账本不变，靠 `clear_at_least` 挡住重复压 | 每轮仍会走一遍「试算 + 判门槛」（不花钱，但白算）；而 `clear_at_least` 的语义是「值不值得压」，不是「要不要压」—— 两件事混一处，`skipped` 那个诊断值就说不清了 |
| 用「账本大小 − 已裁掉那段的估算」当 `before` | 等于手工重算一遍投影，还少了截断与思维链清理那两项 —— 不如直接量投影本身 |

## 什么时候该重新看这条决定

- **若接上真分词器**：`count` 不再需要校准项，`overhead` 记 0 即可（协议与调用点都不用再动）。
- **若上游开始对「工具 schema 那部分 token」单独计价**：`overhead` 里混着工具 schema（实测约 3600 token）与提示词模板，要拆出来才归因得清。
- **若阈值改成按「窗口占比」表达**（而不是绝对 token 数）：判据仍是投影，但水位线的算法要重推 —— 那时回看 0005 末尾那条「压缩的理由是窗口与首字延迟，不是省钱」。
- **若 `estimate_drift` 在真机上一直很大**：说明启发式的比例偏差比预期严重，那时该考虑的是「换一把尺子」（真分词器），而不是把校准项做得更复杂。
