# 对话记录落在框架自己的 db 层，不由业务侧另建一套

**Status:** accepted（2026-09-23）

## 决定

「给人看的对话记录」由**框架**写入与查询，落点是 `CharAgent/db/` 那套已经存在的表：

| 表 | 一行是什么 | 谁写 |
|----|-----------|------|
| `charagent_threads` | 一段会话（标题 / 状态 / `pinned_at` / `deleted_at`） | 记录员**懒创建**：第一次写某段会话时按 `thread_id` 取，没有就用首条用户消息当标题建一个 |
| `charagent_runs` | 一次问答（终态 / 轮次 / 用量分解 / 模型名 / 提示词版本） | 记录员**两拍**：跑之前 `begin` 建行，跑完推进到终态 |
| `charagent_messages` | 一条消息（`hidden` 决定推不推给前端） | 记录员在**收尾那一拍**一次写完这一轮 |

**业务侧一行 SQL 都不写。** 它只做两件事：把 `tenant_id` / `user_id` 放进
`RunContext`（框架按这两个字符串过滤与分区），以及在装配时把 `PgDatabase()` 交给
框架（`CharApp/minimall/server.py` 的 `build_service`）。会话列表、历史读取、以及
改名 / 置顶 / 删除三个动作的 HTTP 路由，全部由 `CharAgent/server/` 提供。

换来的是一条干净的分工：**「一段对话的两种表示」两份都在框架里**（账本在
`checkpoint` 包，记录在 `db` 包，见 ADR-0008），业务不认识任何一张表。

## 为什么需要它

**因为「没人用过的接口等于没设计过」正是这个项目立项的理由**（PRD §1 批评的就是
这类东西）。`charagent_threads` / `charagent_messages` 两张表与它们的仓储**早就写好
了**，`hidden` / `reasoning` / `tool_call_ids` 这些形状都设计完了 —— 但 L2.5 之前
**没有任何一个生产调用方**，它们只在测试里活着。一个从没有真实调用方的接口，设计
得对不对是没人知道的；L2.5 让它第一次被真实流量穿过。

它同时解掉一个真实的坑：**会话历史的唯一真相原本活在进程内存里**
（`client/session.py` 的 `_history`）。前端刷新能恢复（靠 `/history` 读内存），但
**服务一重启就全没了** —— 而且不只是前端看不到：`ChatSession` 构造时历史里只有
身份说明，`server` 路径从不 `resume()`，所以**模型也看不到上一进程聊过什么**。
换成 Postgres 快照后端**不会**自动解决这件事：`/history` 读的从来不是 saver。
把记录落进库、再补一条只读水合，才是这件事的落点。

## 代价与边界

- **Postgres 成为业务的硬依赖。** 商城主库是 MySQL，于是本项目现在有**两个库**，
  而且它们是两件不同的事：商城数据（业务事实）在 MySQL，对话记录（框架事实）在
  PG。运维上这意味着多一个要起、要备份、要迁移的东西。
- **框架从此要认识两个身份字符串。** `RunContext` 的 `tenant_id` / `user_id` 是
  「`payload` 不透明」那条纪律的**有意例外**：不透明载荷做不到「列出某个属主的
  会话」。两个字段**刻意不给默认值** —— 给 `""` 会让「忘了填」悄悄变成一个谁也
  看不见的空租户，而且没有任何地方报错。
- **记录是事后投影，与快照不是同一笔事务。** 帧在运行**中途**落盘，记录在运行
  **收尾之后**写。所以进程被 kill 在写入之前，最后一轮会丢：库里有帧、没有那一轮
  的记录。这是明写的边界，不是待修的 bug。
- **记录写不进去时降级，不阻断问答。** 写失败 → warning 日志 + 在记录员上留一个
  内存标记 → 这段会话**下一次**成功写入时先补一条可见的提示行（`role=system`,
  `hidden=False`），再写本轮。诚实边界：当时数据库大概率正不可用，「当次就告诉
  用户」很可能也写不进去；内存标记进程重启会丢；**那一轮的内容补不回来**，提示行
  只说明「这里少了一轮」。
- **`charagent_tool_calls` 至今没有生产调用方。** 表与仓储都在，记录员不写它 ——
  工具调用目前只进 `messages` 的隐藏行。它要等 L3 的可观测（按 run 查「每个工具
  花了多久 / 成没成」）才会被真的用上。**如实记在这里**：这条 ADR 的理由是「让
  框架的 db 层有真实调用方」，而这一张表还没兑现，别把三张表的成绩记成全套。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| **业务侧用 Django / MySQL 新建模型** | 框架已经把这套设计完了（`hidden` / `reasoning` / `tool_call_ids` / 用量分解），业务侧重建等于**抄一遍**，而且此后两份设计会各自漂。更要紧的是：这样「同一段对话的两种表示」会**分居两个库**（账本在 PG、记录在 MySQL），一条「这轮为什么这样答」的排查要跨库对齐 |
| **只靠快照，不另建记录** | 用错了表。快照是**循环的工作数据**：内存后端下它跟着进程走，Redis 后端的 `MAXLEN` / TTL 会吃掉历史。而且它的形状是**给模型**的（工具往返、推理链、补做挂起），不是给人看的 —— 前端要的是「用户问了什么、最终答了什么」 |
| **让业务自己加那几条 HTTP 路由** | 那样框架的 `db` 包就永远没有生产调用方 —— 回到本 ADR 开头那个问题。路由本身也不含业务知识：它问的是「我聊过哪几段」「这段聊到哪儿了」，把身份换成任何别的东西都成立 |
| **记录写在 `server/` 层（HTTP 入口）** | CLI 入口就没记录了。两个入口共用一段装配（`MinimallService`）正是本项目已经吃过的教训（业务曾经抄了一份交互循环，抄完当场开始漂）。记录的落点因此要挂在**运行生命周期**上，而那是框架的地盘 |
| **靠事件流重建记录**（BFF / 业务订阅 SSE 自己攒） | 事件流是**发给浏览器**的东西：它被脱敏过（ADR-0003）、工具结果截到 200 字符、且它断了就是断了。用一份有损的展示流去重建一份要求保真的记录，方向反了 |

## 什么时候该重新看这条决定

- **L3 的可观测落库时** —— 它要写的就是 `charagent_runs`（trace 一行 + JSONB 明细）
  与 `charagent_tool_calls`（每个工具的耗时）。那时这张表才有调用方，本 ADR 那句
  「还没兑现」应当被划掉。
- **若记录量级长到需要归档或分区**：`messages` 是唯一会无界增长的表（软删不删行，
  见 ADR-0007）。要动的是留存策略，不是把记录搬回内存。
- **若出现第二个业务上下文**（第二个租户、第二个 tenant 字符串）：`tenant_id` 那
  一列正是为它准备的 —— 但它至今只有两个真实取值（`minimall` 与 `minimall-cli`，
  同一个人的网页端与命令行），「多租户」这件事目前是**设计上成立、流量上未被验证**的。
