# 删除一段会话是软删（行与消息都留着）

**Status:** accepted（2026-09-23）

## 决定

用户在左栏点「删除」时，我们**只写一个 `deleted_at` 时刻**（`charagent_threads`
的一列，`0002_thread_management` 加的），**不删任何行**：

- `charagent_threads` 那一行留着（只是带上 `deleted_at`）；
- 它名下的 `charagent_runs` / `charagent_messages` / `charagent_tool_calls` /
  `charagent_checkpoints` 全部**原样留着**；
- 「删除」在**所有**会话查询里表现为一个过滤条件（`deleted_at IS NULL`），封在
  `ThreadsRepository._visible()` 一处；
- 用户能观察到的效果只有一条：**它从列表里消失了**。

同一个动作在三个层次上的含义各不相同，这也是这条决定最容易读岔的地方：

| 层次 | 效果 |
|------|------|
| 用户看到 | 列表里没了；继续问也不会问进那一段 |
| 接口 | `POST /conversations/delete` 写一个时刻，**幂等**（再删一次照样 200） |
| 库里 | 一行都没少，只有一列从 NULL 变成时刻 |

## 为什么需要它

**硬删会连带删掉两样东西，而那两样都有主。**

第一样是**成本**。运行表（`charagent_runs`）上挂着 token 用量，L3 的成本记账要
按它回答「上周花了多少钱」。外键的动作是 CASCADE（`runs.thread_id` →
`threads.thread_id`），所以硬删一段会话 = 让上周的账单凭空少一块 —— 而且**没有
任何地方会报错**，只是数字对不上。

第二样是**证据**。快照（`charagent_checkpoints`）是回答「模型为什么忘了 / 当时它
看到了什么」的唯一材料，而 ticket 24 起 `checkpoints.thread_id` 也是 CASCADE。
用户删掉的那段对话，恰恰可能是几天后要排查的那一段。

**而用户要的本来就不是「销毁」。** 买家点「删除」的意图是「别让它占着我的列表」，
不是「从贵公司的数据库里抹掉这段历史」。这两个诉求在绝大多数产品里都是分开的：
前者是**列表**的事，后者是**留存策略**的事（谁、多久之后、依据什么删），而后者
要有法务与运维参与，不是前端一个按钮能定的。把它们合成一个动作，等于让用户的一次
误点触发了本该由策略决定的事。

顺带一个副作用：软删让「删除」这个接口天然幂等。用户连点两下、两个标签页各按一次
（第二个标签页拿的是过期列表），都不会冒出「找不到这段会话」——因为那一行一直在，
WHERE 里只有归属条件。

## 代价与边界

- **数据只会变多，不会变少。** 真删要有人（或一条定时任务）在很久之后做，本项目
  **不做**，这是明写的已知边界。代价是可预见的：库会随着被删的会话一起长。
- **「删除」不等于「看不见」，但也不等于「还列得出来」。** 行还在库里，按编号
  `get` 得到、拿 SQL 也查得到；但**列表查询一律不返回它**（`list_for_tenant` 与
  `list_active_with_messages` 都带 `deleted_at IS NULL`）—— 连管理端那条也一样，
  因为「删掉的还算不算这个租户的会话」只有一个诚实的答案。要一个「含已删」的视图，
  得**另开一个显式说明意图的方法**（本项目暂时不铺）。将来若要做「彻底删除」，那是
  **新的一条决定**（谁来删、多久之后、怎么审计），不是把这一列改回硬删。
- **列表少了一类「删掉的」视图。** 用户删完之后想找回来说不了话，只能找客服 ——
  本项目没有「回收站」，也没有「撤销」。做一个是产品决定，不是这一列能顺带给的。
- **两次删除的时刻会被覆盖。** 第二次调用写的是第二次的时间戳（想留住第一次要
  写 `coalesce(deleted_at, :now)`）。不换：那是个表达式，而仓储的写入形状一律是
  「等值条件 + 直接给值」（测试替身也只认这个形状），为一列排查用的时间戳破掉它不值。

## 考虑过的替代方案

- **硬删（`DELETE FROM charagent_threads`）** —— 否。上面那两样东西（成本、证据）
  会跟着 CASCADE 一起没，而且**不可逆**：用户误点一下就没了。要真删的那一天，
  应该是**策略**在删，不是按钮在删。
- **只把会话从列表查询里过滤掉，不落任何列** —— 说不通：没有那一列就没有「哪些被
  删了」这个事实，「过滤掉」也就无从说起。而且用户看到的会是"删了又回来了"（列表
  查询有几条，哪条都在自己写过滤条件）。
- **加一个 `status = 'deleted'` 取值（复用 `ThreadStatus`）** —— 也不行：`status`
  回答的是「这段对话在业务上算不算进行中」（`active` / `closed` / `escalated`），
  那是**客服的事**；「用户把它从自己列表里删了」是**用户的事**。两件事会独立发生
  （一段已归档的会话照样可以被用户删掉），挤进一列之后，任何一次读取都得先问自己
  「我现在关心的是哪一件」。
- **留着行、但把 `messages` 也一起标删** —— 否。消息是**记录**，而记录这一层的
  契约是「用户看到的历史永不改写」（见 ADR 里那条账本 / 视图分离）。为了一个列表
  偏好去改写记录，是把两层混在一起。

## 什么时候该重新看这条决定

- **要做「彻底删除」或「留存策略」时** —— 那是这条决定的另一半（本 ADR 只定了
  「按钮不真删」，没定「多久之后真删」）。
- **成本记账（L3）哪天不再挂在 `runs` 表上时** —— 硬删的第一个理由会跟着消失，
  届时要重新算这笔账。
- **会话量级长到 `deleted_at IS NULL` 这个过滤条件开始拖慢列表时** —— 那时要的是
  索引（`(user_id, deleted_at, updated_at)` 之类），不是改回硬删。
