# MCP 工具重名：默认当场报错，前缀是唯一的出路

**Status:** accepted（2026-10-05）

**消费侧唯一"不显然"的那条规则**（`CharAgent/docs/DESIGN.md` ⑨ #50 点名要解决的
"同名仲裁"）。它不是业务规则而是框架规则，但决定是在本仓这四条经历里统一记的，
所以落在这一页。

## 决定

1. **重名一律拒绝**：跨 server 出同名工具时，`McpToolProvider.start()` 当场抛
   `McpConfigError`，报错里带上两台 server 的名字与那个撞了的工具名。**不合并、
   不覆盖、不裁决优先级**。
2. **出路只有一条：给其中一台配 `tool_prefix`**（配置里的键，默认空）。配了前缀的
   工具名是 `前缀 + 远端原名`，调用时用的仍是远端原名 —— 前缀只改模型看到的那个
   名字，不改它在协议上打到哪儿。
3. **判据落在启动期，不落在调用期**：仲裁在 `start()` 里做完（`arbitrate`），
   于是"配错了"在**起进程**那一刻就知道，不必等到第一次提问。
4. **同一个 server 内部重名另报**（`McpServerError`）：MCP 规范要求一台之内工具名
   唯一，出现两个就是那台 server 自己的 bug —— 我们能做的只有把它说清楚，改法不在
   我们这边。

## 为什么这么定

- **"后注册的赢"是最坏的失败形态**：模型看到 `search` 这一个工具名，以为调的是 A
  家，请求实际打到 B 家。它拿到一个"看起来对"的结果继续往下答，而错在哪儿没有任何
  地方报错 —— 排查要从"模型为什么答错"一路倒推到"两家都叫这个名字"。
- **顺序敏感是隐藏的坑**：没人会记得"谁先连上的"这件事，配置顺序一调整行为就变，
  而两次运行的行为差异没有任何痕迹。
- **前缀是复现"两家都要"的那条正道**：多 server 场景下同名是**常态**（`search` /
  `read` 这类通用词），我们要给的不是"选出赢家"，而是"让两家都活着且各叫各的"。
- **默认不加前缀是刻意的**：工具名是给模型看的提示词（`search_products` 这种名字里
  的动词与名词就是路由线索）。默认给每个远端工具挂上 `文件系统_` 这样的前缀，等于
  替所有现有评测与 prompt 改一遍输入 —— 那是**用一个默认值换一次静默的行为漂移**。
  撞了才加，加的时候人明确知道自己在改什么。

## 代价与边界

- **多一层配置**：两台 server 撞名时，使用者要做一次决定（改名还是别连它），不能
  "先连上再说"。
- **前缀是拼接，不是命名空间**：`tool_prefix="fs_"` + 远端 `read` = `fs_read`。
  没有分隔符规范，也不做长度裁剪 —— 但**结果的名字要在本地过一遍模型侧的工具名规范**
  （字母 / 数字 / 下划线 / 连字符，1~64 字符），不合格当场报（`_checked_name`）：
  本地工具在 `@tool` 那层就有这道闸，远端工具是直接构造的，少了它就会一路带到上游
  变成一句看不懂的 400。
- **不做优先级配置**（"同名时优先用 A 的"）：那等于把上面第一条的危害包一层糖，
  而且模型侧仍然只看到一个名字。
- **仲裁只在启动期做一次**：远端工具集在连接期间不会再列（我们不轮询 `tools/list`）。
  远端中途换工具（MCP 有 `list_changed` 通知）**这一版不处理** —— 见下一条。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 后注册的覆盖前一个 | 就是上面"最坏的失败形态"；而且它是**静默**的 |
| 前一个胜出（先到先得） | 与上一条同害，只是方向相反；顺序仍然决定行为 |
| 自动加前缀（默认 `f"{server}_"`） | 名字是提示词的一部分，默认改名会一次改掉所有工具名（评测样本、prompt 里的引用一起漂）；且多数情况根本不会撞 |
| `server/tool` 命名空间 | MCP 工具名有字符集与长度约束（本仓的 `@tool` 也限 `[a-zA-Z0-9_-]{1,64}`），斜杠要靠各客户端自己改写，等于把同一件事推给下游 |
| 同名时按"谁先发现的"给后者加后缀 | 名字随机变化（这次跑叫 `search_2`，下次可能叫 `search`），比报错更难查 |
| 让业务侧自己传一份"重名例外表" | 把框架的通用规则做成业务配置；而这条规则与业务无关（谁接两台 server 都会遇到） |

## 什么时候该重新看这条决定

- **接的是同一家的多台 server**（同一套工具的多实例，比如两个环境）：那时"都要"是
  常态、区分只是环境维度 —— 自动前缀可能比"报错 + 手工配前缀"更合用。
- **MCP 的 `tools/list_changed` 进来之后**：远端工具集会变，仲裁就不能只在启动期做
  一次；那时要决定的是"变了之后要不要重连/重排"以及"新来的撞名算谁的"。
- **工具多到需要分组**（几十上百个工具，模型侧选择质量下降）：那时讨论的就不是
  同名仲裁，而是**工具路由**（先按 server 分组做一层筛选），前缀会变成那套机制的
  一部分。
