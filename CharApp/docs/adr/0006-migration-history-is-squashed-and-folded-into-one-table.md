# 迁移历史在发布前压缩成一条；版本表兼作审计表

**Status:** accepted（2026-09-23）

## 决定

两件事一起定，因为它们互为前提（没有压缩，「版本表兼审计」就答不全「上过哪几版」）：

1. **四条迁移压成一条**。`0001_core` / `0002_run_usage_breakdown` /
   `0003_migration_audit_log` / `0004_frame_run_linkage` 删掉，合成一条
   `CharAgent/alembic/versions/0001_core.py`（`revision = "0001_core"`，
   `down_revision = None`）。此后照旧：**已发布的迁移是冻住的历史，要改结构就加新的**。
2. **alembic 的版本表就是 `charagent_migrations`**（原先那张 `charagent_alembic_version`
   不要了）。版本表天生只有一行（当前 head），我们在这同一行上补两列：`name`（当前
   这一版的标题）与 `history` —— **`history` 是字典，键 = 迁移编号**，值 = 这一版
   **最近一次成为当前版**时的 `{from, at, by}`（`from` 为 null = 从空库起的那一步）。
   原先那张「一行一条迁移」的累积审计表随之取消。

压缩时还顺手重排了两张表的物理列序（回到 `db/schema.py` 的声明序）：`charagent_runs`
的五个用量列与 `last_checkpoint_id`、`charagent_checkpoints` 的 `run_id` —— 它们原先
都是 `ALTER ADD COLUMN` 追加在表尾的。`checkpoints` 的两列外键排在前面
（`thread_id` → `run_id` → `loop_id`），读的人先看到「它属于谁」。

## 为什么需要它

**压缩的理由是「还没发布」。** 那四个编号只在本机这一个库（`charlotte`）里跑过，
没有别的环境、没有别人的 alembic 记着它们。压掉不欠谁的，而收益是：新环境第一次
`alembic upgrade head` 时跑的是一条「一步到位」的初始迁移，而不是四条层层叠加的
历史 —— 读的人不必在脑子里做四次加法才知道表长什么样。

**两张表合成一张，是因为它们说的是同一件事的两种读法，却要时刻保持一致。** 旧设计
里 `charagent_alembic_version` 记「现在在哪一版」、`charagent_migrations` 累积「依次
上过哪几条」，任何一次迁移之后两者必须互相印证，否则就有一处在撒谎。而 alembic 把
版本表的形状写死了（`alembic/ddl/impl.py` 的 `version_table_impl`：必须有一列
`version_num`；`runtime/migration.py` 的 `get_current_heads`：**一行 = 一个 head**，
多一行就被当成「分叉的 head」直接报错）—— 所以那张表**不可能**长成累积形状，两张表
无法真正合一，只能二选一。既然「现在在哪一版」与「上过哪几版」只是同一条时间线的
两个读法，就让它们落在同一行里。

## 代价与边界

- **`history` 记的是「最近一次」，不是「首次」**：回退时改写的是**退到的那一版**那个
  键，所以那一版的「首次上线时刻」会被覆盖。换来的是**回退也留痕** —— 只记首次的话，
  一次 `downgrade` 之后这一行就在撒谎（旧设计里「应用插一行、回退删一行」那条性质
  正是靠这个保住的）。字典以编号为键，天生装不下「同一版被上过两次」的多次记录。
- **回退到 base 会连 `history` 一起清掉**：alembic 删掉唯一那一行（它在线模式从不删
  版本表本身），我们拦不住也不该拦 —— 回退到 base 就是「这张库回到未初始化」，留一
  行历史反而是撒谎。要留档就先导出。
- **版本表不再是「我们的表」**：`version_num` 与主键名（`charagent_migrations_pkc`）
  都由 alembic 定，所以它**不进 `db/schema.py` 的表定义**（声明一份只会与 alembic
  打架）。`alembic check` 会按 `version_table` 把它从代码侧与库侧**两边**排除，不声明
  照样零差异。形状与那两列的来历写在 `0001_core.py` 的 docstring 里。
- **钩子必须在两列被拆掉时安静跳过**：`downgrade base` 的最后一步是「0001_core 的
  downgrade 先拆两列，alembic 的回调后跑」—— 判一下列在不在（`information_schema`），
  否则一次本该成功的回退会失败在最后一步。
- **顺带补的那条外键有一条行为契约**：`charagent_checkpoints.thread_id` 现在是指向
  `charagent_threads` 的外键（`ON DELETE CASCADE`）。这一列不能为空，所以只能 CASCADE
  不能 SET NULL，于是**写帧之前会话行必须存在** —— 直接拿 `PostgresCheckpointSaver`
  单独用（不配记录层）的调用方要先自己建一行。如实记录在这里，因为它会让人在「帧写不
  进去」的第一次遇到时一头雾水。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 保留四条迁移，只在 README 里解释「为什么有四条」 | 每次新环境建库都要走四步；而四条里三条是「加几列 / 建张表 / 改个名」这种修补，读的人得到的只有噪音。压缩的成本此刻为零，以后只会越来越贵 |
| 压缩 + 保留两张表（版本表 + 累积审计表） | 用户要的正是消掉这处冗余；且 alembic 那张表不由我们做主，留着就是「同一件事记两处、还要求两者永远一致」 |
| `history` 用**数组**：每跑一步追加一条 `{from, to, at, by}` | 键就是编号，一条即一版 —— 数组的「第几条」是位置，不是身份：查「这一版什么时候上的」要扫一遍，同一版上过两次也分不清。**本 ADR 的定稿就是从这个形状改过来的**（2026-09-23，用户判定） |
| `history` 用字典但**只记首次**（回退不改它） | 回退在审计里不留痕。既然要记，就记「最近一次成为当前版」——它同时回答了「现在这一版是什么时候成为当前版的」 |
| 合并成一行，审计信息用 `applied_at` / `applied_by` 两个独立列 | 那两列是 `history` 里当前那一版那条的投影 —— 同一件事存两处，一处漏更新就自相矛盾 |
| 把 `checkpoints.thread_id` 改成可空 + `SET NULL`（与 `run_id` 的哲学一致） | 会出现无人认领的孤儿帧，且「分区键」这个语义被弱化。帧属于一个真实会话，这是对的语义 |

## 什么时候该重新看这条决定

- **发布之后**：`0001_core` 与它后面新加的每一条都进入「冻住」状态。压缩是发布前的
  一次性动作，**发布后再没有这种例外** —— 若那时还想合并，代价是「别的环境里的
  `version_num` 失去对应的脚本」，只能靠 `stamp` 打补丁。
- **若「首次上线时刻」真的被需要**（多人多环境、要追第一期是何时上的）：`history` 的
  值里加一个 `first` 字段即可，形状不必推倒；但先问清楚谁要拿它做什么 —— 多数场合
  想要的是「最近一次」。
- **若 alembic 改了版本表的形状约定**（它是内部约定，`_pkc` 那个主键名不在公开 API
  里）：`0001_core` 只依赖「表存在 + `version_num` 列」，加列不影响；但 `alembic check`
  的排除行为如果变了，要重新确认「不声明它」还成不成立。
