# 挂起不建审批表：一次工具调用的状态就是审批单

**Status:** accepted（2026-09-24）

## 决定

HITL 的挂起**不引入任何新表**。一次挂起的全部状态由两处既有结构表达：

| 状态 | 落在哪 |
|------|--------|
| 挂了什么（哪次调用、什么工具、什么参数） | `charagent_tool_calls` 那一行（`status = needs_approval`） |
| 谁批的 / 什么时候批的 | 同一行的 `approved_by` / `approved_at`（`approved_at IS NULL` = 还没批） |
| 欠着哪几条没做（恢复时补做哪一个） | 快照里的 `Suspension.pending`（`checkpoint/utils/types.py`） |

`Suspension.approval_id` **保持 `None`** —— 这不是"暂时留空"，是这条决定的结论：那个字段在本项目里**永远没有**指向对象（它的 docstring 早就写明「P0 允许为 None —— 机制先备好，审批表与本字段的接线留待后续阶段」，本 ADR 就是那个"后续阶段"给出的答案：不接）。

## 为什么

**审批单在这个项目里没有独立生命周期。** 它没有"审批单列表"、没有多级审批、没有审批意见、没有转交、没有审批单状态机 —— 它就是一个**二元事实**："这一次工具调用，批了没有、谁批的、什么时候"。而这个事实的天然宿主是那次工具调用自己。

**再开一张表等于把同一件事存两份。** 两份必然漂移：一种最可能的漂移是工具调用行活在事务里、审批行活在另一个事务里，于是"库里有审批单、但调用行还是 `needs_approval`"这种状态迟早出现，而它**没有任何一条路径能自愈**。

**更重要的一层：`db/README.md` 已经在 2026-09-18 把 `approvals` / `audit_logs` 等四张表移出了框架**（归业务侧独立迁移链）。那条决定回答的是"如果有审批表，它在业务侧"；本 ADR 回答的是更强的那个问题——**根本不需要表**。两条不冲突，方向一致。

## 代价与边界

- **运行重启后"还有没有未决挂起"必须查 PG，不能查内存。** `server/sessions.py` 的 `_busy` 集合目前管的是「运行中」，而挂起时 run 会 `release(thread_id)` —— 于是挂起期间会话**不忙**，用户可以发新消息撞上未决快照。修法是把 `_busy` 的语义扩成「运行中 **或** 有未决挂起」，但**判据必须是 PG 里的那一行**：`sessions.py` 自己写明部署是单进程、重启后内存集合清空，只靠内存拦不住。这条落在 issue 34。
- **一次挂起只挂一条需审批的调用。** 框架的 `Suspension.pending` 是列表（形状允许一批），但"一次确认配一份一次性载荷"这个语义要求载荷的归属无歧义。若模型一轮发出两条需审批的调用，只挂起第一条、其余以「请先处理前一条」的理由回填。这条在 issue 34 定实现、issue 35 验。
- **将来真要做"审批单作为一等实体"**（审计、多级、转交、超时升级），缝合点就是那个一直留着的 `approval_id`，加上一张业务侧的审批表。届时本 ADR 改为 `superseded by`。**判据是"审批单开始有自己的生命周期"**，不是"审批次数变多了"。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 业务侧建审批表，`approval_id` 指向它 | 框架要**跨层读一张业务表**才能完成恢复，把 `CharApp → CharAgent` 的单向依赖弄脏；而它换来的"可追溯性"由工具调用行 + 帧 + 运行记录三者已经给了 |
| 框架侧建 `charagent_approvals` | 直接推翻 2026-09-18 那条分层决定，且没有任何新论据支持推翻它 |
| 不落 `charagent_tool_calls`，只用快照里的 `Suspension` 表达 | 挂起态就成了**快照内部的私有数据**，查不到、聚合不了（"上周挂起了几次"要解 JSONB），而 `needs_approval` 这个状态值在表里**本来就是为它留的** |
| 在 `charagent_runs` 上记账（`suspended_at` / `approved_at` 列） | 挂起是**每条调用**的粒度不是每次运行的：一轮里可以有一条退款在等批、另一条查询已经跑完。记在 run 上会把粒度弄丢 |

## 什么时候该重新看这条决定

- **若"审批单"开始有独立生命周期**（多级审批 / 审批意见 / 转交他人 / 超时自动升级）：那时它不再是一次调用的一个状态，缝合点是 `approval_id`。
- **若同一个会话需要多个未决挂起**（比如"两笔待确认的支付"）：本 ADR 的"一次挂一条"是这条决定能成立的一半原因，届时这条边界要一起重看。
- **若挂起要支持"审批人不是发起人"的通用角色分离**（DESIGN #25 提过）：买家本人确认自己发起的操作，在"发起方是模型"这个前提下不构成自我审批，所以现在不做；换成真人的多角色审批时，`approved_by` 一个列就不够表达了。
