# MCP 暴露侧：只开只读工具，且只代表配置里那一个账户

**Status:** accepted（2026-10-05）

**兑现 [`0001`](./0001-internal-endpoint-trusts-declared-user-id.md) 自己写下的那条判据**：
那一条说「什么时候必须还」的判据是**信任域有没有被拆开**，并留了一句判断
——「L1b 网页版仍在单机单域内，触发点在把助手服务部署出去的那一刻」。MCP 暴露侧
**正好把信任域拆开了**：接上来的客户端不是 Django 转发层，它没有浏览器的 session
cookie。这一条就是那次触发时按判据做的处置。

## 决定

1. **只暴露只读工具**，判据是本地工具上的 `writes` 注解（不是手抄名单）——
   `CharApp/minimall/mcp_server.py` 的 `read_only_tools` 一处过滤，11 个只读上线，
   8 个会改数据的（`add_to_cart` / `update_cart_item` / `remove_cart_item` /
   `clear_cart` / `place_order` / `cancel_my_order` / `request_refund` /
   `pay_my_order`）一个不上。以后新增写工具，它天然进不了这张表。
2. **只代表一个账户**：买家 ID 从 `CHARAPP_MCP_USER_ID` 读，没配就**起不来**
   （fail closed，同 `CHARAPP_INTERNAL_TOKEN`）。工具的 schema 里**没有任何身份
   参数** —— 客户端不是"不许填"，而是**找不到地方填**。
3. **边界说进握手**：`initialize` 的 `instructions` 里明说「只读 + 代表配置里指定
   的那一个买家账户，不是通用网关」。接上来的模型看得见这句话。
4. **生产化路径记在这里**：换成**内部 JWT**（`sub` claim 带 user_id）或 OAuth，
   由 server 用公钥/授权服务器验签 —— 但要说清**换的只是传输与凭据，验证点不变**：
   「谁在验证用户」仍然是某个真实登录过的人（`0001` 的生产化路径一节）。

## 为什么这么定

- **写操作走不通，不是"不该"而是"没地方确认"**：本业务的写操作靠两件东西把关 ——
  护栏的预算/金额规则与**人按的那一下**（挂起 → 用户在自己页面上确认 → 带一次性
  凭据恢复）。MCP 客户端没有这套 UI（它就是别人家的聊天窗口），暴露 `place_order`
  等于「模型说下单就下单」。只读是唯一能保持原语义的子集。
- **裸采信客户端声明的身份，等于把 `0001` 的前提拆了**：那条 ADR 敢信
  `X-User-Id` 的全部理由是「值由已认证的一方取出并转发，全程不离开同一个信任域」。
  MCP 客户端在域外，它声明的 `user_id` 就是一个**域外的裸声明** —— 与
  `0001` 里被否掉的「把身份做成工具参数」是同一个东西，只是换了个人来说。
- **原地绑定一个账户是"本地演示"形态下最诚实的做法**：server 代表谁在**配置里**
  写死，客户端改不了、模型看不见；代价（一个进程一个账户）在这个形态下为零。

## 代价与边界

- **一个进程一个账户**：想同时服务两个买家就要起两个 server（各带各的
  `CHARAPP_MCP_USER_ID`）。这是有意的 —— 多账户形态需要真鉴权，见下一条。
- **没有鉴权，任何能起这个进程的人都能读那一份数据**：本地演示可接受（进程由本人
  配置、跑在本机、连的是本机 Django）。**一旦这个 server 被别人的机器起起来、
  或者商场不在本机，这条立刻不可接受**。
- **引用编号在进程内累加**（`Citations` 是进程级一份，而不是像助手那样每段对话
  一份）：MCP 这一侧没有"对话"这个概念，一次提问就是一次独立调用。同一段答复里
  的编号仍然唯一且连续，只是不每次从 `[1]` 重数。
- **查询改写那一步不做**（`KnowledgeRetriever(model=None)`）：本进程不连上游模型。
  要开就在装配处把模型传进来，属于"要不要给这个进程一把模型钥匙"的另一个决定。
- **只读那条边界是「按注解筛」，所以它的前提是「会改数据的工具都打了注解」**：
  `writes` 是本仓既有的唯一判据（护栏的预算 / 金额 / 挂起也全靠它，见
  `tools.py` 第 4 条），但它**靠人打** —— 漏打的那个工具既不会被护栏管、也会被
  当成只读放上 MCP。既有的防线是「约定写死在 `tools.py` 的模块注释里 + 各票评审」，
  不是自动的；要它自动，得让「会改数据」这个事实在别处可判（比如按
  `views_agent.WRITE_ENDPOINTS` 反查每个工具打的是哪个端点）—— 那是另一个决定。
- **知识库那条路的冷启动**：两个本地模型加载实测 7~8 秒（C08 的量；每个进程只付
  一次）。本进程与服务进程一样在后台预热（`knowledge/prewarm.py`），不预热的话第一次
  搜政策会把这 7~8 秒算进那次调用，而框架那道 30 秒的工具超时闸是**包住整条协程**
  的（超时 = 结果未知，会中断整次运行）。慢一档的机器或更大的 `retrieve_top_k`
  （精排逐对约 1.1 秒）会把它推到闸口上 —— 所以这里跟随服务进程的做法，而不是另设
  一个超时。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 把 `user_id` 做成工具参数（谁调用谁填） | 与 `0001` 否掉的那条完全一样：参数表会进模型上下文，模型就可能被诱导填别人的值。而且这里是**域外**声明，`0001` 连"同域转发"那点理由都没有 |
| 暴露写工具，靠 prompt 求模型谨慎 | 把"人确认"换成"求模型自觉" —— 本业务已经把确认做成了机制（挂起 + 一次性凭据），退回到 prompt 说服是反向走 |
| 现在就上 OAuth / 内部 JWT | 本地演示没有第二个信任域，也没有授权服务器可谈；真要跨域部署时，密钥/授权方案得按那时的部署形态才能定（与 `0001` 同一条理由） |
| 一个进程多账户（按客户端声明切换身份） | 就是上面两条的合体，且需要审计与限流配套 —— 属于生产化，不属于演示形态 |
| 干脆不做暴露侧（只做消费侧） | 消费侧证明"框架抽象装得下生态标准"，暴露侧证明"业务能力能被任何 MCP 客户端调" —— 后者可演示性极强（配一行就能用自然语言问真数据），且正好兑现 `0001` 那条判据 |

## 什么时候该重新看这条决定

- **这个 server 要被本机之外的东西连**（别人的机器、容器、远程客户端）：换鉴权，
  按上面第 4 条的路径走 —— 传输换成 JWT/OAuth，验证点不动。
- **要服务多个账户**：绑定答案从"配置里一个 ID"变成"按凭据里的 `sub` 取"，同时要
  补审计日志（谁查了谁的哪一条）。
- **只读这条边界要放宽**（有人要 MCP 客户端能下单）：那时要一起设计"客户端侧的确认
  机制"（MCP 的 elicitation 是一条路），而不是直接放写工具上线。
