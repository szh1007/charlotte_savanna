# 运行金额在收尾那一刻算好写死；峰谷价按运行的开始时刻判

**Status:** accepted（2026-09-25）

## 决定

两件事一起定，因为它们同出一个问题（「这次运行花了多少钱」要能跟账单对上）：

1. **金额与算式在运行收尾那一刻算好，写进 `charagent_runs` 两列**（`total_cost` /
   `total_cost_detail`），之后**不再重算**。`total_cost` 改成**可空**：`NULL` = 那一刻
   没算出来（原因写在明细列里），`0` = 真的花了 0 元 —— 与那五列用量分解同一条规矩。
   **算得出来时按当前列重算**（用量那五列是累计值，所以重算出来的就是那一刻的总额；
   这不是「累加」—— 累加会把前面那段算两次），而**算不出来时一个字节都不动**
   （不写 0、也不把已有金额清掉）；状态推进与对账修订碰不到这两列。
2. **价目表支持峰谷两套价**（`peak` / `valley` 各三档），峰谷规则与时区放在**同一份
   部署侧配置**里，**按运行的开始时刻**判定；工作日按中国节假日日历（法定节假日不算、
   调休上班的周末算），峰时段是工作日 9:00–12:00 与 14:00–18:00（半开区间，9 点整算峰、
   12 点整算谷）。业务侧进程启动时自检：价目表读不成、或日历判不了今天，**进程起不来**。

「读那个金额」的入口是 `python -m CharAgent.client.trace <run_id>`：它**只读库**，既不读
价目表也不碰日历（本片最初那版是查询侧现算，已被本决定推翻）。

## 为什么需要它

- **账单是按当时那一版价目表开的。** 查询侧现算的代价是「换一版价目表，历史运行的金额
  跟着变」—— 而「与账单对得上吗」正是这个功能存在的理由。于是 2026-09-24 决定「查询侧
  派生，`total_cost` 永远不填」的那条（**ADR-0005 的推论**）在一天后被推翻：它担心的
  「写死了就只剩一种答案」在**对账**这个用途下恰恰是优点 —— 只要那一种就是账单那一种。
  ADR-0005 自己就写着「不把价格写进运行路径，**留到 L3**」；这就是那次回看。
- **峰谷价逼着把「哪一刻」固定下来。** 同一批 token，工作日 10 点跑与凌晨跑是两个价，
  而「哪一刻」只有运行行知道（开始时刻）。不写下来的话，事后连「这笔该按峰还是谷算」
  都无从复原 —— 更别说换一版价目表之后连「当时是不是峰价」都算不回来（谷价那套的时段
  划分将来也会变）。
- **钱与用量是两类事实。** 用量（五列 token）是运行的事实，钱是「用量 × 当时那版价」的
  结论；两者的寿命不一样：用量永远不变，价会变。分两处存，各自的语义才说得清。

## 代价与边界

- **币种不换算**：屏幕上的 `¥` 是写死的，价目表里的数字必须与它同币种。要支持别的币种
  得连展示层那个符号一起改（一处符号换一个部署侧配置项，眼下不值当）。
- **日历是「国内优先」的假设**：`chinesecalendar` 只覆盖中国的法定节假日与调休，数据每年
  11 月前后随发版更新。换一家境外的供应商，这块要改（这是它与「价目表不内置」那条口径的
  差别：价目表是数据，日历是库）。日历里没有的年份 → 金额留空并写明「升级依赖」，
  **不按「周一到周五」硬猜**（猜出来的峰谷在长假期间会错，而错的金额看起来和真的一样）。
- **金额不可重新计价**：库里那一列是「当时算的」，今天拿另一版价目表算不出它，也没有
  第二条记录可比对。要做「按今天的价重估历史」，那是另一条路（另存一份），不是改这一列。
- **小到 1e-6 以下的花费存不下**：这一列的刻度是 6 位小数，比它还小的金额写成 0 就成了
  「真的没花钱」。那种情况按「没有金额」记（原因写「存不下」），不写一个撒谎的 0。
- **`total_cost_detail` 是 JSONB**：它记「哪套价 + 三个单价 + 三档用量」或「为什么没有
  金额」，金额与单价一律存字符串（钱不能过浮点）。只留一个数字的话，事后没人能验算，
  连「这是峰价还是谷价算的」都看不出来。
- **收尾那一刻算不出来不是错误**（没配价 / 上游没报某一档 / 日历过期）：运行照常结束，
  金额留 `NULL` + 明细记原因。**在启动时能查出来的**（配置写错、日历过期）则在启动那一刻
  就拦住 —— 与其让每一趟的钱都空着事后人工补，不如一开始就不接活。
- **重试那件事**：同一批 token 的重试花费**已经**在用量列里（那五列是累计值），所以金额
  按列重算即可，**不能按次累加** —— 累加会把同一笔钱算两次。真的出现「一次运行的账分两笔
  报上来」时，正确的做法是让**列**累加、金额跟着涨。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 查询侧现算（本片 2026-09-24 的初版） | 换一版价目表历史金额就变，与账单永远对不上；峰谷更是算不回来（判据是运行开始时刻） |
| 三档表装峰谷（拿两个模型名当峰谷） | 价目表是「模型 -> 价」，塞进时段会让模型名与时段混成一维，字段语义坏掉 |
| 峰谷规则写死在框架里 | 「哪个时段算贵」是供应商的作息。内置默认值 = 换家供应商静默算错钱（正是本仓那条「报 0 比报不出来更糟」的同类） |
| 节假日按「周一到周五」硬判（不引日历） | 2026-09-25 是**周五但休息日**（真数据），2026-09-20 是**周日但调休上班** —— 硬判会在这两天算错，而错的金额看起来很正常 |
| 日历超出范围时退回「按周末判」 | 标着「可能偏高」的金额用着用着就没人看那行标注了；宁可留空 + 说清「升级依赖」 |
| `trace` 读不到金额时用**今天的**价补算显示 | 那是另一笔钱（今天的价），显示出来会让人以为库里存的就是它 |
| 金额累加（每次收尾加一遍） | 五列是累计值，累加 = 把前面那段算两次；「不许被改成 0」靠的是「只写一次 + 算不出来不动它」，不是靠加法 |
| 把峰谷档位单独存一列 | 一个 JSONB 明细就够（能用 `total_cost_detail->>'tier'` 查），多一列多一处要同步的地方 |

## 什么时候该重新看这条决定

- **若换了一家境外供应商**：峰谷规则与节假日日历都要跟着换（规则已经在配置里，日历还在
  依赖里）。
- **若要支持第二种币种**：把展示层那个 `¥` 与价目表绑成一处配置。
- **若需要「按今天的价重估历史」**：另存一份重估结果，别改 `total_cost`。
- **若 `chinesecalendar` 停更**：换库，或把「非工作日日期表」挪到部署侧配置里（本片选它
  是因为它把调休也算对了，而调休表只在国务院公布之后才有）。
- **若某天要给「挂起等人工审批」的运行单独定价**：那是**另一次运行**的开始时刻的事
  （挂起补做会开新的一段），口径仍然是「谁开始，谁的时刻」。
