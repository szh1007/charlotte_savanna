# 一段对话有两种表示：账本 append-only，视图每轮现算，给人看的那份永不压缩

**Status:** accepted（2026-09-23）

## 决定

同一段对话在系统里有**三份**东西，它们从同一个来源长出、此后各走各的：

| 名字 | 是什么 | 会不会变短 | 谁在读 |
|------|--------|-----------|--------|
| **账本**（快照） | 每一轮落一帧，只追加不改写；含工具往返与推理链的**全量** | **不会** | 断点续跑与回溯（机器） |
| **视图**（上下文视图） | 每次模型调用**前现算**一份：身份说明 + 压缩摘要 + 最近 N 轮完整对话 | 会，越聊越短 | 模型 |
| **记录**（transcript） | 一条消息一行，标着要不要展示给前端 | **永不** | 人（前端刷新、左栏点开） |

**「两种表示」说的是落地的那两份**（账本 / 记录）—— 视图是账本的一层投影，不落地、
不算第三种。标题写「两种」而表格列三份是有意的，两者说的是两件事：**数得着的落地物
是两份，运行期同时存在的是三份**。（审查指出过这处容易读岔，所以在这里点明：
ADR-0009 说「一份对话的两种表示都在框架里」时，指的正是账本与记录这两份落地的。）

三句话把这条决定说完：

1. **账本是账本、视图是视图。** 压缩只改「这一次请求送给模型什么」—— 它是一层
   **投影**，算完就丢，不落地。帧里存的永远是全量账本（`agent/loop.py` 落帧时写的
   是 `state.history`，不是投影后的那份）。
2. **视图不是一个新东西，是把「本来就要拼的那份」说清楚。** 框架在此之前也把
   「系统提示 + 历史」拼给模型，只是那份恰好等于账本；现在它多了一条摘要、少了几轮。
3. **给人看的记录永不压缩。** 用户刷新后看到的、在左侧列表点开的那份是**记录表**，
   它只增不减。压缩这件事在它身上完全不发生。

投影器是 `CharAgent/agent/compaction.py`（`CompactionPolicy` 协议 + 框架给的
`TrimAndSummarize` 默认实现）；业务侧配五个旋钮（阈值 / 保留轮数 / 工具结果截断 /
摘要开关 / 水位线），框架默认不压缩（`compactor=None` 时与从前逐字一样）。

## 为什么需要它

**起因是一个线性增长的成本，而不是一个性能指标。** 前端标签页里的
`conversation_id` 是固定的（存在 `sessionStorage`），所以历史只增不减 —— 每一轮
都要把全量历史重发一遍，成本与首字延迟随轮数线性上涨，直到撞上模型窗口。框架的
难点清单把它记作 **#7 上下文压缩（P1）**：*摘要 + 截断，但绝不能破坏 `tool_calls`
的结构*，而那条一直没实现。

三条门槛逐条对上：

- **难回退。** 它决定三件事：压缩写在哪儿（框架的 `agent/` 层）、会话历史从哪读
  （记录表，不是快照）、前端看到什么（记录表的投影）。改它要同时动**框架 + 业务 +
  前端**三处。
- **无上下文时反直觉。** 「为什么用户看到的历史**比模型看到的**多」是必问题 ——
  三份东西里有两份叫「历史」，而它们**故意不一致**。
- **存在真实取舍。** 见下面那几条被否的方案，每一条都有人会真心觉得更好。

## 代价与边界

- **两边的历史从此不一致，这是设计不是缺陷。** 排查口径随之分成两条：问「模型
  为什么忘了」去**账本**（快照），问「用户看到什么 / 少了哪条」去**记录表**。把
  两个问题混在一个数据源上问，会得到自相矛盾的答案。
- **压缩是有损的，而且是有损两次。** ① 被摘要替掉的那几轮原文不再进视图；② 摘要
  是**滚动**重压的（上一条摘要 + 本次新裁掉的段一起交给模型重写），所以更早的信息
  会被逐次稀释 —— 不是「每段各压各的、旧的永远保真」。
- **摘要会失败，且失败是静默降级。** 摘要模型没给出正文时，本次**只做裁剪**，
  事件里带 `summarized=false` 与一条 warning（真机上真发生过，见 issue 18 的开放项）。
  降级不阻断问答，所以它必须有一条能被看见的信号。
- **视图不落地 = 每次运行多算一遍。** 这是有意的：落了地就有第二份会过期的真相。
  代价是 CPU（估算 token + 切段），省下的是「视图与账本谁先更新」这类同步问题。
- **触发条件是 token 阈值，不是轮数。** 阈值按**单次请求**的估算大小算，水位线
  决定在哪一档开始压；所以「聊到第几轮会压」不是一个固定数字。
- **压缩的理由是窗口与首字延迟，不是省钱** —— 为什么压掉旧前缀反而可能更贵（缓存
  命中价那笔账），ADR-0005 已经算过，这里不重抄一遍，免得两处日后各自漂。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| **只压展示**（把用户看到的记录也压掉） | 两头都不对。① **省钱为零**：花钱的是发给模型的那份，不是给人看的那份 —— 压记录对成本一分钱影响都没有。② 它毁掉一条已经写进别的决定的契约：**记录永不改写**（ADR-0007 拒绝「删会话时顺手标删消息」用的正是这条理由）。用户刷新一次少一段，是这个产品最不能出的错 |
| **只压视图、不落全量账本**（视图压完就当成新的账本） | 账本就没有全量了。**断点续跑与回溯要的正是全量** —— 「模型为什么忘了」只有账本能答；而压缩是有损的，压掉之后没有第二份可以对照。另外它与「快照是给『接着跑』用的工作数据」这条既有定位冲突：一份**被压缩改写过的**帧，无法回答「上一轮它到底看见了什么」 |
| **两份都留全量**（不压缩，视图 = 账本） | 就是 L2.5 之前的状态。代价是线性上涨的成本与首字延迟，撞窗口之后连错都报不出来（只是越来越慢、越来越贵，直到请求被拒） |
| **摘要写回账本**（把摘要当成一轮新对话追加进快照） | 账本就成了「原文 + 摘要」的混合体，`resume` 时读到的历史会**同时包含**被压掉的原文与替代它的摘要 —— 送回去的视图比不压还长。摘要属于视图，它的落点在**记录表**（`hidden=True` 那条），不在账本 |
| **在 prompt 里让模型自己「记住要点」** | 不解决结构问题：成本来自**重发的字节数**，不来自模型记不记得。它至多影响摘要的质量，属于 L4 的调优清单 |

## 什么时候该重新看这条决定

- **若「发给模型的那份」与「给人看的那份」被要求一致**（比如要做「回放当时模型
  看到的上下文」这个功能）—— 那是一条**新功能**，做法是给视图加一次显式的落盘，
  而不是把三份东西合并回两份。
- **若压缩开始伤害答案质量**（用户抱怨「它忘了前面说过的」）：先分类 —— 是**摘要
  写漏了**（改摘要指令）还是**保留轮数太少**（改旋钮），别直接调阈值。badcase 的
  回流归 L4 的评估集。
- **若模型侧的窗口或缓存定价变到「全量重发更便宜」**（长上下文缓存再降一档就可能
  发生）：那时压缩从收益变成纯损失，应当**关掉它**（`compactor=None` 这条路一直
  留着），而不是改造投影器。
- **若要做上下文参数的 A/B**（不同阈值 / 不同保留轮数跑同一批问题）：视图**每轮
  现算**这条设计正好支持 —— 换一份 `CompactionPolicy` 就是一次对照，不必动账本。
