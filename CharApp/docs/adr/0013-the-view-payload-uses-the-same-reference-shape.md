# 帧里的视图也走引用（v7）：`metadata.view` 与进度同构

**Status:** accepted（2026-09-23）

## 决定

**帧 v7**：`metadata.view` 里的身份说明也摘出去，存成与进度同格式的引用。

```jsonc
"metadata": {
  "view": {
    "dropped": 2, "truncated": 0, ...,   // 那一套计数
    "messages": [...],                    // 摘掉第 0 条之后的视图
    "prompt_ref": {"name": "system/v2", "sha256": "..."}
  }
}
```

规则与 v5 对进度那条**逐字同构**：`prompt_ref=None` 表示「这一份没剥离过，正文就在 `messages` 里」（老帧、或没配身份说明的会话）；写侧由**造帧的人**摘（`prompt/ref.py` 的 `detach_view_identity`，loop 的 `_turn_metadata` 里调）；读侧按引用把正文取回来前插。迁移 `_v6_to_v7` 只给老帧补 `prompt_ref=None` —— 不替它摘正文（那会让老帧少一条消息，而「当时它看到了什么」正是帧要回答的事）。

## 为什么需要它

`metadata.view` 记的是「这一轮**真的发出去**的那份」（ticket 22），而那份的第 0 条恒为身份说明 —— 压缩策略直接拿 `history[0]` 当视图第 0 条（`compaction.py` 的 `_view`）。于是：

- 身份说明那几千字**每帧抄一遍**，而它**就是**进度那边那一条（同一个对象）；
- 帧里已经有 `state.prompt_ref` 描述它，视图里再来一份是同一件事说两遍。

这与 0005 是同一条思路的收尾：那一版把「配置」从**进度**里按引用记，这一版把**视图**补上 —— 于是「一帧里装什么」这个问题，两边给的答案终于一致了。

## 代价与边界

- **`view.messages` 不再是「可以直接发给模型的完整列表」**。读的人要先按 `prompt_ref` 把正文取回来前插。这条必须写死在字段 docstring 里 —— 拿它直接喂模型，模型就少了一条人设，而且不报错、只是答得不像那个人（与 0005 记的是同一种失败模式）。
- **两个引用恒等**（`view.prompt_ref == state.prompt_ref`），因为视图第 0 条就是 `history[0]`。存两份是**用一点冗余换 `view` 的自描述**：读的人不必知道「得去 `state` 那边找」。若要零冗余，那就是「`view` 不带引用，按约定取 `state` 那份」—— 省几十字节，换一层隐式约定。
- **`view["messages"]` 为 None 时（视图 == 账本）也记引用**：没得摘，但引用照记 —— 它说的还是「这一段的身份说明在哪」，读的人据此知道账本那条要不要补。
- **计数那一族仍是宽松读取**（不逐字段校验），但**引用走严格校验**（复用 `_read_prompt_ref`：恰好两个键、非空字符串）。它不是计数，是读的人**按它取正文**的凭据，畸形了会让「这一段用的是什么身份说明」答不上来。
- **摘的动作仍在造帧那一侧**，不进编解码器 —— 三个后端里内存版不编码，放进去会让「帧里存不存正文」随后端而变（0005 踩过这个坑，是被一条会话级用例当场抓出来的）。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 不摘，保持现状（视图里带着身份说明） | 每帧多抄几千字，而它**已经**在进度那边记过一次。0005 解决同一类重复时的结论是「按引用记」，没有理由在视图这边换成另一个答案 |
| `view` 不带 `prompt_ref`，读的人按约定取 `state` 那份 | 零冗余，但把「两份引用恒等」变成一个**隐式约定** —— 读一帧的人必须知道去哪找，而帧本来就该自解释 |
| 在编解码器里摘 | 三个后端会存出两种形状（内存版不编码）。0005 已经用这条否掉过一次 |
| 迁移时把老帧视图里那条**提取成引用** | 提出来只能标「版本未知」（老帧的 `view` 本来就来自某个版本的 `state`，但没记是哪个），还原时还得猜；不提则老帧完全自描述，零损失 |
| 顺手把 `view.messages` 也压缩一遍再存 | 帧是**审计材料**，它要回答的是「当时它看到了什么」—— 那一份已经是压缩过的视图了，再压一次就答不准 |

## 什么时候该重新看这条决定

- **若「帧的保留期策略」开始做**（`checkpoint/postgres.py` 里明写「属后续阶段」）：那时 `view` 与 `state` 的保留口径要一起定 —— 视图那份的引用指向同一个提示词版本，两者不能一个留一个删。
- **若有人真去拿 `view.messages` 直接喂模型**：那是这条决定最可能的翻车方式（少一条身份说明且不报错）。护栏可以做成「读取侧返回一个标记过的类型」，但那要等它真的发生过。
- **若 `view.prompt_ref` 与 `state.prompt_ref` 不再恒等**（比如将来允许「视图用另一份人设」）：那时「存两份」就从冗余变成了必需，这个 ADR 的第二节要重写。
