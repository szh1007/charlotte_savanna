# 幂等先做、工具超时推后：依赖方向是单向的

**Status:** accepted（2026-09-24）

## 决定

L3b 做 **#17 幂等**（含它一直缺的持久化存储），**#15 工具超时继续推后**，并**改判** `DESIGN.md` §② #17 那条判断：

> 原文：「#15 与 #17 是一对，**要么一起做，要么都不做**」

改为：**依赖方向是 #15 → #17，不是双向的，所以可以拆。**

## 为什么那条判断该改

原文给的理由是「超时造成『结果未知』，而『结果未知』必须先靠幂等或先查状态解决」—— 这句话说的是**超时需要一个幂等的存储来解决自己的问题**，即 **#15 依赖 #17**。它从头到尾没有说 #17 依赖 #15。

而 #17 缺的从来不是"超时"这个调用方，是**任何**调用方。它挡的是「**同一个动作被执行两次**」，而框架里此前不存在这条路径（重试只包模型调用，工具执行是"跑一次 → 失败文本回填 → 模型自己决定要不要再发一次"，那是**一次新的调用**，不是同一个动作的重放）。

**HITL 的挂起-恢复正是它等的第一个调用方**，而且是原文自己点名的两条之一：

> 恢复被触发两次就重放同一个 `(run_id, message_id, tool_call_id)`

（原文写作 `(run_id, tool_call_id)`，完整键是三列 —— 上游每轮从 `call_0` 重新编号，单靠 `run_id + tool_call_id` 在多轮之间会撞，见 `db/schema.py` 那段注释。）

恢复被触发两次**不是理论风险**：`POST /runs/{run_id}/resume` 是 HTTP 端点，用户双击、网络重发、前端重试都会产生第二次。而第二次重放的是**"给这一单付款"**。

## 代价与边界

- **工具超时（#15）仍未做，且现在没有排期。** 修法（分层超时：模型 60s / 工具 10-30s / run 总超时）与它的推论（"结果未知"要靠幂等或先查状态解决）都还在 DESIGN 里，只是**不再挂着 #17 当搭子**。它下一次被想起的合理解释是"真机上一次工具卡住了"，那时本 ADR 是它的入口。
- **持久化存储必须和 #17 一起补**，不能只把 `IdempotencyStore` 的进程内实现接上去。理由在设计里早就写了：`retry/idempotency.py` 的模块 docstring 明说「P0 边界：进程内 dict，无 TTL / 无持久化 / 跨实例失效」，而 HITL 的两次恢复**跨进程**（两次 HTTP 请求可能落在同一个进程，也可能不是；用户关掉浏览器隔天再点也不是没有可能）。表已经在 `db/README.md:142` 规划好：`idempotency_keys`，**P1 只加这一张**。
- **改判要落在两处**，不是只改 DESIGN：`DESIGN.md` 的 #17 硬骨头段，以及 `retry/idempotency.py` 的模块 docstring（它末尾抄了同一段话）。**两处不同步比不改更糟** —— 读代码的人会相信 docstring。

## 考虑过的替代方案

| 方案 | 为什么否掉 |
|------|-----------|
| 遵守原文，两个一起做 | 把"分层超时"（一个与 L3 主题无关的稳定性机制）塞进 L3b。它会让 L3b 从"挂起与代付"扩成"挂起、代付、超时"，而超时那部分**没有任何真实触发场景** —— 正是 PRD §1 批评的"预设但没人用过的接口"，也正是原文说 #17 零调用方的同一个理由 |
| 两个都不做，#17 继续等 | HITL 就成了"恢复被重放就重复付款"的机制。这条不是可接受的边界，是一张会在演示时爆的雷 |
| 只做幂等的内存实现，持久化推后 | 见上：跨进程重放正是它要挡的东西，内存实现在跨进程这个场景下等于没有 |

## 什么时候该重新看这条决定

- **若 #15 工具超时开始做**：它就是本 ADR 说的"下一次被想起"，届时幂等的存储已经在（本 ADR 已把它建好），#15 直接接上去用。
- **若幂等键的粒度需要变**（现在按 `(run_id, message_id, tool_call_id)`）：比如将来要挡"跨 run 的同一个动作"，键要加维度。届时 `KEY_PATTERN` 的白名单与表结构一起改。
- **若允许同一 run 并发恢复**：现在靠 ADR-0014 的"一次挂起一条" + `resume` 端点的串行化避免，若放开，幂等键就从"兜底"变成"唯一的闸"。
