# 工具事件在业务侧脱敏，不靠前端隐藏

**Status:** accepted（2026-09-21）

## 决定

助手服务（`CharApp/minimall/`）**在自己包装的 `event_sink`** 里，把 `tool_call` 与 `tool_result` 两个事件的真实载荷换成人话：`arguments` / `summary` / `error` 替换成一个 `label`（「正在查询订单」/「订单获取成功」）。

**框架与 Django BFF 一行不改** —— 框架继续只发事实，BFF 继续只搬字节。

## 为什么是这一层

诉求是「订单号、地址、余额、商品明细不该出现在浏览器上」。三层都能做到：

| 落点 | 数据到哪为止 | 代价 |
|------|------------|------|
| **业务侧包装 `event_sink`** | **不出 CharApp 进程** | 几乎为零（业务本来就持有 sink） |
| Django BFF 改写 | 已经跨进程到了 Django | 把 BFF 从「逐帧搬字节」变成「解析协议 + 改写」 |
| 前端隐藏 | 到了浏览器 | **根本不算脱敏** —— devtools 的网络面板里原文可见 |

选第一层的决定性理由不是「最省事」，是**它本来就是一个现成的改写点**：框架的 `SessionProvider.provide(context, *, event_sink)` 把事件出口交给业务，业务再递给 `ChatSession`。业务站在唯一出口上，包一层就是脱敏，不需要框架新开一个口子。

第三层与第二层的区别在演示时是实打实的：**敢不敢当着面试官的面打开 devtools。** 第一层敢。

## 哪些改、哪些不改

| 字段 | 处置 | 理由 |
|------|------|------|
| `arguments` | → `label` | 原样 JSON，里面有订单号、slug、价格区间 |
| `summary` / `error` | → `label`（成功 / 失败两种话术） | 工具返回值截断到 200 字符的正文，订单号、地址、余额全在里面 |
| `tool_name` | **保留** | 工具标识（`get_my_order`），不含任何用户数据；却是演示时讲「模型选了哪个工具、有没有选错」的唯一素材 —— 而 L4 的工具数量 A/B 正要讲这个 |
| `tool_call_id` / `duration_ms` / `turn` | **保留** | 内部噪音，对用户无意义，但也无信息风险 |
| `status` | **保留**（2026-09-22 补记） | 同上（`ok` / `error`，无用户数据）；而页面靠它决定工具行红不红 —— 只留 `label` 的话，那一行就没法区分「做到了」与「没做到」 |
| `reasoning` | **不动** | 那是模型自己的话（它会**复述**刚查到的订单号、余额）。遮掉它会让 L3 的「当时它看到了什么」不可解释；真要收敛应该在 prompt 里要求模型不复述，属 L4 调优，不是展示层的事 |

**不留「演示开关」**：一个「演示时把敏感数据打开」的环境变量是安全反模式 —— 它迟早会在某个不该开的场合被打开。

**这条保证的范围（2026-09-22 补记）**：它管的是**工具事件**的载荷 —— 「工具的参数原文与返回正文不出本进程」。`reasoning` 与 `final` 照旧出去（上表已写明理由），所以它**不是**「浏览器上搜不到任何敏感值」：模型复述一个刚查到的订单号，那个号就会出现在帧里。漏配或改错的判据落在 `CharApp/minimall/redaction.py` 与它的用例上，别把它当成一道能兜住一切的闸。

## 代价（说清，否则这条 ADR 就是自我辩护）

**关掉了「在浏览器里看模型看到了什么」这个演示窗。** `issues/06` 当初把「工具轨迹原样透传」明确写成了刻意的排查窗（原话：「也是演示时讲『模型看到了什么』的素材」），本次改动把它关掉。

换回来的是敏感数据不离开后端进程。而「看模型看到了什么」并没有丢，只是**搬到了它该在的地方**：L3 的运行轨迹落库（按 run 查「当时它看到了什么」）。那才是正确的排查入口 —— 它不受「谁能看到浏览器」约束，也不要求脱敏，而且能查的比浏览器里那 200 字符摘要多得多。

## 考虑过的替代方案

- **Django BFF 改写** —— 否。数据已经跨进程；而且 BFF 现在的能力边界很干净（认证 / 取身份 / 转发透传），让它理解 SSE 帧的内部结构，是把它从一个薄转发层变成一个有业务知识的层。
- **前端隐藏（保留载荷、只是不渲染）** —— 否。见上表：那不是脱敏，只是不展示。
- **在框架里加「事件脱敏钩子」** —— 否。框架不该知道「什么算敏感」（那是业务知识），而且 `on_event` 是观察点不是改写点（它拿到事件时事件已经进了 sink，改不了）。业务持有 sink 已经是现成的改写点，再加一个钩子等于把同一个位置开两遍。
- **让模型少说（在 prompt 里禁止复述订单号）** —— 不作为本条的替代，作为**补充**：它管的是 `reasoning` 与 `final` 的正文，管不了工具事件的载荷（那是框架按契约发的，不是模型说的话）。已记入 L4 的调优清单。

## 什么时候该重新看这条决定

- **如果前端引入构建链、或事件的消费方不再是浏览器**（比如做一个内部调试面板），脱敏的边界要重画 —— 那时候「谁能看到」这个前提变了。
- **如果 L3 的轨迹落库做成了可查询的界面**，「浏览器里看模型看到了什么」这个诉求应当由它满足，这条决定不受影响。
- 本条**不影响**框架与助手服务之间的任何契约：SSE 帧格式、事件类型、`seq` 语义全部不变，变的只是某些事件 `data` 里的字段内容。框架的帧格式测试（`test_server_sse.py`）逐字钉死的是**框架自己那套玩具业务**的帧，不受影响。
